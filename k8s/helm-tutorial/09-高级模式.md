# 09. 高级模式

## 9.1 Library Chart(可复用组件)

### 概念

Library Chart 是 `type: library` 的 Chart,**只包含命名模板,不部署任何资源**。它用于跨 Chart 共享通用逻辑(labels、annotations、复杂函数)。

```yaml
# common-lib/Chart.yaml
apiVersion: v2
name: common-lib
type: library
version: 0.3.0
description: 通用 helpers
```

```text
common-lib/
├── Chart.yaml
├── values.yaml         # 默认值
└── templates/
    ├── _labels.tpl     # 通用 labels
    ├── _annotations.tpl
    ├── _secrets.tpl
    └── _utils.tpl
```

```yaml
# common-lib/templates/_labels.tpl
{{- /* 标准化 labels */ -}}
{{- define "common-lib.standardLabels" -}}
app.kubernetes.io/name: {{ .name }}
app.kubernetes.io/instance: {{ .instance }}
app.kubernetes.io/version: {{ .version | quote }}
app.kubernetes.io/managed-by: {{ .managedBy | default "Helm" }}
app.kubernetes.io/part-of: {{ .partOf }}
helm.sh/chart: {{ printf "%s-%s" .chartName .chartVersion | replace "+" "_" }}
{{- end -}}
```

### 在 application chart 中使用

```yaml
# myapp/Chart.yaml
dependencies:
  - name: common-lib
    version: 0.3.0
    repository: file://../common-lib
```

```yaml
# myapp/templates/deployment.yaml
metadata:
  labels:
    {{- include "common-lib.standardLabels" (dict
        "name" "myapp"
        "instance" .Release.Name
        "version" .Chart.AppVersion
        "managedBy" .Release.Service
        "partOf" "myorg"
        "chartName" .Chart.Name
        "chartVersion" .Chart.Version
      ) | nindent 4 }}
```

### 用 `import-values` 共享默认参数

```yaml
# common-lib/values.yaml
labels:
  name: ""
  instance: ""
  partOf: ""
  managedBy: Helm
```

```yaml
# myapp/Chart.yaml
dependencies:
  - name: common-lib
    version: 0.3.0
    import-values:
      - child    # 父 chart 的 common-lib 路径 = common-lib 自己的 values
```

### 实战:把 common-lib 部署为 OCI

```bash
helm package ./common-lib
helm push common-lib-0.3.0.tgz oci://registry-1.docker.io/myorg
```

```yaml
# 消费方
dependencies:
  - name: common-lib
    version: "~0.3.0"
    repository: oci://registry-1.docker.io/myorg
```

## 9.2 Library Chart 实战:标准化 labels

在 10+ 微服务的组织里,labels 不一致会导致 Prometheus 监控混乱、kubectl 过滤困难。Library Chart 强制标准。

```yaml
# common-lib/templates/_labels.tpl

{{/* 必须 labels(selector 也能用) */}}
{{- define "common-lib.identityLabels" -}}
app.kubernetes.io/name: {{ .name }}
app.kubernetes.io/instance: {{ .instance }}
{{- end -}}

{{/* 推荐 labels */}}
{{- define "common-lib.standardLabels" -}}
{{ include "common-lib.identityLabels" . }}
app.kubernetes.io/version: {{ .version | default "0.0.0" | quote }}
app.kubernetes.io/component: {{ .component | default "" }}
app.kubernetes.io/part-of: {{ .partOf | default "" }}
app.kubernetes.io/managed-by: {{ .managedBy | default "Helm" }}
{{- end -}}

{{/* chart labels(用于 helm 管理) */}}
{{- define "common-lib.chartLabels" -}}
helm.sh/chart: {{ printf "%s-%s" .chartName .chartVersion | replace "+" "_" | trunc 63 | trimSuffix "-" }}
{{ include "common-lib.standardLabels" . }}
{{- end -}}
```

## 9.3 Helm + Kustomize 混合

Helm 处理"模板化",Kustomize 处理"补丁"。两者结合应对复杂场景。

```yaml
# 1. 用 helm template 输出 yaml
helm template myapp ./myapp > base.yaml

# 2. 用 kustomize 补丁
```

```text
kustomize/
├── base/
│   ├── kustomization.yaml
│   ├── base.yaml            # helm template 输出
│   └── patch-deployment.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── patch-replicas.yaml
```

```yaml
# overlays/prod/kustomization.yaml
resources:
  - ../../base
patches:
  - path: patch-replicas.yaml
```

**适用场景**:
- 团队已用 Kustomize 基础架构
- 多个团队协作,需要叠加 patch
- 不想深改 Helm chart

**不推荐**:能用 values 解决就别上 Kustomize,增加复杂度。

## 9.4 Helm Operator / Flux Helm Operator

Helm Operator(已并入 Flux)是 Kubernetes 风格的 GitOps 工具,把 Helm Release 建模为 CRD。

```yaml
# HelmRelease CRD
apiVersion: helm.toolkit.fluxcd.io/v2beta1
kind: HelmRelease
metadata:
  name: myapp
  namespace: flux-system
spec:
  chart:
    spec:
      chart: myapp
      version: "1.x"
      sourceRef:
        kind: HelmRepository
        name: myrepo
  interval: 5m
  values:
    replicaCount: 3
    image:
      tag: 1.2.3
```

Flux Helm Operator 的优势:
- GitOps 友好,自动 reconcile
- drift detection(自动修复偏离的状态)
- 多环境多 release 易于管理
- 见 12 章

## 9.5 多集群与多租户

### 模式 1:同一 chart,多 kubeconfig

```bash
for ctx in dev staging prod; do
  kubectl --context $ctx apply -f ns.yaml
  helm --kube-context $ctx install myapp ./chart \
    -f values-$ctx.yaml \
    -n my-ns
done
```

### 模式 2:Release 命名空间隔离

```text
dev-tenant-a/
  namespace: dev-tenant-a
  release: app
dev-tenant-b/
  namespace: dev-tenant-b
  release: app
```

模板里**所有**资源加 namespace 限制,加上 NetworkPolicy 隔离。

### 模式 3:Cluster-Admin 控制 + Tenant 自治

- 平台团队:用 `Chart.yaml` + 基础 chart 维护
- 业务团队:只能改 values,不能改 chart

通过 OPA / Kyverno 强制:

```yaml
# Kyverno policy
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-helm-versions
spec:
  validationFailureAction: enforce
  rules:
    - name: forbid-latest
      match:
        resources:
          kinds: ["Pod"]
      validate:
        message: "image tag 'latest' 不允许"
        pattern:
          spec:
            containers:
              - image: "!*:latest"
```

## 9.6 Chart 模板复用:模板继承

Helm 没有真正的继承,但可以通过**包含公共 chart**实现。

```text
base-chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── _helpers.tpl
    └── resources/

extended-chart/
├── Chart.yaml          # 依赖 base-chart
├── values.yaml
└── templates/
    └── resources/
        └── extra.yaml  # 新增资源
```

在 extended-chart 中:
```yaml
{{- /* 重新定义 base 的资源,追加额外逻辑 */ -}}
{{- define "myapp.deploymentSpec" -}}
...base 逻辑...
{{- with .Values.extra }}
...扩展...
{{- end }}
{{- end -}}
```

更优雅的做法:**用 Kustomize 组合多个 helm template 输出**(见 9.3)。

## 9.7 Schema-driven templates(进阶)

用 `cue` 或 `jsonnet` 生成 Helm values / templates,把"配置"和"模板"解耦。

```cue
// values.cue
appName: string & =~"^[a-z][a-z0-9-]{0,62}$"
replicaCount: int & >=1 & <=100
image: {
  repository: string
  tag: string
}
```

```bash
# 用 cue 校验 values
cue vet values.yaml values.cue
```

`helmfile` + `cuelang` 是一种严谨的栈,但复杂度较高,适合超大型组织。

## 9.8 Helm + Jsonnet

```bash
# 1. 用 jsonnet 生成 values
jsonnet -y values.libsonnet > values.json

# 2. helm install 用 -f values.json
helm install myapp ./chart -f values.json
```

适合:
- 复杂计算(组合、合并、过滤)
- 团队熟悉 jsonnet

## 9.9 高级控制流模式

### 资源可选生成

```yaml
# 同一文件用 if 控制多资源
{{- if .Values.rbac.create }}
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
...
{{- end }}
{{- if .Values.networkPolicy.create }}
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
...
{{- end }}
```

### 跨 chart 引用(import-values 后)

```yaml
# 父 chart 模板
spec:
  containers:
    - name: app
      env:
        - name: DB_HOST
          value: {{ .Values.mydb.service.host | default (printf "%s-postgresql" .Release.Name) }}
```

### 动态生成 ServiceAccount Token 引用

```yaml
spec:
  serviceAccountName: {{ include "myapp.fullname" . }}
  automountServiceAccountToken: true
```

## 9.10 大型 Chart 的拆分

超过 50 个模板?考虑拆分:

| 方式 | 适用 |
|------|------|
| umbrella chart(依赖) | 同一团队,多组件 |
| helmfile | 多团队,多 release |
| 共享 library chart | 复用基础逻辑 |
| 多 git repo + ArgoCD | 多团队,独立发布周期 |

## 9.11 本章小结

- **Library Chart** = 只提供命名模板的 chart,跨 chart 共享 helpers
- **Helm + Kustomize** = 模板 + 补丁,适合需要叠加 patch 的场景
- **Flux HelmRelease** = 把 Helm 装入 GitOps 循环
- **多集群/多租户** = 命名空间 + NetworkPolicy + RBAC 隔离
- **Schema 驱动** = cue / jsonnet 生成 values,适合大型组织
- 避免单 chart 膨胀,50+ 模板应考虑拆分
