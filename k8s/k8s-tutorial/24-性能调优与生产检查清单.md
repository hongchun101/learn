# 24. 性能调优与生产检查清单

## 24.1 性能调优的方法论

**性能调优 = 找瓶颈 → 测数据 → 改 → 再测**。

```text
1. 找到瓶颈
   - 是 CPU/内存/磁盘/网络?
   - 是应用层 / runtime / 调度层?
2. 量化
   - 测基线(改动前)
   - 设定目标
3. 改
   - 一次只改一项
4. 验证
   - 比较基线
5. 持续
   - 性能是渐变
```

**常见误区**:
- 没有测量就改 → 不知道改了什么
- 一次改多个 → 不知道哪个有效
- 改完不测 → 不知道效果
- 没有目标 → 改了也可能更差

## 24.3 K8s 组件调优

### 1. kube-apiserver

```yaml
# /etc/kubernetes/manifests/kube-apiserver.yaml
spec:
  containers:
  - command:
    - kube-apiserver
    - --max-requests-inflight=2000           # 2000 in-flight 读
    - --max-mutating-requests-inflight=1000  # 1000 in-flight 写
    - --request-timeout=60s
    - --watch-cache-sizes=node#1000,pod#5000,service#2000
    - --enable-priority-fairness=true         # K8s 1.22+ 限流
    - --api-audiences=api
    - --feature-gates=...
    - --v=2
    resources:
      requests: { cpu: 500m, memory: 1Gi }
      limits:   { cpu: 4, memory: 8Gi }
```

**关键参数**:
- `max-requests-inflight`:总 in-flight 请求数
- `max-mutating-requests-inflight`:写 in-flight
- `request-timeout`:请求超时
- `watch-cache-sizes`:watch 缓存
- `--enable-priority-fairness`:流控(防止某个用户打满)

### 2. etcd

```yaml
# /etc/etcd/etcd.config
data-dir: /var/lib/etcd
listen-client-urls: https://0.0.0.0:2379
advertise-client-urls: https://10.0.0.1:2379
# 关键
quota-backend-bytes: 8589934592      # 8GB
# 性能
heartbeat-interval: 100
election-timeout: 1000

# 启动参数
--quota-backend-bytes=8589934592
--max-request-bytes=10485760
```

**关键点**:
- SSD 磁盘(IOPS > 10k)
- `quota-backend-bytes`:etcd 存储上限
- 写多 = 瓶颈,需要分片

### 3. kube-scheduler

```yaml
# /etc/kubernetes/scheduler-config.yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler
  plugins:
    score:
      disabled:
      - name: NodeResourcesLeastAllocated    # 大集群关掉
```

**关键**:
- 减少 plugin 数量(关不用的)
- `percentageOfNodesToScore`:评估节点百分比(5-50%)

## 24.10 容量规划

### 公式

```text
总 CPU = 业务 CPU 总和 × 1.3(HA buffer) / 利用率(0.7)
总内存 = 业务内存总和 × 1.5
总磁盘 = 业务存储 × 1.5
节点数 = 总资源 / 单节点资源

示例:
  业务总: 50 核 / 200Gi
  集群总: 50 / 0.7 × 1.3 = 93 核
  单节点: 8C32G
  节点数: 93/8 = 12 节点
```

### 业务分级

```text
核心服务:   20% 资源,3 副本,跨 AZ
重要服务:   40% 资源,2 副本
普通服务:   30% 资源
批处理:    10% 资源,低优先级
```

```bash
# 2. 看 TCP 慢请求
bpftrace -e '
  kprobe:tcp_sendmsg {
    @start[tid] = nsecs;
    @comm[tid] = comm;
  }
  kretprobe:tcp_sendmsg /@start[tid]/ {
    $lat = (nsecs - @start[tid]) / 1000;
    if ($lat > 1000) {
      printf("%d us: %s\n", $lat, @comm[tid]);
    }
    delete(@start[tid]);
    delete(@comm[tid]);
  }
'

# 3. 文件系统缓存命中率
bpftrace -e '
  kprobe:mark_page_accessed { @access++; }
  kprobe:balance_dirty_pages { @dirty++; }
  END { printf("Hits: %d / Dirty: %d\n", @access, @dirty); }
'
```

## 24.21 真实性能调优案例

### 案例 1:API 延迟 P99 飙到 2s

```text
问题:
  - P99 突然从 200ms 飙到 2000ms
  - CPU/内存正常
  
排查:
  1. Grafana 看延迟分布 → 主要慢在某个 API
  2. pprof 抓 30s profile → 50% 时间在 json.Marshal
  3. 代码 review → 新增字段没标 omitempty
  4. 修复: 加 omitempty,加 tag
  
结果: P99 回到 180ms
```

### 案例 2:节点 OOM 频繁

```text
问题:
  - 节点 OOMKilled
  - cAdvisor 指标内存使用 80%+,但没真正 OOM 应用
  
排查:
  1. dmesg | grep oom → 看到 cgroup 被杀
  2. 检查 cgroup memory.high, memory.max
  3. 某个 DaemonSet 内存泄漏(fluentd)
  4. 重启后内存持续增长
  
修复:
  - 升 fluentd 内存 limit 到 1Gi
  - 监控加上 memory working_set 趋势告警
  - 定期重启(不优雅但有效)
```

### 案例 3:etcd 写延迟高

```text
问题:
  - kubectl apply 卡顿
  - etcd write latency P99 > 100ms
  
排查:
  1. etcd 监控 → fsync wal_fsync 慢
  2. iostat → 磁盘 util 100%
  3. 用云盘 gp3,IOPS 不够
  
修复:
  - 换 io2 Block Express(高 IOPS)
  - 启用 etcd defrag 定期执行
  - 减少大对象写入
```

## 24.23 全链路性能预算

```text
请求 P99 < 200ms 分配:
  - LB/Ingress:        5ms
  - Sidecar/Istio:     2ms
  - 应用:           100ms
  - 业务逻辑:        50ms
  - DB 查询:         30ms
  - 缓存:             5ms
  - 返回:             5ms
  - 网络(全链路):     3ms
  
监控: 每层单独 P99,定位慢在哪
```

### Apdex Score(应用性能指数)

```text
Apdex = (satisfied + tolerating/2) / total
  - satisfied: < T(目标,如 100ms)
  - tolerating: T~4T
  - frustrated: > 4T
  
目标: 0.85+ 优秀, 0.7+ 良好
```
