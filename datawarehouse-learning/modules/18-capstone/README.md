# 模块 18：电商数据仓库综合实战

本模块把前面关于分层建模、维度建模、SQL 开发、数据质量和性能治理的知识收束为一个可运行的电商数仓项目。所有示例都使用仓库统一的小规模 Parquet 数据集，并在单机 DuckDB 中完成，因此不需要 Hadoop、Spark 或云端集群。`src/capstone_pipeline.sql` 复用了 `sql-contract/reference_duckdb.sql` 规定的表名、字段和分层不变量，在其上补充了 RFM 五分位评分、日 KPI 看板、订单金额异常检测和质量审计表。学习重点不是背诵一组 SQL，而是建立“业务口径—数据契约—分层加工—质量验证—服务消费—监控闭环”的完整思考方式。

## ch01 项目背景

假设我们为一家综合电商平台建设统一分析仓库。平台已经积累用户、商品、订单、订单明细和埋点事件五类数据，但业务团队仍依赖临时 SQL：运营计算 GMV 时是否包含退款并不统一，用户团队无法稳定识别高价值客户，财务每天需要手工核对订单金额，风控只能在投诉发生后回查大额订单。数据虽然存在，却没有形成可重复、可审计的决策资产。

源数据分别位于 `ods.users`、`ods.products`、`ods.orders`、`ods.order_items` 和 `ods.user_events`。用户表描述姓名、等级、注册日期、年龄与性别；商品表包含类目和价格；订单事实记录订单金额、状态与业务时间；明细表记录商品数量及成交单价；事件表记录浏览、加购、收藏、支付等行为。它们共同覆盖“人—货—场”的基本链路，也刻意保留了生产系统常见的风险：重复主键、空关键字段、非法枚举、不同时间粒度以及事实与维度失配。

项目采用统一 SQL 契约，而不是为每个引擎随意设计一套表。契约规定 ODS 到 DWD 的清洗关系、DWS 用户日粒度、SCD-2 当前版本唯一性、引用完整性、幂等性以及端到端金额守恒。DuckDB 版本是可执行规格；将来迁移到 Hive、Spark、Trino 或湖仓表格式时，物理语法可以改变，业务不变量不能改变。这种做法让测试验证“结果是否正确”，而不是验证某段实现文本是否恰好长得一样。

本项目的成功标准包括三个层面。第一，数据正确：每个订单在清洗层只有一个最新版本，各汇总层金额可以回溯到明细。第二，产品可用：运营可以直接读取日看板和 RFM 标签，风控可以筛选超过用户平均订单金额十倍的记录。第三，工程可运维：任务可重复执行，失败可定位，质量规则有严重级别，关键指标有基线和告警责任人。单机演示虽小，但流程与真实生产数仓一致。

## ch02 业务需求

业务需求必须先翻译为可计算口径。管理层要求按自然日观察订单总额、下单用户数、订单数、客单价、完成态 GMV、退款订单率，以及浏览到支付的转化率。这里的 `ads.gmv_daily.gmv` 为全部合法订单金额之和，用于验证各层金额守恒；`completed_gmv` 仅累计状态为 `completed` 的订单，避免将不同口径混为同一字段。客单价等于当日订单金额除以订单数，支付转化率等于支付事件数除以浏览事件数，分母为零时结果保留为空而不是伪造为零。

用户运营要求建立 RFM 模型。R 代表距快照日最近一次下单的天数，越小越活跃；F 代表累计不同订单数，越大越频繁；M 代表累计订单金额，越大价值越高。快照日取订单数据中的最大业务日期，避免测试或补数时依赖机器当前时间。三个指标分别用 `NTILE(5)` 划分为 1 到 5 分，排序时增加 `user_id` 作为稳定的并列裁决条件。最终形成三位 `rfm_code`，并映射为冠军、忠诚、潜力、流失风险和普通用户等分群。没有订单的注册用户也必须保留，频次与金额为零，最近购买天数使用显式哨兵值。

风险团队要求发现异常大额订单。当前规则是：某订单金额严格大于该用户全部订单平均金额的十倍时，标记 `is_anomaly=true`。结果表同时保留用户均值、历史订单数和金额倍数，便于复核。它是教学用的可解释规则，不等同于生产反欺诈模型：新用户样本不足、异常订单本身会抬高均值、用户消费季节性等都会影响效果。生产环境应进一步使用排除当前订单的历史均值、中位数绝对偏差、同类目基线和模型评分，但这些增强不能偷偷改变本模块明确的十倍规则。

财务与数据团队要求每层均可对账。ODS 记录数应不少于去重后的 DWD；DWD 金额、DWS 用户日汇总、DWT 用户累计主题和 ADS 日汇总的总金额应在货币精度内一致；DWS 的 `(user_id, dt)` 必须唯一；订单用户必须存在于当前用户维度；状态必须属于约定枚举。上述需求被写成八个自动测试与六项质量审计，而不是只放在需求文档里。测试既覆盖正常样例，也向 ODS 注入一条极端订单后重跑全链路，以证明异常规则真正能够触发。

## ch03 整体架构

整体采用 ODS、DWD、DIM、DWS、DWT、ADS 六层结构。ODS 是源数据的落地区，尽量忠实保留上游字段和业务时间；DWD 将订单、明细、事件清洗为统一明细事实；DIM 保存用户 SCD-2 维度；DWS 按稳定业务粒度做轻度汇总；DWT 保存跨日累计主题状态；ADS 面向看板、运营和风控形成可直接消费的数据集。分层不是为了制造更多表，而是隔离变化：源系统字段变化在 ODS/DWD 消化，公共汇总只实现一次，应用层可以快速响应产品需求。

数据流为 Parquet 文件加载到 `ods.*`，随后执行 `capstone_pipeline.sql`。脚本首先以 `CREATE SCHEMA IF NOT EXISTS` 创建命名空间，再使用“先删后建”的方式生成派生表。DWD 完成关键字段过滤、类型转换、状态标准化和订单去重；DIM 生成当前用户版本；DWS 生成用户日订单及商品日销售；DWT 累计用户首购、末购、活跃天数、终身订单与金额；ADS 依次生成日 GMV、RFM、KPI、异常订单和质量审计。

运行方式是批处理全量重建，适合教学数据。每个派生表在写入前执行 `DROP TABLE IF EXISTS`，因此同一输入重复运行得到相同结果，也不会因上次残留而叠加。生产环境数据量更大时，可将该逻辑改为按 `dt` 分区覆盖、`MERGE INTO` 或湖仓快照提交，但仍应保留相同的输入输出契约。增量化的核心不是简单加一个日期过滤，而是处理迟到订单、状态更新、跨分区去重、维度生效区间和失败重跑边界。

架构中的控制面同样重要。代码仓库保存 SQL、测试和规则；调度器负责依赖与业务日期；元数据系统记录表、字段、负责人和血缘；质量任务输出规则结果；监控系统采集耗时、数据量、延迟与业务指标；告警平台依据严重级别路由。数据平面负责“算出什么”，控制面负责“何时算、是否可信、谁来处理”。本模块在 DuckDB 中物化 `ads.data_quality_audit`，并在 Python 测试中调用 `shared/data_quality.py`，展示 SQL 质量审计与可复用规则引擎如何共同工作。

## ch04 数据模型

订单是本项目的核心事实。`dwd.orders` 的粒度是一行一个 `order_id`，包含用户、金额、标准状态、业务日期 `dt` 和事件时间 `order_ts`。订单明细 `dwd.order_items` 的粒度是一行一个 `item_id`，通过 `order_id` 连接订单、通过 `product_id` 连接商品。必须明确两种金额含义：订单 `total` 是业务系统确认的订单级金额，明细的 `quantity * unit_price` 是商品销售分析金额；优惠、运费和四舍五入会使二者天然不完全相等，因此不能拿明细金额强行替代订单对账口径。

事件事实 `dwd.user_events` 粒度是一行一个 `event_id`。`event_type` 被规范为 `pv`、`cart`、`fav`、`pay`，其他值落为 `other`；日期从 `event_ts` 派生。KPI 看板将事件按日聚合后与订单日指标连接。这里使用订单日期作为看板日期主轴，因此只有事件但没有订单的日期不会单独出现。若产品要求完整时间序列，应引入日期维度作为主表，再分别左连接订单和行为，这属于业务语义调整，不应在无需求时自行扩展。

用户维度 `dim.user_scd2` 演示缓慢变化维第二型：`valid_from` 和 `valid_to` 描述版本有效区间，`is_current` 标记当前版本。现有演示数据只有初始快照，所以每位用户恰好一条当前记录，起始日期固定为 2024-01-01，结束日期为 9999-12-31。真实增量中，等级或姓名变化时，应先关闭旧版本，再插入新版本；事实关联历史维度时使用业务时间满足 `fact_time >= valid_from AND fact_time < valid_to`，而不是永远连接当前版本。

DWS 与 DWT 体现不同汇总职责。`dws.user_order_1d` 一行代表某用户某日，保存订单数、不同订单数、金额和完成态 GMV；`dws.product_sales_1d` 一行代表某商品某日，保存销量和明细口径 GMV。`dwt.user_topic` 一行代表一个有订单的用户，保存跨日累计状态。ADS 是面向用例的宽而小的数据：`gmv_daily` 支撑对账，`daily_kpi` 支撑看板，`user_rfm` 支撑运营，`order_anomalies` 支撑规则筛选，`data_quality_audit` 支撑可信度展示。

## ch05 ODS实现

ODS 的目标是可追溯，不是过早清洗。测试夹具遍历 `data/small/*.parquet`，以文件名作为表名加载到 `ods` 模式，因此五张源表的类型由 Parquet 元数据决定。加载过程在内存数据库中完成，每个测试获得独立连接，不会相互污染。生产落地时应额外记录来源系统、抽取批次、摄取时间、文件路径和校验和，以回答“这条记录来自哪里、何时到达、能否重放”。

ODS 应采用业务日期和摄取日期的双时间观念。订单的 `order_date`、`order_ts` 决定业务归属，摄取时间决定何时被仓库看见。迟到数据可能今天到达却属于上月分区，不能简单以加载日替代订单日。本项目的 DWD 明确把 `order_date` 转为 `dt`，因此迟到记录仍落入正确业务日期。真实增量任务应设置可回溯窗口或维护变更日志，避免只扫描当天文件而漏掉迟到与更正。

源数据进入 ODS 前可以做文件级技术校验，例如文件能否读取、列是否存在、类型是否兼容、行数是否异常、分区是否齐全；但不应静默丢弃业务异常。无法解析的记录应进入隔离区并记录原因，合法记录继续入仓，严重结构变化则阻断任务。结构契约需要区分向后兼容的新增可空列与破坏性变更，如删除关键字段、把数值改为文本或改变主键含义。

本模块没有在 SQL 中重新创建 ODS 表，这是有意的边界设计：运行器负责数据接入，管道负责从已注册的 `ods.*` 开始加工。这样 SQL 契约可以在不同加载方式下复用。直接运行 SQL 前，必须先加载五张源表；测试已经完成这一前置步骤。若只复制 SQL 到一个空数据库，创建模式会成功，但读取 `ods.orders` 会失败，这种显式失败优于用空表或虚假数据掩盖依赖缺失。

## ch06 DWD实现

订单清洗先过滤 `order_id`、`user_id`、`total` 为空的记录，再按 `order_id` 分组，以 `order_ts DESC` 计算 `ROW_NUMBER()`，仅保留最新版本。金额转换为 `DECIMAL(18,2)`，日期转换为 `DATE`，合法状态原样保留，未知状态映射为 `unknown`。去重排序字段必须能够表达版本先后；若源系统同一订单可能出现相同时间戳，还需要增加 CDC 位点或摄取序号作为稳定裁决键。

订单明细过滤空的明细主键与订单外键，并统一单价精度。事件明细过滤空的事件主键与用户外键，标准化事件类型并派生日期。这些规则刻意保持简洁，但每一项都有数据契约含义。空关键字段无法可靠关联，应隔离；金额使用定点数避免二进制浮点累计误差；枚举标准化防止下游每张报表重复编写不同 CASE；日期字段预先派生便于分区裁剪和统一日粒度。

DWD 不应混入应用口径。例如完成态 GMV、客单价、支付转化率都不属于订单明细本身，放在 DWD 会让事实粒度变得模糊。相反，DWD 应保留构建这些指标所需的原子字段。字段命名也要稳定：本契约统一使用 `dt` 表示业务日期，后续 DWS、DWT、ADS 均复用它。迁移到其他引擎时可以改变存储格式、分区语法和表属性，但不应随意重命名或改变状态含义。

幂等性通过派生表重建验证。对相同 ODS 连续运行脚本，DWD 行数和内容不变。测试中的异常案例把新订单插入 ODS 后重新运行全管道，证明新数据会经过同一条清洗路径进入 DWD，而不是直接修改结果表绕过业务逻辑。生产任务失败时也应以原子分区覆盖或事务提交保证读者只看到旧的完整版本或新的完整版本，不能看到半成品。

## ch07 DWS实现

`dws.user_order_1d` 是最重要的公共汇总，主键语义为 `(user_id, dt)`。它从 DWD 订单计算 `COUNT(*)`、`SUM(total)`、`COUNT(DISTINCT order_id)` 和完成态金额。虽然去重后普通订单数应等于不同订单数，同时保留两列可以作为持续诊断：若未来加工逻辑引入重复，二者差异会立即暴露。自动测试既检查该粒度没有重复，又逐用户逐日比较 DWS 金额和 DWD 重新聚合结果。

`dws.product_sales_1d` 通过订单明细连接订单，以订单业务日期归属商品销售，计算数量与 `quantity * unit_price`。关联选择内连接意味着没有合法订单的孤立明细不会进入销售汇总。生产中不应只让孤立行消失，还应把孤立数量写入质量审计并追查上游到达顺序。如果订单与明细异步到达，可以设置等待窗口，或在订单到达后重算受影响分区。

公共汇总层的价值是统一复用。日看板、用户累计主题和 RFM 不必各自扫描原始订单来计算相同的用户日金额。与此同时，不要预聚合所有想象中的维度组合；每增加一张汇总表都会带来存储、调度、补数与口径维护成本。只有粒度稳定、复用广泛、计算昂贵或服务时延明确受益的指标才适合进入 DWS。

增量实现时，用户日汇总应按受影响日期覆盖，而非简单追加。订单状态更新、金额修正或迟到订单都可能改变已存在的 `(user_id, dt)`。一种可靠策略是根据本批变更收集受影响日期，删除或覆盖这些分区，再从当前 DWD 完整重算；更精细的差量聚合需要正确处理撤回值，复杂度更高。无论采用何种策略，金额守恒和粒度唯一测试都必须保留。

## ch08 ADS实现

`ads.gmv_daily` 从用户日汇总再次按日期聚合，输出订单金额、付费用户数和订单数，并按日期排序。它既是简单的应用表，也是端到端对账锚点：`SUM(dwd.orders.total)`、`SUM(dws.user_order_1d.order_amount)`、`SUM(dwt.user_topic.lifetime_amount)` 和 `SUM(ads.gmv_daily.gmv)` 应一致。若不一致，应先按日期定位，再按用户定位，最后回到订单主键，而不是直接在报表层补差额。

`ads.daily_kpi` 合并订单日、事件日和 GMV 日结果，提供完成态 GMV、退款订单数、PV、加购、支付、客单价、支付转化率和退款率。事件数用条件聚合一次完成，空值用 `COALESCE` 归零；比率使用 `NULLIF` 防止除零。金额保留数值类型供 BI 再格式化，不在数仓中拼接货币符号。看板应展示口径说明、数据更新时间与质量状态，避免用户把“没有数据”“真实为零”和“任务失败”看成同一情况。

`ads.user_rfm` 先计算原始 R/F/M，再以窗口函数形成五分位评分。R 按天数从大到小分箱，使最近购买者获得高分；F、M 按数值从小到大分箱，使高频高额用户获得高分。分群 CASE 按优先级匹配，因此冠军用户不会再次落入忠诚用户。五分位是相对评分，适合规模变化较大的运营池；如果业务需要跨月可比，应改用固定阈值并进行版本管理。

`ads.order_anomalies` 为每个用户计算窗口平均值和订单数，对每条订单输出金额倍数与布尔标记。保留未标记记录让规则可审计，也方便统计异常率；消费方只需过滤 `WHERE is_anomaly`。小样本用户应在看板中同时展示 `user_order_count`，避免将一次普通首单误解为有稳定历史基线。异常检测的输出不是自动处罚依据，后续还需身份、支付工具、设备和历史行为等信号进行人工或模型复核。

## ch09 数据质量

质量体系分为字段、记录、集合、跨表和业务五个层次。字段层检查关键字段非空、金额范围和枚举域；记录层检查订单主键去重；集合层检查用户日粒度唯一；跨表层检查订单用户在当前 SCD-2 维度中存在；业务层检查 DWD、DWS、DWT、ADS 金额守恒。只检查非空远远不够：一张每列都有值但金额翻倍的报表仍然是错误数据。

SQL 管道物化 `ads.data_quality_audit`，每行包含检查名、严重级别和违规数量。六项检查分别覆盖订单关键键、金额范围、状态域、DWS 唯一性、引用完整性和端到端金额对账。在本演示中所有 `error` 的违规数量都应为零。审计表便于 BI 展示质量状态，也能保留每次运行历史；生产版应再加入 `run_id`、业务日期、检查时间、阈值、样例主键和负责人。

Python 测试调用 `shared.data_quality.orders_rules()` 与 `evaluate()`，对 DWD 订单 DataFrame 执行共用规则。这样既验证 SQL 结果，又证明通用规则库可以用于不同模块。规则失败应报告名称、严重级别、数量与描述，不要只抛出一个模糊的“数据有问题”。`error` 通常阻断发布，`warn` 允许任务完成但触发关注；阈值必须由业务影响决定，而不是为了让流水线变绿而不断放宽。

八个测试构成可执行验收：ODS 到 DWD 去重与日期完整、DWD 到 DWS 粒度及金额、四层金额守恒、SCD-2 与引用完整、共享规则与审计、注入异常的命中、RFM 用户覆盖和五档评分、KPI 与订单事件重算一致。测试使用独立内存库和确定性数据，避免执行顺序依赖。它们验证观察得到的业务结果，而非搜索 SQL 文本，因此实现可以在保持契约的前提下重构。

## ch10 监控告警

调度监控至少采集开始时间、结束时间、运行状态、重试次数、输入输出行数、扫描字节、业务日期和代码版本。数据新鲜度应从“最新成功业务日期”衡量，不能只看进程是否成功。一个读取昨日旧文件却返回零错误的任务，在技术上成功，在业务上仍然失败。依赖图应明确 ODS 加载完成后才能启动 DWD，公共汇总完成后才能发布 ADS，质量阻断规则通过后看板才切换版本。

指标监控要结合技术基线与业务基线。技术侧关注 DWD 行数突降、去重率突升、孤立外键、空值率、分区大小和运行时长；业务侧关注 GMV 日环比、付费用户、转化率、退款率、异常订单率和 RFM 分群占比。固定阈值适合硬约束，如主键重复必须为零；波动指标更适合同比、环比、移动中位数或季节性区间。告警消息应包含指标、实际值、阈值、业务日期、影响表、任务链接和处理手册。

告警应分级和路由。P1 表示金额对账失败、核心表不可用或大面积数据缺失，需要立即停止发布并通知值班人员；P2 表示新鲜度超时或重要指标显著偏移，需要在约定时间内处理；P3 表示成本或趋势提醒，可进入工作时间队列。重复失败应聚合，恢复时发送恢复通知，避免告警风暴。每条告警必须有明确负责人和升级路径，无人负责的告警等于没有监控。

故障处理遵循“止损、定位、修复、补数、复盘”。先冻结错误 ADS 或回退到最近可信快照；再按血缘从 ADS 到 DWS、DWD、ODS 缩小范围；修复源数据或转换逻辑后，在隔离环境重跑并通过契约测试；随后按业务日期补数并核对下游缓存；最后记录根因、影响、发现方式和预防措施。不要直接手工修改报表数字，因为这会破坏血缘和可重复性，也会让下一次重跑覆盖补丁。

## ch11 案例总结

本案例最终形成一条可重复执行的电商分析链路：ODS 保留五类原始实体，DWD 清洗并统一订单、明细和事件，DIM 管理用户历史版本，DWS 固化用户日与商品日公共粒度，DWT 汇总用户生命周期，ADS 提供金额对账、日 KPI、RFM、异常检测和质量审计。SQL 复用参考契约的核心表与不变量，扩展需求没有绕开原有层次，而是建立在可信公共数据之上。

最重要的工程经验有四点。第一，先定义粒度和口径，再写 SQL；一行代表什么说不清，任何聚合都可能重复。第二，把正确性写成可运行测试；金额守恒、唯一性和引用完整性比代码风格更能保护重构。第三，区分公共模型与应用模型；DWD/DWS 稳定复用，ADS 面向场景快速变化。第四，质量与监控不是上线后的附件，它们决定数据何时能够被信任和发布。

学习者可以按以下顺序练习：先阅读 `sql-contract/reference_duckdb.sql` 和不变量说明，再逐段运行管道并查询各层行数；选择一个用户从 ODS 订单追踪到 DWS、DWT、RFM；选择一个日期核对 DWD、DWS、GMV 和 KPI；向 ODS 注入重复、非法状态、负金额或极端大额记录，观察清洗、审计和测试分别如何响应；最后尝试将全量重建改为按日期覆盖，同时保证八个测试仍通过。

若将项目推广到生产，下一步不是盲目增加工具，而是依据瓶颈演进：数据增长后引入分区湖仓和增量计算，并发查询增长后引入专用 OLAP 服务，血缘复杂后接入元数据平台，规则增多后引入集中质量服务。无论技术栈如何变化，业务契约、可追溯时间、幂等发布、端到端对账和告警闭环都应保留。一个成熟数据仓库的价值，不是“每天生成了很多表”，而是让业务在已知口径、已知时效和已知质量的前提下安全决策。
