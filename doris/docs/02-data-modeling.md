# 02｜表模型与物理设计

表设计决定性能上限。索引、物化视图和参数只能在这个上限内优化。先确定业务语义，再选择数据模型、Key、分区、分桶和索引。

## 1. 三类表模型

| 模型 | 相同 Key 的语义 | 适合 | 主要风险 |
|---|---|---|---|
| Duplicate Key | 全部保留 | 事件、日志、不可变明细 | 重放会重复；更新需另行设计 |
| Unique Key（主键） | 只保留同 Key 的最新版本 | CDC 当前快照、订单状态、维表 | Key 选错会覆盖业务上不同的行；写放大 |
| Aggregate Key | 按 Key 合并 Value 聚合 | 固定粒度预聚合、指标状态 | 丢失明细；聚合函数与查询语义绑定 |

**决策顺序**：

1. 一行代表什么业务事实？
2. 同一业务 Key 再来一条数据，是保留、覆盖还是合并？
3. 是否需要乱序更新、部分列更新、删除？
4. 最常用过滤、Join、聚合和保留策略是什么？

不要因为“以后可能更新”就全部用 Unique。事件明细通常应保留每次事实；当前状态表才适合覆盖。

### 1.1 Duplicate Key

`fact_order_items` 以 `(order_date, shop_id, order_id)` 开头排序。Key 是排序/前缀索引的一部分，不保证唯一。上游重发必须通过事件 ID、导入 label、ETL 去重或下游语义控制。

### 1.2 Unique Key

`fact_orders` 使用 `(order_id, order_date)`。同 Key 的新版本覆盖旧版本。Merge-on-Write 使读取更快，代价是写入/Compaction 成本。生产 CDC 还要处理：

- 乱序：旧事件晚到不能覆盖新状态；使用序列列或来源版本控制，精确语法按当前版本文档；
- 删除：确认逻辑删除/DELETE 信号如何映射；
- 部分更新：区分“缺失字段”和“写 NULL”；
- Key 包含分区列时，上游更新分区列可能实质上是跨分区删除 + 插入。

### 1.3 Aggregate Key

`agg_shop_daily` 把 GMV、件数、订单 Bitmap、买家 HLL 保存为可合并状态。它适合固定粒度，不适合作为唯一事实来源。

- `BITMAP`：精确去重，适合可映射到整数域的 ID；资源随基数增长。
- `HLL`：近似去重，内存稳定但有误差；不能用于财务结算。
- `SUM/MIN/MAX/REPLACE` 等聚合行为必须与业务可结合性一致。

## 2. Key 与列顺序

排序 Key 设计遵循查询，而不是照搬 OLTP 主键：

1. 高频等值过滤列；
2. 高频范围列；
3. 能显著聚簇和压缩的列；
4. 兼顾 Join/聚合局部性。

低选择性列若几乎每个查询都会过滤，仍可能值得前置；高基数但很少过滤的 UUID 不应机械前置。用真实 workload 的扫描字节验证。

列顺序也影响前缀索引。不能只创建很多二级索引来弥补错误排序。

## 3. 分区：裁剪与生命周期

时间事实表通常按事件日期或业务日期做 RANGE 分区。选择粒度时权衡：

- 日分区：便于按日保留、回灌；多年数据会有大量分区；
- 月分区：元数据少；单日查询多扫、单日回滚不便；
- 动态分区：减少人工 DDL，但必须监控未来分区是否成功创建；
- 自动分区：适合到达值驱动的分区管理，仍需控制分区爆炸。

硬规则：查询必须尽量携带分区列范围；生命周期用分区删除，不用巨量逐行 DELETE；提前创建未来分区并对无分区导入告警。

## 4. 分桶：并行与均衡

Hash 分桶应选稳定、分布均匀、常用于 Join 的列。目标不是桶越多越好，而是让 Tablet 尺寸、并行度和调度开销平衡。

估算流程：

1. 测量单分区压缩后大小 $S_p$；
2. 设目标 Tablet 大小区间 $T$（用真实硬件测试决定）；
3. 初始桶数约为 $\lceil S_p/T \rceil$；
4. 再检查是否足以利用 BE 并行、是否导致小 Tablet；
5. 检查 Top Key 占比和每桶行数/字节差异。

不要写死一个全公司的桶数。随机分桶适合没有好 Hash Key 的明细写入，但会失去基于 Key 的数据局部性。自动分桶适合快速开始，不替代容量评审。

## 5. 索引选择

| 索引 | 典型谓词 | 不适合 |
|---|---|---|
| 排序/前缀 | Key 前缀等值、范围 | 任意非前缀组合 |
| Min/Max | 有聚簇性的范围过滤 | 值在每个块内都很散 |
| Bloom Filter | 高基数等值/IN | 低基数、范围、强模糊匹配 |
| Bitmap | 低/中基数组合过滤 | 超高基数且频繁写 |
| 倒排索引 | 文本搜索、任意字段快速过滤 | 不验证分词器就做语义假设 |
| NGram | LIKE/文本子串的特定场景 | 所有字符串列默认开启 |
| 向量索引 | ANN 相似检索 | 需要绝对精确全排序却不做召回评估 |

索引有存储、写入和 Compaction 成本。上线前做 A/B：导入吞吐、索引大小、目标查询扫描量和 P95。

## 6. Schema Change 与类型

- 金额用 `DECIMAL`，不要用浮点数承担结算语义。
- ID 若不计算，优先以能保持来源语义的整数或字符串存储。
- 时间统一时区策略，明确事件时间、处理时间和业务日期。
- `VARCHAR` 长度、`NULL`、默认值必须表达业务，而不是为压缩随意选择。
- `ARRAY`/`MAP`/`STRUCT`/`JSON`/`VARIANT` 能容纳半结构化数据，但高频分析字段应显式治理；否则类型漂移和不可预期路径会污染指标。
- Schema Change 前评估重写、磁盘峰值、并发写和回滚；大表先在同规模预生产演练。

## 7. 星型模型、宽表还是实时快照

- **星型模型**：治理清晰、维度复用；多 Join 对统计信息与网络敏感。
- **宽表**：查询简单；维度更新、冗余和回填成本高。
- **主键快照**：实时状态查询好；历史变化需另存事件或拉链。
- **预聚合**：极快固定指标；灵活性低，必须可从事实表重建。

专家通常混合使用：不可变事实 + 当前状态 + 维表 + 少量由工作负载证明有价值的物化/聚合层。

## 8. 设计评审清单

每张表必须回答：

- 粒度、唯一性、迟到/重复/删除语义；
- 日增行数/字节、保留期、压缩实测、峰值导入；
- Top 10 查询的过滤、Join、聚合；
- 模型、Key 顺序、分区、分桶及证据；
- 目标 Tablet 数量/大小、数据倾斜；
- 索引收益与写入代价；
- 回灌、Schema Change、删除与重建方式；
- 数据质量断言和负责人。

## 9. 实验

1. 运行示例，证明 Duplicate 保留明细、Unique 覆盖、Aggregate 合并；
2. 将查询谓词改为非 Key 前缀，比较扫描行/字节；
3. 制造一个 `shop_id` 占 70% 的数据集，观察桶倾斜；
4. 分别用明细 `COUNT(DISTINCT)`、BITMAP、HLL 计算 UV，比较准确性和资源；
5. 给一个没有业务 Key 的日志表做设计答辩，明确为什么不选 Unique。

## 10. 过关标准

能在 15 分钟内为新表给出有数字、有失败语义、有验证计划的设计；能识别分区爆炸、Tablet 过多、热点 Key、Key 覆盖错误四类事故风险。
