# 05 — Pitfalls (Common Mistakes and How to Avoid Them)

> Every PostgreSQL expert has made most of these mistakes at least
> once. The goal of this document is to help you make them *once*.

Organized by Part of the curriculum.

---

## Part 1 — SQL Core

### P1.1 Using `real` or `double precision` for money

**Symptom**: `sum` of a column doesn't add up. Some rows have values
like `19.9899999` instead of `19.99`.

**Cause**: IEEE 754 floating point. `0.1 + 0.2 != 0.3` in floating
point, even on a clean room.

**Fix**: Use `numeric(12, 2)` (or `decimal`, the alias). For amounts
that don't need a fixed precision, only use `double precision` when
you understand the rounding.

**Prevention**: `numeric` for currency, percentages, and any quantity
that is summed many times.

---

### P1.2 Using `serial` instead of `IDENTITY`

**Symptom**: Migrations that drop and recreate the sequence break
foreign keys; the `serial` pseudo-type is a hack that doesn't
compose with `pg_dump --schema-only`.

**Cause**: `serial` is shorthand for `int NOT NULL DEFAULT nextval(...)`.
The sequence is owned by the column, but it's awkward to dump.

**Fix**: Use `GENERATED ALWAYS AS IDENTITY` or `GENERATED BY DEFAULT
AS IDENTITY`. The latter is equivalent to `serial`; the former is
strict (you cannot override the value).

**Prevention**: Standard rule in the curriculum. Module 04.

---

### P1.3 Using `ORDER BY` without `LIMIT` and expecting deterministic order

**Symptom**: Tests pass in development, fail in production. The data
is the same but the order is different.

**Cause**: Without `ORDER BY`, the planner is free to return rows in
any order. With ties on the `ORDER BY` columns, even the order is
unspecified.

**Fix**: When order matters, add a tiebreaker. `ORDER BY created_at,
id` is the canonical safe pattern.

**Prevention**: Code review rule. Every `SELECT` without `LIMIT` and
without an `ORDER BY` is suspect.

---

### P1.4 Using `SELECT *` in production code

**Symptom**: A column rename breaks production at 2 AM.

**Cause**: `SELECT *` is convenient. The cost is that the consumer
depends on the column order *and* existence.

**Fix**: Always name columns in application code. Use `SELECT *`
only in ad-hoc queries.

**Prevention**: Linter rule. Most ORMs let you list columns.

---

### P1.5 Forgetting `DISTINCT` after a JOIN

**Symptom**: A `count(*)` is wrong by a factor of 3.

**Cause**: One-to-many JOINs multiply rows. `count(*)` after a JOIN
counts joined rows, not original rows.

**Fix**: Either `count(DISTINCT original_table.id)` or use a
subquery / CTE to dedupe first.

**Prevention**: `EXPLAIN`. If the row count multiplies after a JOIN,
that's the warning sign.

---

### P1.6 `JOIN` with an `ON` clause that uses `OR`

**Symptom**: Slow query. `EXPLAIN` shows a Seq Scan when an Index Scan
is expected.

**Cause**: `OR` defeats index usage in most predicates. The planner
often can't push a predicate with `OR` into an index.

**Fix**: Either split into `UNION ALL` of two indexed queries, or
use `IN (...)` if the values are bounded.

**Prevention**: Review rule. Any predicate with `OR` on a column
that's indexed needs justification.

---

### P1.7 `BETWEEN` with `timestamptz` and a half-open interval

**Symptom**: A query at midnight misses the last row of the day.

**Cause**: `timestamptz` has microsecond precision. `placed_at
BETWEEN '2025-12-01 00:00:00+00' AND '2025-12-01 23:59:59+00'` works
*almost*. But `BETWEEN` is inclusive on both ends; for a date range
you want half-open: `placed_at >= '2025-12-01' AND placed_at <
'2025-12-02'`.

**Fix**: Always use half-open intervals for ranges. `tsrange` and
`daterange` have `[]` (closed) and `[)` (half-open) bounds.

**Prevention**: Code review.

---

### P1.8 Putting `count(*)` in the same `SELECT` as a window function

**Symptom**: `count(*)` doesn't match the expected number of rows.

**Cause**: A window function's frame is per-row. `count(*) OVER ()`
counts the rows in the window, not in the table.

**Fix**: Use `count(*) OVER ()` if you want the table count; use a
plain aggregate if you want the partition count.

**Prevention**: Module 07 (window functions).

---

### P1.9 Using `IN (subquery)` instead of `EXISTS`

**Symptom**: Slow query on a large table.

**Cause**: `IN (subquery)` materializes the subquery. `EXISTS` does
not.

**Fix**: For "does this row exist?" use `EXISTS`. For "is this value
in a list?" use `IN (literal list)` or `= ANY(ARRAY[...])`.

**Prevention**: Module 09.

---

### P1.10 Joining on `text` columns without thinking

**Symptom**: Slow query. The plan shows a hash join on a million-row
table.

**Cause**: Hash join is fine. But joining on a `text` column
without an index forces a hash, which is fine, until the text
column is large enough that the hash spills to disk.

**Fix**: Either add an index on the join column or rewrite the
join. If the join is many-to-many, consider a denormalization.

**Prevention**: Module 11.

## Part 2 — Advanced SQL

### P2.1 Creating an index and assuming the planner will use it

**Symptom**: Slow query, but `EXPLAIN` doesn't show the index.

**Cause**: The planner picks a plan based on cost, not on your
intent. If the index would scan more pages than a sequential scan,
the planner picks the seq scan.

**Fix**: Verify with `EXPLAIN`. If the index is not used, the
predicate probably doesn't match the index. Or the table is too
small.

**Prevention**: Module 11. Always run `EXPLAIN` on the production
workload after adding an index.

---

### P2.2 Using a function on the indexed column

**Symptom**: Index not used.

**Cause**: `WHERE lower(name) = 'foo'` doesn't use an index on
`name`. The function call hides the value from the index.

**Fix**: Build an expression index:
```sql
CREATE INDEX name_lower_idx ON table (lower(name));
```

**Prevention**: Module 11.

---

### P2.3 `SELECT DISTINCT` to dedupe when `GROUP BY` is what you want

**Symptom**: Slow query. The plan shows a Sort then Unique.

**Cause**: `DISTINCT` and `GROUP BY` without aggregates behave
similarly, but `GROUP BY` is sometimes cheaper, especially with
multiple columns.

**Fix**: Use `GROUP BY` when you want one row per group; use
`DISTINCT` when you want to dedupe arbitrary rows.

**Prevention**: Module 06.

---

### P2.4 Materialized view refresh blocking writes

**Symptom**: Application hangs during `REFRESH MATERIALIZED VIEW`.

**Cause**: Default `REFRESH` takes an `ACCESS EXCLUSIVE` lock.

**Fix**: Add a unique index to the materialized view, then use
`REFRESH MATERIALIZED VIEW CONCURRENTLY`.

**Prevention**: Module 12.

---

### P2.5 Trigger that calls `pg_notify` inside an uncommitted transaction

**Symptom**: Notifications are received but the data isn't there
when the listener queries.

**Cause**: `NOTIFY` messages are sent at `COMMIT`, not when the
trigger fires. The receiver gets them, but if the receiver reads
the row before the COMMIT lands on the replica (in a replication
setup), the data isn't there yet.

**Fix**: This is by design. Document the behaviour. If you need
read-your-notify-consistency, the receiver must wait for the
transaction to be visible.

**Prevention**: Module 13.

---

### P2.6 PL/pgSQL function marked `VOLATILE` by accident

**Symptom**: Slow query, the function is called row by row.

**Cause**: Default volatility for PL/pgSQL functions is `VOLATILE`.
That means the planner cannot inline the function or call it once
for many rows.

**Fix**: Mark the function `STABLE` if it doesn't modify the
database and always returns the same result for the same
arguments in a single query. `IMMUTABLE` if the same is true
across queries.

**Prevention**: Module 13.

---

### P2.7 `SECURITY DEFINER` without `SET search_path`

**Symptom**: Function works for the owner but fails for other users.

**Cause**: A `SECURITY DEFINER` function runs with the privileges
of its owner. But `search_path` is still the caller's. A user with
a malicious schema in their search_path can intercept the function's
SQL.

**Fix**: Always `SET search_path = pg_catalog, public` (or similar)
in the function definition. Or specify it explicitly on each
object.

**Prevention**: Module 23.

---

### P2.8 RANGE-partitioning by a column with NULLs

**Symptom**: A NULL row goes into the default partition. A query on
the partition key misses it.

**Cause**: `NULL` is not in any range, so it's caught by the
default partition (if you have one).

**Fix**: Either make the column `NOT NULL` or partition by `LIST`
and explicitly include `NULL`.

**Prevention**: Module 14.

---

### P2.9 Foreign table on a remote server without `fetch_size`

**Symptem**: A `SELECT *` from a remote table pulls all rows in one
query, blocking.

**Cause**: `postgres_fdw` defaults to fetching the whole result
set.

**Fix**: `ALTER SERVER … OPTIONS (fetch_size '1000')`.

**Prevention**: Module 15.

---

## Part 3 — Internals

### P3.1 Doing `SELECT count(*) FROM huge_table`

**Symptom**: Slow query.

**Cause**: PostgreSQL has to read every row to count them. Index-only
scans can do `count(*)` if the visibility map is fully set, but
that's rare for actively-written tables.

**Fix**: Use `pg_stat_user_tables.n_live_tup` for an approximate
count. Use `count(*) WHERE …` for a precise subset. Use a
materialized view for repeated queries.

**Prevention**: Module 10.

---

### P3.2 Long transaction blocking vacuum

**Symptom**: Bloat grows even though vacuum runs.

**Cause**: A long-running transaction (an `idle in transaction`
session, a long `SELECT`) prevents vacuum from reclaiming tuples.

**Fix**: Find the long transaction; kill it. Application code must
not hold transactions open during user think time.

**Prevention**: Module 19.

---

### P3.3 Disabling autovacuum

**Symptom**: "Vacuum doesn't work, why?"

**Cause**: Autovacuum is disabled (per-table or globally).

**Fix**: Re-enable. Run a manual `VACUUM` if necessary, but never
disable autovacuum.

**Prevention**: Module 19.

---

### P3.4 Thinking the WAL is just a redo log

**Symptom**: Misunderstanding what archive_mode is for.

**Cause**: The WAL is *also* the source of truth for streaming
replication, logical replication, and PITR. It's not just for crash
recovery.

**Fix**: Read module 17.

**Prevention**: Module 17.

---

### P3.5 `shared_buffers = 16GB` on a 16GB box

**Symptom**: OOM killer fires.

**Cause**: `shared_buffers` is just one region of memory. Other
regions: `work_mem * connections`, `maintenance_work_mem`,
process-private buffers. 25% of RAM is the rule of thumb.

**Fix**: Lower `shared_buffers`. Lower `work_mem`.

**Prevention**: Module 18 and the tuning cheatsheet
(`docs/06-tuning-cheatsheet.md`).

---

## Part 4 — Admin & Ops

### P4.1 Running a destructive migration without testing on a copy

**Symptom**: Downtime at 2 AM.

**Cause**: The migration took an `ACCESS EXCLUSIVE` lock. Or it
rewrote a billion rows. Or it broke a foreign key.

**Fix**: Restore from backup. Apply the migration on a copy first.
Use `CREATE INDEX CONCURRENTLY` in production.

**Prevention**: Always. No exceptions.

---

### P4.2 `pg_dump` and assume that's your backup strategy

**Symptom**: A 5 TB database, a 5-day restore.

**Cause**: `pg_dump` is logical, so it takes O(database size) time
to restore. For a 5 TB database, use `pg_basebackup`.

**Fix**: `pg_dump` for small databases (< 100 GB), schema-only
dumps, or selective data dumps. `pg_basebackup` for full-cluster
backup. Combine with WAL archiving for PITR.

**Prevention**: Module 21.

---

### P4.3 Replication slot with no consumer

**Symptom**: Disk fills up.

**Cause**: A replication slot holds WAL until the consumer has
acknowledged. If the consumer is gone, WAL piles up.

**Fix**: Drop the slot if there's no consumer. Monitor slot lag.

**Prevention**: Module 20.

---

### P4.4 Putting pg_hba.conf with `trust` in production

**Symptom**: Anyone on the network has superuser access.

**Cause**: `trust` skips authentication. Useful in dev, fatal in
prod.

**Fix**: `scram-sha-256` is the default since PG 10. Use `md5` only
if you need to talk to PG < 10 clients. Use `peer` for local Unix
socket.

**Prevention**: Module 23.

---

### P4.5 RLS policy that depends on a session variable that isn't set

**Symptom**: Application sees zero rows.

**Cause**: The policy uses `current_setting('app.actor_id', true)`.
If the application forgot to set it, the policy returns NULL, and
the row is filtered out.

**Fix**: The policy is correct, but the application must always
set the variable. Document this. Add a `NOT NULL` check on a default
value.

**Prevention**: Module 23.

---

### P4.6 Installing extensions without checking licenses

**Symptom**: Legal issues.

**Cause**: Some extensions are GPL, some are BSD, some are
proprietary. `pgvector` is PostgreSQL-like (BSD-ish). `postgis` is
GPL. `citus` is AGPL.

**Fix**: Check before installing. Most are fine for commercial use,
but verify.

**Prevention**: Module 24.

---

## Part 5 — Performance

### P5.1 `SELECT FOR UPDATE` on every read

**Symptom**: Slow application, lock contention.

**Cause**: Application locks rows on read, blocking concurrent
reads.

**Fix**: Only lock when you actually need to mutate. `SELECT FOR
KEY SHARE` is much weaker than `FOR UPDATE`.

**Prevention**: Module 26.

---

### P5.2 `SKIP LOCKED` without a unique constraint

**Symptom**: Same row processed twice.

**Cause**: Two workers both `SELECT … SKIP LOCKED LIMIT 1`. Both
see the same row, both skip it, both pick the next one. Wait, that
doesn't double-process.

**Cause (real)**: Without a unique constraint, the queue table
allows duplicates. Two workers insert the same work item.

**Fix**: Unique constraint on the queue.

**Prevention**: Module 26.

---

### P5.3 Disabling sequential scans with `enable_seqscan = off`

**Symptom**: Slow query, because forcing the index is slower than
the seq scan.

**Cause**: The planner was right; you overrode it.

**Fix**: Re-enable seq scan. Find the real fix (work_mem, stats,
index).

**Prevention**: Module 18.

---

### P5.4 `pg_prewarm` on a 100 GB table

**Symptom**: Cluster runs out of memory.

**Cause**: `pg_prewarm` loads the whole table into `shared_buffers`.

**Fix**: Use `pg_prewarm` selectively — preload the index, not the
heap. Or pre-warm the OS page cache, not `shared_buffers`.

**Prevention**: Module 27.

---

### P5.5 Sharding when a bigger box would do

**Symptom**: Complexity explodes; bugs multiply.

**Cause**: Engineering chose the most expensive option first.

**Fix**: Vertical scaling first. 32 cores / 256 GB / NVMe is
enough for most OLTP workloads. Sharding is for the
post-10-TB stage.

**Prevention**: Module 28.

---

## Part 6 — Misc

### P6.1 Not using `EXPLAIN` at all

**Symptom**: "I don't know why this query is slow."

**Fix**: Use `EXPLAIN (ANALYZE, BUFFERS)` for every query in a
performance-sensitive path. This is the single highest-leverage
habit in the curriculum.

**Prevention**: Module 10.

---

### P6.2 `psql` without `\pset null` and `\x auto`

**Symptom**: Misreading query output.

**Cause**: Default `psql` shows NULL as empty string. Wide output
is unreadable.

**Fix**: In `~/.psqlrc`:
```
\pset null '∅'
\x auto
\timing on
```

**Prevention**: Module 10.

---

### P6.3 `DELETE` instead of `TRUNCATE` for full-table clears

**Symptom**: Slow cleanup.

**Cause**: `DELETE` writes a WAL record per row. `TRUNCATE` writes
one record for the whole table.

**Fix**: `TRUNCATE big_table RESTART IDENTITY;` (when you mean it).

**Prevention**: Module 02.

---

### P6.4 Wrapping everything in a transaction

**Symptom**: Idle-in-transaction sessions; long lock-hold times.

**Cause**: The application opens a transaction, then calls an
external service, then commits. The transaction is open for
seconds.

**Fix**: Only open a transaction when you actually write. Read
transactions don't need to be wrapped.

**Prevention**: Module 16.

---

### P6.5 Not reading the docs

**Symptom**: Re-inventing the wheel; using deprecated syntax.

**Cause**: PostgreSQL has the best documentation of any database
system. It's linked from every module.

**Fix**: When in doubt, read the module's README "See also"
section. Then read the linked PostgreSQL manual chapter.

**Prevention**: Throughout.

---

## The meta-rule

If you find yourself thinking "this is taking a long time, let me
just write a script to do it in a loop", stop. PostgreSQL is a
set-oriented engine. If you're looping, you're doing it wrong.
There's a set-based solution, and it's almost always faster.
