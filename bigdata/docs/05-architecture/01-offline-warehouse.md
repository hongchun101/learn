# 离线数仓:分层、建模与命名规范

## 一、为什么要分层

没有分层的数仓,ETL 是"一张表读全量、反复 join、批量重算",一旦上游 schema 变更,下游全部崩盘。分层的目的不是"好看",而是:

1. **收敛重复逻辑**——同一份聚合只算一次,下层引用上层结果;
2. **降低口径成本**——指标负责人只看一张 DWS,业务消费只看 ADS;
3. **支持高效回刷**——DWD 错改了一列,只需重跑 DWS/ADS,不需要回到 ODS 重写一遍;
4. **解耦存储压力**——冷数据沉 ODS(压缩、Orc/Parquet),热数据浮 ADS。

## 二、经典四层模型

### 1. ODS(Operational Data Store)贴源层

- **职责**:原始数据落地,**不做任何业务清洗**,字段与源系统 1:1 对齐。
- **典型来源**:MySQL binlog(Kafka)、业务日志(Flink CDC)、第三方接口落盘。
- **存储格式**:Iceberg/Hudi,Parquet+压缩,zstd/gzip。
- **保留策略**:大多数表 90 天滚动,合规字段(身份证/银行卡)需脱敏或只存哈希。

### 2. DWD(Data Warehouse Detail)明细层

- **职责**:面向业务过程的明细,做**清洗 + 维度退化**。
- **关键动作**:去重(`row_number` 取最新)、空值填充、单位统一(分→元只在展示时做)、脏数据打标。
- **典型模型**:`dwd_trade_order`、`dwd_user_register`、`dwd_page_log`。
- **粒度**:一笔订单一行,一次曝光一行,**不可汇总**。

### 3. DWS(Data Warehouse Summary)汇总层

- **职责**:面向主题的轻度汇总(分钟/小时/天),**宽表化**。
- **特点**:宽表化(>20 列),同一主题把多 DWD join 起来,比如"用户 × 商品 × 商家 × 时间"的日宽表。
- **典型模型**:`dws_user_action_day`、`dws_sku_sale_day`、`dws_gmv_topic_day`。
- **聚合粒度**:可按主题分层(day/周/月),指标在 DWS 内一次性产出。

### 4. ADS(Application Data Store)应用层

- **职责**:面向报表/接口的主题输出,**强耦合业务取数需求**。
- **形态**:大宽表/物理视图/接口结果表,直接对接到 BI、自助取数、API。
- **注意**:ADS 一张表通常只服务一个产品/一个看板,字段冗余,生命周期短。

## 三、经典建模法对比

### 1. Inmon(自顶向下)

- **方法**:先建全企业级 3NF 数据模型(EDW),再从 EDW 派生数据集市。
- **优点**:一致性高,数据冗余少。
- **缺点**:前期投入大,见周期长,中国互联网公司很少纯走这条路。

### 2. Kimball(自底向上)

- **方法**:维度建模——事实表 + 维度表,总线矩阵(Conformed Dimension)串起数据集市。
- **核心概念**:事实(可度量、可加性)、维度(谁/何时/何地/什么)、缓慢变化维(SCD 1/2/3)。
- **优点**:迭代快、上手容易,**国内 90% 的离线数仓**采用此思路。

### 3. Data Vault(中间路线)

- **方法**:Hub(业务键)+ Link(关系)+ Satellite(属性)的 DV 2.0。
- **优点**:全量可追溯、对源系统变更友好、按需扩展。
- **缺点**:表多、查询需要多次 join,工程复杂度高,只在金融/保险领域被严格执行。

## 四、命名规范示例(国内某厂)

```
层级_主题_业务过程_[统计周期]_[分区]
dwd_trade_order_inc              -- ODS 增量
dwd_trade_order_full             -- DWD 明细
dws_trade_goods_sale_1d         -- DWS 1 天汇总
ads_bi_dashboard_gmv_di          -- ADS 日报表
```

| 字段 | 含义 |
|-----|------|
| `dt` | 分区字段 yyyy-MM-dd |
| `hour` | 分区字段 HH |
| `event_time` | 业务时间(用户行为发生时间) |
| `proc_time` | 处理时间(Flink 机器时间) |
| `etl_source` | 来源系统标识 |

## 五、口径与生命周期治理

- **同名不同义**:把 GMV、退款 GMV、净 GMV 在 DWS 层一次性区分清楚,通过视图/字段注释落到 ADS。
- **生命周期**:ODS 90 天、DWD 1 年、DWS 永久(冷热分层)、ADS 按业务定。
- **回刷机制**:DWS/ADS 必须支持按分区 idempotent 回刷,Flink/Hive/Spark 任务幂等键 = partition_key + biz_key。

## 六、常见踩坑

1. **ODS 全量分区爆炸**:MySQL 全量 + 每天一个分区,半年就过百万分区,改名/查询全废。解决:CDC + Iceberg 的 snapshot,按小文件合并策略。
2. **DWS 太宽(50+ 列)**:join 慢、输出慢、回刷痛苦。解决:拆主题宽表 + 字典表二阶段查询。
3. **ADS 与 DWS 同名**:二者在 BI 上"看上去一样",业务报表变更时怀疑口径,务必保持命名差异。

> **结论**:分层与命名不是文档问题,是数据治理问题。命名混用意味着责任链断裂,后续 DQ、字段血缘、成本分析全部失效。
