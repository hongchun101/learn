# Lambda 与 Kappa:双链路困境与流批一体的真正解

## 一、Lambda 架构的起源

Nathan Marz 在 2011 年基于他在 BackType/Twitter 的经验提出 Lambda 架构,核心假设是"任何系统都无法同时满足低延迟、高吞吐、可重算三者"。

- **Batch Layer**:周期长(T+1)但结果精确,处理全量数据;
- **Speed Layer**:实时但近似,只处理增量;
- **Serving Layer**:合并两路结果对外服务。

国内 2014—2020 年绝大多数大厂数仓的"实时 + 离线"双链路都源自这一思路。

## 二、Lambda 的工程灾难

随着业务推进,Lambda 架构的痛点不是"理论"上的,而是工程上极其具体:

| 现象 | 代价 |
|-----|------|
| 两套代码(Spark + Flink)维护同一份业务逻辑 | 研发成本 ×2、回滚策略 ×2 |
| 两套口径(批/流答案对不齐) | 业务投诉"昨天和今天不一样" |
| 两套存储(MySQL/Hive vs Kafka/HBase) | 成本高、治理难、字段血缘断 |
| 一次回刷 = Batch 重跑 + Speed 重跑 | 出错率直线上升 |
| 凌晨调度资源争抢,实时任务旁路 | SLA 难以保证 |

**典型场景**:电商大促期间,实时 GMV 与离线 GMV 对不上,运营拿 BI 截图质问。

## 三、Kappa 架构的救赎

Jay Kreps(LinkedIn Kafka 作者)在 2014 年提出 Kappa:用 Kafka 作为唯一数据源,把批处理退化为"流的一段时间窗"。

- **核心动作**:
  - 业务日志、数据库变更全部入 Kafka(topic 长期保留,7—30 天);
  - Flink 处理 Kafka 流,实时写入下游(DB/OLAP);
  - 当算法或口径变化时:**重新计算并替换结果**(reprocessing),把历史消息重新消费一次。
- **优点**:一套代码、一份口径、一套存储,工程极简。
- **前提条件**:
  1. Kafka 等消息中间件可长期保留(≥ 7 天);
  2. 消息顺序、幂等性、回放机制成熟;
  3. 计算引擎支持流式重算且成本可控。

## 四、Kappa 的真实挑战

**1. Kafka 不是存储**

Kafka 的日志结构虽然支持重放,但它不是数据库/数据仓库:

- 长期保留成本高,Schema 演化难;
- 没有 ACID 事务,Kafka 自身的 ISR 故障可能导致丢失;
- 缺少"时间旅行"能力,合规审计不易;
- 长时间窗口(>30 天)回放,光攒消费位移就要消耗大量带宽。

**2. 流不能解决所有问题**

训练机器学习、出 T+1 报表、做大批量 join 时,纯流方案在成本/复杂度上急剧上升。

**3. 回放压力**

当上游错乱需要重算,re-processing 全量 Kafka 主题会引发:

- 集群带宽打满;
- 下游 OLAP 短时间写入压力飙升;
- 任务调度链式排队。

## 五、为何 Iceberg/Hudi/Paimon 是"流批一体"的关键

Lambda 和 Kappa 都试图抹平两套系统的鸿沟,真正的解法是把**"批"与"流"的边界平移到数据格式层**。

### 1. Iceberg 的解法

- **Snapshot 模型**:每次写入都生成一个不可变快照,流写入也是"小快照";
- **Hidden Partition**:写入时自动算 partition,不用下游关心分区字段;
- **Time Travel**:可通过快照回查任意时间点;
- **多引擎**:Trino、Spark、Flink 同时读写一张表;
- **流批统一**:Flink 实时写、Spark 批重算,下游查的是同一份 Iceberg,口径天然一致。

### 2. Hudi 的解法

- **Copy-on-Write / Merge-on-Read**:近实时 upsert 场景的两种选择;
- **Record-Level Index**:把每条数据的"在哪个文件"记录到索引,upsert 时无需全表扫描;
- **Timeline**:CRUD 的全量审计。

### 3. Paimon 的解法

- **LSM + Primary Key**:Flink 流写入就是主键 upsert,无外部 KV 依赖;
- **Changelog**:既产生流式 changelog 也可消费 changelog;
- **Append/Bucketed Tables**:批场景 + 流场景共用表。

这些表格式让"批是流的特殊情形"成立:Flink 写的流,Spark/Hive/Trino 用 T+1 跑一遍就行,口径天然对齐。

## 六、真正的"流批一体"参考架构

```
                    ┌───────────────────────┐
                    │   Kafka / Pulsar      │
                    └──────────┬────────────┘
                               │
                  ┌────────────┴──────────────┐
                  │  Flink(实时 + 批模式统一)  │
                  └──────┬──────────┬─────────┘
                         │          │
                ┌────────▼───┐ ┌────▼──────────┐
                │  Paimon    │ │  Iceberg       │
                │ (PK Update)│ │ (Append/CDC)   │
                └────────┬───┘ └────┬──────────┘
                         │          │
              ┌──────────▼──────────▼─────────┐
              │   Trino / StarRocks / Spark   │
              └────────────────────────────────┘
```

关键点:
1. 写入层一份,引擎多套;
2. 历史的批口径任务直接在 Iceberg/Paimon 上跑,不依赖 Kafka 回放;
3. 当口径变更,流重写 + 批覆写同时进行,Consumer 既能从快照读也能从流读。

## 七、混合范式:Hudi/Paimon 实践中的妥协

即使是 Paimon,生产环境也常出现"实时主键模型 + 离线聚合模型"两条线:

| 实时线 | 离线线 |
|--------|--------|
| 分钟级 DWD/DWS | 日级 DWS/ADS |
| 供秒级看板 | 供 T+1 财报表 |
| upsert 流 | 批快照 |
| 短生命周期 | 长生命周期 |

它并不是"消灭 Lambda",而是把 Lambda 的双链路**收敛到数据格式层**,让两者的物理存储统一。

## 八、面试高频追问

- "Lambda 架构的核心痛点?" — 同口径双代码、双存储、双回滚。
- "Kappa 为什么不直接取代 Lambda?" — Kafka 不是存储、长期保留昂贵、回放压力大。
- "Iceberg/Paimon 凭什么流批一体?" — Snapshot/LSM 把"流"与"批"建模成同一份不可变数据。
- "生产上的混合架构怎么权衡?" — 实时线主键表,离线线批表,二者不打架的关键是同一份 CDC source + 同一套 ETL 算子复用。

> **结论**:Lambda/Kappa 是工程史的两个里程碑,真要"流批一体"还得靠开放表格式。让一份数据同时承担流与批两个语义,这是 Lakehouse 时代的核心红利。
