# 13 · 选型决策、性能、可观测与最佳实践

> 目标:把所有方案"用得起来"——选型决策树、性能优化、可观测落地、踩坑清单、Debug 套路。

---

## 1. 选型决策树

```
                       ┌── 一致性要求 ──►
                       │      │
                       │   强一致
                       │      │
                跨库 / 跨服务? ─────► 强一致 + 同步 ──► 2PC / XA / NewSQL
                       │
                    最终一致
                       │
           ┌───────────┴───────────┐
       长事务?                  短事务?
           │                       │
         Saga                    性能优先? ──► 可靠消息 / Outbox
                                   │
                                 强隔离?
                                   │
                                   ▼
                                 TCC
```

### 1.1 决策矩阵

| 场景 | 优先 | 推荐 |
| --- | --- | --- |
| 传统金融资金账 | 强一致 | TCC + XA(对账双保险) |
| 电商下单库存 | 强一致 | TCC |
| 电商下单优惠 | 最终一致 | 可靠消息 / Outbox |
| 跨境汇款、跨行清算 | 最终一致 | Saga + 对账 |
| 高并发计数 / 排行榜 | 最终一致 | 最大努力通知 + Redis |
| 全局日志、通知类 | 最终一致 | MQ + 最大努力通知 |
| 跨地域写入 | 强一致 | NewSQL(Spanner、TiDB) |
| 简单通知 | 最终一致 | 最大努力通知 |
| 已有 Seata 体系 | 多种 | Seata(AT/TCC/Saga) |

## 2. 性能调优

| 方案 | 优化 |
| --- | --- |
| 2PC/XA | 减少参与方、缩短持锁时间、合理分布协调者 |
| TCC | Try 阶段避免远程 RPC,资源预冻结本地化 |
| Saga | 异步化、子事务拆分 |
| MQ | 批量发送、削峰填谷、消费者并行、幂等去重 |
| NewSQL | 避免大事务、热表拆分、Region 打散 |

### 2.1 TCC 性能优化

- **Try 预冻结本地化**:资源冻结字段与业务字段同表,避免 RPC 风暴。
- **批量预冻结**:多个 SKU 一次冻结。
- **预冻结异步化**:把冻结逻辑放本地事务,确认时才真正扣减。

### 2.2 Saga 性能优化

- **异步化**:Saga 子事务异步执行。
- **拆分粒度**:把"5 步 Saga"拆成"2 + 3"并行。
- **补偿异步**:补偿失败可异步重试,不要阻塞主流程。

### 2.3 消息性能优化

| 维度 | 优化 |
| --- | --- |
| 批量 | 一次 Send 100+ 条消息 |
| 削峰 | 上下游容量差,中间积压在 MQ |
| 并行消费者 | Partition / Queue 数量 |
| 幂等 | Redis SETNX(避免 DB 唯一索引写) |
| Trace | MDC 注入 xid |

### 2.4 NewSQL 性能优化

- **Region 打散**:热点表人工打散 Primary Key。
- **避免跨 Region**:跨 Region 事务延迟数十 ms。
- **大事务拆分**:TiDB 单事务不超过 1000 行。
- **索引设计**:避免覆盖索引之外的回表。

## 3. 可观测(Observability)

### 3.1 三大支柱

| 支柱 | 工具 | 关键指标 |
| --- | --- | --- |
| **Trace** | OpenTelemetry / Skywalking | 全链路 xid 串联 |
| **Metrics** | Prometheus / Grafana | 事务成功率、平均时延、P99、Saga 完成率 |
| **Logs** | ELK / Loki | 事务 ID(xid)、分支 ID(branchId)、状态迁移 |

### 3.2 关键监控指标

| 指标 | 公式 | 阈值 |
| --- | --- | --- |
| 事务成功率 | success / total | > 99.9% |
| 平均事务时延 | sum / count | < 业务预期 |
| 悬挂事务数 | 当前 UNKNOWN 状态 | 0 |
| 死信队列堆积 | DLQ 长度 | < 1000 |
| 协调者 QPS | tx / sec | 待评估 |
| Saga 补偿率 | 补偿 / 总数 | < 1% |

### 3.3 控制台

- **Seata**:自带控制台,展示全局事务、分支事务、状态。
- **DTM**:自带 dashboard,展示 Barrier 状态、悬挂事务。
- **RocketMQ**:DLQ 监控、消费延迟。

### 3.4 告警策略

| 告警 | 阈值 |
| --- | --- |
| 悬挂事务 | > 0 |
| 长时间 UNKNOWN | > 5 分钟 |
| 死信队列激增 | > 上小时 10 倍 |
| 事务成功率下降 | < 99% |
| 补偿率上升 | > 5% |

## 4. 最佳实践清单

### 4.1 通用

1. **统一事务 ID**:贯穿 MQ、日志、DB 行。
2. **幂等覆盖一切写**:消息消费、Try/Confirm/Cancel、回调、扣款。
3. **幂等表 + 业务唯一索引** 双保险。
4. **重试有上限**:防止雪崩。
5. **对账是兜底**:任何异步链路都不能省对账。
6. **资源预留与回滚**:Try 资源要"软冻结",Cancel 要可重复。
7. **单元 + 集成测试 + 故障注入**:ChaosBlade / Litmus / Toxiproxy。
8. **读写分离 / 缓存**:隔离性低时可引入 Redis、Elasticsearch 提升查询体验。
9. **文档与状态机**:给每个事务一份"流程图 + 异常路径"文档。
10. **避免大事务**:NewSQL 仍需控制事务行数和持续时间。

### 4.2 TCC 专项

- Try 资源字段与业务字段分开。
- Cancel 前先查 txLog。
- Try 前先查 Cancel 状态。
- 全程打点(包含 txId、状态)。

### 4.3 Saga 专项

- 状态机持久化。
- 不可逆操作放在 Saga 尾部。
- 补偿动作幂等。
- 编排者高可用。

### 4.4 消息专项

- 幂等键覆盖到业务唯一键。
- 死信队列必接告警。
- 重试策略分阶梯(立即 / 1min / 5min / 30min)。
- CDC 监控 binlog 位点。

## 5. 切忌踩坑

1. **不要在最终一致场景追求强一致**:徒增复杂度。
2. **不要把消息当事务唯一手段**:必须叠加幂等 + 重试 + 对账。
3. **不要忽视悬挂 / 空补偿**:提交流程必须先判断事务分支状态。
4. **不要在 NewSQL 之外硬上 SSI**:成本不划算。
5. **不要混用多种方案**:统一收敛到 1~2 种全局模式。
6. **不要自己实现 Raft**:用 etcd / TiKV 提供的 KV。
7. **不要忘记 CDC 监控**:binlog 位点落后是隐性故障。
8. **不要让 Coordinator 部署为单点**:Seata/DTM 至少 3 节点。

## 6. 故障排查(Debug 套路)

### 6.1 业务反馈"资金对不上"

1. 查 xid → 定位全局事务。
2. 查 txLog → 各分支状态。
3. 查 undo_log → Seata AT 回滚记录。
4. 查对账 → 终态差异。

### 6.2 业务反馈"订单卡住"

1. 查订单状态机 → 哪个状态超时。
2. 查超时任务 → 30 分钟取消是否触发。
3. 查库存回补 → 库存事件是否消费。
4. 查营销回补 → 营销事件是否消费。

### 6.3 业务反馈"消息积压"

1. 查 Consumer 延迟 → 是否慢 SQL / 慢 RPC。
2. 查 DLQ → 是否失败堆积。
3. 查重试 → 是否配置错误。
4. 临时扩容 Consumer → 优先恢复业务。

### 6.4 业务反馈"Seata 启动失败"

1. 查 TC 集群 → 节点是否健康。
2. 查 store mode → DB/Redis 持久化是否正常。
3. 查 vgroup-mapping → 客户端与 TC 是否一致。
4. 查网络 → 8091 端口是否通。

## 7. 评估矩阵

新建一个分布式事务项目时,逐项打分:

| 维度 | 评估问题 | 分值 |
| --- | --- | --- |
| 一致性 | 必须强一致还是最终一致? | 0/1 |
| 性能 | QPS 峰值?P99 延迟要求? | 0/1 |
| 隔离 | 是否允许脏读? | 0/1 |
| 复杂度 | 多少服务参与?多少数据库? | 0/1 |
| 运维 | 团队是否熟悉 NewSQL / Seata? | 0/1 |

> 强一致 + 低 P99 → TCC / 2PC。
> 高 QPS + 最终一致 → 消息 / Outbox。
> 跨地域 + 强一致 → NewSQL。

## 8. 实战选型口诀

> **强一致看 TCC 或 NewSQL,长事务走 Saga,异步靠 MQ,通知用最大努力。任何方案 → 幂等是底线,对账是兜底。**

## 10. 面试高频问题

**Q1. 选型时优先看一致性还是性能?**
- 业务 layer 决定优先级,不是技术。
- 资金账:一致性优先,性能其次。
- 电商下单:一致 + 性能折中,核心链路 TCC,周边链路 MQ。
- 通知类:性能优先,最终一致。

**Q2. 怎么判断一个事务设计是否合格?**
- 一致性目标是否明确(谁都不能差 vs 允许短暂不一致)?
- 三把刀是否全部处理(空补偿 / 防悬挂 / 幂等)?
- 异常路径是否覆盖(超时、断网、Coordinator 宕机)?
- 对账兜底是否就位?

**Q3. 性能优化第一步是什么?**
- 量级评估:当前 QPS、目标 QPS、单事务耗时。
- 找瓶颈:Trace 看哪一步最慢。
- 上下文切换:同服务优先、入库逻辑本地化。
- 避免"高一致性 = 高性能"的幻觉。

**Q4. 故障排查时最重要的工具是什么?**
- Trace:跨服务的 xid 必须串联。
- Metrics:看指标拐点。
- 日志:看具体 txId / branchId。

**Q5. 团队没经验,推荐从哪种方案入手?**
- 先 Seata AT:零侵入,接入快。
- 逐步迁移到 TCC:核心业务上线后。
- 长期规划:看 NewSQL 落地价值。
