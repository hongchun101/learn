# 01 · 分布式事务理论基石

> 目标:把 ACID / CAP / BASE / 一致性模型四个常被混用的概念讲清楚,建立后面所有方案的"坐标系"。

---

## 1. ACID(单机事务)

| 特性 | 含义 | 谁来保证 |
| --- | --- | --- |
| A 原子性 | 事务中的操作要么全部成功,要么全部失败 | DB 引擎(undo log) |
| C 一致性 | 事务前后,数据从一个一致状态变换到另一个一致状态 | 业务约束 + 原子性 + 隔离性 |
| I 隔离性 | 并发事务之间互不干扰 | DB 引擎(锁 / MVCC) |
| D 持久性 | 事务一旦提交,修改永久生效 | DB 引擎(redo log + WAL) |

> 关键点:C 是"业务态"的描述,不是某种隔离级别本身。

---

## 2. CAP 定理(2000, Brewer)

$$
\text{CAP}: \quad C \land A \land P \;\;\text{不可同时成立}
$$

- **C(Consistency)**:线性一致性(Linearizability)——任何一次读都能看到最近一次写。
- **A(Availability)**:每个非故障节点都能在有限时间内响应请求。
- **P(Partition tolerance)**:网络分区时系统仍能继续提供服务。

> 因为 P 在分布式场景下不可避免,实际是 **CP vs AP** 的选择。

| 取舍 | 典型系统 | 代价 |
| --- | --- | --- |
| **CP** | ZooKeeper / etcd / Consul / HBase | 分区期间不可写(或不可读) |
| **AP** | Eureka / Cassandra / DynamoDB / Couchbase | 分区期间可能读到旧值 |
| **CA** | 传统单机关系库 | 分布式场景下不现实 |

---

## 3. BASE 理论

| 概念 | 含义 |
| --- | --- |
| **B**asically Available | 基本可用:响应时间降级、功能降级 |
| **S**oft state | 软状态:允许中间状态(副本同步中) |
| **E**ventually consistent | 最终一致:停止写入后,有限时间内所有副本收敛 |

> BASE 是 AP 选择的工程化总结,**不是新理论**,而是把"放弃 C 之后怎么办"落到制度。

---

## 4. ACID vs BASE

| 维度 | ACID | BASE |
| --- | --- | --- |
| 一致性 | 强一致 | 最终一致 |
| 复杂度 | DB 内置 | 应用层处理 |
| 性能 | 锁竞争,吞吐受限 | 高并发友好 |
| 典型场景 | 金融、ERP、订单核心 | 电商、社交、物流、内容 |
| 对应 CAP | C | AP |

---

## 5. 一致性模型谱系

```
强 ───────> 弱
线性一致性 > 顺序一致性 > 因果一致性 > 读已写一致性 > 单调读一致性 > 最终一致性
```

| 模型 | 含义 | 典型实现 |
| --- | --- | --- |
| 线性一致性 (Linearizability) | 任意一次读都能看到最近一次写 | ZooKeeper、etcd、Spanner |
| 顺序一致性 (Sequential) | 存在全局顺序,各客户端相对顺序保留 | 理论模型 |
| 因果一致性 (Causal) | 因果相关的操作有序,无因果操作可并发 | COPS 系统 |
| 读已写一致性 (Read-your-writes) | 写入者后续读必能看到自己刚写入 | 多数 Web 业务 |
| 单调读一致性 (Monotonic Reads) | 不会读到旧值后再读到新值 | 通常由会话级实现 |
| 最终一致性 (Eventual) | 停止写入后,有限时间收敛 | DNS、Cassandra |

---

## 6. 衡量分布式系统的指标

| 指标 | 含义 |
| --- | --- |
| 可用性 | 可用时间 / 总时间 → SLA(99.9 / 99.99 / 99.999) |
| 延迟 | P50 / P99 / P999 |
| 吞吐 | QPS / TPS |
| RTO | 故障恢复时间 |
| RPO | 数据丢失容忍 |
| 一致性等级 | 见第 5 节 |

---

## 7. 常见误区

| 误区 | 真相 |
| --- | --- |
| "CAP 中三选二" | 实际是 CP / AP,因为 P 不可避免 |
| "BASE 比 ACID 弱,所以 BASE 简单" | BASE 把复杂度从 DB 推到应用层,工程上反而更难 |
| "我们做不到强一致,所以选最终一致" | 资金账目必须强一致;只有非核心业务才适合最终一致 |
| "分布式事务 = 两阶段提交" | 2PC 是其中之一,还有 TCC / Saga / 消息 / NewSQL 等 |

## 9. 面试高频问题

**Q1. CAP 中的 C 和 ACID 中的 C 有什么区别?**
- ACID 的 C 是业务一致性(约束不破坏)。
- CAP 的 C 是线性一致性(读到的总是最新写入)。
- 两者完全无关,容易在面试中被混淆追打。

**Q2. 为什么分布式系统只能选 CP 或 AP?**
- P 在分布式下不可避免(只要有网络,就可能分区)。
- 选了 CP → 分区时放弃 A;选了 AP → 分区时放弃 C。
- CA 是单机/主备的浪漫,分布式用不上。

**Q3. 业务一致性是不是必须选 ACID?**
- 不是。业务一致性可以由应用层 + 最终一致 + 对账兜底来保。
- 关键是"账不能错",而不是"必须用 ACID 库"。
- 例如支付宝/微信的转账都靠最终一致 + 对账兜底,而非传统 XA。
