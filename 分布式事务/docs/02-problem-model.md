# 02 · 问题模型与四大流派

> 目标:先认清"分布式事务"到底在解决什么问题,再去看每种方案如何取舍。"问题模型"是后面所有方案的对照表。

---

## 1. 为什么需要分布式事务?

单机 ACID 事务在跨节点场景下失效的根因:

| 跨域 | 典型场景 |
| --- | --- |
| 跨数据库 | 订单库 + 库存库 + 支付库 |
| 跨服务 | 订单服务 / 库存服务 / 支付服务 |
| 跨地域 | 多机房 / 多区域 |
| 跨存储 | MySQL + Redis + ES + Hive |
| 跨异构 | 与外部银行 / 第三方支付 / 物流对接 |

> 单机事务的 4 个特性(A/C/I/D)在跨节点场景下全部需要重新设计,本质是**边界条件变了**。

---

## 2. 经典案例

### 2.1 电商下单

```
下单服务 → 订单中心(创建订单)
        → 库存服务(扣减库存)
        → 优惠券服务(核销券)
        → 支付服务(创建支付单)
        → 物流预约
```

任一失败 → 全部回滚。

### 2.2 跨行转账

A 行扣款 + B 行加款,任何一方失败都不能让资金账目失衡。

---

## 3. 业务层面的常见诉求

| 诉求 | 解决方案 |
| --- | --- |
| 不允许资损 | 强一致(TCC、AT、Saga 编排) |
| 允许短暂不一致 | 最终一致(消息、Outbox、最大努力通知) |
| 性能优先 | Saga + 异步 / 消息 / 最大努力通知 |
| 强隔离 | 同步阻塞(2PC/XA、TCC) |

---

## 4. 四大流派

```
┌──────────────────────────────────────────────────────────────────┐
│                  分布式事务实现流派                                │
├──────────────────────────────────────────────────────────────────┤
│ 1. 基于 XA/2PC 协议(数据库层)              →  强一致、阻塞、低吞吐    │
│ 2. 基于补偿/工作流(Saga、TCC)              →  业务侵入、最终一致    │
│ 3. 基于可靠消息(MQ、Outbox)                →  最终一致、性能好      │
│ 4. 基于共识协议(Raft、Spanner)             →  全球强一致、NewSQL   │
└──────────────────────────────────────────────────────────────────┘
```

### 4.1 流派一:XA / 2PC

- **核心**:数据库层两阶段(PREPARE / COMMIT),靠 XA 接口协调多个 RM。
- **优点**:对应用透明,强一致。
- **缺点**:同步阻塞、协调者单点、性能差。
- **代表**:MySQL XA、Oracle XA、Atomikos、Bitronix。
- **详细**:见 [03 · 强一致性方案](03-strong-consistency.md)

### 4.2 流派二:补偿 / 工作流

- **核心**:把业务拆成 N 个子事务 + N 个补偿;失败时反向补偿。
- **代表**:TCC、Saga、AT(自动化 2PC)。
- **优点**:业务可控、性能好、支持长事务。
- **缺点**:业务侵入、需补偿设计、隔离性弱。
- **详细**:见 [04 · TCC](04-tcc.md)、[05 · Saga](05-saga.md)、[06 · AT 模式](06-at-seata.md)

### 4.3 流派三:可靠消息

- **核心**:把分布式事务拆成本地事务 + 异步消息投递;靠重试 + 幂等达成最终一致。
- **代表**:本地消息表、RocketMQ 事务消息、Kafka 事务、Outbox + CDC。
- **优点**:性能好、对业务侵入小。
- **缺点**:最终一致、需幂等设计 + 对账兜底。
- **详细**:见 [07 · 消息、Outbox、通知](07-messaging.md)

### 4.4 流派四:共识协议 + NewSQL

- **核心**:把共识协议(Raft/Paxos)与事务结合,直接给跨节点强一致读写。
- **代表**:Spanner、TiDB、CockroachDB、YugabyteDB、OceanBase。
- **优点**:全球强一致、对应用完全透明。
- **缺点**:成本高、运维复杂、有限制(Region、事务大小)。
- **详细**:见 [08 · 共识](08-consensus.md)、[09 · NewSQL](09-newsql.md)

---

## 5. 选型初判

| 业务特征 | 优先流派 |
| --- | --- |
| 核心资金账、强隔离 | 流派一(XA)或流派二(TCC) |
| 跨服务多步骤、可补偿 | 流派二(Saga、AT) |
| 高吞吐、最终一致可接受 | 流派三(消息、Outbox) |
| 跨地域强一致、写少读多 | 流派四(NewSQL) |

---

## 6. 跨语言的共同问题

无论选哪种流派,以下问题都必须解决(详细见 [11 · 隔离与异常](11-isolation-anti-patterns.md)):

1. **幂等**:所有可能重试的写操作都必须幂等。
2. **对账**:任何异步链路都必须有对账兜底。
3. **悬挂**:Try 后 Cancel 必须先到;Cancel 后 Try 不能后到。
4. **空补偿**:Cancel 到达时 Try 还没执行。
5. **可观测**:全链路打点 / Trace / Monitor。

## 7. 面试高频问题

**Q1. 一笔支付涉及订单、库存、账户,如何选方案?**
- 库存与订单强一致 → TCC 或 AT。
- 账户扣减可异步 → 可靠消息 + 对账。
- 支付结果 → 异步回调 + 幂等 + 重试。
- 不要全链路 2PC,XA 撑不住双 11 量级。

**Q2. 既然 NewSQL 这么强,为什么还要学 TCC / Saga?**
- NewSQL 强在"无侵入",弱在"成本 + 运维"。
- 中小业务、强隔离、跨异构(对接外部银行) → TCC / Saga 更现实。
- 选型看业务,不是看哪个"更高级"。

**Q3. 幂等 + 消息是否就等于分布式事务?**
- 不等于。消息 + 幂等只是"最终一致",不是"原子提交"。
- 资金账目场景不能仅靠消息;必须配合 TCC / XA / NewSQL。
