## 1. 数据模型与所有权

### 1.1 学习目标

- 区分概念数据模型、逻辑数据模型与物理数据模型。
- 掌握数据所有权(data ownership)的判断方法与边界规则。
- 能在多租户场景下选择合适的隔离模式(schema-per-tenant、database-per-tenant、schema-sharing 等)。

### 1.2 核心概念

- **数据模型 (data model)**:对现实世界中实体及其关系的形式化抽象。
- **概念数据模型 (conceptual data model)**:面向业务领域,不依赖具体存储,通常用 ER(Entity-Relationship,实体-关系)表示。
- **逻辑数据模型 (logical data model)**:与具体 DBMS 无关,但确定字段类型、键、外键、约束。
- **物理数据模型 (physical data model)**:包含分片键、索引、分区、列存/行存、压缩、存储格式等工程参数。
- **数据所有权 (data ownership)**:在一组服务/组件中,谁是某个数据条目的**权威写入者**(authoritative writer)。所有权决定同步方向、冲突解决策略与责任边界。
- **多租户数据隔离模式 (multi-tenant data isolation patterns)**:
  - 共享数据库+共享 schema(`Shared DB, Shared Schema`),以 `tenant_id` 列区分。
  - 共享数据库+独立 schema(`Shared DB, Separate Schema`)。
  - 独立数据库(`Database-per-Tenant`)。

### 1.3 理论模型

#### 1.3.1 三层模型映射函数

设 $M_C$ 为概念模型,$M_L$ 为逻辑模型,$M_P$ 为物理模型。存在映射:

$$
\varphi_{CL}: M_C \to M_L,\quad \varphi_{LP}: M_L \to M_P
$$

其中:

- $\varphi_{CL}$ 应尽量保持领域语义，但实体可能被拆分、合并或重述，因此通常不是一一映射。
- $\varphi_{LP}$ 在语义约束下优化查询、写入、容量、成本和运维目标；不存在脱离工作负载的“最优物理结构”。
- 反向恢复通常是**不唯一或有损**，而非数学上绝对“不存在”：多个逻辑模型可能映射为同一物理结构，物理库中也可能包含逻辑模型未表达的分区键和冗余字段。分片键应作为架构元数据显式记录。

#### 1.3.2 所有权判定规则

给定服务集合 $S = \{S_1,S_2,\dots,S_n\}$ 与需要单写者治理的数据集合 $D$，可定义权威写入映射 $\omega:D\to S$。该模型是治理策略，不是所有分布式数据类型的定理：多主、CRDT 或外部共同主数据可能有多个合法写入者，但必须显式定义合并规则、冲突语义与责任主体。对采用单写者策略的数据，应满足：

1. **唯一权威写入**：每个事实只有一个负责接受或裁决变更的边界。
2. **受控变更**：其他服务经该边界的接口、命令或约定事件提出变更，不直接绕过不变量。
3. **可检测性**：越权写入能被权限、静态规则、审计或运行监控发现。

> **反例：绕过权威边界写入。** 订单状态同时由订单服务与履约服务直接 UPDATE 数据库，既无唯一裁决者，也无合并协议，是典型的共享写入风险；后文 Saga 与 Outbox 小节会继续分析。

#### 1.3.3 多租户隔离度选择函数

设 $C_T$ 为单个租户的合规要求(法规、合同),$Q_T$ 为租户查询 QPS,$N_T$ 为租户数量,$S_T$ 为租户存储占用。隔离模式的选择函数 $f$:

$$
\text{isolation} = f(C_T, Q_T, N_T, S_T)
$$

经验区间(非定理,工程近似):

| 主要条件 | 可考虑模式 | 主要取舍 |
| --- | --- | --- |
| 强物理/地域隔离、租户较少或高价值 | Database-per-Tenant | 审计、恢复、迁移和独立扩容清晰；连接、版本和运维对象多 |
| 需要一定逻辑隔离、租户数量可控 | Schema-per-Tenant | 共享实例但对象数与迁移复杂度上升；不同数据库的 schema 语义不同 |
| 大量租户、希望池化资源 | Shared Schema with `tenant_id` | 利用率高、运营简单；必须工程化授权、噪声隔离与租户搬迁 |

> 模式不能由“合规强/弱、数量大/小”单独推出。租户负载偏斜、恢复粒度、数据驻留、密钥、迁移频率、数据库限制和单位经济共同决定选择；不存在“占库 40% 就切独立库”的通用阈值。

### 1.4 方法步骤

1. **概念建模**:从业务事件(下单、支付、发货)反向抽取实体与不变量(invariant)。
2. **逻辑建模**:定义主键、唯一约束、外键、可空性;标注每个实体的"事实来源(source of truth)"。
3. **所有权分配**：标记每类事实的权威写入/裁决边界；若采用多写者，定义冲突与合并语义。聚合、服务和数据库边界不必一一对应。
4. **隔离模式选择**：比较共享表、独立 schema、独立数据库和分层混合方案，并设计租户搬迁与恢复。
5. **物理映射**:选择分片键、索引、压缩、TTL。

### 1.5 权衡与失败模式

- **过度规范化 (over-normalization)**:订单与订单项分离后,跨分片查询成本高,热点场景不适用。
- **过度反规范化 (over-denormalization)**:库存反写到订单项副本,出现"副本与权威"差异。
- **隐藏依赖**:分片键同时承担业务查询条件,但未在概念模型中显式记录,导致跨分片扫描。
- **租户泄漏 (tenant leakage)**:SQL 缺少 `tenant_id` 谓词,跨租户读取。
- **案例失败模式**:商品中心为减少 JOIN,在订单服务冗余商品名;商品名变更事件丢失,导致订单显示旧名。

### 1.6 示例:电商平台概念模型与所有权

```
Tenant(id, name, plan, region)
  │
  ├── Item(id, tenant_id, sku, title, price)         所有权: Catalog Service
  ├── Stock(item_id, tenant_id, available_qty)       所有权: Inventory Service
  ├── Coupon(id, tenant_id, code, discount)          所有权: Coupon Service
  ├── Order(id, tenant_id, user_id, status, total)   所有权: Order Service
  │     └── LineItem(order_id, item_id, qty, price) 所有权: Order Service
  ├── Payment(order_id, tenant_id, status, amount)   所有权: Payment Service
  └── Fulfillment(order_id, tenant_id, status)       所有权: Fulfillment Service
```

判定:

- `Order.status` 的权威写入者是 `Order Service`。`Payment` 仅能通过事件 `PaymentCaptured` 通知订单服务,而不是直接 UPDATE。
- `Stock.available_qty` 需要一个明确的权威裁决协议；单写 Inventory Service 是简单候选，多仓/离线多写则必须定义分区所有权或合并规则。超卖由并发控制和业务不变量决定，不只是“服务唯一”决定。

### 1.7 检查清单

- [ ] 每个聚合根有且仅有一个权威服务。
- [ ] 跨服务写入仅通过接口或事件,不直接 UPDATE 对方表。
- [ ] `tenant_id` 列在所有租户数据表中存在且非空。
- [ ] 分片键在概念模型或逻辑模型中有显式说明。
- [ ] 反范式的副本有明确的同步事件与一致性级别。

### 1.8 练习

1. **所有权推演。** 在电商平台案例中,为 `Coupon`(优惠券)分配所有权并给出聚合边界。若大促期间券码校验 QPS 达到 50 万/秒,库存服务与订单服务是否应该拥有 `coupon` 的读副本?为什么?
2. **隔离模式选择。** 给定三家品牌商分别有 8 万 SKU、200 万 SKU、2000 万 SKU,$C_T$ 相同,$N_T$ 较少,你会如何为它们分配隔离模式?写出你的 $f$ 参数并解释。
3. **失败案例分析。** 描述一个"跨服务直写导致的双写反模式"的真实化场景,并指出违反 1.3.2 哪条规则。

## 2. 事务、隔离级别与异常

### 2.1 学习目标

- 严格区分 ACID 中的四个性质,识别常见的工程近似。
- 掌握 ANSI SQL 与后续研究定义的隔离级别,包括快照隔离(snapshot isolation, SI)与可串行化(serializable)。
- 能在分布式场景下选择恰当的隔离级别与重试策略。

### 2.2 核心概念

- **事务 (transaction)**:一组要么全部生效要么全部不生效的操作单元。
- **ACID**:
  - **原子性 (Atomicity)**：事务中的变更按协议整体提交或整体中止。
  - **一致性 (Consistency)**：若事务逻辑正确且初态满足声明的不变量，提交后仍满足这些不变量；数据库不会自动知道全部业务规则。
  - **隔离性 (Isolation)**：并发事务的可观察效果受所选隔离模型约束，不是笼统“互不干扰”。
  - **持久性 (Durability)**：提交结果在声明的故障模型和存储保证下可恢复；灾难性介质丢失、错误备份或实现缺陷仍可能造成数据损失。
- **隔离级别 (isolation level)**:
  - **读未提交 (Read Uncommitted)**。
  - **读已提交 (Read Committed, RC)**。
  - **可重复读 (Repeatable Read, RR)**(MySQL InnoDB 默认,注意 ANSI RR 与 SI 的差别)。
  - **快照隔离 (Snapshot Isolation, SI)**。
  - **可串行化 (Serializable)**。
- **异常现象 (anomalies)**:脏写、脏读、不可重复读、幻读、丢失更新、写偏序、读偏序、幻读(广义)。

### 2.3 理论模型

#### 2.3.1 ANSI SQL 异常表

ANSI SQL-92 定义了三种异常与三种隔离级别的对应(简化):

$$
\text{RC} \not\Rightarrow \text{Dirty Read},\quad \text{RR} \not\Rightarrow \text{Phantom},\quad \text{SR} \Rightarrow \text{None of the Above}
$$

> **历史提示。** 1995 年后研究(Critique of ANSI SQL Isolation Levels)指出 ANSI 定义不完备;真正的"可重复读"在 PostgreSQL 上是 SI,在 MySQL InnoDB 上是 SI + 部分幻读控制。

#### 2.3.2 快照隔离的形式化

设事务 $T_i$ 的读集为 $R_i$、写集为 $W_i$、开始时间为 $S_i$。经典快照隔离（SI）通常保证：

1. **一致快照**：$T_i$ 从与 $S_i$ 对应的已提交版本快照读取，事务内重复读取保持稳定。
2. **并发写冲突处理**：两个时间区间重叠的事务若写同一数据项，最多一个能提交，常称 First-Committer-Wins。具体检测时点和错误语义取决于数据库实现。

> **重要警示。** SI 不等价于可串行化。它通常阻止脏读、不可重复读和读侧幻读，并避免并发写写冲突同时提交，但仍允许写偏序（write skew）。

#### 2.3.3 写偏序反例:医生值班表

```text
初始：Doctor A 与 Doctor B 都在班
约束：至少一名医生在班
事务 T1：读取 A、B 均在班；将 A 改为不在班；commit
事务 T2：读取同一快照中 A、B 均在班；将 B 改为不在班；commit
```

两事务写不同记录，因而都可能在 SI 下提交；组合结果却是无人值班。每个事务单独看都保持约束，并发组合破坏不变量，这就是写偏序。

#### 2.3.4 隔离保证不是所有实现中的简单单调阶梯

在特定形式模型中，可按被排除的历史集合比较隔离保证；可串行化排除所有非串行化历史。但 SQL 标称级别与具体实现并不形成统一的

$$\text{RU}<\text{RC}<\text{SI}<\text{Serializable}$$

线性阶梯：ANSI Repeatable Read、Snapshot Isolation、游标稳定性及不同数据库实现允许的异常并不相同。选择时应核对目标数据库的实际语义并用业务不变量构造并发反例。PostgreSQL 的 Serializable Snapshot Isolation（SSI）通过跟踪读写依赖并中止危险结构实现可串行化，可能产生需要应用重试的 serialization failure；这不是“误中止”，而是保证安全性的机制。

### 2.4 方法步骤

1. **识别依赖链**:对每条业务链路,识别读后写(read-modify-write)、写后读(read-your-writes)、交叉写。
2. **选择最低必要隔离**:RC + 显式行锁、SI + 乐观重试、Serializable + 必要边界。
3. **重试策略**:对乐观冲突、串行化中止,可指数退避 + 抖动,但必须**有上限**(避免饥饿)。
4. **验证异常**:构造反例,如写偏序,确认在所选隔离级别下被阻止。

### 2.5 权衡与失败模式

- **过低隔离导致业务错误**:商品上下架用 RC,导致重复上架。
- **过高隔离导致吞吐塌方**:全部 Serializable,长事务阻塞短事务。
- **乐观重试无限放大**:同一热点行被 10 个事务争抢,每个都重试 5 次,雪崩。
- **跨服务事务假象**:用 Spring `@Transactional` 同时跨 MySQL 与 Redis,以为强一致,实际 Redis 无回滚。

### 2.6 示例:电商平台订单创建的隔离选择

场景:用户下单,需校验库存与优惠券,并扣减两者。

- **库存扣减**:写后写冲突(同一 SKU),用悲观行锁或 SI + FCW。
- **券码核销**:写后写冲突(同一券),同样需冲突检测。
- **订单写入**:快照隔离下读取当前快照,提交时检测与库存/券的写冲突。

```
T_order:   BEGIN; SELECT stock WHERE item_id=?; UPDATE stock; UPDATE order; COMMIT;
T_coupon:  BEGIN; SELECT coupon WHERE code=?; UPDATE coupon_used; UPDATE order; COMMIT;
```

若 T_order 与 T_coupon 并发,在 Serializable 下两者均需排序;在 SI 下若不冲突可同时提交;在 RC 下可能重复使用同一券码。

### 2.7 检查清单

- [ ] 所有事务标识其隔离级别与回滚策略。
- [ ] 重试按总 deadline、幂等性、冲突率和业务价值设有界次数/时间，不套用固定 3 次。
- [ ] 事务内外部 HTTP 调用的锁与不确定结果风险已分析；优先缩短事务或改用预留/工作流，而非绝对禁止。
- [ ] 关键并发不变量有目标数据库上的异常测试，包括写偏序、丢失更新或唯一约束竞争。
- [ ] 跨边界工作流明确实际语义：同库事务、2PC、Saga/TCC、预留或异步收敛，不用“强一致”口号代替。

### 2.8 练习

1. **写偏序构造。** 在电商平台中,设计一个写偏序场景:两个事务各自合法,但并发提交后破坏业务不变量。
2. **隔离级别对比。** 对"扣减库存 + 创建订单"这一对操作,分别写出 RC、SI、Serializable 三种实现,并列出各自可能发生的异常。
3. **乐观重试上限。** 设计一个热点 SKU 的秒杀链路,使用 SI + 有限重试(≤ 3)。给出退避策略与放弃后的兜底(例如占位订单 + 异步补偿)。

## 3. 分布式一致性模型:CAP 与 PACELC

### 3.1 学习目标

- 准确陈述 CAP 定理及其适用边界。
- 掌握 PACELC 扩展模型。
- 区分"定理 / 工程近似 / 宣传术语"三个层次。

### 3.2 核心概念

- **CAP 定理（CAP theorem；Brewer 猜想，Gilbert–Lynch 2002）**：
  - **一致性（Consistency）**：这里指线性一致性；操作表现得像在调用与返回之间某一时刻原子发生。
  - **可用性（Availability）**：所有由未失效节点收到的请求最终都得到响应；响应不保证包含最新值。
  - **分区（Partition）**：节点间任意多消息可能丢失，网络被分成无法通信的部分。P 不是与 C、A 同类的可选服务属性，而是模型中的故障条件。
  - 结论：在分区持续期间，读写对象不能同时保证线性一致性和上述可用性。
- **PACELC（Daniel Abadi, 2010）**：一个分类启发式，而非像 CAP/FLP 那样的已证明“不可能性定理”。发生分区（P）时讨论 A/C；否则（E, else）仍需讨论延迟（L）与一致性（C）的工程取舍。
- **线性一致性 (linearizability)**:操作存在全序,且与真实时间偏序一致。
- **顺序一致性 (sequential consistency)**:操作存在全序,但不必与真实时间一致。
- **因果一致性 (causal consistency)**:有因果关系的操作必须有序,无因果的操作可并发。

### 3.3 理论模型

#### 3.3.1 CAP 的严格陈述(Gilbert–Lynch)

设异步网络模型下存在分区。证明:

> 不存在同时满足 C、A、P 的读写对象(register)实现。

> **重要边界。**
>
> 1. CAP 的不可能性结论针对发生分区的执行；无分区时仍有延迟、一致性、持久性和成本等取舍，但不是这一定理给出的结论。
> 2. Gilbert–Lynch 形式化对象是原子读写寄存器；不要直接用 CAP 推导多对象事务的全部性质。
> 3. CAP 的 A 要求未失效节点收到的每个请求最终响应，不要求成功写入或返回最新值。实际系统还会受超时和部分故障检测影响。

#### 3.3.2 PACELC 的二维平面

```
                 ┌───────────────────────────────┐
                 │              P               │
                 │      A  vs  C                │
                 └───────────────────────────────┘
                 ┌───────────────────────────────┐
                 │              !P              │
                 │      L  vs  C                │
                 └───────────────────────────────┘
```

常见的工程选择:

| 系统/配置 | 分区时倾向 | 正常时主要取舍 |
| --- | --- | --- |
| 异步主从数据库 | 通常拒绝无法确认主节点的写入以避免脑裂；具体行为取决于故障切换协议 | 从库读以较低延迟换陈旧风险；主库读可更强 |
| Dynamo 风格 / Cassandra | 一致性级别可调；较小读写仲裁倾向可用性 | 仲裁大小在延迟、冲突和新鲜度之间取舍 |
| Spanner / CockroachDB | 无法达到多数派时停止相关范围写入，倾向一致性 | 共识与时钟/事务协调增加延迟 |
| Cosmos DB | 依账户配置的一致性级别和区域策略而变 | 在延迟、可用性和一致性保证之间提供多档选择 |

#### 3.3.3 区分定理、近似与术语

- **定理/不可能性结果**：CAP、FLP；使用时必须写明系统模型与保证。
- **分类框架**：PACELC 帮助讨论分区态与正常态取舍，但不是严格定理。
- **已定义的一致性模型**：最终一致性、因果一致性、线性一致性等都有语义定义；“最终”不等于“在业务认为合理的时间内”，其基本定义本身通常不给收敛时间上界。
- **模糊宣传术语**：“强一致”“实时一致”若未给正式模型和作用域就不可验证。读己之写与单调读是会话保证；仅有二者也不足以推出完整因果一致性。

### 3.4 方法步骤

1. **按业务不变量分类**：识别需要线性化点、单调保证、因果顺序或只需最终收敛的路径；不要把资金、库存一概标签化。
2. **同时定义正确性和延迟预算**：若强保证超时，选择报错、排队、只读或业务补偿。除非业务明确允许，不能静默“降级一致性”后仍宣称操作成功。
3. **分区演练**：验证客户端、复制协议和故障切换在丢包、延迟、单向隔离下的可观察行为，而不是给整个产品贴一个固定 CP/AP 标签。
4. **术语审计**：为每个数据流写出对象范围、读写操作、故障条件和一致性保证。

### 3.5 权衡与失败模式

- **混用术语**:文档说"强一致",代码用异步复制。
- **延迟不可控**:为追求线性一致性,跨区域写入 P99 200ms,长尾超时。
- **分区测试缺失**:从未注入过网络分区,信"理论"假设分区罕见,实际并不罕见。

### 3.6 示例:电商平台一致性级别分层

| 路径 | 一致性级别 | 理由 |
| --- | --- | --- |
| 下单扣库存 | 对单个库存配额做条件原子更新或串行化事务 | 唯一/检查约束本身不等于线性一致；需明确原子读改写和复制确认语义 |
| 订单写入 + 优惠券核销 | Saga + 各步骤本地不变量 + 可观察中间态 | “因果一致”不能替代跨服务业务正确性；需定义预留、补偿和重复处理 |
| 商品浏览数 | 最终一致 | 业务容忍计数误差与延迟 |
| 评论列表 | 写后读会话保证；跨用户可最终/因果一致 | “自己的评论立即可见”只要求读己之写，不自动要求完整因果一致 |
| 物流轨迹 | 最终一致 | 数据源天然最终一致 |

### 3.7 检查清单

- [ ] 每个数据流标注一致性级别(线性 / 顺序 / 因果 / 最终)。
- [ ] 需要更强保证的路径同时定义延迟/可用性预算与超时失败语义。
- [ ] 分区演练频率按变更、风险和恢复目标设定；季度可作示例，不是固定标准。
- [ ] 文档不混用"强一致 / 最终一致 / 实时一致"等模糊术语。
- [ ] CAP 不被用于证明"我们必须放弃一致性"。

### 3.8 练习

1. **CAP 判定。** DynamoDB 默认配置属于 CAP 哪个分支?若开启强一致读呢?
2. **PACELC 选型。** 为电商平台的"商品详情页"与"下单"两条路径分别给出 PACELC 选择,并解释为何 P 时与 !P 时选择可能不同。
3. **术语审计。** 找一段你熟悉的产品文档,识别其声称的一致性级别是否被实际实现支撑。

## 4. 共识与复制

### 4.1 学习目标

- 理解主从复制、多主复制与无主复制的工程取舍。
- 掌握 Raft、Paxos 等共识算法的核心思想与不可能性结果。
- 能在多租户场景下选择合适的复制协议。

### 4.2 核心概念

- **复制 (replication)**:在多个节点保存相同数据。
- **主从复制 (primary-backup replication)**:一个主节点写入,多个从节点复制。
- **多主复制 (multi-primary)**:多个节点都可写入,需冲突解决。
- **无主复制 (leaderless)**:如 Dynamo、Cassandra,使用仲裁(quorum)读写。
- **共识（consensus）**：参与者对提议值达成满足一致性、有效性和终止条件的决定；不同模型对故障与终止条件定义不同。
- **FLP 不可能性（Fischer–Lynch–Paterson, 1985）**：在完全异步消息传递系统中，即使至多一个进程崩溃，任何确定性共识协议都存在一种允许的执行永不决定；它不是说共识在现实中无法完成。
- **Raft / Paxos**：在正常网络期依赖最终同步/故障检测等活性假设取得进展；超时不是对 FLP 的“绕过”，而是工程实现的一部分。

### 4.3 理论模型

#### 4.3.1 复制与一致性的关系

设 $N$ 为副本数，$W_q$ 为一次成功写入需确认的副本数，$R_q$ 为一次读取查询的副本数。若

$$W_q+R_q>N$$

则每个读仲裁与最近成功写仲裁至少重叠一个副本。但**仲裁重叠本身不保证线性一致读**：还需要版本比较/合并、并发写处理、故障切换与读修复等协议；某些 Dynamo 风格系统即使满足该不等式也只提供可调的一致性或新鲜度保证。

#### 4.3.2 Raft 的安全与活性

- **安全性（safety）**：Raft 的选举安全、日志匹配、Leader 完整性和状态机安全等性质确保节点不会对同一日志位置应用冲突的已提交命令；“已提交条目永不丢失”还依赖多数成员持久存储、正确成员变更和故障模型。
- **活性（liveness）**：当多数节点可通信、消息最终能在选举超时内传递且超时配置合适时，随机化选举帮助系统选出 Leader 并取得进展。
- **不可能性边界**：完全异步执行中协议无法同时保证确定性终止；实际部署依赖最终同步、时钟和故障模型假设。

#### 4.3.3 共识算法的能力边界

共识可解决:

- 领导选举(单一 Leader)。
- 复制状态机(replicated state machine)。
- 分布式锁(粗粒度)。

共识**不可**解决:

- 标准 Raft/Paxos 不处理拜占庭故障；BFT 需要 PBFT、HotStuff 等不同协议和假设。
- 共识不能消除热点或提高单 Leader 写吞吐；它提供复制决策基础。
- 共识是许多原子提交/复制事务协议的组成部分，但不单独定义跨资源事务语义；2PC、事务共识协议或 Saga 解决的是不同问题，Saga 也不提供原子提交。

### 4.4 方法步骤

1. **选型**:单主 vs 多主 vs 无主,基于写热点、地域分布、冲突频率。
2. **副本拓扑**:同城多 AZ、跨区域异步复制只读副本。
3. **故障切换**:Raft 自动切换 vs 人工接管,后者更稳但慢。
4. **冲突解决**:多主下,LWW(Last-Write-Wins)、CRDT(Conflict-free Replicated Data Types)、业务合并。

### 4.5 权衡与失败模式

- **脑裂 (split-brain)**:两个节点都认为自己是 Leader,写入冲突。
- **同步复制延迟塌方**:全部同步写入 3 副本,延迟翻 3 倍。
- **异步复制丢数据**:主写入即返回,从尚未同步时主宕机。
- **Raft 选举风暴**:网络抖动,大量节点同时选举,选不出 Leader。

### 4.6 示例:电商平台订单库的复制拓扑

- **主库**(主区域)Raft 3 副本,同步提交,写延迟 P99 < 50ms。
- **从库**(同区域只读副本)异步复制,承载读流量。
- **异地灾备副本**异步复制,RPO(Recovery Point Objective,数据可丢失时长)≤ 5 分钟。
- **多主冲突点**:购物车在多端(PC、移动)并发修改,采用 CRDT(例如 OR-Set)或业务层 LWW(以服务端时间戳为准)。

### 4.7 检查清单

- [ ] 副本数与读写仲裁有明确数值。
- [ ] 主从切换(Raft 或外部协调)有演练记录。
- [ ] 异步复制副本标明 RPO。
- [ ] 多主场景有冲突解决策略。
- [ ] 共识不可达场景(FLP)有退化路径(只读、报错)。

### 4.8 练习

1. **仲裁计算。** 副本数 $N=3$、写仲裁 $W_q=2$、读仲裁 $R_q=2$，是否保证读写仲裁相交？若 $W_q=1$ 呢？相交还缺哪些条件才可能提供线性一致读？
2. **Raft 行为分析。** 在 5 节点 Raft 集群中,Leader 与一个 Follower 同时网络分区,Follower 被提升为 Candidate,但因多数派未达而失败。描述此时系统行为。
3. **多主选型。** 电商平台购物车应选多主 + CRDT 还是单主 + 同步?说明理由。

## 5. 分区

### 5.1 学习目标

- 掌握分片键(partition key / sharding key)选择方法。
- 区分水平分区(horizontal partitioning)与垂直分区(vertical partitioning)。
- 应对热点、跨分片事务与跨分片 JOIN。

### 5.2 核心概念

- **分区 (partitioning / sharding)**:将数据按规则拆分到多个分片。
- **水平分区**:按行拆分,同一表不同行分散到不同节点。
- **垂直分区**:按列拆分,常用于冷热分离。
- **分片键 (sharding key)**:决定数据归属的字段。
- **一致性哈希 (consistent hashing)**:用于无主或分布式缓存,降低扩缩容抖动。
- **热点 (hot spot)**:某分片 QPS 或存储远超其他分片。
- **跨分片事务 (cross-shard transaction)**:涉及多个分片的事务,代价高。

### 5.3 理论模型

#### 5.3.1 分片键的函数表达

设键空间为 $K$,分片数为 $N$,分片函数 $h: K \to \{0, 1, \dots, N-1\}$。理想 $h$ 满足:

1. **均匀性 (uniformity)**:$\Pr[h(k) = i] \approx 1/N$。
2. **迁移成本**：扩缩容时迁移多少键取决于分配算法、权重、虚拟节点和新旧容量。对理想均匀哈希从 $N$ 个等容量节点增加 1 个节点，新节点期望接收约 $1/(N+1)$ 的键；一致性哈希的价值是避免简单取模造成大范围重映射，但不存在文中可对任意 $N'$ 使用的通用下界公式。

#### 5.3.2 热点检测

设分片 $i$ 的 QPS 为 $q_i$,平均为 $\bar{q}$。热点指数:

$$
H_i = \frac{q_i}{\bar{q}}
$$

$H_i$ 用于相对比较，但热点阈值应由单分片在目标 SLO 下的容量、突发持续时间和故障余量决定；不能套用 $H_i>3$。

#### 5.3.3 跨分片 JOIN 的代价

跨分片 JOIN 的网络与计算代价取决于数据共置、分区裁剪、广播小表、shuffle、过滤选择性和查询引擎。朴素地对两边所有分片做笛卡尔请求可能达到 $n\times m$ 个交互，但成熟引擎通常不会机械这样执行；应以执行计划、移动字节数、阶段数和尾延迟评估，不能据此断言“大表 JOIN 几乎不可用”。

### 5.4 方法步骤

1. **选择分片键**:候选包括 `tenant_id`、`user_id`、`order_id`。
2. **热点评估**：用真实流量、键频率分布和容量曲线识别热点；任何 $H_i$ 指标及阈值都必须先定义，不能直接套“>3”。
3. **二级索引处理**：比较全局索引、按路由键局部索引、搜索/读模型、scatter-gather 与数据重排；产品名不能替代一致性、写放大和恢复分析。
4. **跨分片事务**：先判断是否真的需要跨片原子性；可选同库分布式事务/2PC、共识型事务协议、重新分片、预留或 Saga。不要因口号避开 2PC，也不要用 Saga 冒充原子提交。

### 5.5 权衡与失败模式

- **分片键选错**:用 `tenant_id` 分片,大租户占 50% 流量,直接热点。
- **跨分片 JOIN 滥用**:不分片时正常,分片后查询塌方。
- **热点打散失败**:仅靠加机器无法解决热点,因为热点在分片键上。
- **分片再平衡 (rebalance) 抖动**:扩容时迁移导致尾延迟飙升。

### 5.6 示例:电商平台订单库分片

- 订单分片候选：先按 `tenant_id` 路由到租户单元，再按 `order_id` 哈希；这提高租户局部性但不天然“保证单库”，取决于路由与再分片规则。
- 热点缓解：依据租户的持续吞吐、数据量、SLO 与故障半径将其搬到独立单元；10 万 QPS 只是情境假设，不是阈值。
- 库存：按 SKU/仓库权威分区，使不变量尽量局部维护；哈希本身不防超卖，仍需条件原子更新、序列化或等价协议。
- 订单关联商品：可保存成交快照、构建读模型或按需查询；Binlog + Flink 宽表只是一个高成本候选。

### 5.7 检查清单

- [ ] 每个核心表有显式分片键并写入数据字典。
- [ ] 分片键变更、扩容、缩容有演练。
- [ ] 跨分片 JOIN 被禁止或强制走异步通道。
- [ ] 热点租户或商品有独立打散策略。
- [ ] 再平衡策略(一致性哈希或范围)与目标系统一致。

### 5.8 练习

1. **分片键选择。** 为 `Order`、`Stock`、`Payment` 三张表分别设计分片键,并解释为何选这个键。
2. **热点识别。** 给定 1000 个租户,其中 5 个租户贡献 80% 订单,若按 `tenant_id` 分 10 片,会出现什么热点?给出至少 2 种缓解方案。
3. **跨分片 JOIN 改造。** 原 SQL `SELECT * FROM order JOIN item ON order.item_id=item.id WHERE order.tenant_id=?`,分片后如何改造?写出至少两种方案。

## 6. 时间与顺序

### 6.1 学习目标

- 理解分布式系统中的时间难题。
- 区分物理时钟、逻辑时钟与混合逻辑时钟(HLC)。
- 为业务事件选择合适的全局排序方案。

### 6.2 核心概念

- **物理时钟 (physical clock)**:基于硬件时钟(NTP、PTP)。
- **单调时钟 (monotonic clock)**:保证不回退,用于延迟测量。
- **逻辑时钟 (logical clock, Lamport 1978)**:基于事件偏序,不与真实时间挂钩。
- **向量时钟 (vector clock)**:捕获因果依赖,可检测并发。
- **混合逻辑时钟 (Hybrid Logical Clock, HLC)**:物理 + 逻辑,Kubernetes 的 etcd、CockroachDB 使用。
- **TrueTime (Spanner)**:GPS + 原子钟,提供不确定时间区间 [earliest, latest]。

### 6.3 理论模型

#### 6.3.1 偏序与全序

- **偏序 (partial order)**:事件集合 $E$ 上的关系 $\to$,满足自反、反对称、传递。
- **全序 (total order)**:任意两元素可比。
- Lamport 时钟提供与 happened-before 兼容的标量序；若需从并发事件中构造确定性全序，可再用进程 ID 等打破相同时间戳，但该全序不表示真实时间或因果关系的逆命题。

#### 6.3.2 HLC 的形式化

设 $l$ 为 HLC 时间戳,$(pt, l)$ 满足:

$$
l.e = \max(pt.now(), l.e_{\text{prev}})
$$
$$
l.l = \begin{cases}
l.l_{\text{prev}} + 1, & \text{if } l.e == pt.now() \\
0, & \text{otherwise}
\end{cases}
$$

其中 $pt.now()$ 是本地物理时钟读数。HLC 的目标是保持与因果顺序兼容，同时让物理分量接近本地时钟；其偏差界依赖底层时钟同步/漂移假设，不是 HLC 自动保证“在 NTP 精度内”。若 $a\to b$，完整 HLC 时间戳按字典序满足 $HLC(a)<HLC(b)$；唯一性通常还需节点 ID 或额外序号，不能仅凭 $(l,c)$ 跨节点保证。

#### 6.3.3 TrueTime 的不确定区间

Spanner 的 TrueTime 返回包含真实时间的区间 $[earliest,latest]$。为提供外部一致性，Spanner 在提交协议中执行 commit-wait，等待直到提交时间戳确定早于当前真实时间；等待量与当时不确定度相关，但不能简单表述为每次固定等待区间宽度。

### 6.4 方法步骤

1. **识别是否需要全局顺序**:资金、库存强扣减需要;评论、点赞不需要。
2. **选择时钟**:物理时钟(NTP)用于粗粒度;Lamport 用于因果;HLC 用于既需要排序又需要可读时间戳的场景。
3. **不可变日志**：若需要某个共识组内的提交顺序，可使用复制日志索引；它不提供跨组全局顺序。
4. **跨区域顺序**：时钟可以同步但有误差；根据所需保证选择共识、版本/ fencing token、逻辑时钟或业务键，不把“时钟无法保证”泛化成只需去重。

### 6.5 权衡与失败模式

- **NTP 跳变**:闰秒、NTP 同步异常导致时间回退,事件顺序错乱。
- **客户端时钟不可信**:客户端时间戳被用于排序,客户端改本地时间即可操纵。
- **向量时钟爆炸**:节点多时向量长度大,工程复杂度高。

### 6.6 示例:电商平台订单事件排序

- 订单事件采用 Raft 日志索引作为主排序键。
- 业务审计日志使用 HLC(物理 + 逻辑混合),既可读又能排序。
- 客户端提交订单的时间显示用服务端 HLC,不信任客户端时间。

### 6.7 检查清单

- [ ] 全局顺序与因果顺序的需求被明确区分。
- [ ] 服务端时钟使用 NTP 或 PTP 同步,且有监控。
- [ ] 业务事件时间戳由服务端生成,不信任客户端。
- [ ] 跨区域写入不假设时钟同步。
- [ ] TrueTime 类不确定区间方案仅在确实需要外部一致性时使用。

### 6.8 练习

1. **时钟选择。** 为以下场景选择时钟:订单支付成功事件流、用户评论发布时间、库存扣减日志、分布式追踪 Span。
2. **TrueTime 实现。** 在没有 GPS/原子钟的普通数据中心,如何近似 TrueTime 的不确定区间?
3. **NTP 异常。** 描述一个 NTP 跳变导致业务错误的场景,并给出工程对策。

## 7. 幂等

### 7.1 学习目标

- 严格定义幂等(idempotency),区分"操作幂等"与"系统幂等"。
- 掌握幂等键(idempotency key)的设计与去重实现。
- 应对重试、消息重投、用户重复点击等场景。

### 7.2 核心概念

- **幂等 (idempotency)**:同一操作执行多次与一次的效果相同。
- **幂等键 (idempotency key)**:客户端提供的唯一标识,服务端据此去重。
- **去重表 (dedupe table)**:存储已处理的幂等键与结果。
- **副作用 (side effect)**:除返回值外的状态变更(发送邮件、扣款等)。

### 7.3 理论模型

#### 7.3.1 幂等的代数定义

设操作为 $f: X \to X$。幂等要求:

$$
\forall x \in X,\ f(f(x)) = f(x)
$$

对分布式操作的工程解释:

$$
\forall n \ge 1,\ \text{execute}(f, n) = \text{execute}(f, 1)
$$

但**这个等式只在"系统可见状态"层面成立**,不要求每次执行的中间状态相同。

#### 7.3.2 副作用的幂等分离

- **操作幂等**:数据库 UPDATE 设置 `status='paid'`,执行 3 次结果相同。
- **副作用幂等**:发送邮件给用户,执行 3 次会发 3 次。需要外部副作用去重,例如:
  - 邮件按 `message_id` 去重(发送前查询幂等表)。
  - 网关调用按 `out_trade_no` 去重。

#### 7.3.3 幂等键的强度

设幂等键为 $k$,操作 $f$,结果 $r$。强幂等要求:

$$
\text{process}(k) = \begin{cases}
r_{\text{stored}}, & \text{if } k \text{ exists} \\
\text{execute}(f), & \text{otherwise}
\end{cases}
$$

弱幂等只阻止重复执行,不保证返回原结果(如乐观重试时返回当前真实状态)。

### 7.4 方法步骤

1. **为写操作设计幂等键**:通常是业务键(`out_trade_no`)或客户端 UUID。
2. **去重存储**:使用强一致 KV(主键约束)或独立去重表。
3. **副作用幂等化**:把"发邮件、发推送、调外部网关"封装成幂等任务。
4. **超时场景**:第一次执行超时但实际成功,客户端重试时服务端返回首次结果(强幂等)。

### 7.5 权衡与失败模式

- **幂等键丢失**:客户端没传幂等键,服务端无法去重。
- **去重表满**:幂等表无限增长,需定期清理(基于过期时间)。
- **副作用爆炸**:重试导致重复发短信、重复扣款,未做副作用去重。
- **过期边界**:幂等键 TTL 过期,旧请求被当作新请求重新执行。

### 7.6 示例:电商平台支付回调幂等

支付通道回调(`/callback/payment`)需强幂等:

```
幂等键: payment_id + channel_trade_no
去重表: (key PRIMARY KEY, result JSON, created_at)
处理:
  SELECT result FROM dedup WHERE key=?
  if hit: return result
  else: process payment → store result → return
```

退款同理,以 `out_refund_no` 为幂等键。

### 7.7 检查清单

- [ ] 所有外部回调具备幂等键 + 去重表。
- [ ] 重试逻辑不直接重发副作用,先查幂等表。
- [ ] 幂等键 TTL 与业务可接受窗口匹配。
- [ ] 副作用(短信、推送、网关)在执行层幂等化。
- [ ] 幂等失败的处理路径有明确日志与告警。

### 7.8 练习

1. **幂等键设计。** 为"创建订单"、"发起退款"、"发放优惠券"分别设计幂等键,并说明理由。
2. **副作用幂等。** 设计一个发送短信的幂等方案,包括去重表 schema 与重试时的行为。
3. **过期边界。** 假设幂等表 TTL 为 24 小时,某客户端在第 25 小时重试,会发生什么?给出至少 2 种缓解方案。

## 8. 消息语义

### 8.1 学习目标

- 区分消息传递的至多一次、至少一次、恰好一次三种语义。
- 理解"恰好一次"实际上是工程近似。
- 在分布式系统中正确选择消息语义并实现。

### 8.2 核心概念

- **至多一次（at-most-once）**：对某个定义清晰的处理边界，每条消息产生 0 或 1 次效果；可能丢失。
- **至少一次（at-least-once）**：协议重试使处理可能发生 1 次或多次；这一保证仍受永久故障、保留期和配置等前提约束。
- **恰好一次效果（exactly-once effect）**：在声明的系统边界、故障模型和时间范围内，每个逻辑输入只改变受控状态一次。它可能由事务、去重、幂等或可重放状态实现，不等于网络只传输一次。
- **Kafka 幂等生产者**：Broker 依据 producer ID/epoch 与每分区序号去除生产重试造成的重复；Kafka 事务还能把多个 Kafka 分区写入和消费位点提交纳入一个事务。
- **事务消息**：产品语义各异。Kafka 事务只原子覆盖 Kafka 资源，不会自动绑定任意业务数据库事务；跨数据库和消息通常仍需 Outbox/CDC 或专用协议。

### 8.3 理论模型

#### 8.3.1 三种语义的边界

令 $H(m)$ 表示逻辑消息 $m$ 在**指定处理边界**产生的已提交业务效果次数：

$$
\begin{aligned}
\text{at-most-once}:&\quad H(m)\in\{0,1\}\\
\text{at-least-once}:&\quad H(m)\ge 1\quad\text{（交付与故障假设成立时）}\\
\text{exactly-once effect}:&\quad H(m)=1
\end{aligned}
$$

发送次数、接收次数与业务效果次数必须分开。崩溃重发可令接收次数大于 1；若消费结果和位点在同一事务提交，或以幂等键去重，受控状态仍可能实现一次效果。邮件、短信、支付网关等外部副作用不参与同一事务时，需要各自的幂等协议、对账与补偿，不能由消息平台单方面保证端到端一次效果。

#### 8.3.2 Kafka 幂等生产者

Kafka 幂等生产使用 producer ID/epoch、每分区序号及 Broker 去重，避免同一受支持生产会话中的重试在分区日志形成重复记录。它不等于端到端恰好一次：事务超时、producer fencing、消费者副作用和外部存储仍需单独处理。

Kafka 事务可以原子提交对**多个 Kafka 分区**的写入，并把 consume-process-produce 流程中的消费位点一并提交；配置 `read_committed` 的消费者不会读取中止事务。因此“不能跨分区”只适用于单纯幂等生产去重，不能描述 Kafka 事务的能力边界。

### 8.4 方法步骤

1. **业务分级**：资金、库存通常采用可重投交付 + 业务幂等、对账和补偿；只有允许采样丢失的遥测才考虑至多一次。
2. **生产端**：若状态都在 Kafka 内，可评估幂等生产和事务；业务数据库 + 消息使用 Outbox/CDC 等方案，不能假设 Kafka 事务自动绑定数据库事务。
3. **消费端**：处理结果与 offset 若不能原子提交，必须接受崩溃窗口内重复或丢失并设计幂等；“处理后手动提交”通常给至少一次，不会消除所有失败窗口。
4. **死信队列 (DLQ)**:处理失败的消息进入 DLQ,避免阻塞主链路。

### 8.5 权衡与失败模式

- **自动提交 offset**:消费未完成时 offset 已提交,下次不重投,导致丢失。
- **重复消费无幂等**:没有幂等表,重投导致重复扣款。
- **事务消息配置错**:本地事务已提交但消息未发出,造成"业务做了但消息没发"。
- **DLQ 无监控**:死信队列堆积无人处理。

### 8.6 示例:电商平台订单事件

- 主题:`order.events`。
- 分区键：若需要订单级顺序，优先使用 `order_id`；用 `tenant_id` 会把大租户流量压到单分区，且分区日志顺序不自动等于业务因果顺序。
- 生产端：订单表与 Outbox 在同一本地事务提交，再由 CDC/发布器写 Kafka；只有输入输出均在 Kafka 内时才可直接用 Kafka 事务覆盖。
- 消费端（履约服务）：以 `event_id` 或“聚合 ID + 版本”去重和检查顺序；提交副作用后再确认 offset，仍处理崩溃造成的重复。

### 8.7 检查清单

- [ ] 生产端开启幂等。
- [ ] 消费端手动提交 offset。
- [ ] 消费处理具备幂等键。
- [ ] 失败处理有 DLQ,且 DLQ 有监控。
- [ ] 事务消息或 Outbox(见 §10)用于"业务 + 消息"原子性。

### 8.8 练习

1. **语义选择。** 为"订单状态变更通知"、"支付回调"、"日志收集"、"秒杀下单"选择消息语义,并说明理由。
2. **Kafka 幂等边界。** 描述一个 Kafka 幂等生产者无法保证恰好一次的真实场景。
3. **DLQ 设计。** 设计一个 DLQ 的结构、告警阈值、人工介入流程。

## 9. 长事务:Saga

### 9.1 学习目标

- 理解 Saga 的目标与适用场景。
- 区分补偿事务(compensating transaction)与回滚(rollback)。
- 掌握 Saga 的两种协调方式:Orchestration 与 Choreography。

### 9.2 核心概念

- **Saga（Garcia-Molina & Salem, 1987）**：把长生命周期事务拆成一系列可提交子事务；失败后执行相应补偿，具体协调和隔离对策由实现定义。
- **补偿事务**：以新的业务动作语义上抵消已提交效果，不是物理回滚；已经被观察或不可逆的外部效果可能无法完全恢复。
- **Orchestration（编排）**：协调者显式驱动状态转换和补偿。
- **Choreography（协同）**：参与者响应事件推进流程；没有单一业务编排器，但消息基础设施和观测仍是共享协调机制。
- **Saga 异常**：补偿失败、乱序/重复、并发 Saga 破坏不变量、长期悬挂和人工处置。

### 9.3 理论模型

#### 9.3.1 Saga 的形式化

设长事务 $T$ 拆为子事务 $T_1, T_2, \dots, T_n$。每个 $T_i$ 有补偿 $C_i$:

$$
T \to T_1 \to T_2 \to \cdots \to T_n \to \text{done}
$$

若 $T_k$ 失败:

$$
T_1 \to \cdots \to T_k \to C_{k-1} \to \cdots \to C_1 \to \text{compensated}
$$

> **重要警示。** Saga **不提供 ACID 隔离**。在 Saga 执行过程中,外部观察者可能看到"部分提交"状态。这与两阶段提交(2PC)的关键差异。

#### 9.3.2 Saga 与 2PC 对比

| 维度 | Saga | 2PC |
| --- | --- | --- |
| 原子性 | 不提供全局原子提交；用补偿达到业务可接受结果 | 参与者遵循协议且日志可恢复时提供原子提交决定 |
| 资源占用 | 各步本地事务较短，但业务预留可能长期存在 | prepared 资源和锁可能保持到最终决定 |
| 故障行为 | 可继续部分业务，但补偿、乱序和中间态复杂 | 协调者/通信故障可使参与者阻塞；复制协调日志可改善恢复 |
| 隔离 | 默认不提供；需语义锁、版本、预留等对策 | 2PC 本身只管原子提交；隔离仍取决于资源管理器和并发控制 |
| 适用 | 长流程、参与者自治、可定义补偿 | 参与者支持协议、需原子提交且能接受耦合与可用性代价 |

#### 9.3.3 Saga 的反向操作语义

补偿**不是**回滚。例如:

- 创建订单 → 补偿是取消订单(状态字段变更),不是 DELETE。
- 扣库存 → 补偿是释放库存(可能引入"补偿库存"记录)。
- 发起支付 → 补偿是退款(异步,可能失败)。

### 9.4 方法步骤

1. **拆分 Saga**：围绕可独立提交的业务步骤和不变量拆分。
2. **定义失败语义**：为可补偿步骤定义幂等补偿；对发货、通知等不可完全补偿动作，设计延迟执行、人工处置或风险接受，不能假设每步都有完美逆操作。
3. **选协调方式**：Orchestration 状态显式、易追踪但集中；Choreography 减少业务协调中心，却更易形成隐式流程耦合。
4. **超时与重试**：每步有截止时间、幂等重试和最大尝试；结果不确定时先查询/对账，不盲目补偿。
5. **并发控制与可观测性**：Saga ID、聚合版本和状态机全链路透传；按不变量选择语义锁、预留或可交换更新。

### 9.5 权衡与失败模式

- **补偿不可逆**:已发货的订单,补偿不能撤货,只能"召回申请"。
- **悬挂 Saga**:补偿链路中某步一直失败,Saga 永远不结束。
- **隔离缺失**:Saga 执行期间看到中间态。
- **编排耦合**:Orchestrator 演化为"分布式单体",所有变更都要改它。

### 9.6 示例:电商平台下单 Saga

```
T1: OrderService.create_order (orchestrator-driven)
T2: InventoryService.reserve_stock
T3: CouponService.mark_coupon_used
T4: PaymentService.create_payment_intent
T5: FulfillmentService.schedule_pick

补偿链(任意失败触发):
C5: cancel_pick (if scheduled)
C4: cancel_payment (async)
C3: refund_coupon
C2: release_stock
C1: cancel_order
```

### 9.7 检查清单

- [ ] 每个子事务有补偿,且补偿可测试。
- [ ] Saga 实例 ID 全链路日志可追踪。
- [ ] 悬挂 Saga 有超时告警与人工介入通道。
- [ ] 协调方式(Orch/Choreo)与团队规模匹配。
- [ ] Saga 中间态对外的语义被明确文档化。

### 9.8 练习

1. **Saga 设计。** 设计"取消订单"的反向 Saga,包括已支付、已发货、已完成的差异化补偿。
2. **协调方式选择。** 电商平台 Saga 适合 Orchestration 还是 Choreography?说明理由。
3. **悬挂 Saga 应对。** 设计一个 Saga 步骤卡死 1 小时后的处理流程。

## 10. Outbox 与可靠消息投递

### 10.1 学习目标

- 理解 Outbox 模式解决的核心问题:业务事务与消息发送的原子性。
- 掌握 Outbox + CDC(Change Data Capture,变更数据捕获)、Outbox + Polling、Outbox + Transactional Messaging 三种实现。
- 正确处理 Outbox 的去重、顺序与积压。

### 10.2 核心概念

- **Outbox 模式 (outbox pattern)**:业务库中同时写入业务表与 outbox 表,二者共享本地事务;外部进程读取 outbox 并发布到消息总线。
- **CDC (Change Data Capture)**:捕获数据库变更流,Debezium 是常见实现。
- **Polling publisher**:定时轮询 outbox 表。
- **Transactional outbox**:业务 + outbox 一表多写,使用数据库事务保证原子性。

### 10.3 理论模型

#### 10.3.1 双写反模式

最常见的错误做法:

```
db.begin();
db.insert("order", ...);
kafka.send("order.created", ...);   // 与 db.commit 非原子
db.commit();
// 可能:commit 成功但 send 失败 → 消息丢失
// 可能:send 成功但 commit 失败 → 消息被消费但业务未发生
```

Outbox 将业务状态与“待发布事实”放进同一本地事务，消除这两个写入之间的原子性缺口；后续发布仍是异步的，会重复、乱序或积压，因此没有消除所有双写/端到端一致性问题。

#### 10.3.2 Outbox 的形式化

设业务事件为 $e$,outbox 行为 $O$。在本地事务 $T$ 内:

$$
T: \text{INSERT INTO business} \land \text{INSERT INTO outbox}
$$

发布进程 $P$:

$$
P: \text{SELECT FROM outbox WHERE published = false} \to \text{send to bus} \to \text{UPDATE published = true}
$$

发布与业务**不强一致**(发布进程是异步),但**因果一致**(业务有,outbox 必有)。

#### 10.3.3 三种实现路径对比

| 路径 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Polling | 定时扫 outbox | 简单、与 DB 解耦 | 延迟受轮询周期影响,DB 压力大 |
| CDC | Debezium 监听 binlog | 低延迟、无侵入 | 运维复杂,需保证 binlog |
| 事务消息 | RocketMQ / Kafka TX | 单系统内闭环 | 绑定 MQ 实现,跨 MQ 迁移成本 |

### 10.4 方法步骤

1. **建表**:outbox(id, aggregate_id, type, payload, created_at, published)。
2. **业务同写**:业务 INSERT 与 outbox INSERT 在同一事务。
3. **发布**:用 CDC 或 polling 推送到 MQ。
4. **幂等去重**:消费端按 `event_id` 去重(配合 §8 幂等)。
5. **积压监控**:outbox 表 `published=false` 行数超阈值告警。

### 10.5 权衡与失败模式

- **outbox 膨胀**:发布进程故障,未发布行无限增长。
- **binlog 丢失**:MySQL binlog 配置不当(ROW 格式、保留时长),CDC 漏数据。
- **顺序错乱**：若业务要求同一聚合的日志顺序，可用相同分区键、单调聚合版本和消费者缺口检测；同分区只保证 Broker 记录顺序，重试、多主题和并发处理仍可能打乱业务应用。
- **重复消费**：发布进程在“已发但未标记”窗口重发，消费者需幂等或与结果原子提交。

### 10.6 示例:电商平台订单事件 Outbox

```
表:
  outbox_event(id, aggregate_id=order_id, type, payload_json, created_at, published=false)

业务流程:
  BEGIN;
  INSERT INTO order (id, ...);
  INSERT INTO outbox_event (aggregate_id=order_id, type='OrderCreated', payload=...);
  COMMIT;

发布进程(CDC, Debezium):
  binlog → Kafka topic `order.outbox`

下游消费者(履约、库存):
  按 event_id 幂等,处理后提交 offset。
```

### 10.7 检查清单

- [ ] outbox 表与业务表同库,共享事务。
- [ ] 发布路径(CDC / Polling / TX)与运维能力匹配。
- [ ] outbox 积压有监控与告警。
- [ ] 消费者按 `event_id` 幂等。
- [ ] 对需要有序的聚合定义作用域、分区键、版本、缺口与乱序处理；不把“同分区”当完整顺序保证。

## 11. 缓存一致性

### 11.1 学习目标

- 理解缓存一致性的常见模式:Cache-Aside、Write-Through、Write-Behind、Read-Through。
- 识别缓存与数据库的并发更新异常。
- 为电商平台选型合适的缓存策略。

### 11.2 核心概念

- **Cache-Aside (Lazy Loading)**:读时填缓存,写时失效缓存。
- **Write-Through**:写缓存同时写 DB,缓存层同步。
- **Write-Behind (Write-Back)**:写缓存,异步写 DB。
- **Read-Through**:缓存层代理读源,源读不到由缓存层加载。
- **缓存击穿 (cache stampede)**:热点 key 失效瞬间大量请求打 DB。
- **缓存穿透 (cache penetration)**:请求不存在的数据,绕过缓存。
- **缓存雪崩 (cache avalanche)**:大量 key 同时失效或缓存层整体宕机。

### 11.3 理论模型

#### 11.3.1 双写不一致

设 DB 与缓存非原子更新。序列:

```
t1: 写 DB.x = 1, 缓存失效
t2: 读请求 A: 缓存 miss → 从 DB 读 x = 1 → 写缓存 x = 1
t3: 写 DB.x = 2, 缓存失效
t4: 读请求 A 在 t2 写的缓存尚未完成 → 实际缓存值仍为 1(陈旧)
```

> **理论边界。** 即使每次写都正确失效缓存,**双写不一致仍可能发生**,因为"读路径写缓存"和"写路径失效缓存"是并发竞争。

#### 11.3.2 解决双写不一致的工程方案

| 方案 | 描述 | 代价 |
| --- | --- | --- |
| 强一致读 | 缓存未命中时加分布式锁,只允许一个线程回填 | 复杂度 |
| 版本号 | 缓存带版本,陈旧则丢弃 | 内存 |
| 延迟双删 | 写 DB 后,延迟 N ms 再删缓存 | 经验值,不可靠 |
| 单写源 | 通过 MQ 异步更新缓存,顺序写入 | 链路复杂度 |

> **重要警示。** "延迟双删"是网络流传经验,**不是定理**,在分布式系统中无法保证不出错。

#### 11.3.3 缓存击穿的概率

设缓存 TTL 为 $T$,QPS 为 $Q$,请求耗时 $t$。在 TTL 过期瞬间,有约 $Q \cdot \Delta t$ 个请求同时打 DB。击穿概率:

$$
P_{\text{stampede}} \approx 1 - e^{-Q \cdot \Delta t / n}
$$

其中 $n$ 为 DB 节点数。QPS 越大,击穿概率越高。

### 11.4 方法步骤

1. **选择模式**:电商平台多数读场景用 Cache-Aside;配置类数据用 Read-Through。
2. **避免双写**:写路径只"失效缓存",不在写路径同步写缓存(避免不一致窗口)。
3. **热点保护**:对热点 key 加 mutex / singleflight,避免击穿。
4. **冷启动预热**:大促前预热热点数据。
5. **雪崩防御**:TTL 加随机抖动 + 多级缓存 + DB 限流。

### 11.5 权衡与失败模式

- **Write-Behind 丢数据**:缓存宕机,异步队列未刷盘。
- **缓存击穿**:热点商品秒杀,缓存过期瞬间 DB 被打挂。
- **缓存穿透**:恶意请求不存在 ID,DB 持续空查询。
- **缓存不一致**:写库后只失效部分 key,造成长时间不一致。

### 11.6 示例:电商平台商品缓存策略

| 数据 | 模式 | 说明 |
| --- | --- | --- |
| 商品详情 | Cache-Aside + TTL + 随机抖动 | 读多写少,容忍秒级不一致 |
| 商品价格 | 浏览缓存 + 结算时权威报价/版本校验 | Write-Through 本身不保证缓存与数据库原子一致 |
| 库存 | 权威扣减不依赖缓存；展示可用近似缓存 | 缓存不能裁决不变量，但完全“不进缓存”不是必要条件 |
| 推荐列表 | Cache-Aside + 后台异步重建 | 允许陈旧并显示合适语义 |
| 购物车 | 权威存储 + 会话读己之写；可按负载加缓存 | Write-Through 不是实现用户立即可见的充分条件，需定义并发与故障语义 |

### 11.7 检查清单

- [ ] 每个缓存键有 TTL + 随机抖动。
- [ ] 写路径只失效缓存,不直接写缓存。
- [ ] 热点 key 有击穿保护(singleflight / mutex)。
- [ ] 缓存雪崩有 DB 兜底限流。
- [ ] 缓存穿透有布隆过滤器或空值缓存。
- [ ] Write-Behind 的数据丢失风险被显式接受或消除。

### 11.8 练习

1. **模式选择。** 为商品价格、购物车、推荐列表、库存分别选择缓存模式,并说明理由。
2. **击穿演练。** 设计一个缓存击穿的演练方案,模拟 TTL 过期瞬间的 DB QPS 突增。
3. **延迟双删评估。** 在你熟悉的系统中,延迟双删是否能根除双写不一致?给出你的推理。

## 12. 流批一体

### 12.1 学习目标

- 理解 Lambda 架构与 Kappa 架构的差异。
- 掌握流批一体的常见实现路径。
- 为电商平台选型合适的实时+离线融合架构。

### 12.2 核心概念

- **Lambda 架构 (Nathan Marz, 2011)**:批处理层(Batch Layer)+ 速度层(Speed Layer)+ 服务层(Serving Layer)。同一逻辑用两套代码实现。
- **Kappa 架构 (Jay Kreps, 2014)**:只有流处理,通过重放(replay)历史数据完成批处理。
- **流批一体 (unified stream-batch)**:同一套代码同时处理流与批,典型实现 Flink + Iceberg / Hudi。
- **物化视图 (materialized view)**:把查询结果持久化为表,典型增量物化 Flink。

### 12.3 理论模型

#### 12.3.1 Lambda 的双代码问题

同一业务逻辑需维护两套代码:

$$
\text{Logic} = f_{\text{batch}}(\text{history}) \cup f_{\text{stream}}(\text{recent})
$$

二者结果需在服务层合并:

$$
\text{result} = f_{\text{batch}}(\text{history}) \cup f_{\text{stream}}(\text{recent})
$$

合并误差与双代码维护成本是 Lambda 的核心缺陷。

#### 12.3.2 Kappa 的可重放性

Kappa 假设流存储可保留足够长时间的历史:

$$
\text{流存储容量} \ge Q_{\text{event}} \times T_{\text{retain}}
$$

例：每日 10 亿事件、保留 7 天，需要保存约 70 亿事件，不是“70 亿/日 × 7 = 490 亿”。若平均压缩后 1 KB/事件，原始容量约 7 TB，再计复制、索引与日志段开销。Kappa 不要求历史永远只放 Kafka；可重放日志也可分层到对象存储。

#### 12.3.3 流批一体的形式化

设同一份代码 $C$,流输入 $S(t)$、批输入 $B(T)$。流批一体的核心条件:

$$
\text{output}(C, S(t)) \equiv \text{output}(C, B(T)) \quad \text{在语义等价前提下}
$$

实际“统一”的程度可能来自同一 API/SQL、同一执行引擎或一致语义的数据源，但流与批在事件时间、水位线、状态、迟到数据、失败恢复和资源调度上仍有差异。Flink、Iceberg、Hudi 是候选组合，不是流批一体的必要条件。

### 12.4 方法步骤

1. **识别时效需求**：从决策截止时间、允许陈旧和修正语义推导流/批，而非把库存预占等在线事务误放进分析流处理。
2. **比较方案**：现有双路径是否真的漂移；历史是否可重放；重算时限、状态规模、团队能力和成本如何。Lambda、Kappa 与统一 API 可混合使用。
3. **存储分层**：按重放时间、吞吐和成本选择日志与对象存储，不固定“热 Kafka、冷 Iceberg”。
4. **正确性**：定义事件时间、水位、迟到/修正、去重和对账，不只比较最终数字。

### 12.5 权衡与失败模式

- **Lambda 双代码漂移**:批逻辑改了,流逻辑忘了改。
- **Kappa 重放成本**:重放 7 天数据耗时数小时,无法快速回溯。
- **流批一体调试复杂**:状态后端、Changelog、Checkpoints 链路复杂。
- **对账缺失**:流批结果长期不一致无人发现。

### 12.6 示例:电商平台实时看板

- 流:Flink 消费订单事件,实时计算 GMV(商品交易总额)。
- 批:每晚 Flink Batch 跑全量订单,出"准确版"GMV。
- 对账:实时 GMV 与批 GMV 偏差 > 0.5% 时告警。
- 报表层:用户看"实时"时显示流结果,看"准确"时显示批结果。

### 12.7 检查清单

- [ ] 实时需求被显式识别,非必要不上流。
- [ ] Lambda 的双代码有版本管理与漂移检测。
- [ ] Kappa 重放路径有演练。
- [ ] 流批对账机制存在。
- [ ] 流批一体的状态后端、Checkpoint 策略明确。

### 12.8 练习

1. **架构选型。** 为"实时 GMV 看板"、"每日销售报告"、"用户画像"分别选择架构(Lambda / Kappa / 流批一体)。
2. **对账设计。** 设计一个流批对账方案,包括触发频率、偏差阈值、告警通道。
3. **Kappa 容量。** 假设每日 50 亿事件、平均事件 1KB、保留 30 天,计算 Kappa 所需存储与成本。

## 13. 数据湖仓

### 13.1 学习目标

- 区分数据仓库(data warehouse)、数据湖(data lake)、数据湖仓(lakehouse)。
- 掌握主流开放表格式(Open Table Formats):Iceberg、Hudi、Delta Lake。
- 为电商平台选型合适的数据平台。

### 13.2 核心概念

- **数据仓库（data warehouse）**：面向分析的受治理数据平台，可能使用星型/雪花模型，也可采用其他建模；Snowflake、BigQuery、ClickHouse 的架构与事务能力不同。
- **数据湖（data lake）**：以低成本对象/文件存储承载多种结构和处理方式；不是天然“无 schema”，仍可有 schema-on-read、目录和治理。
- **数据湖仓（lakehouse）**：试图在开放/低成本数据存储上提供数据仓库式管理与查询能力，是架构范式/行业术语，不是严格标准。
- **开放表格式**：Iceberg、Hudi、Delta Lake 等管理快照、元数据和并发提交；“开放”程度与生态兼容需具体评估。
- **Time Travel**：在保留策略允许范围内查询历史快照。
- **Schema/Partition Evolution**：能力和限制依表格式、引擎与具体变更类型而异，不保证任意列增删改都无损兼容，也不保证修改分区永不重写历史数据。

### 13.3 理论模型

#### 13.3.1 三层架构

```
┌─────────────────────────────┐
│  查询引擎 (Trino / Spark /  │
│  Flink / Dremio)            │
└─────────────────────────────┘
┌─────────────────────────────┐
│  开放表格式 (Iceberg /      │
│  Hudi / Delta)              │
└─────────────────────────────┘
┌─────────────────────────────┐
│  对象存储 (S3 / OSS /       │
│  HDFS / MinIO)              │
└─────────────────────────────┘
```

#### 13.3.2 ACID 在湖仓中的实现

- **Iceberg**:基于快照(manifest list + manifest file),乐观提交,Snapshot 隔离。
- **Hudi**:Copy-on-Write(读优化)与 Merge-on-Read(写优化)两种模式。
- **Delta Lake**:基于 `_delta_log/` 的 JSON/Checkpoint 日志,Optimistic Concurrency。

> **边界。** “湖仓 ACID”必须按表格式和引擎说明：通常提供表级快照、原子提交与某种乐观并发，部分实现也支持行级更新/删除。它不等于“无行级能力”，也不自动具备 OLTP 的低延迟、高并发、约束和多表事务语义。

#### 13.3.3 湖仓的代价函数

设表大小 $S$、文件数 $F$、查询延迟 $L$。湖仓的代价:

$$
L = f(\text{元数据扫描}) + f(\text{数据扫描})
$$

小文件会增加元数据、列举、调度和打开文件成本，但目标文件大小取决于格式、查询选择性、写延迟、对象存储和引擎；256 MB–1 GB 可作某些工作负载起点，不是 Iceberg 通用推荐范围。

### 13.4 方法步骤

1. **选表格式与目录**：按引擎兼容、并发写、更新/删除、分区演进、锁/目录、恢复和退出成本做实验，不用“Iceberg 开放、Hudi 写优、Delta 配 Spark”标签代替测试。
2. **建模分层**：ODS/DWD/DWS/ADS 是一种常见数仓命名，不是湖仓必要结构；按数据产品、语义和消费边界选择。
3. **治理**：目录、权限、血缘、质量、保留与数据责任一起设计。
4. **查询/计算**：按工作负载选择引擎并验证同一表格式版本、类型与并发提交兼容性。

### 13.5 权衡与失败模式

- **小文件问题**:流式高频写入产生百万级小文件,查询慢。
- **元数据膨胀**:Iceberg manifest 过多,提交慢。
- **读时合并(MOR)延迟**:Hudi MoR 模式下读最新数据需合并 base + log。
- **锁竞争**:湖仓的乐观锁在高频写入时冲突率高。

### 13.6 示例:电商平台数据湖仓分层

```
ODS (原始):
  - ods_order (订单原始事件)
  - ods_payment (支付原始事件)
DWD (明细):
  - dwd_order_detail (订单明细宽表)
DWS (汇总):
  - dws_sku_daily (商品日维度汇总)
ADS (应用):
  - ads_sales_dashboard (看板)
  - ads_user_recommendation (推荐特征)
```

### 13.7 检查清单

- [ ] 表格式选型有理由,并对社区活跃度有评估。
- [ ] 分层规范明确,数据血缘可追溯。
- [ ] 小文件治理按实际文件分布、查询/写入成本触发，不机械定期合并。
- [ ] 目录、表格式与 Spark/Trino/Flink 等引擎的兼容矩阵已验证，不要求“元数据服务版本一致”这种模糊规则。
- [ ] 读写并发、隔离、提交冲突和流/批消费语义已测试；不把“批写流读”当固定架构。

### 13.8 练习

1. **表格式选型。** 比较 Iceberg、Hudi、Delta Lake 在"高频流式写入 + 中等查询频率"场景下的表现。
2. **小文件治理。** 设计一个小文件治理流程,包括检测阈值、合并策略、调度频率。
3. **分层设计。** 为电商平台设计 ODS → DWD → DWS → ADS 的具体表清单与更新周期。

## 14. 数据治理

### 14.1 学习目标

- 理解数据治理的核心范畴:元数据、血缘、质量、安全、生命周期。
- 掌握多租户场景下的数据隔离、访问控制与审计。
- 区分"治理(governance)"与"管理(management)"。

### 14.2 核心概念

- **元数据 (metadata)**:描述数据的数据,分技术元数据(表结构、分区)与业务元数据(业务定义、责任人)。
- **数据血缘 (data lineage)**:数据从源到目标的流转路径。
- **数据质量 (data quality)**:完整性、准确性、一致性、时效性、唯一性。
- **数据安全 (data security)**:访问控制、加密、脱敏、审计。
- **数据生命周期 (data lifecycle)**:从创建、使用、归档到销毁的全过程。
- **数据目录 (data catalog)**:可搜索的数据资产目录。
- **多租户治理**:在共享存储上做行级/列级隔离与权限。

### 14.3 理论模型

#### 14.3.1 数据治理能力成熟度

设 $M$ 为成熟度等级,$0-5$ 级:

| 等级 | 描述 |
| --- | --- |
| 0 | 无治理,数据混乱 |
| 1 | 被动治理,出问题再处理 |
| 2 | 有目录,无血缘 |
| 3 | 有血缘,有质量规则 |
| 4 | 自动质量监控 + 生命周期管理 |
| 5 | 自适应治理 + AI 辅助 |

#### 14.3.2 数据质量的度量函数

设数据集 $D$,质量函数 $Q(D)$:

$$
Q(D) = \frac{1}{N} \sum_{i=1}^{N} w_i \cdot m_i(D)
$$

其中 $m_i$ 为单项质量度量(完整性、准确性、唯一性等),$w_i$ 为权重。

#### 14.3.3 多租户隔离的访问控制模型

设租户 $t$,用户 $u$,资源 $r$。访问决策:

$$
\text{allow}(u, r) = \text{role\_check}(u, r) \land \text{tenant\_check}(u, t(r))
$$

其中 $t(r)$ 是资源 $r$ 的租户。强制每条 SQL 携带 `tenant_id` 谓词(通过视图、Row-Level Security 或查询改写)。

### 14.4 方法步骤

1. **建立目录**:用 Apache Gravitino、Unity Catalog、DataHub 等搭建数据目录。
2. **采集血缘**:通过解析 SQL、捕获 ETL 元数据,自动构建血缘。
3. **质量规则**:关键指标设质量规则(订单金额 > 0、租户 ID 非空)。
4. **访问控制**:列级脱敏、行级 RLS、字段级加密。
5. **生命周期**:热数据 → 冷数据 → 归档 → 删除,有 SLA。
6. **审计**:所有数据访问留痕,满足合规(等保、GDPR、SOC2)。

### 14.5 权衡与失败模式

- **治理过度**:每个表都要文档化、血缘完备,反而拖慢交付。
- **治理缺位**:无目录、无审计,出问题无法定位。
- **权限粒度过细**:行级 + 列级 + 字段级,运维成本陡增。
- **租户泄漏**:RLS 未配置或被绕过。
- **生命周期不闭环**:热数据长期不归档,存储成本失控。

### 14.6 示例:电商平台数据治理

- **元数据**:用 Gravitino 统一目录,每个表标注租户、责任人、更新频率。
- **血缘**:Flink / Spark 任务自动采集血缘,展示在 DataHub。
- **质量规则**:订单金额非负、SKU 存在性、租户 ID 与上游一致。
- **访问控制**:RLS 强制 `tenant_id` 谓词,敏感字段(身份证、银行卡)加密 + 脱敏。
- **生命周期**:订单详情保留 3 年,日志保留 90 天,临时表保留 7 天。
- **审计**:所有数据访问写入审计表,关键操作(导出、删除)实时告警。

### 14.7 检查清单

- [ ] 有数据目录,且覆盖率(已登记表 / 总表)≥ 80%。
- [ ] 血缘可视化,关键链路 100% 覆盖。
- [ ] 关键数据有质量规则与监控。
- [ ] 租户隔离有 RLS 或强制谓词。
- [ ] 敏感字段加密 + 脱敏。
- [ ] 生命周期策略自动化执行。
- [ ] 审计日志保留周期满足合规。

### 14.8 练习

1. **治理规划。** 为电商平台设计一份 6 个月数据治理路线图,包括目录、血缘、质量、安全四个维度。
2. **租户泄漏检测。** 设计一个静态扫描工具,检测 SQL 是否缺少 `tenant_id` 谓词。

## 16. 章节小结

- **数据模型与所有权**：明确权威写入、允许的多写者合并语义和责任边界。
- **事务与隔离**：SI 不等于 Serializable；用业务不变量和并发历史选择保证。
- **CAP / PACELC**：区分不可能性结果、分类框架与模糊术语。
- **共识与复制**：Raft/Paxos 提供特定故障模型下的复制决策基础；多主另需冲突语义。
- **分区**：分片键强烈塑造局部性、热点与跨片操作成本，但不是唯一决定因素。
- **时间与顺序**：客户端时钟不可作为全局真相；逻辑时钟、HLC 和有界时钟各有保证边界。
- **幂等**：按副作用与重试边界选择幂等键、状态机、条件写或去重表，不把单一实现当标配。
- **消息语义**：先定义交付边界和业务效果；一次效果可在受控事务边界内实现，跨外部副作用通常靠至少一次交付、幂等、对账与补偿组合。
- **Saga**：补偿不是回滚，Saga 默认不提供隔离或全局原子提交。
- **Outbox**：原子连接本地业务状态与待发布记录；仍需处理发布重复、顺序、积压和消费副作用。
- **缓存一致性**:Cache-Aside + 写失效,警惕双写不一致。
- **流批一体**:三种架构各有适用场景,流批一体非万能。
- **数据湖仓**:ACID 表格式改变了数据湖,但有边界。
- **数据治理**:目录、血缘、质量、安全、生命周期五位一体。
