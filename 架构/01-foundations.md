# 第 1 章　架构本质、理论基础与成长路线

> 面向有工程经验、希望系统成长为架构师的读者。本教程把“架构”当作一种在不确定性、约束和组织协作中持续作出可验证决策的工程学，而不是一组产品名词或图形模板。
>
> 文中的案例统一采用“多租户电商平台”：平台服务多个相互隔离的商户（租户），每个租户拥有商品、订单、促销和运营人员；终端买家可能跨租户访问；平台还要处理支付、库存、履约、结算、审计与平台治理。

---

## 第一部分　架构本质与理论基础

### 学习目标

完成本章后，读者应能够：

1. 用结构（structure）、属性（properties）和决策（decisions）三个互补视角定义和描述架构，而不把架构等同于组件图或技术选型。
2. 区分系统的本质复杂性（essential complexity）与偶然复杂性（accidental complexity），识别约束、边界和利益相关者如何共同塑造可行解。
3. 解释抽象（abstraction）、分解（decomposition）、内聚（cohesion）和耦合（coupling）之间的关系，并判断何时不应继续拆分。
4. 把架构和详细设计看作连续谱，根据决策的影响范围、变更成本和不确定性分配设计责任。
5. 使用形式化模型讨论约束优化、局部/全局最优、帕累托前沿（Pareto frontier）以及反馈回路（feedback loop）。
6. 在多租户电商平台案例中，写出可追溯、可验证、可演化的架构决策，并识别常见反例。

### 核心概念

### 1. 架构是关于“选择和后果”的系统描述

**软件架构（software architecture）**是系统基本组织（fundamental organization）的可审查描述：它包括系统元素、元素之间的关系、这些关系在运行时和开发时的约束，以及指导系统设计与演化的原则。这个定义比“系统的高层结构”更严格，原因有三点：

- 只有结构，没有约束，读者无法知道哪些变化是允许的；
- 只有当前状态，没有决策理由，团队无法判断未来是否还能安全地改变它；
- 只有技术视角，没有利益相关者（stakeholders）及其关切（concerns），就无法说明“好架构”究竟好在哪里。

架构不是图，也不是某个职位的专属产物。图是投影，文档是证据，决策才是承担后果的工程活动。一个没有图但边界和约束清晰的系统，可能比拥有几十张漂亮图却没有约束执行的系统更有架构；反过来，口头共识若没有记录和验证，通常不能称为可维护的架构资产。

### 2. 三视角：结构、属性、决策

同一架构至少应从三个相互校验的视角观察：

| 视角 | 要回答的问题 | 典型产物 | 容易遗漏的风险 |
| --- | --- | --- | --- |
| **结构视角（structure view）** | 有哪些元素？如何连接？边界和依赖是什么？ | 模块图、部署图、数据流图、运行时拓扑 | 把“画出来”误认为“受控”；忽略非功能约束 |
| **属性视角（property view）** | 系统具有什么质量属性（quality attributes）和可观测行为？ | 质量属性场景、SLO、容量模型、威胁模型、成本模型 | 用形容词代替可测量目标；忽略属性间冲突 |
| **决策视角（decision view）** | 为什么这样组织？有哪些备选、假设、代价和退出条件？ | ADR（Architecture Decision Record，架构决策记录）、权衡表、演进路线 | 事后合理化；遗忘不可逆承诺；决策与代码脱节 |

三视角不是三个独立文档，而是同一个系统的三个投影。结构改变会改变属性，属性目标会反过来限制结构，决策则解释二者为何在某一时点形成当前形态。例如：

- 将订单与库存拆为两个服务（结构）可能提高独立扩展能力（属性），但引入跨服务一致性和运维复杂度（属性），因此需要记录“允许何种库存短暂超卖、由谁补偿”（决策）。
- 选择按租户分库（结构）不是“隔离更好”这样一句口号；它意味着迁移、备份、连接池、成本和故障域的具体承诺（属性与决策）。

### 3. 复杂性：不可消除的部分与可避免的部分

**复杂性（complexity）**不是代码行数的同义词。它是理解、预测、修改和协调系统状态所需的认知与操作负担。至少要区分：

- **本质复杂性（essential complexity）**：借用 Brooks 的区分，来自问题本身、在当前问题定义下无法靠更换实现工具消除的复杂性，例如支付状态、不变量和法规差异。它会随范围与业务模型变化，不是绝对不可约。
- **偶然复杂性（accidental complexity）**：解决方案表达、工具、流程或历史额外引入的负担，例如重复转换、无意义中间层、过度分布、配置分散和不可观测异步链；它通常可降低，但很少能完全消失。
- **结构复杂性**：元素数量、依赖边、状态与交互路径造成的复杂度。
- **动态复杂性**：时间、并发、重试、故障、部署顺序和反馈延迟造成的复杂度。
- **认知/协调复杂性**：一个人或一个团队必须同时理解的概念数量，以及跨团队沟通的成本。

架构师的目标通常不是“让复杂性为零”，而是把本质复杂性放在正确的边界内，并以较低偶然复杂性表达它。删除一个无法解释业务约束的抽象层，可能比增加一套框架更能降低复杂性。

### 4. 约束、目标与可行解

**约束（constraint）**是架构必须服从的限制；**目标（objective）**是希望优化的方向。二者不能混用：法律要求数据驻留在某区域是硬约束，而“尽量低成本”是优化目标；把目标写成绝对约束会压缩不必要的解空间，把硬约束当偏好则可能导致违规。

约束可按来源分类：

- 外部约束：法律、支付机构协议、云厂商区域、客户合同。
- 内部约束：现有团队技能、遗留接口、交付期限、预算、组织结构。
- 技术约束：协议语义、数据库事务模型、设备能力、网络分区。
- 过程约束：发布窗口、审计流程、变更审批、回滚能力。
- 隐含约束：未写下但被默认遵守的组织习惯；它们往往是最危险的“幽灵约束”。

架构空间（architecture space）是满足约束的候选方案集合。架构活动的关键不是寻找“唯一正确方案”，而是明确哪些方案不可行、哪些方案在何种权衡下更合适。

### 5. 系统边界与上下文

**系统边界（system boundary）**规定哪些责任由本系统承担，哪些责任交给外部参与者、平台或组织。边界不是自然存在的线，而是为了某个关切而作出的选择。边界至少有四种维度：

1. 责任边界：谁对业务规则、数据正确性和补偿负责？
2. 变化边界：哪些部分预计一起变化，哪些部分应独立演进？
3. 故障边界：一个部分失效时，影响能否被隔离？
4. 认知/组织边界：哪个团队能够端到端理解、开发、运行和排障？

**系统上下文（system context）**包括买家、租户、支付服务、仓储、物流、税务、身份提供商和运营组织。若只画系统内部，不画外部依赖，就会把外部故障和契约误认为“偶然事件”。

边界选择不是越细越好。边界把耦合移到接口上；接口本身也有语义、版本、延迟和失败模式。一个边界若没有独立的责任、变化理由或故障收益，往往只是把一个模块改名成服务。

### 6. 抽象、分解、内聚与耦合

**抽象（abstraction）**隐藏与当前决策无关的细节，同时保留能支撑推理的语义。抽象不是删信息越多越好，而是保留“对当前问题足够”的信息。

**分解（decomposition）**把系统划分为可理解、可改变、可验证的部分。好的分解通常具有：

- 高内聚：同一部分中的职责共享变化理由、领域概念或不变量；
- 低耦合：部分之间的依赖少、稳定、显式且可测试；
- 明确契约：接口描述行为和失败语义，而不只是字段格式；
- 可替换性：在不破坏外部承诺时能替换实现。

耦合不只是“调用次数”。数据共享、事务边界、发布节奏、团队协调、隐含时序、共同运维和共同故障域都可能构成耦合。一个完全无耦合的系统通常也无法完成任何有意义的协作；追求的是**必要耦合最小化**，而不是耦合绝对为零。

### 7. 架构与设计是连续谱

架构与设计不应被当作两个互斥层级。可以用三个变量判断一个决策在连续谱上的位置：

- 影响范围：影响一个函数、一个模块、一个团队，还是整个生态？
- 变更代价：改变它是否需要数据迁移、跨团队协调、停机或合同重谈？
- 不确定性与延迟：错误后果多久显现，是否容易回滚？

“选择 HTTP 客户端库”通常靠近局部设计；“规定所有订单写入必须经由幂等命令接口，并以事件驱动下游履约”更靠近架构。边界会随系统规模、团队规模和阶段变化：小团队中的一个类设计，在大型组织中可能成为跨产品的架构约束；反之，某个可替换的实现细节不应被架构文档过度治理。

### 理论模型

### 1. 三投影模型：结构、属性与决策的可追溯关系

把系统表示为四元组：

\[
\mathcal{S}=(V,E,A,D)
\]

其中：

- $V$ 是元素集合（模块、服务、数据存储、团队、外部系统等）；
- $E$ 是元素关系集合（调用、发布、拥有、部署、依赖、共同变更等）；
- $A$ 是属性集合及其观测值（延迟、可用性、隔离强度、成本、可恢复性等）；
- $D$ 是决策集合，每个决策包含目标、候选、假设、证据、后果和复查条件。

结构视图主要是 $(V,E)$ 的投影；属性视图是函数

\[
Q: (V,E,\text{workload},\text{failure})\rightarrow \mathbb{R}^{n}
\]

它把拓扑、负载和故障条件映射为 $n$ 维质量结果；决策视图则定义从约束与证据到结构/属性的映射：

\[
D_i=(C_i,G_i,K_i,H_i,O_i,R_i)
\]

其中 $C_i$ 为约束，$G_i$ 为目标，$K_i$ 为候选，$H_i$ 为假设，$O_i$ 为后果，$R_i$ 为复查/退出条件。

追溯关系可写成：

\[
\text{Concern}\rightarrow\text{Quality Scenario}\rightarrow\text{Decision}\rightarrow\text{Structure}\rightarrow\text{Evidence}
\]

若链条中断，就会出现“有要求无设计”“有设计无验证”或“有技术无理由”。例如“高峰期结算延迟不超过 2 秒”应能追溯到流量假设、队列策略、数据模型、压测证据和监控指标。

### 2. 复杂性模型：规模、交互、状态与耦合

为了比较候选方案，可以使用如下启发式模型，而不是把它当作物理定律：

\[
C_{total}=C_{essential}+\alpha N+\beta E+\gamma S+\delta K+\epsilon T
\]

- $C_{essential}$：领域本质复杂性；
- $N$：需要理解的元素数；
- $E$：交互/依赖边数；
- $S$：显式或隐式状态数；
- $K$：跨边界耦合强度，可按数据、时序、发布和故障依赖加权；
- $T$：反馈延迟与运行时不确定性；
- $\alpha,\beta,\gamma,\delta,\epsilon$：在当前团队和场景下的权重。

该模型的价值在于提出问题：拆分服务减少 $N$ 吗？通常不一定；它可能增加部署、契约和运维元素。拆分是否降低 $K$？只有当业务变化、数据所有权和故障隔离边界真的对齐时才可能。引入异步队列可能减少同步耦合，却增加状态、延迟和调试复杂度。

可进一步估算交互路径的状态空间。若有 $m$ 个独立状态变量，第 $j$ 个变量有 $s_j$ 个可能值，则理论状态数为：

\[
|\Omega|=\prod_{j=1}^{m}s_j
\]

实际系统常有不变量使可行状态少于该上界，但并发、重试和部分失败会重新扩大需要推理的路径。把支付、订单、库存都放进一个“万能事务”并不会消灭状态，只是把状态隐藏在更难观测的边界内。

### 3. 约束优化与帕累托前沿

设候选架构为 $x\in X$，质量目标向量为 $q(x)$，成本与风险为 $c(x),r(x)$，硬约束为 $g_i(x)\le 0$。一个简化的选择问题是：

\[
\begin{aligned}
\min_{x\in X}\quad & w_c c(x)+w_r r(x)-\sum_{j=1}^{n}w_j q_j(x)\\
\text{s.t.}\quad & g_i(x)\le 0,\quad i=1,\ldots,k
\end{aligned}
\]

- $w_c,w_r,w_j$ 是当前阶段的权重；
- $q_j$ 是希望越大越好的质量指标，或先统一成“损失”方向；
- 约束条件只表示必须满足的底线，不应与偏好混为一谈。

权重并非客观真理。不同租户、业务阶段或监管环境会给出不同权重，因此更可靠的产物是**帕累托候选集**：不存在某个方案在所有目标上都不差且至少一项更优。架构评审的任务是让利益相关者明确选择了哪一个前沿点，以及牺牲了什么。

**局部最优**是在当前边界、指标和时间窗口内最优；**全局最优**是在整个系统及其长期演化路径上最优。局部优化常见于：让商品查询单接口延迟最低，却增加跨租户缓存污染和结算数据复制；让一个团队交付最快，却把协调成本转移给平台运维。全局最优也不是无限远期的完美方案：若交付窗口已错过，理论上的全局最优没有现实价值。应明确优化视界（horizon）和可接受回撤。

### 4. 边界模型：切分是减少变化耦合，不是减少文件数

设组件集合为 $V$，依赖矩阵为 $M$，其中 $M_{ij}$ 表示组件 $i$ 对组件 $j$ 的依赖强度。给定一个分区 $P=\{P_1,\ldots,P_k\}$，跨分区耦合可粗略表示为：

\[
K_{cross}(P)=\sum_{i\ne j,\;P(i)\ne P(j)}M_{ij}
\]

但单纯最小化 $K_{cross}$ 会把整个系统合并成一个组件。必须同时考虑分区内部的变化一致性、责任、故障和团队容量。一个更有用的目标是：

\[
J(P)=\lambda K_{cross}(P)+\mu C_{coord}(P)+\nu C_{failure}(P)-\rho H_{cohesion}(P)
\]

- $C_{coord}$：跨团队、跨发布和跨测试协调成本；
- $C_{failure}$：故障传播或隔离不足的代价；
- $H_{cohesion}$：分区内部共享不变量和变化理由的程度；
- 系数表示本阶段的关注重点。

分区的好坏必须在具体场景下判断。按技术层切成“商品服务、订单服务、数据库服务”可能让每个名词独立，却使一个订单用例横跨所有层；按业务能力和不变量切分，通常更容易形成端到端责任，但并非在所有组织和负载条件下都成立。

### 5. 抽象模型：信息损失与决策充分性

抽象可以看作从详细状态 $s\in S$ 到模型状态 $a\in A$ 的映射 $f:S\to A$。若两个具体状态在当前关切下具有相同决策结果，就可以合并；若抽象隐藏了会改变决策的差异，则抽象不充分。

可定义一个与关切相关的损失：

\[
L(f)=\mathbb{E}_{s}[\ell(\text{decision}(s),\text{decision}(f(s)))]
\]

当 $L(f)$ 低于当前可接受阈值且模型成本足够低时，抽象是有用的。这个模型解释了两个反例：

- 把“订单状态”抽象成布尔值“是否完成”，隐藏支付已扣款但履约失败的中间状态，导致补偿策略错误；
- 把支付提供商统一成接口，若接口没有暴露授权、捕获、退款和异步拒付语义，抽象看似简洁，实际损失很高。

### 6. 反馈回路与架构演化

架构不是一次性规划，而是控制回路（control loop）：

\[
\text{观测}\rightarrow\text{建模}\rightarrow\text{决策}\rightarrow\text{实施}\rightarrow\text{度量}\rightarrow\text{复盘}\rightarrow\text{再观测}
\]

设系统真实状态为 $z_t$，我们通过观测 $y_t=h(z_t)+\eta_t$ 获得带噪信号，其中 $\eta_t$ 是观测误差；决策 $u_t$ 影响下一时刻状态：

\[
z_{t+1}=F(z_t,u_t,\xi_t)
\]

$\xi_t$ 表示不可预测扰动。反馈延迟过长时，团队会在问题尚未显现前连续叠加修复，形成振荡；指标只看平均值时，尾延迟和少数租户的伤害会被掩盖；没有可逆实验时，反馈回路无法区分因果与巧合。

### 7. 三条经验规律及其边界

#### 7.1 Conway 定律（Conway’s Law）

> 设计系统的组织，其设计往往受组织沟通结构约束并呈现相似形态。

它是社会技术系统的经验观察，不是形式化决定论。若团队分别拥有目录、订单、支付和履约，而跨域协作成本高，接口和语义常会映射这些边界。跨职能团队、平台和治理机制可以改变映射，但需要持续的信息流与决策权支持。

#### 7.2 Gall 的观察（Gall’s Law）

> 可工作的复杂系统通常被观察到由可工作的较简单系统演化而来；从零设计的大型复杂系统往往难以直接工作。

它来自 John Gall 的经验性表述，不是证明微服务、单体或某种交付顺序的定理。“简单”也不等于省略安全、隔离和审计，而是尽早建立可运行闭环并验证关键风险。


#### 7.3 Lehman 软件演化定律（Lehman’s Laws of Software Evolution）

Lehman 观察到持续使用的软件必须不断变化，否则其对环境的适应性和用户满意度会下降；复杂性也会随演化增长，除非主动维护和重构。不同版本的表述强调持续变化、复杂性增长、质量下降与反馈调节等现象。

它们的工程含义是：架构债务（architecture debt）不是一次还清的账单；每次需求、法规和流量变化都会改变架构的适应性。反例是把“稳定”理解为冻结接口和拒绝变化，结果通过旁路脚本和未治理复制引入更大的隐性复杂度。定律也不是放弃设计的借口：主动简化、删除功能、自动化验证和调整组织都能改变增长曲线。

### 方法步骤

### 步骤 1：定义任务、系统和时间视界

先写一段可证伪的任务声明，而不是“建设高可用平台”。至少包含：服务对象、核心价值、主要工作负载、不可接受的失败、时间视界和已知约束。

示例：

> 在未来 18 个月内，为 500 个租户提供共享电商能力；大促期间支持峰值每秒 20,000 次商品查询和每秒 1,000 个下单请求；租户间不得读取彼此订单；支付重复请求不得造成重复扣款；平台可在单区域故障后恢复核心交易。

这里的数字是假设，必须在发现阶段验证；它们不是架构师可以擅自“补全”的事实。

### 步骤 2：画上下文并声明边界

列出外部参与者、系统、组织和契约。对每条边界写清：

- 责任：谁产生、验证、持久化和修正数据？
- 契约：同步/异步、超时、重试、幂等、版本和错误语义。
- 故障：依赖不可用时，允许降级、排队、拒绝还是人工处理？
- 所有权：谁可以改变规则，谁承担运维和合规责任？

不要先选“服务”这个名词；先选责任和不变量。

### 步骤 3：收集利益相关者关切并改写为质量属性场景

利益相关者包括租户开发者、买家、客服、财务、平台运维、合规人员和业务负责人。将模糊词改写成六元场景：**刺激源—刺激—环境—工件—响应—响应度量**。

例如：

- 刺激源：大促流量；刺激：商品查询突增；环境：缓存命中率下降；工件：商品读取链路；响应：可水平扩展并保护下单资源；度量：P99 小于 300 ms、下单错误率不超过 0.1%。
- 刺激源：恶意租户请求；刺激：携带另一租户订单 ID；环境：正常运行；工件：订单读取 API；响应：拒绝且产生审计事件；度量：零越权读取，拒绝延迟小于 100 ms。

### 步骤 4：区分硬约束、软目标和未知数

建立约束表，给每项标记来源、证据、违反后果、可谈判性和验证方式。未知数不能伪装成约束；将其转为假设，并安排实验、访谈或测量。

### 步骤 5：识别不变量和变化轴

**不变量（invariant）**是在所有合法状态中必须成立的规则，例如“订单只能由订单所有租户读取”“已捕获金额不能超过授权金额”“同一支付命令的业务键只产生一次扣款意图”。

同时列出变化轴：租户规则是否独立变化、支付供应商是否替换、库存是否按仓库扩展、结算是否按地区法规变化。边界应优先围绕不变量和变化轴，而不是围绕当前表数量。

### 步骤 6：提出少量候选架构并做约束分析

比较真实可行候选，并在维持现状可行时把它作为基线。例如：

- 模块化单体：共享进程和数据库，但以领域模块、依赖规则和租户上下文隔离；
- 领域服务：订单、目录、支付、履约按业务能力拆分；
- 按租户/区域分片的混合架构：控制面共享，数据面按隔离和规模分层。

对每个候选记录收益、代价、风险、迁移路径和可逆性。不要使用“业界最佳实践”作为证据；要把它翻译成当前约束下可观测的后果。

### 步骤 7：选择决策并记录退出条件

ADR 至少包含：上下文、问题、决策、备选、理由、假设、后果、验证、所有者和复查日期。尤其记录“何时不再成立”：例如当单租户订单量超过某阈值、合规要求变化或跨团队发布协调超过某阈值时，重新评估模块化单体是否需要拆分。

### 步骤 8：用小实验和运行证据验证

优先验证最危险、最不可逆的假设：租户隔离穿透、支付幂等、尾延迟、数据迁移、单区域恢复、跨团队发布。实验要有成功标准、输入、环境、观测指标和清理方式。架构图不等于证据；压测、故障演练、契约测试、恢复演练和真实运行指标才是证据。

### 步骤 9：建立演化回路

定期比较目标与现实：质量指标、事故、交付 lead time、变更失败率、云成本、开发者认知负担。把偏差归因到模型、决策、实现或组织，而不是只给某个组件贴“性能差”的标签。每次复盘都应产生可执行的保留、调整、删除或实验动作。

### 权衡与失败模式

### 1. 把架构等同于技术栈

**反例**：团队先决定“必须使用某消息队列和微服务”，再寻找能够套上的业务边界。结果订单创建需要同步读写五个服务，任何一个超时都会让买家重复提交；技术名词增加了，核心不变量却无人负责。

**修正**：先写关切、场景、不变量和故障语义，再判断技术是否帮助满足它们。技术选型是决策的一类，不是架构的定义。

### 2. 过早分布式化

**反例**：只有三名开发者、每天数千订单的团队，把每个领域拆成独立服务。单个功能需要修改多个仓库、等待多个流水线，开发和排障成本远高于业务收益。

**边界**：当独立扩展、故障/合规隔离或团队自治有证据支持时，分布式边界可能合理；仅以模糊“未来规模”为由拆分，通常违背从可工作的较简单系统获取反馈的思想，但不能仅引用 Gall 的观察否决方案。

### 3. 以平均指标掩盖尾部与隔离问题

**反例**：平台平均响应 100 ms，但某个大租户占满共享连接池，其他租户 P99 达到 8 秒；平均值看似达标，公平性和商业承诺已经失败。

**修正**：按租户、区域、请求类型和故障场景切片观测；为关键租户设定资源配额、舱壁（bulkhead）和可解释的降级策略。

### 4. 局部最优导致全局退化

**反例**：目录团队为降低查询延迟复制订单相关商品快照；复制没有所有权和失效策略，结算读取了过期税率，客服还要在三个系统修正同一事实。

**修正**：评审中显式列出被转移的成本：数据一致性、运维、组织协调、迁移和认知负担。局部指标必须放进系统级目标函数。

### 5. 把 Conway 定律当作宿命

**反例**：团队说“组织如此，所以接口只能如此”，拒绝改变沟通机制。实际上，跨域产品小组、共享事件契约评审和端到端值班可能降低镜像效应。

**修正**：把组织结构当作架构约束之一，同时承认组织和架构都可改变；任何改变都要计算迁移和过渡成本。

### 6. 抽象过度或抽象不足

- 过度抽象：为一次性规则建立五层策略工厂和通用 DSL，真正业务语义被间接调用隐藏。
- 抽象不足：支付、库存和订单各自定义“成功”，导致状态无法对齐。

**判断方法**：问“这个抽象隐藏的差异是否会改变决策？”若会，必须暴露；若不会且重复变化，才适合合并。

### 7. 文档化架构但不治理约束

**反例**：图上写着“订单不得直接访问支付库”，代码没有依赖检查，半年后报表脚本绕过接口。文档与现实分叉，评审反而产生虚假安全感。

**修正**：把关键规则转为可执行架构测试、代码所有权、契约测试、部署策略或运行时策略；文档记录意图和例外，不替代执行。

### 8. 没有反馈或反馈太慢

**反例**：平台每季度才看一次成本和故障指标，期间持续复制数据和新增异步链，最终无法判断哪次变更导致尾延迟恶化。

**修正**：为高风险决策设置短周期信号；对不可逆决策先做小规模、可观测的切片；注意反馈延迟造成的过度修复和振荡。

## 示例：多租户电商平台的第一次架构决策

### 问题背景

平台要支持多个租户。租户之间既有共同能力（商品搜索、购物车、订单、支付、履约），又有独立规则（价格、促销、税率、售后和数据保留）。平台初始团队为 8 人，预计 18 个月内达到 500 个租户；大促峰值远高于平时，但多数租户的流量分布不均。

### 1. 上下文和关键场景

| 关切者 | 关切 | 场景与度量 |
| --- | --- | --- |
| 租户 | 数据隔离、公平资源、规则可配置 | 越权读取为 0；单租户突发流量不得使其他租户 P99 超过 1 秒 |
| 买家 | 下单可靠、支付不重复 | 相同业务命令重试不重复扣款；订单状态可解释 |
| 运维 | 故障隔离、可恢复 | 单租户异常可限流；核心交易在单区域故障后 30 分钟内恢复 |
| 财务/合规 | 可审计、可结算 | 每笔资金变更可追溯到租户和授权事件；保留期限可配置 |
| 业务负责人 | 交付速度、成本 | 早期新租户接入不需复制整套系统；成本随活跃度近似增长 |

### 2. 候选比较

| 候选 | 主要收益 | 主要代价/风险 | 初始判断 |
| --- | --- | --- | --- |
| 模块化单体 + 共享数据库 | 事务简单、团队交付快、局部调试容易 | 共享资源争用；模块边界可能被绕过 | 适合早期，但必须执行模块依赖和租户上下文 |
| 全量微服务 | 独立扩展和故障部署 | 分布式一致性、发布协调、运维认知负担 | 当前团队和不确定性下风险高 |
| 控制面共享 + 数据面分层 | 可按租户规模/合规选择隔离级别 | 迁移、路由、备份和多形态运维复杂 | 作为演进目标，先验证隔离和迁移路径 |

### 3. 初始决策

选择“模块化单体 + 显式租户上下文 + 领域所有权 + 可迁移的数据访问端口”，而不是把共享数据库当作无规则的公共内存。关键规则包括：

1. 每次请求必须解析并验证 `tenant_id`，且不能由客户端任意覆盖；
2. 订单、支付意图、库存预留分别拥有自己的不变量和状态机；
3. 模块只能通过公开端口访问其他模块，不得直接访问对方表；
4. 关键异步事件包含租户、因果 ID、版本和幂等键；
5. 先为超大租户提供资源隔离和数据迁移实验，再决定是否拆成独立服务或库。

这里的“模块化单体”不是永久承诺。ADR 的退出条件是：独立发布需求持续阻塞交付、某领域需要不同故障/合规边界、或共享资源无法以配额和舱壁控制；每个条件都要有数据和阈值，而非感觉。

### 4. 局部/全局最优分析

订单团队若单独选择同步调用支付并等待最终结果，可能使“订单成功率”局部提高，却在支付供应商延迟时拖垮下单线程池。全局方案可能是：先记录不可变支付意图和订单待支付状态，通过幂等命令与异步确认推进状态机；这增加了用户体验和补偿设计，但降低了故障传播。选择哪一种取决于业务是否允许待支付订单、退款规则和可观测性，而不是“异步一定先进”。

### 5. 反馈计划

- 用租户隔离测试和故障注入验证访问路径；
- 用混合租户负载测试连接池、缓存和队列公平性；
- 每周审查 P95/P99、租户级错误率、重复支付告警、变更失败率和云成本；
- 每次事故复盘更新不变量、边界或监控，而不仅是增加重试；
- 每月检查 ADR 退出条件是否接近阈值。

### 检查清单

### 架构定义与视角

- [ ] 是否用结构、属性、决策三视角描述了同一系统？
- [ ] 每个重要质量目标是否有场景、环境、响应和度量？
- [ ] 每个高影响决策是否写明备选、假设、后果和退出条件？
- [ ] 图中的边界、依赖和所有权是否能在代码、部署和组织中找到证据？

### 复杂性与约束

- [ ] 是否区分了本质复杂性与偶然复杂性？
- [ ] 是否列出硬约束、软目标和待验证未知数？
- [ ] 是否计算了状态、重试、并发和部分失败带来的额外交互？
- [ ] 是否识别成本被转移到其他团队、数据管道或运行阶段？

### 边界与分解

- [ ] 每个边界是否拥有明确责任、不变量、变化理由或故障收益？
- [ ] 接口是否定义超时、重试、幂等、版本和错误语义？
- [ ] 是否避免以数据库表、技术层或团队名称机械切分？
- [ ] 是否有从当前形态到下一形态的可逆、小步迁移路径？

### 反馈与演化

- [ ] 关键决策是否有可观测指标和短反馈周期？
- [ ] 指标是否按租户、区域、请求类型和尾部切片？
- [ ] 是否设置了重评估触发器，而不是一次性“最终架构”？
- [ ] 是否考虑 Conway、Gall 和 Lehman 定律的适用边界，而非引用口号？

### 练习

1. **三视角重建**：为一个你熟悉的系统写出 $(V,E,A,D)$。分别画出结构投影，列出三个质量属性场景，再为其中一个场景写一份 ADR 的上下文、备选、后果和退出条件。指出三者中哪条追溯链最薄弱。
2. **复杂性预算**：假设方案甲有 12 个部署单元、30 条跨单元依赖、8 个关键状态；方案乙有 5 个部署单元、45 条模块依赖、12 个关键状态。用本章复杂性启发式模型选择权重，说明为什么不能仅凭部署单元数量断言乙更简单。
3. **边界实验**：将多租户电商平台分别按技术层、业务能力和租户规模切分。对每种切分评估变化耦合、故障隔离、团队认知负担和迁移成本，给出至少一个不适用场景。
4. **局部与全局**：设计一个“降低目录查询 P99”的局部优化，并追踪它可能对订单、缓存公平性、成本和数据一致性产生的二阶影响。再提出一个全局目标函数或约束，使团队能够讨论而非争论。
5. **反馈回路**：为“支付重复扣款”建立观测—决策—实施—度量回路，标出至少两个反馈延迟和一个可能造成振荡的错误修复。说明如何用小实验缩短因果确认时间。
6. **定律反例**：分别写出一个看似支持、一个可能反驳 Conway 定律的组织/架构案例；说明反驳案例需要哪些持续机制才能成立，并判断它是否只是把镜像效应转移到另一层。

## 第二部分　架构师能力模型与学习路线

### 学习目标

完成本章后，读者应能够：

1. 用可观察的行为而非职位名称定义架构师职责。
2. 建立包含认知、技术、交付、运行、经济、沟通和演化能力的能力矩阵（capability matrix）。
3. 识别自己的能力瓶颈，设计分阶段、以证据为终点的学习路线，而不是按工具清单消费课程。
4. 运用刻意练习（deliberate practice）、反馈回路和双环学习（double-loop learning）提高架构判断力。
5. 在多租户电商平台中把学习目标转化为真实架构产物、实验和复盘证据。
6. 识别“架构师成长”的常见失败模式，包括架构剧场、局部最优学习、只读不做和脱离运行现实。

### 核心概念

### 1. 架构师是责任集合，不是头衔

**架构师（architect）**承担一组持续责任：把模糊目标转为可推理的问题，识别约束和风险，提出并验证结构与决策，协调不同边界上的取舍，保证系统在交付和运行中可演化。一个人可以没有“架构师”头衔却承担这些责任；拥有头衔也不自动具备这些能力。

架构师的产出不是“知道最多”，而是让团队在关键不确定性上更快、更安全地达成可逆或可追责的决定。能力证据包括：

- 能否在需求尚不完整时明确未知数和最小验证实验；
- 能否说明一个决策对延迟、成本、风险、组织和未来变化的影响；
- 能否让实现者理解边界并发现决策不成立的信号；
- 能否在事故、指标和新约束出现后修正模型，而不是保护个人方案。

### 2. 认知模型：从事实到可检验决策

架构工作可抽象为六个认知动作：

1. **观察（observe）**：收集用户行为、业务目标、代码、指标、事故、组织和外部约束；区分事实、解释和传闻。
2. **建模（model）**：用上下文图、状态机、数据流、依赖图、容量模型和威胁模型压缩信息；标注不确定性。
3. **推理（reason）**：寻找因果关系、不变量、边界条件、二阶影响和反例；比较候选而非寻找神奇答案。
4. **决定（decide）**：选择当前足够好的方案，声明假设、权衡、可逆性和退出条件。
5. **沟通（communicate）**：根据受众提供决策所需的最小充分上下文；让异议可见并可记录。
6. **学习（learn）**：用运行证据、交付结果和事故反馈更新模型、技能和组织机制。

这不是线性流程。新证据可能让你回到观察或建模；沟通中的异议经常暴露未识别的约束。成熟度体现为能在循环中定位“错在事实、模型、决策还是执行”。

### 3. 能力矩阵：T 型深度与系统宽度

能力矩阵用领域和熟练等级描述成长，而不是用“初级/高级”标签替代证据。建议至少覆盖：

- **问题框定与领域建模**：目标、边界、事件风暴、状态、不变量、业务语言；
- **结构与技术推理**：模块化、并发、网络、存储、分布式协议、安全；
- **质量属性工程**：性能、可用性、可靠性、可维护性、可观测性、隐私与成本；
- **交付与验证**：版本、迁移、测试策略、发布、回滚、实验设计；
- **运行与韧性**：SLO、容量、故障域、恢复、值班、事故学习；
- **经济与风险**：总拥有成本、机会成本、供应商锁定、合规和风险暴露；
- **沟通与组织**：书面决策、利益相关者协商、团队拓扑、冲突处理、教练；
- **治理与演化**：原则、架构适配度函数、技术债务、平台策略、淘汰机制。

T 型并不意味着“每项都浅”。它表示至少在一个领域形成可独立判断和教学的深度，同时拥有足够宽度理解相邻领域的约束与语言。

### 4. 刻意练习：针对瓶颈的高反馈活动

**刻意练习**不是重复做熟悉的任务，而是：

- 目标明确且略高于当前能力；
- 任务边界小，结果可以观察；
- 有及时、具体、可信的反馈；
- 练习者主动复盘错误并调整策略；
- 重复同一类判断，逐渐提高难度和变化条件。

“读完一本分布式系统书”是输入，不是刻意练习；“为支付幂等设计三个候选，预测故障行为，做故障注入，再与真实指标比较”才是练习。架构能力尤其需要**反事实练习**：如果负载扩大十倍、网络分区、租户恶意、供应商变更，原决策是否仍成立？

### 5. 证据优先于自我感觉

能力声明应绑定证据等级：

1. 了解术语并能复述；
2. 在指导下完成局部任务；
3. 能独立完成并解释权衡；
4. 能在陌生约束下稳定迁移；
5. 能教会他人并改进组织机制。

“我用过 Kubernetes”无法证明架构能力；“在资源受限的多租户集群中定义隔离策略，完成故障演练，解释成本和恢复取舍，并让团队能独立运维”才是更强证据。证据必须包含上下文，否则很容易把偶然成功误判为通用能力。

## 理论模型

### 1. 能力向量与瓶颈模型

设能力域集合为 $D=\{d_1,\ldots,d_n\}$，个人在各域的熟练度为向量

\[
\mathbf{s}=(s_1,s_2,\ldots,s_n),\quad s_i\in[0,5]
\]

目标岗位或目标项目需要的能力向量为 $\mathbf{r}$，重要性权重为 $\mathbf{w}$。简单差距可写为：

\[
G=\sum_{i=1}^{n}w_i\max(0,r_i-s_i)
\]

$G$ 适合发现总体差距，但架构工作常受最弱关键环节限制，因此还要识别瓶颈：

\[
B=\min_{i\in D_{critical}}\frac{s_i}{r_i}
\]

$D_{critical}$ 是当前系统或岗位的关键能力域。若一个人技术深度为 5，但无法把业务目标、风险和决策讲清楚，端到端架构影响力仍可能受沟通与问题框定瓶颈限制。反之，沟通很强但无法验证并发和恢复假设，也会形成另一种瓶颈。

权重和关键域应随任务变化。不要用固定分数给人贴标签；每次路线规划都要从目标系统、责任范围和近期机会重新估计需求。

### 2. 学习收益模型：反馈密度、难度与迁移

可以把一次练习的预期收益表示为启发式函数：

\[
\Delta s_i \approx \kappa_i\times q\times f\times t\times m
\]

- $\Delta s_i$：能力域 $i$ 的可观察提升；
- $\kappa_i$：个人已有基础和练习设计质量；
- $q$：挑战是否落在“可完成但不舒适”的区间；
- $f$：反馈的及时性、具体性和可信度；
- $t$：主动思考与复盘时间；
- $m$：迁移机会，即能否在不同上下文复用。

这不是测量人的物理公式，而是帮助诊断低效学习：只增加阅读时长而不增加反馈，$f$ 近似为零；只做一次大型重构而不切片，难以知道哪项判断导致结果，$m$ 和反馈质量都低。

### 3. 双环学习：修正动作，也修正规则

单环学习（single-loop learning）是在既定目标和规则下纠偏，例如调大连接池、增加重试、优化查询。双环学习（double-loop learning）进一步询问：目标、边界、指标或决策原则是否本身有问题？

可写为两个嵌套回路：

\[
\text{结果偏差}\rightarrow\text{调整行动}
\]

以及：

\[
\text{反复偏差}\rightarrow\text{检验假设/规则/目标}\rightarrow\text{重设行动}
\]

在多租户平台中，若单租户总是占满资源，单环做法是不断扩容；双环问题是“共享资源和公平性的边界是否定义错了？SLO 是否只看全局平均？商业套餐是否承诺了不可能的突发性？”架构师成长也一样：若每次失败都归结为执行不够努力，就不会更新认知模型。

### 4. 学习路线是有依赖的反馈图，不是课程清单

把能力域和实践活动建成有向图 $L=(D,A)$，边 $d_i\rightarrow d_j$ 表示前者为后者提供必要基础。例如领域建模和数据不变量通常先于跨服务一致性推理；可观测性和发布能力是安全进行架构实验的基础。

一条路线应满足：

- 先获得能支撑反馈的基础工具，再承担更大影响范围；
- 每阶段有可观察产物和真实责任；
- 活动之间形成短反馈回路，避免数月后才发现方向错误；
- 允许根据瓶颈重排，而不是服从固定日历。

可以用路线价值近似表示：

\[
V(path)=\sum_{a\in path}\frac{I(a)\times F(a)\times M(a)}{C(a)+R(a)}
\]

$I$ 是对目标责任的影响，$F$ 是反馈密度，$M$ 是迁移性，$C$ 是时间/金钱成本，$R$ 是失败风险。它不是精确排序器，但能防止只按“热门程度”选择学习活动。

### 5. 个人学习中的局部与全局最优

局部最优学习通常是：短期掌握当前项目最急需的框架，马上提高产出；全局最优学习则会保留可迁移的原理、实验设计、写作和系统思维。只追求全局会陷入永远准备，错过真实反馈；只追求局部会成为工具专家，换项目就失效。

一个平衡策略是“当前责任 70%、邻近能力 20%、远期基础 10%”之类的预算，但比例不是定律，应根据风险和阶段调整。关键是每项投入都说明：它解决当前哪个瓶颈、产生什么证据、如何迁移到下一个上下文。

## 方法步骤

### 步骤 1：定义目标责任，而不是先定义职位

写清未来一阶段要承担的责任范围：例如“负责订单和支付边界的架构决策”“主导一个跨团队迁移”“建立平台级可靠性机制”。责任比“成为高级架构师”更容易观察，也更能决定所需能力。

### 步骤 2：建立能力矩阵并收集证据

对每个能力域记录四列：当前行为、证据、缺口、下一次机会。分数只能作为索引，不能替代叙述。证据应包括上下文、你的具体动作、结果、反例和他人反馈。

示例条目：

| 能力域 | 当前证据 | 缺口 | 下一次机会 |
| --- | --- | --- | --- |
| 领域建模 | 能画订单流程，但未明确退款状态不变量 | 不能处理跨租户规则变化 | 主持售后/结算状态机工作坊 |
| 分布式推理 | 了解消息队列，未做重复投递实验 | 缺少故障与一致性判断 | 为支付事件写幂等实验和恢复演练 |
| 沟通决策 | 能写技术方案，评审异议未结构化 | 不能让业务看到机会成本 | 用一页 ADR 比较三个候选并主持评审 |
| 运行韧性 | 会看服务日志，未参与值班 | 不会从 SLO 反推设计 | 建立租户级 P99 和错误预算看板 |

### 步骤 3：选一个真实、有限、可回滚的练习场

优先选择能在 1—6 周内完成反馈闭环的任务：

- 给一个高风险接口补充幂等、超时和契约测试；
- 为一个租户隔离规则做威胁建模和负向测试；
- 对一个查询链路建立容量模型并验证 P99；
- 写一份包含备选和退出条件的 ADR，跟踪其实施后果；
- 主持一次事故复盘，并把结论转为可执行约束。

不要一开始就承诺“重构全平台”。大型目标不能提供清晰因果反馈，也难以证明个人学习效果。

### 步骤 4：按刻意练习循环执行

每轮循环包含：

1. 预测：在实施前写下状态、风险、指标和你预计会看到的结果；
2. 实作：在最小安全范围内实现或实验；
3. 观测：记录度量、失败、反例和意外行为；
4. 对照：比较预测与结果，标出模型误差；
5. 解释：区分知识不足、假设错误、沟通失败和执行缺陷；
6. 重练：改变一个变量，再做一次或迁移到相邻场景；
7. 固化：更新 ADR、检查清单、示例代码或团队规则。

### 步骤 5：分阶段扩展责任半径

#### 阶段 A：工程基础与局部可靠性

目标不是学完所有技术，而是能独立交付可运行、可观测、可回滚的模块。重点能力：代码设计、数据建模、测试、版本控制、日志/指标/追踪、基本安全与性能。

**完成证据**：能解释一个模块的不变量和边界；能定位一次线上问题并补上回归防线；能用实验验证一个性能或并发假设。

#### 阶段 B：系统设计与端到端交付

承担一个业务能力的完整链路：需求、边界、接口、数据、发布、监控、故障和成本。重点能力：质量属性场景、容量估算、状态机、异步语义、迁移和回滚。

**完成证据**：能比较至少两个方案，说明约束和二阶后果；系统在真实或仿真负载下满足关键 SLO；变更有回滚和数据修复方案。

#### 阶段 C：跨团队架构领导

从“设计一个系统”转向“让多个团队在共享约束下持续交付”。重点能力：架构原则、契约治理、组织沟通、冲突协商、平台能力、风险排序和教练。

**完成证据**：跨团队决策能被实现；不同团队可以独立发布而不破坏契约；你能让异议可见并在结果不佳时修正方案，而非依靠职权压服。

#### 阶段 D：系统与组织演化

关注多年度变化：架构投资组合、平台经济、组织拓扑、技术淘汰、合规变化、业务模式和生态伙伴。重点能力：演化路线、期权思维、复杂适应系统、治理反馈和战略沟通。

**完成证据**：能用指标说明架构投资改善了交付、风险或成本；能删除过时能力；能在组织或法规变化时重画边界并完成迁移。

阶段不是固定年限，也不是只能向前。遇到新领域可回到基础阶段做局部练习；达到阶段目标的标志是证据和责任范围，不是完成课程数量。

### 步骤 6：建立个人反馈和同伴评审机制

每周保留一份架构学习日志：事实、假设、决策、预测、结果、反例、下一步。每两周请实现者、运维、产品和安全角色分别评审同一方案，避免只从架构师视角获得同温层反馈。每月选择一个失败案例做双环复盘，询问“什么规则或目标让这个错误变得合理”。

### 步骤 7：形成可迁移的作品集

作品集不应只是图和链接，应包括：

- 问题上下文与约束；
- 关键质量场景和不变量；
- 候选比较及被否决原因；
- ADR 与可执行约束；
- 实验设计、预测和结果；
- 运行指标、事故或迁移反馈；
- 后续如何修正，以及哪些判断不能迁移。

### 步骤 8：用复盘更新路线

每个阶段结束时重新计算能力差距和关键瓶颈。若连续三次练习都在沟通中失败，不要继续堆技术课程；若能说服所有人但系统实验总失败，也不要把问题归咎于“团队执行”，而应补充分布式、容量或运行知识。路线是模型，结果是反馈，必要时应改变路线本身。

## 权衡 / 失败模式

### 1. 以工具覆盖能力缺口

**反例**：为证明“懂云原生”连续学习多个编排工具，却无法回答租户隔离、恢复点目标、成本上限和发布回滚。工具知识没有连接到决策场景，迁移到别的环境即失效。

**修正**：每学一个工具，至少配一个可验证问题：它改变了哪个质量属性？引入什么新状态和故障？何时应不用它？

### 2. 阅读很多，反馈很少

**反例**：读完分布式系统经典书籍后直接设计跨区域订单，却没有做时钟、重试、网络分区和恢复实验。概念熟悉感掩盖了行为预测能力的缺失。

**修正**：把阅读转为预测题、纸上推演、最小实验和同伴质询；让错误尽早、低成本暴露。

### 3. 只做当前项目的局部最优

**反例**：为了本季度交付，熟练掌握某供应商专有服务，却没有学习接口语义、数据迁移和故障模型。短期产出提高，长期锁定风险和议价能力下降。

**修正**：在当前责任之外保留少量可迁移基础，并要求每个工具决策写出替代方案和退出路径。

### 4. 只追求全局理论而不承担责任

**反例**：花一年整理“理想架构原则”，却不值班、不参与发布、不处理数据修复，因此对真实故障和协调成本没有一手反馈。

**修正**：理论学习必须绑定一个真实边界和可观察结果；不能安全接触生产时，用故障演练和影子项目建立近似反馈。

### 5. 架构剧场（architecture theater）

表现包括：图越来越复杂、评审越来越多、术语越来越新，但没有减少事故、交付延迟或认知负担。常见原因是把文档数量、会议次数和采用产品数当作能力指标。

**反例**：为每个模块创建独立服务和团队，却没有清晰数据所有权；组织看似“现代化”，发布和排障反而变慢。

**修正**：以结果证据衡量：变更失败率、恢复时间、关键 SLO、成本、跨团队等待时间、租户投诉和规则违反次数。

### 6. 英雄架构师与知识集中

**反例**：所有关键决策都要经过一个人，团队不敢修改图，架构师休假后无人排障。短期一致性换来单点认知故障和组织脆弱性。

**修正**：用清晰原则、ADR、可执行检查和教学分散决策权；架构师的成功标志是团队变得更自主，而不是个人成为不可替代的审批者。

### 7. 用分数替代证据

**反例**：把“沟通能力”打成 4/5，却没有任何跨利益相关者决策或冲突处理案例；分数带来虚假精确。

**修正**：分数只用于排序，必须附上下文、行为、结果、失败和反馈。承认不确定性比伪造精确更专业。

### 8. 忽视组织和运行环境

**反例**：设计了理论上可隔离的订单服务，但值班团队不拥有它、发布窗口不同、没有跨团队事件响应；架构在纸面上成立，在组织中无法运行。

**修正**：把 Conway 定律纳入能力训练：访谈团队拓扑、发布权限、激励和沟通路径；把运维责任写进架构边界。

### 9. 把失败归因给个人而不更新模型

**反例**：支付超时后只要求开发者“更仔细”，没有检查同步边界、供应商契约和错误预算。相同事故反复发生。

**修正**：运用双环学习：除了修补行动，还检查目标、规则、指标、组织和架构假设是否需要改变。

## 示例：围绕多租户电商平台设计四阶段成长路线

### 起点与目标责任

假设读者是一名有两年后端经验的工程师，加入多租户电商平台，当前负责商品查询模块，目标是在一年内承担订单与支付边界的系统设计，并能参与跨团队架构评审。不要把目标写成“学会微服务”；应写成可观察责任：

> 能在租户隔离、支付幂等、峰值流量和单区域恢复约束下，独立提出候选架构，完成一个小范围验证，并让订单、支付、运维和财务角色共同接受可执行的决策。

### 阶段 A：商品模块的可靠交付

**练习**：建立租户级查询指标、缓存命中/失效实验、越权负向测试和回滚演练。

**能力证据**：

- 能画出请求从身份解析到数据访问的信任边界；
- 能解释缓存键为何必须包含租户维度，以及失效失败时的后果；
- 能在指标中区分大租户和小租户，不用全局平均掩盖不公平；
- 能在发布失败后恢复，并写出模型误差。

### 阶段 B：订单闭环

**练习**：为下单流程画状态机，明确订单、库存预留和支付意图的不变量；设计重复提交、支付超时、库存不足和回调乱序的实验。

**能力证据**：

- 能比较“同步完成支付”和“支付意图 + 异步确认”；
- 能说明每个状态的用户可见语义、补偿动作和审计记录；
- 能使用业务幂等键而非仅依赖消息 ID；
- 能给出迁移和回滚方案，而不是只给新接口。

### 阶段 C：跨团队决策

**练习**：主持订单、支付、库存、财务和运维评审。将争论改写成场景、约束和指标，记录不同团队的局部目标，并形成 ADR。

**能力证据**：

- 被否决的方案和理由可追溯；
- 团队能在不依赖个人口头解释的情况下实现契约；
- 评审后能用小流量或故障演练验证关键假设；
- 发现支付供应商变化时，能重新评估边界而非固守原图。

### 阶段 D：演化与治理

**练习**：根据租户规模、合规级别和流量模式设计数据隔离分层的演进路线：共享表、按区域分库、专属库或专属集群。建立触发器、迁移工具和成本/风险看板。

**能力证据**：

- 能说明为何不是所有租户都采用最高隔离级别；
- 能量化迁移、备份、连接池和运维代价；
- 能把架构原则转为自动检查、运行策略和团队责任；
- 能删除不再有价值的组件，避免只会增加系统。

### 一个完整的刻意练习样例

练习主题为“支付回调乱序是否会破坏订单状态”：

1. **预测**：若回调 $A=成功$ 在 $B=失败$ 之后到达，状态机应拒绝非法回退；预计重复事件不会增加捕获金额。
2. **建模**：列出事件版本、业务幂等键、订单状态和支付提供商状态的关系。
3. **实验**：随机打乱、重复和延迟回调；注入数据库重启和网络超时。
4. **观测**：检查状态不变量、资金账、审计链、告警和人工修复队列。
5. **复盘**：若实验失败，判断是状态模型不足、事务边界错误、观测缺失还是契约误读。
6. **迁移**：把同样方法用于库存预留释放或退款事件，而不是只记住某个框架的配置。

这个练习同时训练领域建模、分布式推理、质量验证、运行韧性和沟通表达；它比孤立学习某个消息中间件更接近架构责任。

## 检查清单

### 责任与认知

- [ ] 是否把目标写成责任和可观察结果，而非头衔或工具？
- [ ] 是否区分事实、假设、解释、决策和证据？
- [ ] 面对异议时，是否回到关切、约束、不变量和可验证场景？
- [ ] 是否能指出自己模型最不确定的部分，以及最小验证实验？

### 能力矩阵

- [ ] 是否覆盖问题框定、技术推理、质量属性、交付、运行、经济、沟通和演化？
- [ ] 每个能力评分是否附有上下文、行为、结果和反馈？
- [ ] 是否识别了当前任务的关键瓶颈，而不是平均提升所有项目？
- [ ] 是否同时保留至少一项深度和足够的相邻领域宽度？

### 刻意练习与反馈

- [ ] 练习是否略高于当前能力且边界足够小？
- [ ] 是否在实施前做预测，在实施后比较预测与结果？
- [ ] 反馈是否及时、具体、来自不同角色，并能区分因果？
- [ ] 是否进行过双环复盘，检验目标、规则和模型，而不只修补动作？

### 学习路线

- [ ] 每阶段是否有真实责任、可观察产物和退出标准？
- [ ] 是否先建立可运行、可观测、可回滚的基础，再扩大影响半径？
- [ ] 是否为局部交付保留可迁移的原理和方法？
- [ ] 路线是否能根据新的证据和组织变化重排？

### 架构领导

- [ ] 决策是否能被实现者、运维、产品、安全和财务理解并执行？
- [ ] 是否分散知识和决策权，避免英雄架构师？
- [ ] 是否用交付、可靠性、成本和认知负担结果衡量架构影响？
- [ ] 是否把 Conway 定律、Lehman 演化和组织反馈纳入长期计划？

## 练习

1. **能力证据盘点**：建立自己的八域能力矩阵。每个域只写一个最有力证据和一个失败证据，计算加权差距 $G$，再指出由关键域决定的瓶颈 $B$。说明为什么分数可能误导。
2. **刻意练习设计**：为“多租户订单越权读取”设计一周练习。要求包含预测、威胁模型、负向测试、运行指标、同伴反馈和迁移练习；说明每一步的反馈来源。
3. **双环复盘**：假设你连续三次通过扩容解决队列堆积，但成本翻倍且恢复时间变长。分别写出单环行动和双环问题，列出至少三个需要重新检查的目标或规则。
4. **路线依赖图**：把领域建模、数据不变量、并发、分布式一致性、可观测性、发布回滚、经济分析和跨团队沟通画成有向依赖图。找出两个可能并行的学习支线，以及一个不能跳过的前置能力，并解释原因。
5. **局部/全局学习取舍**：当前平台急需你掌握某云厂商的专用数据库功能，但你担心锁定。制定一个四周计划，同时交付当前功能、验证退出路径，并学习至少一个可迁移的数据一致性原理。
6. **架构评审角色扮演**：为“控制面共享、数据面按租户分层”的方案分别扮演租户、财务、运维、平台开发和安全角色。每个角色提出一个相互冲突的目标；写出一份决策记录，明确哪项目标被牺牲、为什么、如何监测以及何时重评。
7. **成长的反例**：找出一个你曾经参与的“看起来更先进但结果更差”的架构或学习决策。用 Conway、Gall、Lehman、局部/全局最优和反馈延迟中的至少三个概念重构因果链，并提出一个可在两周内验证的替代行动。

## 本两章的术语速查

| 中文 | 英文 | 本教程中的工作含义 |
| --- | --- | --- |
| 架构 | architecture | 元素、关系、约束、原则及其决策后果的系统组织 |
| 结构 | structure | 元素及元素间关系的可观察组织 |
| 质量属性 | quality attribute | 可通过场景和度量讨论的系统属性 |
| 架构决策记录 | Architecture Decision Record (ADR) | 记录上下文、备选、理由、后果和复查条件 |
| 本质复杂性 | essential complexity | 问题领域不可约的复杂性 |
| 偶然复杂性 | accidental complexity | 由实现、工具、历史或组织额外引入的复杂性 |
| 约束 | constraint | 必须服从的限制或底线 |
| 抽象 | abstraction | 隐藏无关细节并保留当前决策所需语义 |
| 分解 | decomposition | 将系统划分为可理解、可改变、可验证的部分 |
| 内聚 | cohesion | 部分内部职责共享不变量或变化理由的程度 |
| 耦合 | coupling | 部分之间因数据、时序、发布、故障或认知而相互依赖的程度 |
| 刻意练习 | deliberate practice | 有明确挑战、及时反馈、复盘和迁移的针对性练习 |
| 双环学习 | double-loop learning | 同时检验行动及其背后的目标、规则和假设 |
| Conway 定律 | Conway’s Law | 系统设计倾向反映组织沟通结构的观察 |
| Gall 定律 | Gall’s Law | 复杂系统更可能由可工作的简单系统演化而成 |
| Lehman 软件演化定律 | Lehman’s Laws of Software Evolution | 持续使用的软件需要持续变化，复杂性需主动控制 |

> **阅读提示**：本章的公式主要是推理工具和启发式模型，不是脱离上下文的精确预测器。架构判断的质量取决于变量定义、证据质量、反馈速度以及是否诚实地说明未知数。
