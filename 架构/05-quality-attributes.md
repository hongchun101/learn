# 第 5 章 质量属性：可靠性、性能、可观测性、安全、弹性

> 统一引用案例：**多租户电商平台（Multi-Tenant E-Commerce Platform，MTEP）**——一家向中小品牌商提供 SaaS 商城服务的公司。系统承载订单、支付、库存、履约、营销、风控等核心链路,以 Kubernetes 上的微服务为主,数据层混合使用 MySQL、Redis、Kafka、Elasticsearch。本章所有方法、公式、示例均围绕此案例展开,术语首次出现给中英文。

## 5.0 学习目标

完成本章后,读者应能够:

1. 用 **SLI / SLO / SLA**（Service Level Indicator/Objective/Agreement,服务等级指标/目标/协议）三级抽象把"可用性"从口号变成可度量的工程契约,并设计可消耗的 **错误预算（Error Budget）**。
2. 用 **可用性计算（Availability Calculation）**、**故障树分析（Fault Tree Analysis, FTA）** 推导系统级可靠性,把单组件指标组合成端到端承诺。
3. 选择并组合 **可靠性模式（Reliability Patterns）**：冗余（Redundancy）、故障检测（Fault Detection）、隔离（Isolation）、限流（Rate Limiting）、熔断（Circuit Breaker）、重试（Retry with Backoff）、幂等（Idempotency）、降级（Degradation）、舱壁（Bulkhead）等,并能讲清每种模式的副作用。
4. 运用 **排队论（Queueing Theory）**、**Little 定律（Little's Law）**、**Amdahl 定律（Amdahl's Law）** 进行容量规划与瓶颈定位,理解 **延迟百分位（Latency Percentile, P50/P95/P99/P999）** 的工程意义与陷阱。
5. 设计 **背压（Backpressure）** 机制,区分同步阻塞、异步队列、令牌桶（Token Bucket）、漏桶（Leaky Bucket）,避免级联崩溃（Cascading Failure）。
6. 搭建 **可观测性（Observability）** 体系: **日志（Logs）**、**指标（Metrics）**、**追踪（Tracing）**,并落地 **RED / USE / SLI** 等方法论。
7. 执行 **威胁建模（Threat Modeling, STRIDE / DREAD / Attack Tree）**,实施 **零信任（Zero Trust）**、**最小权限（Least Privilege）**、**纵深防御（Defense in Depth）**,并满足隐私合规。
8. 设计 **弹性（Resilience）** 策略:故障域隔离、混沌工程（Chaos Engineering）、多区域灾备、爆炸半径（Blast Radius）控制。

## 5.1 核心概念

### 5.1.1 质量属性的可观测、可度量、可交易三角

- **可观测（Observable）**：属性必须能用数字度量,而不是用形容词描述。
- **可度量（Measurable）**：度量值必须可重复、可解释、可低成本采集。
- **可交易（Tradeable）**：属性之间存在取舍（Performance ↔ Cost,Security ↔ Usability,Latency ↔ Consistency）。

> **多租户电商平台示例**：将"系统很快"改写为"P99 下单链路端到端延迟 ≤ 400 ms,月度错误率 ≤ 0.1%"。这就是 SLO 的雏形。

### 5.1.2 SLI / SLO / SLA

| 抽象层 | 定义 | 谁定义 | 谁消费 | 例子 |
|---|---|---|---|---|
| **SLI**（服务等级指标） | 直接测量的指标 | 工程团队 | 工程师 / SRE | 下单 HTTP 200 比例、支付 RPC P99 |
| **SLO**（服务等级目标） | SLI 在一段时间窗口内的目标值 | 工程 + 产品 | 工程团队、错误预算治理 | 月度可用性 99.95% |
| **SLA**（服务等级协议） | 写入合同的承诺 + 违约赔付 | 法务 + 业务 | 客户 / 法务 | 月度可用性 99.9%,否则返 10% 月费 |

> 三者关系：**SLI 测量 → SLO 内部目标 → SLA 外部承诺**。SLO 通常应比 SLA 更严格以保留风险缓冲，但差距取决于赔付结构、测量口径、故障相关性和业务风险，不存在固定“宽松一个 9”的规则。

> 表中 99.95% 到 99.9% 只是“内部允许失败量为外部承诺一半”的示例，不是最低差距或行业规则；两者还必须使用一致或明确换算的 SLI 口径。

### 5.1.3 错误预算

- **定义**：对二元“好事件/总有效事件”SLI，目标为 $SLO$ 时，窗口内允许的坏事件比例是 $1-SLO$；允许坏事件数为 $(1-SLO)\times N_{eligible}$。时间型 SLI 才可换算为允许坏分钟，且需明确维护窗口等口径。
- **形式**：请求型、时间型和任务截止型 SLI 各自计算预算，不能把“43.2 分钟”与失败请求数直接混用；多 SLO 通常分别治理或明确组合规则。
- **政策**：按燃烧率、剩余预算、用户影响和变更风险触发响应；可限制高风险变更、优先可靠性工作并复盘，但不机械冻结安全修复。

### 5.1.4 可靠性 vs. 可用性 vs. 韧性

- **可靠性（Reliability）**：在给定条件下、给定时间内,系统**无故障运行**的概率 $R(t)$。
- **可用性（Availability）**：$\displaystyle A = \frac{\text{MTTF}}{\text{MTTF} + \text{MTTR}}$（MTBF = MTTF + MTTR）,强调**可恢复**。
- **韧性（Resilience）**：系统在**已故障**时吸收冲击、维持核心功能、优雅退化的能力。

### 5.1.5 性能（Performance）与延迟（Latency）

- **吞吐量（Throughput）**：单位时间完成的工作量（req/s、TPS、QPS）。
- **延迟（Latency）**：单个请求从进入到响应的时间。
- **利用率（Utilization）**：$\rho = \text{忙时间} / \text{总时间}$,根据 **利用率定律（Utilization Law）** $U = \frac{\text{busy time}}{\text{time}}$。
- **饱和度（Saturation）**：队列长度、待处理任务数、连接占用比。

### 5.1.6 安全（CIA + 隐私 + 信任）

经典三要素：**机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）**。现代软件系统还需要:

- **可问责性（Accountability）**：每一步操作可追溯到主体。
- **隐私（Privacy）**：满足 GDPR / 个保法 / CCPA,默认最小化数据收集。
- **抗抵赖（Non-Repudiation）**：关键操作带签名。

### 5.1.7 弹性（Resilience）的五个维度

1. **吸收（Absorb）**：在故障点就地处理（限流、熔断、重试）。
2. **恢复（Recover）**：以秒/分钟级回滚、灰度、重启。
3. **适应（Adapt）**：根据负载弹性扩缩容。
4. **退化（Degrade）**：关闭非核心功能,保留核心路径。
5. **学习（Learn）**：通过事故复盘、混沌实验持续改进。

## 5.2 理论模型

### 5.2.1 可用性计算

#### 单组件可用性

$$\displaystyle A = \frac{\text{MTTF}}{\text{MTTF} + \text{MTTR}}$$

**变量解释**：

- $\text{MTTF}$（Mean Time To Failure,平均失效前时间）：组件平均连续无故障运行时间。
- $\text{MTTR}$（Mean Time To Repair,平均修复时间）：从故障到恢复的平均时间。
- $\text{MTBF} = \text{MTTF} + \text{MTTR}$（Mean Time Between Failures,平均故障间隔）。

#### 串联系统（任一节点故障即整体故障）

$$\displaystyle A_{\text{series}} = \prod_{i=1}^{n} A_i$$

**例 1**：下单链路有 5 个微服务,每个组件 $A_i = 99.95\%$,则

$$A_{\text{series}} = 0.9995^5 \approx 0.997503 \approx 99.7503\%$$

（与直觉相反：5 个 99.95% 串联后掉到 99.75%。）

#### 并联系统（冗余,任一存活即整体存活）

$$\displaystyle A_{\text{parallel}} = 1 - \prod_{i=1}^{n} (1 - A_i)$$

**例 2**：支付服务用 2 个实例冗余,每个 $A_i = 95\%$（无自愈）,

$$A_{\text{parallel}} = 1 - (1-0.95)^2 = 1 - 0.0025 = 0.9975 = 99.75\%$$

**例 3**：3 个独立同分布实例，至少 2 个可用即服务可用；单实例 $A_i = 95\%$：

$$A_{\text{quorum}} = \binom{3}{2}A_i^2(1-A_i)+A_i^3 = 3 \times 0.95^2 \times 0.05 + 0.95^3 = 0.99275 = 99.275\%$$

该结果依赖“实例故障相互独立”的假设。共享电源、区域、配置、发布或依赖会造成相关故障，使真实可用性显著低于计算值。

#### 可用性"九"对照

| 可用性 | 年停机 | 月停机 | 周停机 | 日停机 | 备注 |
|---|---|---|---|---|---|
| 99% (2 个 9) | 87.6 h | 7.2 h | 100.8 min | 14.4 min | 大量内部系统 |
| 99.9% (3 个 9) | 8.76 h | 43.2 min | 10.1 min | 86.4 s | 商用 SaaS 起步 |
| 99.95% | 4.38 h | 21.6 min | 5.04 min | 43.2 s | 平台型服务 |
| 99.99% (4 个 9) | 52.6 min | 4.32 min | 60.5 s | 8.64 s | 关键交易链路 |
| 99.999% (5 个 9) | 5.26 min | 25.9 s | 6.05 s | 0.864 s | 电信级、非常困难 |

### 5.2.2 错误预算推导

**例 4**：下单 SLO = 99.95% 月度可用性,月请求数 1 亿。

- 允许失败数 = $1 - 0.9995 = 0.0005 = 0.05\%$
- 预算内失败数 = $10^8 \times 5 \times 10^{-4} = 50{,}000$ 次 / 月
若请求在一天内均匀分布，预算平均约 1667 次/天；实际预算按整个窗口管理，不能据此形成“每秒可失败 0.019 次”的瞬时配额，突发和用户分群同样重要。

当某次大促因 Redis 故障导致 8 万次符合 SLI 口径的失败，而月预算为 5 万次时，已消耗 160%。后续动作按预算政策决定：限制高风险功能变更，优先修复共享故障点并复核 Redis 故障切换；不机械冻结紧急安全和可靠性改进。

### 5.2.3 故障树分析（FTA）

故障树用 **与门（AND gate）**、**或门（OR gate）** 把"顶层失效事件"分解为基本事件（Basic Event）。

**例 5**：MTEP "下单失败" 顶层事件（TLE: Top-Level Event）

```
                      [下单失败]
                          |
                        OR ─────────────────────────────┐
                       / | \                            \
                      /  |  \                            \
            [支付失败] [库存失败] [账户失败]            [网络分区]
                |          |          |                    |
              OR          OR          OR                  OR
             / \         / \         / \                 / \
      [余额不足]  [渠道超时]  [DB锁] [SKU缺货]   [认证]  [限额]   [DNS故障]  [BGP中断]
```

**量化**：每个门都要按树结构自底向上计算。若某个 OR 节点的子事件相互独立，$P(OR)=1-\prod_j(1-P(E_j))$；若 AND 节点的子事件独立，$P(AND)=\prod_jP(E_j)$。本例需先合并支付、库存、账户、网络各自的叶子，再计算顶层 OR。共享依赖会破坏独立假设；实务中还要处理条件概率与共同原因故障。

工程实践通常用 **故障模式与影响分析（FMEA, Failure Mode and Effects Analysis）** 表,记录模式、影响、严重度（S）、发生度（O）、可探测度（D）,RPN = S × O × D。

### 5.2.4 排队论与 Little 定律

#### Little 定律

$$\displaystyle L = \lambda W$$

**变量解释**：

- $L$：系统中**平均在飞**（in-flight）任务数。
- $\lambda$：**平均到达率**（req/s）。
- $W$：**平均端到端停留时间**（秒）,包括等待 + 服务。

> **关键洞察**：Little 定律**与分布无关**,适用于任何稳态排队系统（M/M/1、M/G/k、有限容量等）。

#### M/M/1 队列（指数到达、指数服务、单服务器）

$$\rho = \frac{\lambda}{\mu},\quad L_q = \frac{\rho^2}{1-\rho},\quad W_q = \frac{L_q}{\lambda} = \frac{\rho}{\mu(1-\rho)}$$

**变量解释**：

- $\mu$：服务率（req/s）。
- $\rho$：**利用率**（traffic intensity），稳定条件 $\rho < 1$。
- $L_q$：平均**队列长度**（不含在服务的请求）。
- $W_q$：平均**等待时间**（不含服务时间）。

**例 6**：订单服务 $\mu = 200$ req/s,实测 $\lambda = 180$ req/s,则

$$\rho = 180/200 = 0.9,\quad L_q = 0.9^2/(1-0.9) = 8.1,\quad W_q = 8.1/180 \approx 45\text{ ms}$$

若 $\lambda$ 涨到 195 req/s:

$$\rho = 0.975,\quad L_q = 0.975^2/0.025 = 38.0,\quad W_q \approx 195\text{ ms}$$

> 队列长度随利用率**非线性**增长：$\rho$ 从 0.9 升到 0.975,延迟上升 4 倍。这就是**为什么不能追求 100% 利用率**。

#### M/M/k 队列（多 worker）

令 offered load $a=\lambda/\mu$，服务器利用率 $\rho=a/k<1$。Erlang C 等待概率为：

$$P_W=\frac{\frac{a^k}{k!(1-\rho)}}{\sum_{n=0}^{k-1}\frac{a^n}{n!}+\frac{a^k}{k!(1-\rho)}}$$

等待时间尾分布为 $P(W_q>t)=P_W e^{-(k\mu-\lambda)t}$，平均等待时间为 $E[W_q]=P_W/(k\mu-\lambda)$。

**例 7**：客户支持平台 $\lambda=90$ calls/h，平均服务时间 4 分钟，所以每名坐席 $\mu=15$ calls/h，业务目标为 80% 来电在 20 秒内接通。

- $k=8$：$a=6$，$\rho=0.75$，$P_W\approx0.357$；20 秒内接通比例约为 $1-0.357e^{-30\times20/3600}=69.8\%$，不达标。
- $k=9$：$\rho\approx0.667$，$P_W\approx0.196$；20 秒内接通比例约为 $1-0.196e^{-45\times20/3600}=84.7\%$，在模型假设下达标。

Erlang C 假设泊松到达、指数服务时间、无限等待且无人放弃。真实系统若有突发、技能分组、重试或客户放弃，需要仿真或实测校准，不能把模型结果当作精确排班答案。

#### 利用率定律（Utilization Law）

$$U = B / T$$

- $B$：单位时间内服务忙的总时长。
- $T$：单位时间。
- $T$ 越长,$U$ 越接近真实利用率。**短窗口的 $U$ 不可信**。

### 5.2.5 Amdahl 定律

$$\displaystyle S_{\text{overall}} = \frac{1}{(1 - p) + p / s}$$

**变量解释**：

- $p$：系统中**可并行化**部分的占比。
- $s$：该部分的**加速比**。
- $S_{\text{overall}}$：**整体加速比**。

**例 8**：某批处理程序总执行时间 400 ms，其中 120 ms 不能被目标优化影响，另外 280 ms 可通过并行计算获得 8 倍加速。则 $p=0.7,s=8$：

$$S=\frac{1}{0.3+0.7/8}\approx2.58$$

优化后时间约 $400/2.58\approx155$ ms；即使可加速部分趋于无限快，极限也为 $1/(1-0.7)\approx3.33$。Amdahl 定律针对同一工作负载中可被某优化加速的比例。把三个相互依赖的远程调用“并行”时，还要看依赖 DAG、资源争用和失败语义，不能直接把链路时长代入。

### 5.2.6 延迟百分位（Percentile）

- **P50（中位数）**：约一半样本不超过该值。
- **P95/P99/P99.9**：分别有约 95%、99%、99.9% 样本不超过该值；选择哪个百分位取决于请求量、用户旅程和风险，P95 不是永远“最常用”，SLO 也不必总用 P99。

平均值和百分位回答不同问题。平均值适合吞吐与总资源估算，却可能掩盖少数慢请求；高百分位揭示尾部，但需要足够样本、明确聚合窗口和直方图精度。不存在“P99 从 500 ms 到 100 ms 通常需要 10 倍资源”的通用比例，先用追踪、分布和排队模型定位机制。

**例 9**：若下单 P99 为 800 ms，可提出候选并用实验验证，而不能预填改善数字：

| 候选机制 | 要验证的假设 | 典型副作用 |
|---|---|---|
| 把非关键步骤移到受控异步流程 | 关键路径确被这些步骤主导，且“已受理”语义可接受 | 中间态、积压、对账与背压 |
| 优化查询/索引或分区 | 数据库等待或扫描主导尾延迟 | 写放大、跨片事务、运维复杂性 |
| 缓存稳定热点 | 命中率和陈旧容忍足够 | 击穿、失效竞态、隔离风险 |
| 改善追踪与直方图 | 当前无法定位尾部来源 | 采集成本；观测本身不会直接降低延迟 |

### 5.2.7 性能模型与排队网络

**M/G/1 队列（一般服务时间分布）**：Pollaczek–Khinchine 公式

$$W_q = \frac{\lambda \mathbb{E}[S^2]}{2(1-\rho)}$$

**变量解释**：

- $S$：单次服务时间（不要求指数分布）。
- $\mathbb{E}[S^2]$：服务时间二阶矩,**方差越大延迟越长**。

> **工程意义**：即使平均服务时间不变,**长尾变长**会显著拉高延迟。这是为什么 GC 偶发 STW（Stop-The-World）会破坏 P99。

### 5.2.8 容量规划（Capacity Planning）

**步骤**：

1. **预测需求**：业务增长曲线、季节性、活动日历。
2. **基线测量**：当前最大 QPS、平均 P99、CPU/内存/IO 利用率。
3. **资源模型**：将流量、单实例在目标 SLO 下的可持续容量、故障/发布余量映射为副本数。若标定容量 $c$ 已是在选定最大利用率下测得，可用 $\lceil\lambda_{peak}F/c\rceil$；不要再次乘同一利用率。
4. **压测标定**：用阶梯和突发负载找拐点，确认流量—尾延迟—利用率曲线及依赖瓶颈。
5. **分别建模余量**：突发、单区故障、滚动发布和预测误差可能重叠，不能一律套 30%–50%。
6. **持续刷新**：按增长速度和扩容提前期复审，不机械按季度。

**例 10**：大促峰值为 5000 TPS；单 Pod 压测确认在目标 P99 下可持续处理 800 TPS，该点 CPU 利用率约 60%。若综合突发和滚动发布取容量因子 $F=1.5$，副本数为 $\lceil5000\times1.5/800\rceil=10$。若“800 TPS”其实是理论满载吞吐，而团队规定最多用到 60%，则才应按 $\lceil5000\times1.5/(800\times0.6)\rceil=16$；必须明确容量口径。

### 5.2.9 背压（Backpressure）的形式模型

背压让下游容量约束沿调用/流通路径传回上游，使系统通过阻塞、减少请求额度、限流、排队上限或拒绝来避免无限积压。长期稳态仍需有效到达率不超过可持续处理率；短时突发可以消耗有界缓冲。

| 形式 | 信号/机制 | 适用场景 | 副作用 |
|---|---|---|---|
| 有界同步并发 | 连接/流窗口、信号量、deadline | RPC 和流传输 | 阻塞传播、线程/连接耗尽 |
| 有界异步队列 | 剩余容量、高水位、暂停消费/生产 | 消息流 | 增加延迟；仅“队列深度+告警”不是背压 |
| 令牌桶 | 入场许可，可允许桶容量内突发 | 入口限流 | 超额请求排队或拒绝，不是必然“突发丢失” |
| 漏桶 | 以近似恒定速率排出 | 流量整形 | 增加延迟，队列满时拒绝 |
| 信用制流控 | 下游显式授予可发送额度 | HTTP/2/自定义协议 | 实现与调参复杂 |
| Reactive Streams | 订阅者 demand 信号 | 进程内/流式处理 | 端到端链路中任一不支持就会断裂 |

### 5.2.10 可靠性模式理论小结

可靠性模式试图限制故障传播并缩短恢复时间；CAP、FLP 则在特定系统模型下描述不可能性边界。不能据此推出“工程上通常选择 AP + 最终一致”：不同对象和操作会在分区时选择拒绝、只读、陈旧读、冲突写或人工确认，必须由业务不变量决定。

## 5.3 方法步骤

### 5.3.1 设计 SLO 的五步法

1. **从用户体验出发**：列出关键用户旅程（如"浏览 → 下单 → 支付 → 履约"）。
2. **定义 SLI**：以**成功请求比例**（availability SLI）与**延迟分布**（latency SLI）为主,辅以吞吐、饱和度。
3. **选择窗口**：窗口应覆盖业务周期并支持及时反馈；滚动 14 天、滚动 28/30 天或日历月各有取舍，Google SRE 方法并未规定 14 天普遍优于 30 天。
4. **设置目标值**：以用户期望、历史能力、依赖、风险和成本为依据；“留 10%–20% 缓冲”不是通用规则。
5. **连接行动**：按燃烧率、剩余预算和变更风险决定限制、修复或实验；预算耗尽不等于无差别冻结。

**例 11**：MTEP 设计

| 用户旅程 | SLI | SLO | 窗口 | 责任团队 |
|---|---|---|---|---|
| 下单可用性 | 成功下单 / 总下单 | 99.95% | 30 d | 交易 |
| 下单延迟 | P99 端到端 | ≤ 400 ms | 30 d | 交易 |
| 支付回调 | 5 分钟内成功回调 / 总 | 99.99% | 30 d | 支付 |
| 列表页 TTFB | P95 TTFB | ≤ 200 ms | 30 d | 平台 |
| 商家后台登录 | 成功登录 / 总 | 99.5% | 30 d | 商家 |

### 5.3.2 错误预算治理

- **预算拥有者**：服务 Owner + SRE 共同管理。
- **预算消耗速率告警**：剩余预算 < 50% 时黄色告警,< 25% 时红色告警。
- **治理动作**：红色后冻结非关键变更,组织"可靠性冲刺"。
- **超额复盘**：识别是否**用足（well-spent）** vs. **挥霍（wasted）**,前者是合理试验,后者是流程失控。

### 5.3.3 可靠性模式工程实施

#### 5.3.3.1 重试（Retry）with Backoff

- **指数退避（Exponential Backoff）**：$\text{delay}_n = \min(\text{base} \times 2^n + \text{jitter}, \text{max})$
- **抖动（Jitter）**：避免**雷暴群（Thundering Herd）**同步重试。
- **幂等键（Idempotency Key）**：客户端为每次"逻辑操作"生成唯一 ID,服务端去重。
- **副作用**：放大对下游的负载（尤其下游已部分降级时）;非幂等操作会引发数据错误;增加延迟方差。

#### 5.3.3.2 熔断器（Circuit Breaker）

三态：**CLOSED → OPEN → HALF_OPEN**。

- CLOSED：正常调用,统计失败率。
- OPEN：达到阈值后直接失败,冷却定时器。
- HALF_OPEN：放少量探测请求,成功则关闭,失败则继续 OPEN。

**副作用**：OPEN 状态下**没有降级逻辑**就直接 5xx 给上游;HALF_OPEN 探测可能击穿已经脆弱的下游。

#### 5.3.3.3 限流（Rate Limiting）

| 算法 | 公平性 | 突发允许 | 复杂度 |
|---|---|---|---|
| 固定窗口 | 边界突刺 | 高 | 低 |
| 滑动窗口 | 平滑 | 中 | 中 |
| 令牌桶 | 平滑 | 是 | 中 |
| 漏桶 | 严格恒速 | 否 | 中 |

**副作用**：**公平限流**让"少量大客户"被误杀;**突发限流**让正常脉冲被裁剪;**全局限流**需要一致存储（Redis）形成单点;限流粒度过粗/过细都会引发问题。

#### 5.3.3.4 舱壁（Bulkhead）

- **线程隔离（Thread Pool Bulkhead）**：为每个下游分配独立线程池,隔离资源。
- **信号量隔离（Semaphore Bulkhead）**：限制并发调用数,共用线程。
- **进程/集群隔离**：按租户、优先级分集群。

**副作用**：增加资源占用;线程池饱和时整个隔离区会被打爆;调参不当反而降低整体吞吐。

#### 5.3.3.5 降级（Degradation）

- **静态降级**：节假日关闭非核心功能（推荐位、优惠券）。
- **动态降级**：根据错误率、延迟、依赖健康度关闭特性（Feature Flag）。
- **读写降级**：写入异步化、读取走缓存。

**副作用**：用户体验下降;动态降级若缺乏可视化会让用户和运营困惑;降级与回滚路径必须**演练**。

#### 5.3.3.6 幂等（Idempotency）

- **自然幂等**：GET、PUT-by-id、状态机转移。
- **人造幂等**：客户端带 Idempotency-Key,服务端缓存 24h–7 天。
- **副作用**：需要持久化存储（Redis/DB）,过期窗口需明确;PUT + 副作用逻辑时需严格定义"同 key 同结果"。

#### 5.3.3.7 超时与截止时间（Timeout & Deadline）

- **连接超时（Connect Timeout）**：建立 TCP/握手的时间。
- **请求超时（Request Timeout）**：单次 RPC 等待。
- **截止时间（Deadline / Timeout Budget）**：链路级总时长,层层分配。
- **副作用**：超时过短 → 误杀慢请求;过长 → 资源被占;**未传递 deadline** 是工程常见 bug。

#### 5.3.3.8 数据复制与冗余

- **同步复制（Sync）**：在声明的故障模型内，可将已确认写的 RPO 设计为 0；延迟至少受所需确认副本影响，可用性取决于仲裁而非简单“最弱节点”。
- **异步复制（Async）**：降低前台确认延迟，但故障切换可能丢失尚未复制的已确认写，RPO 取决于复制滞后；单主异步复制不一定涉及写冲突，多主才必须定义冲突解决。
- **仲裁复制（Quorum）**：$W+R>N$ 只保证读写集合相交；要读到最新值还需版本选择、并发写和故障切换协议，不能仅凭不等式宣称线性一致。

### 5.3.4 性能与容量规划流程

1. **建立基线**：连续一周采集 P50/P95/P99、QPS、错误率、CPU、内存、IO。
2. **建立模型**：将 QPS 映射到资源,绘制容量曲线。
3. **压测校准**：阶梯加压、脉冲、长时间浸泡（Soak Test）。
4. **设置告警**：多窗口多阈值（Multi-Window Multi-Burn Rate, Google SRE 经典方法）。
5. **演练**：限流降级、断网、节点宕机、数据库主从切换。
6. **评审**：每月容量评审会,根据业务变化调整。

### 5.3.5 延迟百分位工程的实战步骤

1. **统一 trace 标签**：traceId、spanId、用户身份哈希、租户 ID、入口 URL。
2. **建立服务依赖图**：自动从 trace 推导,标注 P99 边。
3. **慢请求抽样**：保存 P99 全部 trace 与错误 trace 全量。
4. **归因分析**：自底向上找最深的"长尾贡献者"。
5. **持续改进**：每个长尾改进设 SLO 子目标（如 2 周内 -30%）。

### 5.3.6 背压的设计步骤

1. **识别上下游依赖**：从入口到出口画链路。
2. **设置容量边界**：每个组件明确"最大接收速度"。
3. **实现背压信号**：队列深度、信号量、订阅反馈。
4. **传播到上游**：每个接收方把当前可用容量告知发送方。
5. **设计缓冲**：短时抖动用内存缓冲,长时用持久化队列。
6. **过载保护**：超阈值时**有损服务（Lossy）**而非崩溃。

**例 12**：Kafka 消费背压

- 消费者通过 `max.poll.records` 和 `max.poll.interval.ms` 反馈吞吐能力。
- 若处理跟不上,Kafka 不主动反压,而是提交 offset 滞后,**对账系统**触发告警。
- 治理手段：扩容 consumer 实例、partition 重分布、就地限流。

### 5.3.7 可观测性三支柱 + 方法论

#### 5.3.7.1 三大支柱

| 支柱 | 用途 | 典型工具 |
|---|---|---|
| **日志（Logs）** | 离散事件、上下文、调试 | ELK / Loki / Splunk |
| **指标（Metrics）** | 时序聚合、趋势、告警 | Prometheus / VictoriaMetrics / InfluxDB |
| **追踪（Tracing）** | 跨服务因果、延迟归因 | Jaeger / Zipkin / Tempo / OpenTelemetry |

#### 5.3.7.2 RED 方法（面向服务）

- **R**ate：每秒请求数。
- **E**rrors：每秒错误数。
- **D**uration：延迟分布。

#### 5.3.7.3 USE 方法（面向资源）

- **U**tilization：资源利用率。
- **S**aturation：饱和度（队列长度）。
- **E**rrors：错误事件计数。

#### 5.3.7.4 SLI 仪表盘

把每个 SLO 做成仪表盘:

```text
SLO: 下单可用性 99.95%
┌──────────────────────────────────────────┐
│ 30 d SLI       : 99.962%                 │
│ 已用预算       : 76%                     │
│ 剩余预算       : 24%                     │
│ 快速燃烧告警   : 1 h 与 5 min 窗口均越线 │
│ 慢速燃烧告警   : 6 h 与 30 min 窗口均越线│
└──────────────────────────────────────────┘
```

阈值按目标耗尽时间推导：长度为 $T$ 的 SLO 窗口若以燃烧率 $r$ 持续消耗，约在 $T/r$ 后耗尽全部预算。例如 30 天窗口的 14.4× 约对应 50 小时，而不是 2 小时。多窗口、多条件告警的具体阈值需结合响应能力和误报成本。

#### 5.3.7.5 告警分级

- **症状告警（Symptom）**：用户能感知（错误率上升、P99 超阈值）。
- **原因告警（Cause）**：资源饱和、依赖超时。
- 推荐**优先症状告警**,原因告警只用于排障。

### 5.3.8 威胁建模（Threat Modeling）

#### STRIDE 分类

| 类别 | 威胁 | 缓解 |
|---|---|---|
| **S**poofing 伪装 | 身份冒用 | MFA、证书、签名 |
| **T**ampering 篡改 | 数据/代码被改 | 完整性校验、WORM 存储 |
| **R**epudiation 抵赖 | 否认操作 | 审计日志、签名 |
| **I**nformation Disclosure 信息泄露 | 数据泄漏 | 加密、最小权限 |
| **D**enial of Service | 拒绝服务 | 限流、CDN、Anycast |
| **E**levation of Privilege | 权限提升 | RBAC、纵深防御 |

#### DREAD 评分

DREAD 的五维为 Damage Potential、Reproducibility、Exploitability、Affected Users、Discoverability。若组织仍使用它，可显式写为 $Risk=(Damage+Reproducibility+Exploitability+AffectedUsers+Discoverability)/5$，并固定每维评分锚点。DREAD 评分主观且易产生虚假精度，不应替代威胁场景、资产价值、攻击路径和控制证据。

#### 攻击树（Attack Tree）

**例 13**：MTEP "盗取用户账户"

```
                       [盗取账户]
                           |
                         OR ─────────────────┐
                        / | \                  \
                       /  |  \                  \
             [暴力破解]  [钓鱼]  [凭据填充]   [内部威胁]
                |         |         |             |
              OR         OR        OR            OR
             / \        / \       / \           / \
        [字典] [撞库] [邮件] [短信] [泄漏库] [Bot] [员工] [供应链]
```

**缓解**：MFA + 速率限制 + 设备指纹 + 异常登录告警 + 凭据填充检测 + 员工审计 + 第三方依赖审查。

#### 威胁建模流程（PASTA）

1. **定义业务目标**。
2. **定义技术范围**。
3. **应用分解**（DFD, 数据流图）。
4. **威胁分析**。
5. **漏洞与弱点分析**。
6. **攻击建模**。
7. **风险分析**。
8. **缓解设计**。

### 5.3.9 零信任（Zero Trust）实施

零信任的三大原则:

1. **Never trust, always verify**：每次访问都要鉴权,不依赖网络位置。
2. **Least privilege**：最小权限,按需授予、按时收回。
3. **Assume breach**：假设已被攻破,设计应对。

**技术组件**：

- **身份层（Identity）**：强身份（SSO + MFA）、短时 token。
- **设备层（Device）**：设备态势（patch level、磁盘加密）。
- **网络层（Network）**：微分段（Microsegmentation）、服务网格 mTLS。
- **应用层（Application）**：按资源/动作的授权（OPA / Cedar）。
- **数据层（Data）**：字段级加密、动态脱敏、行级安全（RLS）。

**副作用**：

- 性能损耗：每次 RPC 都做鉴权,mTLS 增加 TLS 握手成本（一般 0.1–1 ms）。
- 运维复杂：策略爆炸,需要可观测性 + 治理平台。
- 用户体验：MFA 增加登录摩擦,需要权衡安全 vs. 转化率。

### 5.3.10 最小权限（Least Privilege）

- **RBAC（Role-Based Access Control）**：按角色分配。
- **ABAC（Attribute-Based Access Control）**：基于属性（时间、IP、租户、风险评分）。
- **PBAC（Policy-Based Access Control）**：以策略即代码（Rego、Cedar）表达。
- **Just-in-Time 提权**：临时获取权限,定时收回。
- **副作用**：策略过严会让生产事件无法响应;过宽则无效果;权限审查需要定期审计。

### 5.3.11 纵深防御（Defense in Depth）

多层防护,任一层失效仍能挡住攻击:

```
[边界] WAF / DDoS 防护
   ↓
[网络] VPC / 子网隔离 / 安全组
   ↓
[主机] OS 加固 / 入侵检测
   ↓
[应用] SAST / DAST / RASP
   ↓
[数据] 加密 / 备份 / 不可篡改日志
   ↓
[运营] 告警 / 应急响应 / 红蓝对抗
```

**副作用**：层与层之间职责不清导致盲区;多层同时告警风暴;成本高,需要风险分级。

### 5.3.12 隐私工程

- **数据分类分级**：公开、内部、机密、严格机密。
- **默认收集最小化**：不要的字段不要存。
- **目的限制（Purpose Limitation）**：只能用于声明的用途。
- **存储期限（Retention）**：到期删除或匿名化。
- **跨境合规**：数据出境合规、加密 + 审计。
- **隐私增强技术（PETs）**：差分隐私（Differential Privacy）、联邦学习（Federated Learning）、同态加密（Homomorphic Encryption）、k-匿名（k-Anonymity）。

**副作用**：差分隐私会损失一定的统计精度;联邦学习增加算力与通信成本;过度匿名化会让数据分析难以进行。

### 5.3.13 弹性（Resilience）策略

1. **多可用区（Multi-AZ）**：跨独立故障域部署，能否容忍整个可用区故障取决于仲裁、容量余量和共享依赖，不能只看实例分布。
2. **多区域（Multi-Region）**：改变灾备故障域；RPO/RTO 是要验证的目标，不是部署后自动“提升”。
3. **多活（Active-Active）**：多区域同时承载流量，需要写入归属、冲突、不变量和分区行为设计，复杂度通常最高。
4. **混沌工程**：在稳态假设、爆炸半径和停止条件下做受控实验；工具不是混沌工程本身。
5. **爆炸半径控制**：灰度、影子流量、Canary、暗启动（Dark Launch）。
6. **事故响应流程**：On-call → 缓解 → 沟通 → 调查 → Postmortem → 行动项闭环。
7. **Runbook / Playbook**：每种故障有应对脚本,演练频率至少季度。

## 5.4 权衡 / 失败模式

### 5.4.1 SLO 设计的常见失败

| 失败模式 | 后果 | 缓解 |
|---|---|---|
| 把 SLA 直接当 SLO | 内部工程目标与外部承诺没有风险缓冲 | 根据赔付、测量口径、故障相关性与业务风险设置差距，不用固定“差一个 9” |
| 指标过于宽泛 | 监控不到关键失败 | 用用户旅程切片 |
| 目标定得过高 | 永远消耗完预算,失去公信力 | 参考竞品 + 历史基线 |
| 没有行动挂钩 | 预算耗尽无人响应 | 预先约定按燃烧率、剩余预算和变更风险调整发布；安全修复与可靠性改进不应被机械冻结 |
| 窗口过短 / 过长 | 反应迟钝或抖动 | 按业务周期选择滚动窗口，并用多窗口燃烧率兼顾快慢故障 |

### 5.4.2 错误预算的副作用

- **预算不足导致研发受阻**：产品 vs. 平台矛盾,需要治理委员会。
- **预算"花光"是设计**：鼓励**有意义的风险**（新功能灰度）而非**无意义的稳健**。
- **超额未必是失败**：可能是重大故障,关键是后续改进是否到位。

### 5.4.3 可靠性模式的副作用总结

| 模式 | 核心副作用 |
|---|---|
| 重试 | 放大负载、引发雪崩、增加延迟方差 |
| 熔断 | OPEN 状态若无降级则直接失败 |
| 限流 | 误杀合法流量、突发丢失 |
| 舱壁 | 资源占用增加、配置不当引发吞吐下降 |
| 降级 | 用户体验下降、需运营告知 |
| 幂等 | 需持久化存储、过期窗口需明确 |
| 超时 | 短了误杀、长了堆积、未传递 deadline |
| 同步复制 | 延迟高、可用性下降 |
| 异步复制 | RPO>0、需冲突解决 |

### 5.4.4 性能优化的副作用

- **缓存**：击穿、雪崩、一致性问题。
- **异步**：最终一致性、链路复杂度、补偿机制。
- **并行**：线程/协程开销、上下文切换。
- **预计算**：数据陈旧、维护复杂。
- **压缩**：CPU 开销、调试困难。

### 5.4.5 可观测性的副作用

- **采样偏差**：固定采样可能错过长尾。**自适应采样**更稳。
- **追踪开销**：高基数标签导致存储爆炸。
- **日志风暴**：错误风暴期间日志压垮下游。
- **指标精度**：聚合函数（平均、百分位）选择不当掩盖真相。

### 5.4.6 安全设计的副作用

| 设计 | 副作用 |
|---|---|
| 强制 MFA | 注册 / 登录转化率下降 |
| 加密传输 | 性能下降 1%–3% |
| 输入校验 | 开发效率下降、误杀 |
| 审计日志 | 存储成本、数据敏感 |
| 漏洞扫描 | 误报噪音 |
| 蜜罐 | 内部安全运维负担 |

### 5.4.7 弹性的失败模式

- **级联故障（Cascading Failure）**：A 慢 → B 等 → C 满 → 整体雪崩。缓解：超时、舱壁、限流、熔断。
- **爆炸半径失控**：一次配置错误导致全平台下线。缓解：灰度、Canary、配置变更审计。
- **假阴性恢复**：熔断后未真正恢复就放流量。缓解：HALF_OPEN + 健康检查。
- **过度耦合**：多区域相互依赖,分区即瘫痪。缓解：单元化架构、流量调度。
- **演练缺失**：Runbook 过期、On-call 不会用。缓解：定期 GameDay。

### 5.4.8 容量规划的副作用

- **过度预留**：资源闲置、成本高。
- **预留不足**：突发过载、SLO 失效。
- **基线陈旧**：业务变化后未刷新。
- **压测不真**：生产流量特征与压测差异巨大。

## 5.5 示例：多租户电商平台（综合应用）

### 5.5.1 案例背景

MTEP 当前面临三个 SLO 风险:

1. **下单链路 P99 = 700 ms**,超出 400 ms SLO。
2. **大促期间库存服务雪崩**。
3. **第三方支付回调存在伪造风险**。

### 5.5.2 SLO / 错误预算设计

```yaml
slos:
  - name: 下单请求成功率
    eligible: 已到达服务且通过请求有效性校验的下单请求
    good: 服务端在截止时间内返回已受理或明确成功
    target: 0.9995
    window: 30d-rolling
  - name: 下单延迟达标比例
    eligible: 同上
    good: 端到端延迟 <= 400ms
    target: 0.99
    window: 30d-rolling
  - name: 支付结果及时收敛
    eligible: 支付机构已确认完成的交易
    good: 5min 内平台账本收敛且可对账
    target: 0.999
    window: calendar-month
```

实际 PromQL 应使用 recording rules 和与窗口匹配的 `increase()`/短周期 `rate()` 聚合。直接对 `[30d]` 使用 `rate()` 再将直方图求 P99 容易产生高成本和跨时段聚合误读；延迟 SLO 更常定义为“阈值内好事件比例”，而不只是一个 30 天 P99 数值。

### 5.5.3 下单链路慢请求归因

通过 OpenTelemetry trace 抽样发现:

| Span | P50 | P95 | P99 |
|---|---|---|---|
| 网关 | 5 ms | 20 ms | 60 ms |
| 鉴权 | 10 ms | 30 ms | 80 ms |
| 风控（同步） | 80 ms | 200 ms | **500 ms** |
| 库存查询 | 50 ms | 150 ms | 200 ms |
| 支付 | 120 ms | 150 ms | 180 ms |

**结论**：风控是 P99 长尾最大贡献者。改进:把风控从同步改为**异步 + 风险预评估**（低风险同步放行、高风险异步审核+冻结订单）。

### 5.5.4 库存雪崩的混沌工程复现

```yaml
# chaos-mesh 实验
apiVersion: chaos-mesh.org/v1alpha1
kind: StressChaos
metadata:
  name: redis-stress
spec:
  mode: one
  selector:
    namespaces: [mtep]
    labelSelectors:
      app: inventory-cache
  stressors:
    cpu:
      workers: 4
      load: 80
  duration: "5m"
```

复现结论:Redis 慢 → 库存服务线程池排队 → Tomcat accept-count 满 → 新连接拒绝 → 上游超时 → 整体下单失败。

**修复**：Redis 前置熔断器 + 库存查询本地缓存兜底 + 舱壁线程池隔离。

### 5.5.5 支付回调的安全设计

#### 威胁建模（STRIDE）

| 威胁 | 攻击路径 | 缓解 |
|---|---|---|
| 伪装 | 伪造 HTTP 回调 | mTLS + HMAC 签名 + 时间戳防重放 |
| 篡改 | 修改回调金额 | 业务侧二次校验（向支付通道拉取真实订单） |
| 抵赖 | 商户称未收到回调 | 完整审计日志 + 双向确认 |
| 信息泄露 | 回调中包含敏感数据 | 字段脱敏、最小披露 |
| 拒绝服务 | 大量伪造回调 | 入口限流、签名校验前置 |
| 权限提升 | 回调触发内部特权操作 | 权限最小化（仅订单状态机） |

#### 防御代码示意

```text
callback_handler(req):
    1. 限流（按 merchant_id + IP）
    2. 校验 mTLS 客户端证书
    3. 校验时间戳（5 分钟窗口）
    4. 校验 HMAC（订单号 + 金额 + 时间戳）
    5. 反查支付通道订单状态（防伪）
    6. 写入审计日志
    7. 状态机转移（订单 → 已支付）
    8. 幂等：Idempotency-Key = (merchant_id, out_trade_no)
```

### 5.5.6 弹性的多区域容灾

```
                    [GeoDNS]
                   /        \
            Region A         Region B
            (主)             (备)
            ┌────┐            ┌────┐
            │App │ ←──MySQL→ │App │
            └────┘   异步    └────┘
              ↓                ↓
         [Kafka MirrorMaker]
              ↓
         [对象存储跨区复制]
```

**RPO 目标**：例如 ≤ 30 秒；必须用复制滞后、故障切换时最后提交点与对账验证，不能把“典型 binlog 延迟 1–10 秒”当保证。
**RTO 目标**：例如 30 分钟；DNS TTL、应用容量、数据校验、密钥与人工决策都进入恢复路径。
**改进方向**：先评估单写区域 + 异步灾备、按租户/分片归属写入或共识复制。双向同步/多主不是默认升级，会新增冲突、脑裂与外部副作用重复。

### 5.5.7 综合可观测性仪表盘

**核心仪表盘**：

- **Overview**：全站流量、错误率、P99。
- **SLO Board**：每个 SLO 当前 SLI、剩余预算、燃烧率。
- **Service RED**：每个服务的 Rate / Errors / Duration。
- **Resource USE**：每个 Pod / 节点的 Utilization / Saturation / Errors。
- **Trace Search**：按 traceId 搜索、P99 长尾列表。
- **Security**：登录失败、异常 IP、敏感操作。

**告警分级**：

- P1：多窗口燃烧率满足“快速耗尽”条件，或已造成重大用户影响；立即响应。
- P2：持续中速燃烧或关键依赖退化；值班跟进并限制风险。
- P3/P4：按症状、原因和紧迫度分级。燃烧率阈值必须结合 SLO 窗口计算，不能把 14.4× 固定解释为“两小时预算耗尽”。

## 5.6 检查清单

### 5.6.1 SLO / SLA / 错误预算清单

- [ ] 每个面向用户的服务至少有一个**可用性 SLI**。
- [ ] 关键链路有**延迟 SLI（P95 / P99）**。
