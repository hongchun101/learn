# 附录：架构师的理论地图、术语表与工作模板

> 本附录不是“背诵清单”。它把分散的理论放进同一张因果地图，帮助你判断：一个理论解释什么、不解释什么，以及如何把它转化为可检验的架构决策。

## 1. 一种决策视角：将部分架构选择建模为受约束多目标决策

当候选、目标和约束足够明确时，教程作者使用以下概念示意作为决策辅助：把架构选择看作在环境与约束下挑选一组结构和演化规则，使相互冲突的目标达到可接受水平。该视角不是“架构的本体定义”，也不涵盖目标函数尚未量化、组织争议或概念性更强的设计阶段。

设：

- $\mathcal{A}$：候选架构集合；
- $K$：硬约束；可行集合 $\mathcal{A}_K=\{A\in\mathcal{A}\mid A\text{ 满足 }K\}$；
- $Q_i(A,E)$：架构 $A$ 在环境 $E$ 下对第 $i$ 个质量属性的表现；
- $w_i$：当前利益相关者偏好；$C(A)$：成本；$R(A)$：按明确口径表达的风险。

若各项被映射到可比较效用尺度、依赖关系已处理且风险口径明确，可用概念示意：

$$A^*=\arg\max_{A\in\mathcal{A}_K}\left[\sum_iw_iU_i(Q_i(A,E))-\lambda C(A)-\mu R(A)\right]$$

这不是架构学标准公式，也不能直接计算。质量属性、成本和风险通常量纲不同、相互依赖且有非可补偿约束；条件不成立时应保留 Pareto 前沿并让决策者显式取舍。以下是建模提醒，不是该式证明的定理：

1. 不存在脱离上下文的最佳架构。
2. 高优先级质量目标需要可观察场景；探索期未知项应成为实验而非伪精度。
3. 决策有时间价值，但保留选择权也有成本和最晚决策点。
4. 局部最优可能把成本转移给全局价值流。
5. 环境、偏好和约束会变化，因此架构需要复审与迁移能力。

## 2. 理论的适用边界

| 理论/定律 | 核心命题 | 能解释 | 不能直接推出 |
|---|---|---|---|
| Conway 定律 | 设计系统的组织受其沟通结构约束，所产生的系统设计倾向复制该组织的沟通结构 | 解释模块边界为何与团队依赖纠缠 | 不证明组织图与模块一一对应，也不推出微服务或团队规模 |
| 逆 Conway 策略 | 主动设计团队交互以促进目标架构 | 组织重构与架构重构如何协同 | 组织图一改系统就会自动变好 |
| Gall 定律 | 可工作的复杂系统通常由可工作的简单系统演进而来 | 渐进演化优于大爆炸设计 | 可以不做前瞻设计 |
| Lehman 演化定律（主要针对 E-type 软件） | 为适应变化的现实环境需持续演化；复杂度倾向增长，除非主动维持或降低 | 为什么长期业务系统需持续反馈与简化 | 所有软件都以同一机制或速率演化 |
| CAP | 分区执行中不能同时保证线性一致寄存器与每个未失效节点请求最终响应 | 特定分区模型下的硬取舍 | 平时延迟、所有一致性语义或整个产品的 CP/AP 标签 |
| PACELC | 分区态讨论 A/C，正常态讨论 L/C 的分类启发式 | 提醒正常态也有延迟/一致性取舍 | 自动选数据库或严格不可能性证明 |
| FLP 不可能性 | 完全异步模型中，即使至多一个崩溃故障，确定性共识也存在永不决定的允许执行 | 共识活性为何需要额外时序/随机假设 | 现实系统不能达成共识 |
| Little 定律 | 长期平均量存在且边界/群体一致时 $L=\lambda W$ | 在途数、吞吐与逗留时间关系 | 短期非稳态或长期平均不存在时的瞬时关系；无限容量本身不使定律失效 |
| Amdahl 定律 | 固定工作负载中未被加速部分限制整体加速 | 为什么局部并行优化收益递减 | 所有扩容都无效或远程调用可直接套用 |
| 排队模型 | 到达/服务有变异且允许排队的常见稳定模型中，利用率逼近 100% 时等待通常急升 | 容量余量、背压、尾延迟 | D/D/1 等无变异特殊情况或分布未知时的精确增长；结果依服务器数、调度和容量 |
| 事务隔离与并发控制 | 不同实现和保证允许或防止不同执行历史中的异常 | 用业务不变量和历史验证隔离选择 | 标称隔离级别不等于实际实现语义，SQL 现象分类也未穷尽写偏差（write skew）、读偏差（read skew）和读写反依赖（rw-antidependency）等异常 |
| 端到端原则 | 某些正确性只能由通信端点完整保证，底层机制只能辅助 | 校验、去重、安全责任为何不能全下沉 | 中间层一律无价值 |
| Postel 定律 | 发送保守、接收宽容 | 早期互联网协议互操作 | 现代 API 应无限容忍畸形输入；这会积累歧义和安全风险 |
| Goodhart 定律 | 指标成为目标后，就不再是好指标 | KPI 游戏、覆盖率或发布次数异化 | 不应该度量 |
| Goodenough 原则 | 工程方案只需达到上下文要求，而非理论极致 | 避免无收益的过度设计 | 可以忽视已知高风险 |

### 2.1 定理、经验规律、启发式必须分开

- **定理**：在明确假设下可证明，如 CAP、FLP、Little 定律的数学条件。使用时必须同时写出假设。
- **经验规律**：从长期观察概括，如 Conway、Lehman。它们是强解释框架，不是机械因果公式。
- **启发式**：帮助在信息不足时行动，如“先模块化单体”“优先可逆决策”。它们需要被上下文证据推翻或确认。
- **模式**：反复出现问题的已知解法与后果组合。模式不是组件目录，更不是供应商产品名。

## 3. 架构推理的追踪检查表（作者综合示例）

下文是教程作者用于追踪提案完整性的检查表，不是“任何提案都必须走完的官方链条”。不同情境（探索原型、合规强制、收购整合、紧急事故响应、阶段性投资）可以省略或重排环节；省略应在 ADR 或评审纪要中说明，事后补齐追溯不能省略风险控制动作。

```text
业务结果
  ↓ 为什么重要
利益相关者关注点
  ↓ 如何观察
质量属性场景 / 业务不变量
  ↓ 受什么限制
约束、假设、不确定性
  ↓ 有哪些选择
候选架构及机制
  ↓ 为什么选它
权衡、成本、风险、证据
  ↓ 如何知道仍然成立
SLI、适应度函数、告警与复审触发器
```

可作为追问线索的常见缺口：

- 从业务目标直接跳到产品：**工具驱动设计**；
- 从功能列表直接画服务：**名词分割法**；
- 只谈收益不谈副作用：**模式崇拜**；
- 记录决定但无证据：**ADR 形式主义**；
- 有指标但无业务目标：**可观测而不可解释**；
- 有目标但无复审触发器：**一次性架构**。

缺少任一环通常是追问信号，**但不是“伪架构”的判决**。事故应急应先控制风险再补追溯；监管和合同推动的强制决定可能无法等待完整证据，但必须明确假设和退出条件。

## 4. 术语表

### 4.1 系统与结构

- **架构（Architecture）**：实体在其环境中的基本组织，体现为元素、它们之间的关系、指导设计与演化的原则。架构描述（architecture description）是用一组视图表达这些基本属性的工作产品。难修改、影响广泛、承载 ASR 等是“架构显著性”信号，不是架构本体定义。
- **模块（Module）**：在模块视图（module view）中描述的实现或构建单元；可与包、库、命名空间等概念对应。
- **组件（Component）**：在组件—连接件视图（component-and-connector view）中描述的运行时计算或数据存储元素，如进程、服务、过滤器、存储等。
- **分配视图（Allocation view）**：将软件元素映射到环境/运行单元的视图。

使用“组件”一词时应明确是哪种视图，否则读者会误把模块、进程、部署单元、服务等概念等同。
- **架构重要需求（Architecturally Significant Requirement, ASR）**：足以显著影响架构形态、成本或风险的需求。
- **连接件（Connector）**：组件间交互的机制与协议，如函数调用、HTTP、消息主题、共享表。
- **视点（Viewpoint）**：规定如何构造某类视图的关注点、元素与表示规则。
- **视图（View）**：从特定视点表达系统结构的实例。
- **边界（Boundary）**：隔离变化、所有权、故障、安全或一致性的分割线。不同边界不必重合。
- **内聚（Cohesion）**：一个单元内部元素共同服务于同一变化原因或业务能力的程度。
- **耦合（Coupling）**：单元之间在知识、时间、数据、协议、部署或组织上的依赖程度。
- **信息隐藏（Information Hiding）**：模块隐藏易变设计决策，只暴露稳定能力，而不只是把字段设为 private。

### 4.2 领域与数据

- **限界上下文（Bounded Context）**：某一领域模型和语言保持一致含义的边界。
- **聚合（Aggregate）**：由聚合根维护业务不变量的事务一致性边界；不是任意对象树。
- **上下文映射（Context Map）**：限界上下文之间语义、依赖和协作关系的显式模型。
- **事实来源（Source of Truth）**：对特定事实拥有权威写入权的系统；不等于所有读取必须回源。
- **线性一致性（Linearizability）**：每个操作看起来在调用和返回之间某一瞬间原子发生，并遵守实时顺序。
- **可串行化（Serializability）**：并发事务结果等价于某种串行执行；不必遵守实时顺序。
- **最终一致性（Eventual Consistency）**：无新更新且通信继续时，副本最终收敛。它没有规定收敛时间、冲突语义或读己之写。
- **幂等（Idempotence）**：同一意图执行一次或多次产生等价的业务效果；HTTP 方法标称幂等不自动保证业务实现幂等。

### 4.3 运行与治理

- **SLI（Service Level Indicator）**：对用户可观察服务行为的定量指标。
- **SLO（Service Level Objective）**：SLI 在时间窗口内应达到的目标。
- **SLA（Service Level Agreement）**：对外承诺及违约后果，通常不应与内部 SLO 完全相同。
- **错误预算（Error Budget）**：在给定 SLI、SLO、时间窗口和有效事件集合下，SLO 与 100% 合规/可靠目标之间可容忍的差额。对事件型 99.9% SLO，才可在口径一致时表述为最多 0.1% 有效事件不合规；时间型、截止时间型或排除维护窗口的 SLI 需要按各自规则计算。
- **可观测性（Observability）**：从系统外部输出推断内部状态的能力；不等于“安装了监控平台”。
- **韧性（Resilience）**：系统在故障、突发负载和依赖退化下维持或恢复关键能力的能力。
- **爆炸半径（Blast Radius）**：一次变化、故障或权限泄露可影响的最大范围。
- **适应度函数（Fitness Function）**：持续验证架构属性是否仍在可接受范围的自动或人工机制。
- **技术债（Technical Debt）**：当前设计/实现相对所需状态的缺口，使未来变更、验证或运行产生额外成本；可有意承担，也可在学习后无意识别。普通缺陷或功能缺失不因“质量差”自动成为技术债。
- **架构治理（Architecture Governance）**：让决策权、原则、标准、例外、证据和复审形成闭环，而不是中央审批所有实现细节。

### 4.4 职业发展与求职（参考第 9–10 章）

- **P 序列 / 职级体系**：国内互联网大厂常见技术级别序列（P6/P7/P8/P9），不同公司具体定义和薪酬差异显著；外企有 L4–L7、IC1–IC6、61–63 等不同体系。"目标 50K 薪资"在不同公司可对应 P7、Staff Engineer 或 Senior Architect。
- **影响力半径（Influence Radius）**：从团队（L1）到跨团队（L2）到业务线（L3）到全公司（L4）到行业（L5）的分级，用于评估 P7+ 架构师的成长阶段。
- **Individual Contributor（IC）路径**：技术深度路径，不带人或带 1–3 人，影响力以"被引用、被采纳"为度量。
- **Engineering Manager（EM）路径**：技术管理路径，承担业务 + 人员 + 战略责任。
- **Tech Lead Manager（TLM）**：混合路径，兼具技术深度和团队管理。
- **STAR-L 框架**：在 STAR（情境/任务/行动/结果）基础上增加 Learning（学习与反思），用于行为面试准备。
- **RADIO 框架**：系统设计面试五阶段（Requirements → Architecture → Data/Deep dive → Identify tradeoffs → Operations）。
- **决策证据化（Decision Evidence）**：简历与面试中用"业务目标 → 关键决策 → 量化结果 → 退出条件"代替单纯技术名词清单的方法。
- **签字费（Sign-on Bonus）**：入职一次性奖金，是薪酬谈判的可变项。
- **限制性股票单位（Restricted Stock Unit, RSU）**：4 年归属、离职失效的股票激励，按现价计税。

### 4.5 现代架构主题（参考第 11 章）

- **云原生（Cloud Native）**：CNCF 定义的技术集合（容器、编排、微服务、可观测性、声明式 API、自动化、服务网格、不可变基础设施）。
- **Kubernetes（K8s）**：容器编排系统，提供调度、扩缩容、自愈能力。
- **Service Mesh**：服务间通信的横切关注点治理层（Istio、Linkerd、Consul Connect），典型通过 Sidecar 代理实现。
- **Sidecar 代理**：与服务实例同生命周期部署的辅助进程（如 Envoy），处理网络、可观测性、安全等横切关注点。
- **GitOps**：以 Git 作为系统期望状态的单一事实来源，自动化 Agent 持续同步与运行时的偏差。
- **内部开发者平台（Internal Developer Platform, IDP）**：把 DevOps 实践产品化为内部"开发者一站式入口"，代表案例 Spotify Backstage。
- **Serverless / FaaS（Function as a Service）**：事件驱动、按调用付费、自动扩缩容的函数执行服务（AWS Lambda、Cloudflare Workers）；"恰好一次"由平台近似，业务仍需幂等。
- **冷启动（Cold Start）**：FaaS/容器首次调用时初始化运行时导致的延迟尖峰。
- **边缘计算（Edge Computing）**：把计算、存储延伸到靠近用户的位置（CDN 节点、运营商 MEC、IoT 边缘），用于降低延迟、节省带宽、满足数据驻留。
- **WebAssembly（Wasm）**：可移植的二进制指令格式，沙箱执行、多语言、近原生性能；用于浏览器插件、边缘计算、多租户插件化平台。
- **OpenTelemetry（OTel）**：CNCF 的可观测性标准，融合 OpenTracing 和 OpenCensus，统一 traces/metrics/logs 采集。
- **Continuous Profiling**：持续收集生产环境的 profiling 数据（CPU、内存、锁、I/O），用于定位性能瓶颈。
- **eBPF（extended Berkeley Packet Filter）**：在内核中安全运行沙箱程序，用于网络（Cilium）、安全（Falco）、可观测性（Pixie、bpftrace）。
- **AIOps（AI for IT Operations）**：用机器学习改进运维（异常检测、告警聚合、根因分析、容量预测），是补充而非替代工程实践。
- **Lakehouse**：在低成本对象存储上提供数据仓库式管理与查询能力的架构范式（Iceberg、Hudi、Delta Lake）。
- **向量数据库（Vector Database）**：存储高维向量并支持相似度检索（KNN/ANN），用于 RAG、推荐召回、语义搜索（Pinecone、Milvus、Weaviate、Qdrant）。
- **零信任（Zero Trust）**：NIST SP 800-207 定义的安全架构原则（永不信任、持续验证、最小权限、假设失陷）。
- **机密计算（Confidential Computing）**：用硬件可信执行环境（TEE，如 Intel SGX、AMD SEV、ARM TrustZone）保护"使用中"的数据。
- **后量子密码学（Post-Quantum Cryptography, PQC）**：抵抗量子计算攻击的密码学算法（NIST 已发布 ML-KEM、ML-DSA、SLH-DSA 标准）。

### 4.6 行业垂直架构（参考第 12 章）

- **多租户架构（Multi-Tenant Architecture）**：一个系统实例服务多个客户的架构模式，隔离级别从共享 DB+tenant_id 到独立 DB 不等。
- **租户路由（Tenant Routing）**：按域名/路径/Header 识别租户并路由到对应租户上下文的机制。
- **租户级 SLA / SLO**：按租户套餐分级承诺的可用性、性能目标。
- **特征存储（Feature Store）**：统一管理 ML 特征（在线 KV + 离线数仓），保证训练-服务一致性（Feast、Tecton、阿里 PAI）。
- **设备影子（Device Shadow）**：在 IoT 系统中记录设备的期望状态（Desired）和上报状态（Reported），用于离线同步和命令重放。
- **OTA（Over-The-Air）升级**：IoT 设备固件远程升级机制，需支持分批灰度、断点续传、回滚。
- **MQTT（Message Queuing Telemetry Transport）**：IoT 常用的轻量级发布-订阅消息协议，适合不稳定网络。
- **CoAP（Constrained Application Protocol）**：IoT 资源受限设备使用的类 HTTP 协议，基于 UDP。
- **实时音视频（Real-Time Communication, RTC）**：低延迟（< 300ms）的音视频通信技术，主流基于 WebRTC/SFU 架构。
- **SFU（Selective Forwarding Unit）**：转发而非混流的媒体服务器，适合多人互动场景（Janus、Mediasoup、LiveKit）。
- **跨境数据合规**：数据出境受法规约束（中国《数据出境安全评估办法》、欧盟 GDPR 等），需数据驻留、匿名化、本地化部署。

## 5. 可复用工作模板

### 5.1 一页式架构简报

```markdown
# <系统/变更名称>

## 业务结果
- 目标：
- 成功指标：
- 截止时间与机会成本：

## 范围与边界
- 系统负责：
- 系统不负责：
```

### 5.4 风险登记模板

若 $P(E)$ 是经校准概率，$E[L\mid E]$ 是同一货币或效用尺度上的条件损失，可计算期望损失：

$$E[L]=P(E)\times E[L\mid E]$$

若只有 1–5 的可能性/影响序数等级，它们没有等距和真实零点，不应相乘成“暴露值”再做精确排序。使用有明确锚点的风险矩阵/有序类别筛选，单独升级任何灾难性单维风险，并记录相关风险与共同原因。

| 风险 | 触发条件 | 可能性等级/证据 | 影响等级/尺度 | 类别 | 缓解 | 应急 | 所有人 | 复审 |
|---|---|---|---|---|---|---|---|---|

### 5.5 架构评审提问

1. 业务结果和系统边界是否明确？谁会因决定失败而受损？
2. 哪三个 ASR 真正塑造了结构？是否有量化场景？
3. 关键业务不变量是什么？由哪个边界维护？
4. 数据由谁拥有？复制品允许多旧？冲突如何解决？
5. 哪些故障被假设为独立，但实际上共享依赖？
6. 峰值、突发、增长与降级路径是否分别建模？
7. 身份、权限、密钥、隐私和审计跨越哪些信任边界？
8. 方案引入了哪些运维和认知负载？团队有能力承担吗？
9. 哪些决定不可逆？是否有更便宜的实验来购买信息？
10. 如何部署、迁移、回滚？数据库变更是否支持版本共存？
11. 哪些指标能反驳当前设计？谁在什么时候复审？
12. 方案总拥有成本是否包含人、云、许可、迁移与退出成本？

## 6. 架构能力评估量表（非标准自省工具）

下表是本教程作者用于自我反思和讨论职责范围的示例，不是行业标准、认证体系或晋升阶梯，未经心理测量意义上的效度/信度验证。实现者、设计者、系统架构师、领域/企业架构师和架构领导者可能是不同岗位职责，也可能由同一人在不同情境承担，不应计算总分、强行排序或直接用于人事评价。

应按目标职责选择行为证据：

| 参考职责 | 问题定义 | 技术推理 | 决策/治理 | 组织影响 | 演进能力 |
|---|---|---|---|---|---|
| 实现/设计 | 澄清局部问题、接口和质量要求 | 比较实现方案与边界 | 记录局部权衡 | 协调相邻实现 | 设计兼容变更 |
| 系统架构 | 将业务目标转为 ASR | 跨数据、分布式、安全、运维推理 | 用证据管理重要决定 | 对齐多个团队边界 | 设计阶段目标和迁移 |
| 领域/企业架构 | 管理能力、产品组合和跨系统约束 | 识别涌现属性、投资与风险 | 管理原则、标准和例外 | 调整价值流与决策权 | 管理长期选择权和淘汰 |
| 架构领导 | 重构问题、约束和反馈系统 | 建立组织级推理机制 | 构建可审计、去中心化决策系统 | 塑造技术文化和学习回路 | 让组织适应未知变化 |

**能力证据示例**不是晋级证明：

- 是否减少了高代价错误；
- 是否让决策依据可追踪、可反驳；
- 是否改善了端到端业务指标；
- 是否降低团队认知负载和变更协调成本；
- 是否使系统在约束变化后仍能安全演进。

## 7. 反模式速查

| 图纸即架构 | 文档漂亮但与运行系统脱节 | 没有明确的所有者、复审触发器和验证机制 | 文档记录意图和例外；高频可机器判定的约束用架构测试或治理即代码强制，其余由所有者通过评审、演练、运行证据和 ADR 历史保护 |
|---|---|---|---|
| 简历驱动架构 | 每个新技术都有位置 | 把新颖性当价值 | 从 ASR 和最小机制反推技术 |
| 分布式单体 | 服务很多，仍同步连锁部署 | 边界没有独立所有权 | 重划业务边界、契约和数据所有权 |
| 万能平台 | 平台试图覆盖所有团队所有需求 | 未定义产品边界和黄金路径 | 平台产品化，测量采用率与认知负载 |
| 共享数据库集成 | 团队直接读写彼此表 | 以短期便利换语义耦合 | 权威写入、显式契约、渐进迁移 |
| 默认微服务 | 按名词切服务 | 把部署单元误认为领域边界 | 先证明独立变更和扩展需求 |
| 最终一致性万能论 | 丢失更新也称“最终一致” | 未定义不变量、读写保证、冲突合并和收敛时间 | 先写不变量、并发保证、合并规则、收敛与可见性要求；仅对可补偿且幂等可审计的业务动作设计补偿，不可补偿状态需明确隔离与人工决策路径；补偿不是回滚，也不代替一致性模型 |
| 100% 利用率 | 资源报表很好看、延迟失控 | 忽略排队非线性 | 容量余量、限流、优先级与背压 |
| 中央架构委员会 | 所有决定排队审批 | 决策权与风险等级不匹配 | 原则和护栏下放，重大不可逆决策集中审查 |

## 8. 理论阅读顺序

阅读不是收集名词。每读一个来源，回答四问：它的假设是什么？解释变量是什么？反例是什么？如何形成可运行的检查？

### 第一层：结构与设计

1. David Parnas：信息隐藏与模块分解——理解“按变化原因分解”而非按流程图分解。
2. *Software Architecture in Practice*——质量属性、视图、战术和架构评估的系统框架。
3. *Designing Data-Intensive Applications*——数据系统机制与权衡的共同语言。
4. Eric Evans / Vaughn Vernon：DDD——理解模型边界和组织语义，不把 DDD 缩减成代码分层。

### 第二层：分布式系统

1. Lamport：时间、事件顺序、状态机复制。
2. Gilbert 与 Lynch：CAP 的严格表述。
3. Fischer、Lynch、Paterson：异步共识不可能性及其假设。
4. Gray、Bernstein 等：事务、并发控制、恢复。
5. Google SRE 系列：把可靠性从愿望转成 SLO、错误预算与运营机制。

### 第三层：演进与社会技术系统

1. Parnas：可变性与软件老化。
2. Lehman：软件演化规律。
3. Conway：组织沟通结构与系统设计。
4. Team Topologies：认知负载、团队类型和交互模式。
5. Accelerate / DORA 研究：交付能力的系统度量，注意相关性不自动等于因果。

## 9. 最终自检：你是否真的在做架构

在提交方案前，逐项回答“是”并附证据：

- [ ] 我能用一句话说明业务结果，而不是只说“建设某平台”。
- [ ] 我明确写出系统不负责什么。
- [ ] 每个关键质量属性都有刺激、环境、响应和量化度量。
- [ ] 我区分事实、约束、假设和偏好。
- [ ] 我比较了真实可行候选；若现状可维持则作为基线，不可维持则记录硬约束或期限。
- [ ] 我解释机制如何导致结果，而不是用产品名替代推理。
- [ ] 我识别一致性、安全、故障和组织边界，并说明它们是否重合。
- [ ] 我计算过数量级：流量、数据量、延迟预算、容量、可用性和成本。
- [ ] 我写出失败模式、爆炸半径、降级和恢复路径。
- [ ] 我考虑部署、迁移、回滚、版本共存和退出成本。
- [ ] 我记录负面后果、风险所有人和复审触发器。
- [ ] 我定义了能反驳该架构的运行证据。

真正成熟的架构方案不是“看起来无懈可击”，而是**假设清晰、权衡诚实、证据可追踪、失败可控制、未来可改变**。
