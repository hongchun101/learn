# 软件架构师系统教程

> 从复杂性、约束与质量属性出发，系统学习架构建模、决策、分布式理论、工程保障、组织治理与演进。

## 这套教程适合谁

读者应有至少一个真实软件项目的开发、测试、运维或技术管理经验。教程不要求你已经担任“架构师”，但默认你理解基本编程、数据库、网络、版本控制和软件交付。

它不教“背 30 个架构模式后去面试”，也不把架构等同于画图、选中间件或拆微服务。核心训练是：

1. 把模糊业务目标转成可验证的系统属性；
2. 在约束和不确定性下建立候选方案；
3. 用理论、数量级和实验解释取舍；
4. 让决定能够交付、运营、复审和演进；
5. 把技术系统作为社会—技术系统治理。

## 建议学习方式

### 路径 A：系统学习，12 周

- 第 1–2 周：第 1 章。用自己的项目重写“系统边界”和三个最难改变的决定。
- 第 3 周：第 2 章。访谈利益相关者，产出质量属性场景、效用树和一个 ADR。
- 第 4–5 周：第 3 章。为同一系统画上下文、容器、组件和部署视图；检查边界是否表达变化原因。
- 第 6–7 周：第 4 章。列出业务不变量，为每条数据标注所有权、一致性和恢复语义。
- 第 8–9 周：第 5 章。建立 SLO、容量模型、威胁模型和故障注入方案。
- 第 10 周：第 6 章。把目标架构拆成可兼容、可回滚的演进步骤。
- 第 11–12 周：第 7 章。独立完成案例，再与参考推理比较；组织一次口头评审。

### 路径 B：项目驱动

遇到新系统或大改造时，按以下顺序使用：

```text
第 2 章：目标、ASR、约束
  → 第 3 章：边界与候选结构
  → 第 4/5 章：验证数据和质量属性机制
  → 第 6 章：设计迁移、团队与治理
  → 第 8 章：ADR、风险和评审模板
```

不要先决定“用微服务/Kubernetes/事件驱动”，再回头为它寻找理由。

### 路径 C：面向评审补缺

先做第 7 章结业案例，把无法明确回答的问题标记出来，再回读对应章节。答案若只有术语而没有“机制 → 后果 → 度量”，视为不会。

## 每章阅读法

对每个理论和模式，强制回答六个问题：

1. **问题**：它究竟解决哪类力与冲突？
2. **假设**：结论依赖哪些环境、故障和组织假设？
3. **机制**：结构如何导致期望属性？
4. **代价**：它把复杂性转移到了哪里？
5. **证据**：用什么指标、模型或实验判断有效？
6. **退出**：假设失效时如何迁移或回滚？

## 最小实践闭环

只阅读不会形成架构能力。每学习一个主题，都完成一次闭环：

```mermaid
graph LR
  O[观察真实问题] --> M[建立模型]
  M --> H[提出可反驳假设]
  H --> D[记录决策与预测]
  D --> E[实现最小实验或增量]
  E --> S[观测运行证据]
  S --> R[复盘并修正模型]
  R --> O
```

建议保留个人“决策日志”：写下当时已知事实、未知数、预测、选择和复审日期。数月后比较预测与结果。架构判断力来自反馈校准，不来自头衔。

## 按风险选择架构交付物

以下是候选集合，不是每个中大型系统必须齐备。依据利益相关者、生命周期、合规和失败模式选择，并为每项写明它回答的问题、责任人和维护机制：

- 业务目标、范围、ASR 与系统上下文；
- 与关键风险相关的结构、动态、数据、部署或信任边界视图；
- 记录真正重要决定的 ADR；
- 按用户旅程定义的 SLI/SLO、容量和恢复目标；
- 适合风险级别的威胁模型、风险登记与迁移路线；
- 自动或人工适应度函数；高频且可机器判定的约束优先自动化。

没有明确读者、问题和维护机制的图或文档应删除或合并。

## 完成标准

完成教程后，你应能：

- 明确区分业务目标、功能、质量属性、约束、假设和架构决定；
- 用场景和数量级讨论可用性、性能、安全、一致性和成本；
- 解释主流架构风格的工作机制、组合方式与失败边界；
- 分析事务、复制、分区、缓存和异步消息的正确性语义；
- 设计可观测、可恢复、可回滚且能渐进演化的系统；
- 让团队结构、决策权和系统边界相互支持；
- 主持一次基于证据、风险和权衡的架构评审；
- 在不确定性下比较继续学习、延期损失与选择权持有成本；到最晚决策点或提前承诺价值更高时作出决定，并用兼容、迁移和退出设计降低不可逆性。

从第 1 章开始。遇到陌生术语，可先查阅[附录](08-reference.md)，但必须回到上下文理解其假设与边界。
