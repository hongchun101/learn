# 第 2 章 架构需求与架构决策

> 本章解决两个相互耦合的问题：如何从模糊的业务诉求中提炼出对架构有约束力的需求，以及如何在多个候选架构方案之间作出可追溯、可复盘的决策。两端若有一处薄弱，架构就会逐渐偏离业务。

## 学习目标

完成本章后，读者应能够：

1. 区分功能需求与质量属性，并说明质量属性为何是架构决策的主导约束。
2. 用六要素减少质量属性场景的歧义，并补充度量窗口、总体/测点、排除规则与假设，使场景可验证。
3. 构造效用树 (Utility Tree)，对架构重要需求按业务优先级排序。
4. 区分约束 (Constraints)、假设 (Assumptions)、风险 (Risks)，并写出三栏追踪表。
5. 在 ATAM (Architecture Tradeoff Analysis Method) 评审中识别风险点、非风险点、敏感点、权衡点。
6. 用 MADR 模板撰写架构决策记录 (Architecture Decision Record, ADR)。
7. 使用加权评分模型 (Weighted Scoring Model) 在多个候选方案之间进行显式比较。
8. 用实物期权 (Real Options) 视角评估"提前投入"与"延后投入"的取舍。
9. 按数据/外部锁定、回退能力、法规影响、爆炸半径与未知数调整决策权、评审强度和验证方式，而不是把不可逆性机械绑定为中央审批。
10. 用当前收益、偿还成本、未来额外变更成本与运行风险评估技术债，并说明不确定性。

## 1 核心概念

### 1.1 利益相关者 (Stakeholder)

定义：利益相关者（Stakeholder）是对系统或架构决定有关注点，或能够影响系统、受到系统/决策影响的个人、群体或组织。恶意主体未必是需求批准者，但应进入威胁模型；无正式发言权却受影响的群体也应被识别，必要时通过代表、合规或安全角色表达其关切。

常见的利益相关者类别：

| 类别 | 例子 | 主要诉求 |
| --- | --- | --- |
| 业务方 | 产品总监、销售 VP | 收入、上市时间、差异化能力 |
| 终端用户 | 终端消费者、租户管理员 | 易用性、响应时间、可信度 |
| 运营方 | 客服、运维团队 | 可观察性、可恢复性 |
| 工程方 | 研发、SRE、安全团队 | 可修改性、可测试性、安全性 |
| 合规方 | 法务、隐私官、审计 | 合规性、可追溯性 |
| 财务方 | CFO、采购 | 总拥有成本 (TCO)、许可费用 |

> 在多租户电商平台案例中，"租户管理员"（负责在后台配置店铺、营销活动）和"平台运营"（负责资源调度、计费、限流）都是必须独立建模的利益相关者，因为他们的需求经常冲突：租户想要无限弹性的容量，平台运营需要在共享资源池中维持整体 SLA。

### 1.2 业务目标 (Business Goals)

定义：业务目标是利益相关者希望系统在一定时间内达到的、可度量的结果。

业务目标通常需要通过利益相关者场景、质量属性、约束与风险追踪到架构决定。链条可按问题裁剪；它是确保“为什么—如何验证—决定什么”不断裂的推理工具，不是每个决定必须机械经过的流程。

```
业务目标
   │  (Why)
   ▼
业务场景 / 用例 (Business Scenario)
   │  (What for whom, in what context)
   ▼
质量属性场景 (Quality Attribute Scenario)
   │  (Measurable stimulus → response)
   ▼
架构重要需求 (Architecturally Significant Requirement, ASR)
   │  (Constrains the architecture)
   ▼
架构决策 (Architecture Decision)
```

这是一种需求到决定的追踪链，与 ATAM 的业务驱动因素、效用树和场景分析思想一致；不要把“效用链”当作 ATAM 的固定正式产物名称。链条断裂通常意味着决定缺乏业务或验证依据，但探索性原型也可以以“降低不确定性”作为直接目标。

### 1.3 架构重要需求 (Architecturally Significant Requirement, ASR)

定义：架构重要需求是对系统结构、关键质量属性、成本或风险产生显著影响的需求；若遗漏、误判或改变它，通常需要重新评估相关架构决定。

ASR 可以是质量属性场景、关键功能、硬约束，也可以是接口、数据或合规语义。例如支付网络协议约束可能塑造状态机；数据驻留要求可能塑造部署和备份。跨多个系统、已经量化或“一旦改变”都是识别信号，不是必要条件。判断方法是比较：满足与不满足该需求时，候选结构、机制、成本或风险是否实质改变，并记录依据与未知数。

## 2 理论模型

### 2.1 功能需求与质量属性

**功能需求（Functional Requirement, FR）**描述系统应提供的能力、行为和业务规则，包括输入/输出、状态转换、交互、权限和业务不变量；它不只是一条“给定输入产生特定输出”的函数。

**质量属性（Quality Attribute, QA）**描述这些能力在特定刺激、环境和约束下应达到的可测属性，例如延迟、吞吐、可用性、隔离性、可修改性和安全性；“非功能”只是历史简称，质量属性也会约束功能实现。

FR 与 QA 不是绝对二分：同一个需求可以同时包含能力与质量约束，二者都可能是架构重要需求。

以下六项是常见示例，不是《Software Architecture in Practice》第 4 版的封闭完整分类：

- **可用性（Availability）**：系统在需要时可提供服务的能力。
- **性能（Performance）**：系统在给定资源下对刺激作出响应的效率，表现为吞吐与延迟。
- **可修改性（Modifiability）**：在不破坏既有行为的前提下修改系统的能力。
- **安全性（Security）**：系统在面对恶意刺激时保护数据与资源的能力。
- **可测试性（Testability）**：通过测试揭示缺陷的容易程度。
- **易用性（Usability）**：用户完成目标的容易程度与主观满意度。

第 4 版还系统讨论可部署性（Deployability）、能效（Energy Efficiency）、可集成性（Integrability）、安全（Safety）等属性；项目还可以根据利益相关者关切定义可观察性、可靠性、公平性、合规性、租户隔离等属性。ISO/IEC 25010 是另一套产品质量模型，不应与该书分类混成一个统一标准。

### 2.2 质量属性场景六要素 (Six Elements)

Bass 等人在《Software Architecture in Practice》中将每个质量属性场景抽象为以下六元组：

| 要素 | 英文 | 含义 |
| --- | --- | --- |
| 源 | Source of Stimulus | 刺激的发出者（人、外部系统、时钟） |
| 刺激 | Stimulus | 触发系统响应的具体事件 |
| 环境 | Environment | 刺激发生时系统所处的状态（正常、过载、降级、维护） |
| 工件 | Artifact | 被刺激影响的系统部分（进程、服务、数据、接口） |
| 响应 | Response | 系统对刺激的可观察反应 |
| 响应度量 | Response Measure | 让响应可比较、可验证的量化指标 |

六要素的作用是消除“快”“稳”“好”的歧义。高优先级场景应尽量补全六要素；在探索早期，未知项也可以显式标为假设和待验证指标，而不应伪造精度。

### 2.3 效用树 (Utility Tree)

效用树是 ATAM 的核心交付物之一。它将业务目标分解为质量属性，再分解为具体场景，形成"效用"的可比较结构。

构造步骤：

1. 列出业务目标及关键利益相关者关切。
2. 将关切映射到质量属性分支。
3. 在每个分支下写出具体、可测试的叶场景。
4. 每个叶场景用二元组（业务重要性，实现难度/架构风险）分别标注 H/M/L，例如 `(H,H)`。
5. 优先分析高重要、高难度/风险场景；高重要低难度场景仍需验证。

### 2.4 约束、假设与风险

三者在架构工作中常被混淆，必须显式区分。

- **约束（Constraint）**：当前决策范围必须满足的限制。来源可以是法规、合同、内部政策、既有系统、预算/时间条件或已接受的架构决定；约束可能被实现违反，但违反意味着方案不可接受、需要例外批准或触发明确后果。每条约束应记录来源、所有者、有效期、验证方式和例外流程。
- **假设（Assumption）**：在证据不足时暂按真实处理的命题，未来可能被证伪，例如“未来 12 个月峰值 QPS 不超过 5 万”。假设应有验证计划、截止时间和失效动作。
- **风险（Risk）**：可能损害业务目标或架构质量的潜在事件/条件。可用校准概率与条件损失排序；若只有序数等级，应使用风险矩阵而不是把等级相乘。ATAM 的评估结果还包括风险点、非风险点、敏感点与权衡点。

三者关系：

```text
约束 → 规定当前可接受解空间，违反时触发拒绝/例外/后果
假设 → 规定决策的前置条件，验证失败时触发回溯
风险 → 指出可能损害目标的事件，驱动缓解、监测与应急
```

### 2.5 ATAM：架构权衡分析方法（Architecture Tradeoff Analysis Method）

ATAM 由 Kazman、Klein、Clements 等人在 CMU SEI 提出（1990 年代末），目的是在多个质量属性之间**显式地暴露并讨论权衡**。

参与角色通常包括评估团队、项目决策者、主持人和广泛利益相关者。评估团队由熟悉评估方法及相关质量属性的人组成，规模按系统关键性和复杂度调整；为降低确认偏差，宜有未直接参与设计者，但“外部架构师”或固定 3–5 人不是 ATAM 硬规则。主持人负责维持方法、时间与讨论质量，不替团队做决定。

九步骤流程（精简版）：

1. 介绍 ATAM。
2. 介绍业务动机。
3. 介绍架构。
4. 识别主要架构方法（architectural approaches）。
5. 生成质量属性效用树，并按重要性与实现难度/风险标注叶场景。
6. 针对高优先级场景分析架构方法，识别敏感点、权衡点、风险与非风险。
7. 由更广泛利益相关者头脑风暴场景并投票排序。
8. 用新发现的高优先级场景再次分析架构方法。
9. 汇总并报告结果、假设与行动项。

四个核心概念：

- **敏感点 (Sensitivity Point)**：某个架构属性对某个质量属性的响应度量影响显著。例：连接池大小对 P99 延迟影响显著。
- **权衡点 (Tradeoff Point)**：同一架构决定对多个质量属性敏感，改变它会影响多个属性，影响不必总是简单此消彼长。例如提高缓存 TTL 可能改善延迟与成本，却增加陈旧窗口。
- **风险点 (Risk)**：根据已知决策和场景，可能妨碍某项质量目标的架构决定或缺口。
- **非风险点 (Non-Risk)**：分析表明在给定假设和场景下可满足目标的决定；它不是永久“已验证”，假设变化后需复审。

### 2.6 架构决策记录（Architecture Decision Record, ADR）

以下采用 **MADR（Markdown Architectural Decision Records）最小字段的改写版**；不同 MADR 版本字段会略有差异，团队应固定版本或模板来源。

```markdown
# ADR-NNN：<动词短语描述决定>

- 状态：提议 | 已接受 | 已取代 | 已废弃
- 日期：YYYY-MM-DD
- 决策者：<姓名/角色>
- 关联：ADR-0001, ADR-0003

## Context and Problem Statement
哪些事实、约束、目标和未知数要求我们作出决定？

## Considered Options
列出实际考虑的可行候选及其机制；若现状可维持则作为基线，不可行时说明硬约束或期限。

## Decision Outcome
我们选择 <方案>，因为 <与决策驱动因素和证据对应的理由>。明确适用范围与不适用范围。

## Consequences
- 正面：
- 负面：
- 中性/迁移成本：
- 验证指标、复审触发器和退出路径：
```

已接受 ADR 的历史应保持可追溯；决定变化时新增 ADR 将旧条目标记为“已取代”，而非静默改写历史。

### 2.7 决策矩阵 (Decision Matrix)

定义：决策矩阵又称加权评分模型 (Weighted Scoring Model)，是 MCDM (Multi-Criteria Decision Making) 的经典方法。

数学形式：

$$
\text{Score}_i = \sum_{j=1}^{n} w_j \cdot s_{ij}
$$

其中：

- $i$ 表示候选方案编号；
- $j$ 表示评估准则编号；
- $w_j$ 表示准则 $j$ 的权重（建议归一化为 $\sum_j w_j = 1$）；
- $s_{ij}$ 是方案 $i$ 在准则 $j$ 上的评分。评分前必须为每个等级定义锚点和方向，例如“迁移演练 RTO≤4h=5 分、4–24h=3 分、无演练=1 分”；否则小数总分只是意见包装。

加权和只是一种可补偿的偏好模型，不自动产生“推荐方案”：

- 先筛掉硬约束不满足的候选；
- 避免准则重复计数或把“成本低”与“运维简单”高度相关项分别加权；
- 对权重、分数和未知项做敏感性/置信度分析；名次轻微变化时应说明结论不稳健；
- 非可补偿风险（法规、灾难性损失）单独评估，不能让高性能分抵消。

### 2.8 Real Options (实物期权)

传统 ROI 常用单点现金流比较，容易忽略“先用小成本购买信息、以后再决定”的价值。实物期权视角把架构接缝、试点、合同退出条款或延迟承诺看成选择权，但选择权不是免费：抽象、双运行、兼容层和认知负担都有持有成本。

- **扩张选择权**：试点验证后可按证据扩大，如先验证一个租户单元。
- **延迟选择权**：在最晚负责时刻前保留候选，如先测量区域需求再决定多活。
- **放弃/切换选择权**：用可导出数据、契约和迁移演练降低退出成本。

金融 Black–Scholes 假设可交易标的、连续价格过程、可估波动率和复制组合，软件架构通常不满足这些条件。直接把 $S,K,r,\sigma,T$ 映射到软件并计算“期权金额”会制造虚假精度，因此本教程不把该公式作为架构估值方法。

实务使用一个显式期权表：现在的持有成本、能推迟到何时、期间能获得什么信息、未来行权/迁移成本、什么信号触发行权或放弃。只有信息价值和风险下降高于持有成本时，保留选择权才有价值。

### 2.9 可逆与不可逆决策

可逆性不是二元属性。至少分别评估：数据迁移/丢失、外部消费者与合同锁定、组织和技能投入、停机/回滚窗口、财务沉没成本、法规影响与爆炸半径。所谓

$$\frac{ReverseCost}{ForwardCost}\times BlastRadius$$

不是公认模型，量纲也未必相容；不应输出一个貌似客观的“不可逆分数”。可以把各维度用有锚点的低/中/高矩阵展示，并规定任何灾难性单维风险都升级评审。可逆且低爆炸半径的决定下放团队；高锁定或不可恢复数据决定要求更强证据、试点、迁移与退出演练。

例子：

- 选择 HTTP/JSON vs gRPC：基本可逆，标准化抽象即可。
- 选择 PostgreSQL 作为主库：可逆但有迁移成本。
- 暴露公开 API 给第三方：基本不可逆，一旦有调用方依赖，修改协议破坏生态。
- 选择地域性的合规云厂商：高度不可逆。

### 2.10 技术债 (Technical Debt) 与成本模型

Martin Fowler 在 2009 年提出 **Technical Debt Quadrant（技术债象限）**，用“故意/无意”和“审慎/鲁莽”两个轴帮助讨论债务形成方式与责任；该象限是沟通与分类工具，不是债务成本计算公式。Kruchten、Nord、Ozkaya 等人的后续研究更关注技术债识别、度量和管理。

|  | 鲁莽 (Reckless) | 审慎 (Prudent) |
| --- | --- | --- |
| **故意 (Deliberate)** | “没时间设计，也不记录后果” | “为截止期接受限制，并安排验证/偿还” |
| **无意 (Inadvertent)** | 因能力缺口制造难以维护结构 | 交付与学习后发现更好的模型 |

象限应与当前收益、未来额外成本、运行风险和偿还决定一起使用。

不要把“立即偿还”和“继续持有”相加成一个总额；它们是需要比较的决策分支。对评估时点 $T$ 和未来窗口 $[T,T+h]$，分别估计：

**分支 A：现在偿还/迁移**

$$C_{repay}(T)=\text{一次性偿还成本}+\text{迁移期间风险与机会成本}$$

**分支 B：在同一窗口继续持有**

$$C_{hold}(T,h)=\sum_{j=1}^{m}E[N_j\mid T,h]\times\Delta C_j+E[L_{risk}\mid T,h]+C_{operate}+Pr(\text{届时需偿还}\mid T,h)\times PV_T\big(C_{repay}(T+h)\big)$$

- $E[N_j\mid T,h]$ 是窗口内第 $j$ 类未来变更的预期次数，单位为次数；
- $\Delta C_j$ 是每次变更因债务增加的工作量/成本；
- $E[L_{risk}]$ 是窗口内事故、安全、合规等期望损失，需声明概率和损失尺度；
- $C_{operate}$ 是继续持有债务的观测、绕行和维护成本；
- 最后一项表示窗口末仍需偿还时的折现偿还成本，避免用短窗口机械偏向继续持有。

分支 A 与分支 B 必须使用同一评估窗口和折现口径。若功能可能退役，应把退役概率、退役成本和残余风险单独列为情景，而不是把它当作自动“零债务”。比较结果是区间或情景分析，不是固定金融利率。登记时记录当前收益、触发条件、领先指标、偿还/接受决定和复审日期。

## 3 方法步骤

将本章理论落到实践，可按以下六步推进。步骤 3 的效用树先由核心参与者构建，步骤 5 的 ATAM 再引入更广泛利益相关者补充和排序；这两个活动不应混为一次“全员确认”。

步骤 1：识别利益相关者

- 输出：利益相关者清单 + 类别 + 主要诉求。
- 检查项：是否包含"非声音类"利益相关者（合规、安全、财务、运维）？

步骤 2：提炼业务目标

- 输出：5–10 条业务目标，每条 SMART (Specific, Measurable, Achievable, Relevant, Time-bound)。
- 检查项：能否用一句话陈述"在多长期望下达到什么业务结果"？

步骤 3：构造效用树

- 输出：效用树文档 + 叶场景列表；记录参与构建者、评分依据和异议。
- 检查项：重要性与难度/风险的评级是否有依据？是否记录哪些利益相关者尚未参与、哪些意见冲突？ATAM 后续的广泛利益相关者头脑风暴与投票用于补充和重新排序场景，不等同于要求所有人事前确认每个 H 场景。

步骤 4：将约束、假设、风险显式列出

- 输出：三栏追踪表（见 4.3 示例）。
- 检查项：每条假设是否有验证方式、过期时间、负责人？

步骤 5：组织 ATAM 评审

- 输出：评审纪要 + 风险点/非风险点/敏感点/权衡点 + 行动项。
- 检查项：是否分析高重要且高难度/风险的场景，并对新投票排序结果重新分析？

步骤 6：撰写 ADR 并评审

- 输出：ADR 仓库（建议 1 个 Git 仓库，1 个 Markdown 文件 1 条决策）。
- 检查项：决策是否有可观察的后果指标？

## 4 权衡与失败模式

### 4.1 常见权衡

| 维度 | 倾向 A | 倾向 B | 典型权衡点 |
| --- | --- | --- | --- |
| 性能 | 强一致性写入 | 最终一致性写入 | 写吞吐 vs 读一致 |
| 可扩展性 | 分库分表 | 共享数据库 | 隔离性 vs 复杂度 |
| 可用性 | 多活多写 | 单写多读 | RPO/RTO vs 复杂度 |
| 可修改性 | 微服务 | 单体 | 演进速度 vs 部署复杂度 |
| 安全与体验 | 每次高风险操作重新认证 | 基于会话、设备与风险的渐进认证 | 攻击面、误拒率、用户摩擦；两者都必须满足最低安全/合规约束 |
| 成本 | 自建机房 | 公有云 | 灵活性 vs 单位成本 |

### 4.2 常见失败模式

- **"快"陷阱**：把"响应快"写成"P99 < 200 ms"，却没说环境（空载/峰值）、工件（哪个接口）、源（哪个用户群）。
- **安全控制弱化换体验**：把“弱鉴权”当成正常候选，绕过最低安全或合规底线。应在底线之上比较每次高风险操作重新认证、基于会话/设备/风险的渐进认证、交易限额和人工复核，并测量攻击面、误拒率和用户摩擦。
- **约束与假设混淆**：把"我们假设 QPS 上限 5 万"当作约束写进架构文档，未来 QPS 真的到 5 万时无人触发回溯。
- **决策无后果**：ADR 的"后果"一栏只写"已与团队对齐"，没有可测量的成功条件。
- **技术债隐藏**：口头承认"我们借了一笔技术债"，但仓库中没有任何 ADR 或 issue 跟踪，导致利息不断滚动。
- **不可逆决策轻率**：公开 API、数据主键设计、区域合规云厂商的选择，未经过 ADR 评审直接拍板。

### 4.3 约束、假设、风险三栏追踪表（多租户电商示例）

| 类型 | 编号 | 陈述 | 影响 | 验证方式 / 缓解 | 负责人 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 约束 | C-001 | 目标部署范围需满足等保三级相关法律、定级与测评要求 | 影响云资源、边界和运营控制 | 由合规/测评机构确认适用范围 | 安全与合规团队 | 持续 |
| 约束 | C-002 | 若平台存储、处理或传输持卡人数据，需按实际数据流满足适用的 PCI DSS 范围；优先用托管支付缩小范围 | 影响支付集成、令牌化、网络与审计 | 范围评估和合规验证 | 合规团队 | 持续 |
| 假设 | A-001 | 单租户日均订单上限约 50 万 | 决定分片粒度 | Q1 数据复盘 | 产品 | 待验证 |
| 假设 | A-002 | 80% 流量集中在 20% 的租户（长尾分布） | 决定缓存与限流策略 | 影子流量分析 | 架构 | 待验证 |

## 5 示例：多租户电商平台端到端

### 5.1 场景设定

一家 SaaS 公司运营多租户电商平台，承载 5,000+ 中小品牌店铺。已上线 3 年，当前架构为单库多租户 + 共用 Schema + `tenant_id` 列。最近发生两次事故：

- 大促期间某个租户的营销插件故障，拖垮了数据库连接池，整体服务降级 30 分钟。
- 由于所有租户共享单一数据库，备份与还原粒度过粗，单租户误删数据无法快速恢复。

业务方提出新一年的目标：

- B1. 平台可用性从 99.9% 提升到 99.95%。示例口径：滚动 30 天、基于有效请求的成功率 SLI ≥ 99.95%；若改为时间型，30 天允许不可用 21.6 分钟、31 天 22.3 分钟，需要明确窗口、维护排除与降级规则，不应直接表述为“月度停机 < 22 分钟”。
- B2. 单租户故障不扩散（噪点租户隔离）。
- B3. 支持业务出海，目标市场包括东南亚（合规要求与国内不同）。
- B4. 一年内签约 1,000 个新租户。

### 5.2 利益相关者清单（节选）

- 业务总监：关注 B1、B4。
- 平台运营：关注 B2、运维工单减少。
- 财务：关注 TCO 不超过今年的 120%。
- 合规：关注 B3 涉及的多区域合规。
- 安全：关注 B1 的实现不能放大攻击面。
- SRE：关注 B2 所需的隔离成本。
- 终端租户：关注"独立备份""独立降级""快速恢复"。

### 5.3 效用树（多租户电商示例）

```
业务成功
├── 收入与增长
│   ├── [(H,H)] 可用性 → "平台可用率月度 ≥ 99.95%"
│   ├── [(H,H)] 可扩展性 → "单租户独立扩容"
│   └── [(M,M)] 易用性 → "租户后台关键任务 5 步内完成"
├── 风险控制
│   ├── [(H,H)] 可用性 → "单租户故障不扩散（噪点租户隔离）"
│   ├── [(H,H)] 安全性 → "租户间数据强隔离（数据库层不可越权）"
│   └── [(H,H)] 合规性 → "支持国内 + 东南亚至少 2 个合规框架"
├── 运营效率
│   ├── [(M,H)] 可观察性 → "全链路追踪覆盖 95% 请求"
│   ├── [(M,M)] 可修改性 → "模块化，单租户可灰度发布新功能"
│   └── [(L,M)] 可测试性 → "租户级契约测试覆盖率 ≥ 80%"
└── 成本与可持续
    ├── [(M,H)] 性能 → "P99 接口延迟 ≤ 300 ms"
    └── [(L,M)] 可移植性 → "可在两个云厂商之间迁移"
```

二元组第一项表示业务重要性，第二项表示实现难度/架构风险；标为 `(H,H)` 或第二项未知的叶场景优先进入分析。低重要性但高风险的场景也不能丢弃，应记录为何暂缓、如何验证。

将优先级为高重要性且高难度/风险，或风险尚未被证实的场景展开为六要素；“H 场景”在本章中不再表示单一等级。

### 5.4 关键决策：多租户数据隔离策略

候选方案：

- A：独立数据库（每租户一库）
- B：共享数据库 + 独立 Schema
- C：共享数据库 + 共享 Schema + `tenant_id` 列（当前方案）
- D：混合（VIP 租户独立数据库，其余共享 Schema）

决策矩阵：

| 准则 | 权重 | 评分锚点示例 | A | B | C | D |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 隔离控制与恢复粒度 | 0.30 | 1=仅应用过滤；3=纵深逻辑隔离；5=独立故障/恢复域并完成演练 | 5 | 4 | 2 | 4 |
| 独立容量治理 | 0.20 | 1=无法隔离；3=配额/搬迁；5=独立扩缩容已验证 | 5 | 3 | 2 | 4 |
| 目标租户规模的运营可行性 | 0.15 | 以迁移时长、对象数和自动化实验评分 | 3 | 4 | 5 | 4 |
| 三年 TCO | 0.15 | 1=最高成本区间；5=最低，含人力和恢复 | 1 | 3 | 5 | 3 |
| Schema 演进 | 0.10 | 以全量迁移/回滚演练时间评分 | 2 | 3 | 4 | 3 |
| 租户级观测与归属 | 0.10 | 以指标覆盖和高基数成本评分 | 5 | 4 | 3 | 4 |
| **示例加权得分** | **1.00** | **仅在锚点与证据成立时有效** | **3.65** | **3.50** | **3.10** | **3.70** |

由于 D 仅领先 A 0.05，且尚无搬迁、PITR、权限负测和 TCO 范围证据，当前结论只能是 A/D 短名单与 D 小范围试点，不是 D 的全量接受。试点结果、敏感性分析和硬约束证据将通过后续 ADR 决定是否推广。

先列硬约束并做资格筛选；示例：

- 部署与运营控制满足已确认的等保定级/测评范围。
- 支付数据流满足已确认的 PCI DSS 适用范围，或通过托管支付避免平台接触持卡人数据。
- 若业务合同确实要求云退出能力，定义数据导出、恢复时间、功能差异和演练频率；“能在两个云迁移”若未量化只是偏好。

候选只有在给出证据证明满足硬约束后才能进入加权评分；不能直接宣称所有方案天然满足。

### 5.5 ADR-0007：多租户数据隔离策略——候选短名单与待验证决定

```markdown
# 0007. 多租户数据隔离候选：混合架构 vs 独立数据库

* 状态：提议 / 待证据
* 日期：2026-04-12
* 决策者：业务、平台 SRE、安全、合规与数据团队代表
* 关联：ADR-0003, ADR-0005, ADR-0011

## 背景与问题陈述

平台当前采用共享数据库、共享 Schema 与 `tenant_id`。单租户插件故障曾耗尽共享连接池；误删数据也无法快速按租户恢复。业务要求改善故障隔离和恢复粒度，同时 TCO 约束不允许未经验证地迁移全部租户。

## 候选短名单

- A：所有租户独立数据库。
- D：VIP 租户独立数据库，其余租户共享 Schema + `tenant_id`。

B/C 作为已分析基线保留在决策矩阵中；短名单不等于已经证明 D 最优。

## 当前决定

不直接接受 A 或 D 的全量目标架构。批准 D 的小范围、可回退试点：选择少量代表性 VIP 租户，建立租户路由、数据迁移、PITR、权限和资源隔离能力；试点期间不得让双写成为长期事实源。

## 必须补充的证据

- 租户搬迁的全量快照、增量追平、校验、写栅栏、路由切换与回退演练；
- PITR 恢复时间、恢复完整性和单租户删除场景；
- 跨租户越权负测、缓存/对象存储/后台任务隔离测试；
- A/D 在不同租户数量、负载偏斜、故障和人力假设下的 TCO 范围分析；
- 噪点租户故障注入以及其他租户 SLO 影响。

## 后果与复审

试点增加路由、备份和运维复杂度，但购买了真实迁移信息。若隔离收益不能覆盖持有成本，停止并回退；若证据证明 D 在合规、恢复和单位成本上满足目标，新增 ADR 将状态改为“已接受”，并规定推广边界。若外部合规或灾备期限迫使提前承诺，单独记录该约束与残余风险。
## 结果与验证边界

物理隔离只能合理预期降低 VIP 之间的数据库争用、缩小部分共享数据库故障的影响范围，并改善单租户恢复粒度；不能直接推出整个平台可用性从 99.9% 升到 99.95%，因为普通租户、应用、网络、支付和其他依赖仍可能失败。99.95% 保留为待验证业务 SLO，分别验证：噪点租户场景下其他租户的成功率/P99、VIP 的 RTO/RPO、权限与删除恢复、以及该类数据库故障对整体错误预算的贡献。

```

### 5.7 实物期权视角下的"是否今年就上多活"

业务方询问：是否今年就上多区域多活 (active-active)？

实物期权分析必须计算两边的成本与证据：

- 方案 A：维持单写区域 + 跨区灾备。投资不为 0，包含复制、恢复演练、合规、容量和维护未来迁移接缝；只有明确最晚决策时点、行权步骤和持续演练，才真正保留升级选择权。
- 方案 B：建设多区域主动服务。增加冲突/写入归属、故障检测、外部副作用和运营成本；99.99% 只能是待验证 SLO，不是“多活自动获得”的属性。

比较期权持有成本、延迟决策造成的业务损失、期间可获得的信息、未来行权成本、到期/失效条件及可用性证据。当前案例可先做 A，是因为区域需求和合规尚未确定，且恢复演练能购买相关信息；若合同截止日已锁定或延迟损失更高，则应更早承诺。

### 6.1 需求识别清单

- [ ] 风险条目是否有可能性证据或明确标记为未知、影响等级/尺度、触发条件、缓解与应急计划？只有具备校准历史或来源时才给出概率区间，并注明估计方法。

### 6.2 ATAM 评审清单

- [ ] 评审前是否已构造效用树并记录参与者、评级依据和异议？
- [ ] 是否覆盖高重要性且高风险/未知风险的叶场景，并在新投票排序后重新分析？
- [ ] 系统寻找并记录敏感点与权衡点；若结果为零，应说明分析范围、模型/证据限制，而不是为了凑数列出虚假项。
- [ ] 每个风险点是否有对应缓解行动项？非风险点是否同时记录为“好消息”和证明来源？
- [ ] 评审纪要是否归档到版本控制系统？
- [ ] 候选覆盖“不改变现状”和真实可行选择，而非为凑数量制造假候选。
- [ ] 比较方法的可补偿、独立性等假设是否成立？
- [ ] 定量评分有锚点、证据、置信度与敏感性分析？
- [ ] ADR 的后果包含可观察结果、负面代价和复审触发器？
- [ ] 验证方法针对关键未知数选择：PoC、迁移/恢复演练、合同或合规审查、历史数据、影子流量等。

### 6.4 技术债清单

- [ ] 债务条目写出当前收益或形成原因、未来额外成本、风险与责任人？
- [ ] 指标能显示债务成本是否增长、下降或因退役消失？
- [ ] 偿还、接受或删除功能的触发条件和计划明确？

### 6.5 实物期权清单

- [ ] 到期前能否获得与决定相关的新信息？
- [ ] 持有成本和延迟损失是否低于学习与灵活性价值？
- [ ] 是否有明确行权路径、最晚决策时点与退出条件？若没有，所谓“保留期权”只是拖延。

### 练习 4：技术债登记与偿还计划（进阶）

## 9 本章小结

- **需求侧**：把模糊的业务目标分解为效用树，把每个 H 优先级场景写成六要素；约束、假设、风险必须显式分离。
- **决策侧**：用决策矩阵暴露偏好和敏感性，用 ADR 保留已接受决定的历史，用实物期权视角评估选择权；这些工具都不能替代证据。
- **治理侧**：登记技术债及其额外成本，以组织自定义的风险/可逆性分级选择评审强度，用 ATAM 场景分析暴露敏感点、权衡点和风险。

> 架构师的工作不是"做决定"，而是"让决定可被理解、被讨论、被追溯、被未来的人复盘"。
