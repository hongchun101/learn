# 第 9 章　架构师面试、求职准备与职业发展

> 本章面向希望从高级工程师成长为架构师、目标 P7～P8（对应年薪 50K×12=60 万起步，至 P8/P9 高阶可达 100 万+）的读者。架构师职位的市场要求、面试形式、考核重点和工程师职位有本质差异：**它考察的是判断力、决策能力、跨团队影响力和对不确定性的处理方式，而不是某个具体技术的熟练度。**
>
> 文中保留多租户电商平台（MECP）作为贯穿案例，必要时引入"金融支付清算"和"短视频推荐"两个对照行业。

---

## 9.0 学习目标

完成本章后，读者应能够：

1. 区分架构师职位的市场分级（P6/P7/P8/P9）与对应的能力、影响力半径和薪酬区间。
2. 构建一份突出"判断力 + 决策证据 + 系统性影响"的架构师简历，而不是把工程师简历简单改名。
3. 系统准备技术架构面试（系统设计、领域建模、故障分析）和行为面试（决策过程、冲突处理、组织影响）。
4. 在限定时间内主持一场白板系统设计面试，输出可讨论的方案、权衡和验证。
5. 掌握薪酬谈判的方法论，包括 base、股票、签字费、绩效和长期激励。
6. 设计 6～12 个月的求职准备计划，按周分配学习、刷题、模拟面试与作品集产出。

## 9.1 架构师职位的市场分级

### 9.1.1 互联网大厂职级与能力对应

不同公司职级体系不同（阿里 P 序列、字节 2-1～3-2、腾讯 T 序列、美团 L 序列、华为 19～22 级、外企 IC1～IC6、创业公司 Staff+/Principal/Architect/Chief Architect）。但市场对"架构师"的能力要求有共同特征：

| 级别 | 中文常见称谓 | 经验区间 | 能力特征 | 影响力半径 | 国内一线薪酬参考（月薪/总包） |
| --- | --- | --- | --- | --- | --- |
| P6 / Senior Engineer | 高级工程师 | 3–5 年 | 独立交付复杂模块；能在指导下做架构提案 | 单团队 | 25K–50K 月薪，40–80 万年包 |
| P7 / Expert / Tech Lead | 技术专家 / 架构师 | 5–8 年 | 独立负责业务能力端到端；可拆分多团队工作 | 跨团队 2–3 个 | 40K–70K 月薪，60–120 万年包 |
| P8 / Senior Expert / Staff | 高级技术专家 / 资深架构师 | 7–12 年 | 主导跨业务架构；可影响公司技术战略 | 跨业务线 1–N 个 | 60K–100K 月薪，100–200 万年包 |
| P9 / Principal / Fellow | 资深专家 / 首席架构师 | 10+ 年 | 制定技术战略；定义行业最佳实践 | 全公司 / 行业 | 80K–150K+ 月薪，200–500 万年包 |
| P10+ / VP / CTO | 副总裁 / CTO | 15+ 年 | 业务 × 技术 × 组织的复合决策 | 公司 + 生态 | 100K–300K+ 月薪，500 万+ 年包（含股权） |

> **重要说明。** 上表是 2024–2025 年国内一线互联网公司的常见区间，**不是统一标准**。外企（Google L5/L6、Meta E5/E6、Amazon SDE II/III、Microsoft 61–63）有自己的级别和定级逻辑；金融、运营商、国企、创业公司差异更大。"目标 50K 薪资"在不同公司可以对应 P7、Staff Engineer 或 Senior Architect，能力要求不直接互译。面试准备应聚焦能力证据而非职级对标。

### 9.1.2 架构师职位的核心能力差异

相比高级工程师，架构师职位在以下维度有显著差异：

| 维度 | 高级工程师 | 架构师 |
| --- | --- | --- |
| 关注点 | 写正确的代码、满足功能需求 | 选对的方向、承担可解释的责任 |
| 决策范围 | 模块/服务内 | 跨服务/跨团队/跨业务线 |
| 时间视界 | 季度/半年 | 1–3 年甚至更长 |
| 证据要求 | 单元测试、压测数据 | 决策 ADR、运行指标、复盘报告 |
| 失败承担 | 局部修复 | 跨团队影响、重新设计、回滚方案 |
| 沟通对象 | 团队内同级与直属 | 跨团队、技术总监、产品 VP、CTO、客户高管 |
| 成功标志 | 功能上线、无重大事故 | 系统可持续演化、关键 SLO 持续达标、人才被培养出来 |

### 9.1.3 50K 月薪架构师的能力门槛（市场调研视角）

为给出**可观察的"50K 能力门槛"**，综合一线大厂 P7 面试反馈、招聘 JD 和资深面试官的共识：

1. **业务追踪性**：能独立把"业务结果"翻译为"系统质量属性场景"，并能解释每个技术决策如何服务于业务。
2. **系统设计能力**：在 45–60 分钟白板时间内独立完成一个陌生领域（如"设计一个外卖订单调度系统"）的多视角架构，包括上下文、容量、关键路径、权衡、风险。
3. **深度 + 广度**：在自己最擅长的领域（分布式存储、消息、数据库、推荐、风控、调度等之一）有可验证的工程深度；同时在 5–8 个相邻领域能讨论到机制级（不是只懂名词）。
4. **故障分析能力**：给定一个生产事故描述（监控告警、日志、变更记录），能在 30 分钟内定位到根因、影响范围、临时止血和长期修复。
5. **决策能力**：面对多个有真实权衡的方案，能在 5–10 分钟内给出推荐、说明假设、写出 ADR 草稿，并能识别被反对方案中的合理点。
6. **组织影响**：在真实项目中跨团队推动过架构落地，不是只在文档里写"建议使用 X"。
7. **学习与反馈**：能诚实说出自己过去决策的失败、归因到模型/沟通/执行而非外部原因，并提出改进。

**反例（50K 能力未达标信号）**：

- 写 10 年 CRUD，从未主导过跨服务/跨团队决策；
- 分布式知识停留在"了解 CAP / 听过 Saga"层面，未做过幂等实验、未做故障注入；
- 简历全是技术名词（"使用 Kafka/RocketMQ/Redis Cluster/DDD"），没有决策证据（"为什么用 X / 替代方案 / 退出条件"）；
- 面试时遇到反例就强辩，不知道"在什么条件下当前决策不成立"。

## 9.2 架构师简历

### 9.2.1 简历的"反简历驱动"原则

README 已经强调："不教背 30 个架构模式后去面试。"简历也遵循同一原则：

> **简历不是技术名词清单，而是"决策证据集"。** 招聘方看简历的目的是：在面试前形成关于"这个人是否在 1–2 个跨团队/跨服务领域做过可验证的架构判断"的可信假设。

### 9.2.2 架构师简历结构（与传统工程师简历的差异）

| 部分 | 传统工程师简历 | 架构师简历（推荐） |
| --- | --- | --- |
| 个人信息 | 姓名/联系方式/教育 | 同上，可加 GitHub/技术博客/技术雷达订阅 |
| 能力摘要 | 3–5 行技术栈 | 2–3 段：业务能力 + 技术深度 + 组织影响 |
| 项目经验 | 项目名 + 角色 + 技术栈 + 关键功能 | 业务目标 → 关键决策（ADR） → 证据（指标/事故/复盘） → 迁移/退出 |
| 技术深度 | 多技术栈并列 | 1–2 个深度领域 + 5–8 个相邻领域 |
| 影响力 | "带过 N 个人" | 跨团队评审数、ADR 数量、故障复盘主导、培训/分享、技术雷达/规范制定 |
| 教育 | 学位/学校/课程 | 同上，可加持续教育（MOOC、会议、内部培训） |

### 9.2.3 优秀架构师简历样例（节选）

> 下面的样例节选用于说明结构，不指向任何真实个人。

**摘要段**：

- 5 年后端 + 3 年架构经验，专注订单、库存、支付链路的可演化架构设计。
- 主导从模块化单体到按业务能力分阶段拆分的演进，3 年内保持月度可用性 ≥ 99.95%。
- 建立团队级 ADR、风险登记、容量评审机制，使交付前置时间缩短 40%。

**项目经验样例 A：MECP 多租户电商平台数据隔离演进**

- 业务背景：从 200 租户增至 1,800 租户，原共享数据库出现噪点租户拖垮全局 P99 的事故，单租户数据误删无法独立恢复。
- 关键决策（ADR-014 主导）：从 `Shared DB + tenant_id` 演进为"VIP 租户独立库 + 长尾租户共享 schema"混合模式。
- 证据：独立库覆盖 3% 租户但贡献 35% 收入，事故爆炸半径从全平台降至单租户；备份恢复 RTO 从 4 小时降至 30 分钟。
- 退出条件：租户数 > 5,000 或 VIP 租户 > 50 个，重新评估独立集群方案；ADR 包含迁移脚本、回滚预案和验证用例。
- 不做的：未选择"每租户一库"——TCO 与运维对象数评估显示不可持续。

**项目经验样例 B：支付链路幂等性改造**

- 业务背景：支付回调重复导致月均 0.7% 重复扣款（绝对值 ~2,100 单），财务对账成本激增。
- 关键决策（ADR-021 主导）：引入"业务幂等键 + Outbox + 异步对账"三件套，幂等键 = `(tenant_id, channel, out_trade_no)`。
- 证据：上线后 6 个月内重复扣款已知事件数为 0；对账偏差从 1.2% 降至 0.05%。
- 跨团队影响：与 3 个支付渠道、2 个财务系统、1 个客服系统建立契约；牵头梳理所有回调入口的幂等策略。
- 失败案例：在 3.0 版本曾因幂等表 TTL 短于渠道回调重试窗口，引入 0.1% 漏单；3.1 版本延长 TTL 并增加渠道侧回放，事件归零。

### 9.2.4 简历自查清单

- [ ] 每段经历都包含**业务目标、关键决策、证据、退出条件**四要素？
- [ ] 技术名词只在"为什么这样选"的上下文中出现，没有孤立列技术栈？
- [ ] 至少 2 段经历包含**失败与复盘**，而不是只展示成功？
- [ ] 量化指标（延迟、可用性、成本、交付时间、租户数）出现 ≥ 5 次？
- [ ] 影响力证据（跨团队评审、ADR 数量、规范制定、团队规模、招聘）清晰？
- [ ] 没有"精通 XXX"等不可证伪的自评，或有"精通"必须附证据？
- [ ] 链接到博客/演讲/ADR/开源贡献可被点开验证？
- [ ] 长度控制：1 页（10 年内经验）或 2 页（资深架构师），不超 3 页？

## 9.3 技术架构面试

### 9.3.1 面试形式与时间分配

主流大厂架构师/资深技术专家面试通常包含：

| 环节 | 时长 | 考察能力 | 评分维度 |
| --- | --- | --- | --- |
| 自我介绍 | 5 分钟 | 结构化表达、突出决策 | 信息密度、证据导向 |
| 简历深挖 | 30–45 分钟 | 真实项目经验、决策过程 | STAR 完整性、诚实度、深度 |
| 系统设计 | 45–60 分钟 | 多视角架构、容量、权衡 | 范围界定、关键路径、权衡、验证 |
| 编码/算法 | 30–60 分钟 | 工程基础 | 看岗位要求（架构师常免算法） |
| 行为面试 | 30 分钟 | 冲突处理、跨团队影响、失败归因 | 反思深度、改进行动、组织意识 |
| 反问环节 | 5–10 分钟 | 业务理解、自我定位 | 提问质量、契合度判断 |

### 9.3.2 系统设计面试方法论：RADIO 框架

把系统设计面试拆为 5 阶段：

1. **R — Requirements Clarification（澄清需求）**：5–10 分钟。先不要画图。

   询问：
   - 用户量级、QPS、峰值、地理分布；
   - 核心功能（必做）和非目标（明确不做）；
   - 关键质量场景：可用性、延迟、扩展、合规、隔离；
   - 现有约束：团队规模、技术栈、遗留系统、预算；
   - 利益相关者：谁是为之设计？冲突目标如何排序？

   范例："设计一个外卖订单调度系统。"
   > - 日单量？峰值？城市？是否跨城？
   > - 商家自配送 vs 平台调度？
   > - 实时性要求（秒级/分钟级）？
   > - 骑手实时位置更新频率？终端数？
   > - 骑手数量？高并发峰值（午餐/晚餐）？
   > - 失败是否可降级为人工派单？

2. **A — Architecture（高层架构）**：10–15 分钟。

   - 上下文图：用户、商家、骑手、客服、外部系统（地图、风控、支付）。
   - 关键服务：订单、调度、骑手、商家、风控、推送。
   - 数据面 vs 控制面分离；同步 vs 异步路径。
   - 关键状态和权威写入者。

3. **D — Data Model & Deep Dive（数据模型与深入）**：10–15 分钟。

   - 核心实体：订单、骑手位置、商家、调度任务、轨迹。
   - 分片键、索引、一致性要求。
   - 关键链路深入：派单算法（贪心 / 优化 / 机器学习）、位置上报频率与合并、骑手状态机。
   - 容量估算：日订单、峰值 TPS、骑手位置 QPS、轨迹存储量。

4. **I — Identify Tradeoffs（识别权衡）**：5–10 分钟。

   - 实时性 vs 公平性 vs 成本；
   - 中心化调度 vs 分布式匹配；
   - 同步分配 vs 异步撮合；
   - 一致性 vs 可用性：订单状态、骑手位置、支付。

5. **O — Operations & Optimization（运维与优化）**：5–10 分钟。

   - 监控与告警：SLO、关键 trace、错误预算。
   - 故障与降级：派单超时怎么办？骑手位置丢失如何补偿？
   - 演进：先做什么？什么是 v1 不做的？

**反例（避免）**：

- 不澄清需求就画图 → 30 分钟后发现题目理解错误。
- 把所有服务都画上"微服务"标签 → 团队规模和当前阶段不支持。
- 谈优化算法不讨论数据规模和冷启动 → 缺乏工程基础。
- 不提失败和降级 → 风险评估能力不足。
- 用"业界标准做法"代替解释 → 没有真正的判断。

### 9.3.3 常见系统设计题与答题要点

下列题目在 P7+ 面试中频繁出现，**重点不是"标准答案"，而是"推理过程"**：

| 题目 | 关键考察 | 答题要点 |
| --- | --- | --- |
| 设计短链生成服务 | 容量、存储、读写比、缓存 | 容量估算（千亿级短链 → 多级缓存 + 预生成 + ID 发号器）、冲突处理（base62 + 分布式 ID）、跳转链路与风控 |
| 设计微信朋友圈 feed | 读写比、推拉结合、关注图、容量 | 写扩散 vs 读扩散权衡、明星用户优化、Feed 时间线生成（拉模型 + 异步合并）、冷热数据分层 |
| 设计外卖派单系统 | 实时性、调度算法、骑手状态、轨迹 | 派单策略（实时撮合 vs 批量分配）、骑手位置合并（同基站/网格）、订单状态机、超时与补偿 |
| 设计秒杀系统 | 流量削峰、热点、库存、超卖 | 入口限流 + 排队 + 资格校验 + 库存分桶 + 异步下单、库存原子扣减、防超卖与可售承诺分离、验证码与风控 |
| 设计消息推送系统 | 多通道、送达保证、量级、延迟分级 | 通道分级（实时/营销/系统）、送达重试策略、设备路由、长连接管理、点击/到达回执、限流与退避 |
| 设计分布式限流服务 | 一致性、性能、降级 | 中心化（Redis 令牌桶）vs 分布式（每节点本地 + 协调）、配置热更新、限流维度（用户/IP/租户/API）、降级策略 |
| 设计直播礼物系统 | 高并发、库存、动画、计费 | 礼物库存扣减（Redis Lua）、动画与计费分离、防作弊、对账、热门礼物 CDN |
| 设计搜索引擎 | 倒排索引、相关性、容量、增量 | 索引构建（MapReduce/Spark）、查询链、相关性排序（BM25 + 学习排序）、增量更新、Query 理解 |
| 设计订单中台 | 多业务接入、状态机、幂等、可演化 | 状态机、幂等、Saga、Outbox、多租户、扩展点（钩子 + 策略）、可演化抽象 |
| 设计配置中心 | 一致性、灰度、推送量、回滚 | 配置分层（环境/集群/租户）、推送通道（长连接 + 轮询）、灰度与回滚、配置审计 |
| 设计监控告警平台 | 高基数、聚合、告警降噪、规则引擎 | 标签索引、存储分层（原始 + 聚合）、告警路由、抑制与合并、规则评估、告警疲劳 |
| 设计跨区域灾备 | RPO/RTO、流量切换、数据复制 | 数据复制（同步/异步）、流量调度（DNS/Anycast）、脑裂处理、回切流程、演练计划 |
| 设计 AI 推荐系统 | 数据流水线、特征工程、模型服务、A/B 测试 | 离线/在线分层、特征存储、模型在线服务、A/B 流量分割、冷启动、反馈闭环、归因 |
| 设计 SaaS 多租户 | 隔离、可扩展、可配置、租户路由 | 隔离模式（共享/独立/混合）、租户上下文、可配置规则、租户级 SLA、租户迁移 |

### 9.3.4 故障分析面试方法

面试官给出事故描述（监控告警 + 日志片段 + 变更记录），考察候选人的定位能力。RADIO 故障版：

1. **R — Reproduce（复现）**：发生了什么？影响面？时间线？
2. **A — Analyze（分析）**：可能根因？信号收敛到哪？变更相关性？依赖？
3. **D — Decide（决策）**：临时止血？回滚？限流？功能开关？继续观察？
4. **I — Investigate（深入）**：5 Whys；组织/流程/技术哪个层面？
5. **O — Output（输出）**：复盘文档、长期修复、跨团队改进、度量指标。

**反例**：

- 立刻跳到"重启/扩容" → 没分析就动手。
- 把责任归咎于具体人 → 缺乏系统性思维。
- 不写 ADR/复盘 → 不积累组织知识。
- 长期修复只有"加监控/加告警" → 没触及根因。

### 9.3.5 行为面试常见题与准备

| 题目 | 评估意图 | 应包含的要素 |
| --- | --- | --- |
| 介绍你主导的最大规模架构决策 | 决策能力、影响力 | 业务背景、约束、备选、推荐、证据、结果、退出条件 |
| 你做过最失败的技术决策？ | 反思能力、诚实度 | 具体失败、归因（模型/沟通/执行/外部）、学到什么、改进行动 |
| 跨团队冲突如何处理 | 影响力、协商能力 | 冲突焦点、对方利益、解决方案、长期关系、验证 |
| 团队不认同你的方案怎么办 | 领导力、谦逊 | 倾听过程、是否被说服、如何折中、复盘 |
| 推动过最大的变革 | 推动力、沟通 | 变革内容、阻力、影响者、节奏、阶段性成果 |
| 如何培养架构师 | 领导力、影响力可持续性 | 路径设计、刻意练习、双环学习、机会赋予 |
| 你的技术雷达 / 反对盲目引入 | 思维独立性 | 当前评估/采用/暂缓的具体技术、证据、反例 |

**STAR-L 框架**（在 STAR 基础上增加 Learning）：

- **S**ituation：场景、约束、利益相关者；
- **T**ask：你的责任和目标；
- **A**ction：具体动作（不是团队动作，要"你"做了什么）；
- **R**esult：可量化结果（指标、范围、影响）；
- **L**earning：学到了什么、改进了什么模型/原则、避免什么。

### 9.4.2 系统设计高频题练习要点

每套题按 RADIO 框架练习：

1. **不参考任何资料**先做一次（45–60 分钟），记录卡点。
2. 对照参考答案，找差距：问题澄清、关键路径、容量、权衡、验证。
3. **第 2 轮**重做同一题，要求加入"被面试官追问"3 个问题。
4. **第 3 轮**用 PPT 或文档写出 1 页 ADR，提交同伴评审。
5. 把题解整理到个人 wiki，每月回顾一次。

### 9.4.3 持续的作品集

招聘方无法在 1–2 小时面试中验证能力，需要通过作品集建立可信度：

- **个人 ADR 库**（GitHub）：对每个有意义的决策写 ADR，可公开部分脱敏版本。
- **技术博客 / 公众号**：每年 6–12 篇深度文章（不是知识点搬运，而是"我如何解决 X"）。
- **技术雷达 / 选型记录**：对 10–20 个主流技术有明确的"评估/试验/采用/暂缓"立场。
- **开源贡献**：1–2 个长期维护的仓库（哪怕是工具类），展示工程纪律。
- **演讲 / 培训**：在公司内或行业会议做 3–5 次分享的录像/PPT。
- **故障复盘**：把可公开的事故写成结构化复盘，展示反思深度。

## 9.5 薪酬谈判

### 9.5.1 总包结构

国内一线互联网 P7+ 架构师/资深技术专家的总包（Annual Compensation）通常包括：

| 部分 | 含义 | 谈判空间 |
| --- | --- | --- |
| 月薪 base | 12 个月基本工资 | 较小（HR 有带宽） |
| 绩效奖金 | 季度/年度绩效，通常 0–6 个月 | 中等 |
| 股票 / RSU | 限制性股票单位，分 4 年归属 | 大（核心谈判点） |
| 签字费（sign-on） | 入职一次性奖金 | 中等（部分公司给） |
| 期权（创业公司） | 公司股权，分 4 年归属 | 极大，但流动性差 |
| 福利 | 保险、补贴、餐补 | 较小 |
| 异地搬迁补贴 | 跨城市入职 | 中等 |

### 9.5.2 谈判方法论

**原则 1：信息先于出价。**

- 通过猎头、朋友、脉脉、Levels.fyi（外企）、Glassdoor（外企）等渠道调研同岗位 P7 的市场区间（base、股票、签字费）。
- 区分"现金等价"和"股权等价"：4 年归属的 RSU 不是 4×annual grant，而是 `grant_value × 4 / 4` 视为年化，归属时按现价计税。

**原则 2：先谈包，再拆。**

- 谈判总包数字，**不要在月薪层面陷入零和**。
- 举例：候选人要求"月薪 +5K" vs HR 只能给"+3K"，但可给"签字费 30K + RSU +5K" → 总包一致，月薪差距 2K 是次要。

**原则 3：建立锚点。**

- 准备 2–3 个对比 offer 或市场数据；
- 不要开过高（被认为不专业）或过低（损失价值）；
- 锚点 = "我对市场的调研是 X，结合我的能力 + 现有 offer Y，希望落在 Z"。

**原则 4：决策清单。**

在谈判前明确：

- 最低可接受值（walk-away 数字）；
- 优先级排序（base > 股票 > 签字费，或反之）；
- 不可妥协项（如不接受 4 年归属 vs 3 年归属的差异）；
- 时间线（HR 通常给 24–48 小时决策，不要拖太久但也不要被"今天必须答复"绑架）。

**原则 5：把 offer 落到纸面。**

- 邮件确认口头 offer 的所有数字、归属曲线、签字费发放时间、奖金条款；
- 警惕"股票按现价"，因为 offer 时股价和归属时股价可能差很大；
- 询问"如果入职时股价跌 30%，是否有保护条款"。

### 9.5.3 谈判中常见误区

| 误区 | 后果 | 修正 |
| --- | --- | --- |
| 直接报"期望 50K" | HR 锁定上限；丧失谈判空间 | 报区间（45–55K），不轻易让步上限 |
| 谎报现有 offer | 背景调查戳穿 | 不要撒谎；可淡化或聚焦市场数据 |
| 反复讨价还价 | 显得不专业；HR 反感 | 2–3 轮足够；用数据和事实而非情绪 |
| 忽略股票和签字费 | 损失 10–30% 总包 | 拆解后全包视角比较 |
| 接受口头 offer 不落纸面 | 入职后变更无法追溯 | 邮件确认所有细节 |
| 离职前不与现公司谈 | 错失现公司 match | 投递前先内部争取 |

### 9.5.4 反歧视与公平

薪酬谈判不应依赖个人议价能力差异。架构师级别的薪酬在大多数成熟公司是按级别定带的，HR 通常不能为同一级别的人开出显著不同的 base。**重点不是压榨谈判空间，而是争取合理的总包、归属曲线和签字费，并保持职业形象。**

## 9.6 求职渠道与雇主选择

### 9.6.1 渠道

| 渠道 | 适用 | 注意 |
| --- | --- | --- |
| 猎头 | P7+ 主流渠道 | 选 1–2 个长期合作的猎头，避免广撒网 |
| 内推 | 高成功率的渠道 | 找前同事/同行；写明"已确认对方愿意" |
| 公司官网/招聘平台 | 主动投递 | 适合"广撒网"早期 |
| 脉脉 / LinkedIn | 拓展机会 | 维护好 profile；被猎头主动找 |
| 技术会议 / Meetup | 弱关系建立 | 长线投资，不直接求职 |
| 技术博客 / GitHub | 被动机会 | 长期建设，可能被"自荐" |

### 9.6.2 雇主选择框架

不只是看月薪和股票。架构师选 offer 时应评估：

| 维度 | 评估问题 |
| --- | --- |
| 业务 | 业务在增长吗？商业模式可持续吗？我会为之骄傲吗？ |
| 技术 | 技术栈匹配吗？有挑战吗？能持续学习吗？ |
| 组织 | 团队健康度？管理风格？跨团队协作？CTO 能力？ |
| 薪酬 | 短期 + 长期（股票归属、晋升）？ |
| 地理 | 城市、生活成本、通勤？远程/混合？ |
| 风险 | 公司财务健康度？近期裁员？产品竞争？ |
| 成长 | 1–3 年后我能从这份工作中学到什么、成为什么？ |

> **反例**："哪个给钱多去哪个。"—— 1–2 年后能力停滞，3 年后被淘汰，损失远大于短期高 base。

### 9.6.3 求职的时机

- **离职前 3–6 个月**开始准备，不要"裸辞"；
- **拿到 offer 后再离职**，不要"先辞后找"（除非有强储蓄或被动收入）；
- **行业旺季**：互联网春招 3–4 月、秋招 9–10 月；社招常年开放但岗位质量随业务周期波动；
- **公司财报季前后**：业务向好时招人多，预算宽；下行时收紧。

## 9.7 面试中的反偏见与公平

架构师面试中存在**已知偏差**：对"非顶尖学校"、女性候选人、年龄较大候选人、回归职场的候选人可能存在隐性偏见。应对策略：

1. **量化成果**：用数字、ADR 链接、运行指标说话，比"我做的系统很好"更不易被偏见影响。
2. **结构化准备**：用 STAR-L 框架、ADR 模板，让面试官按相同维度评估。
3. **盟友网络**：在目标公司找内部人了解面试流程、风格和评估标准。
4. **反问环节**：询问团队的多元化和包容性政策、晋升机制，判断组织文化。
5. **记录过程**：面试后立即记录每轮问题、面试官反馈，便于复盘和应对后续轮次。
6. **勇于反馈**：如遇明显不当问题或评价，可在 HR 反馈环节诚实表达。

## 9.8 模拟面试样例：设计一个外卖订单调度系统

下面给出一个 60 分钟白板系统设计面试的"理想表现"流程，作为准备参考。**真实面试中不必按此逐字执行，但每个阶段都应涉及。**

### 阶段 1：澄清需求（5–10 分钟）

**候选**："我需要先确认一些关键参数，否则方案可能与业务不匹配。"

- 日单量？峰值？北京/上海一类城市还是全国？
- 商家规模？是否有自配送 vs 平台调度比例？
- 派单实时性要求（秒级/分钟级）？还是"承诺 30 分钟内必接单"？
- 骑手终端数量？位置上报频率（5s？30s？）
- 关键失败模式：派单超时？骑手拒单？商家出餐延迟？
- 不做：跨城调度、众包骑手、动态定价（如果业务未确定）。

**面试官**："北京上海一类城市，日单 200 万单，午餐晚餐 8 倍峰谷，平台调度为主，少量众包；要求 30 秒内接单。"

### 阶段 2：高层架构（10–15 分钟）

- **上下文图**：用户/商家/骑手 + 平台订单/调度/推送/地图/风控。
- **核心服务**：订单、调度、骑手、商家、风控、推送、轨迹。
- **数据面 vs 控制面**：订单流转（数据面，60+ 秒延迟敏感）；调度决策（控制面，秒级）。
- **同步 vs 异步**：订单创建/支付为同步；调度计算、风控为异步消息驱动。

**画图**：粗略的方块图，5–6 个核心服务 + 3 个外部依赖。

### 阶段 3：数据模型与深入（10–15 分钟）

**核心实体**：

- `Order(id, user_id, merchant_id, status, items[], total, created_at, dispatch_deadline)`
- `Rider(id, status, location, current_order_id, working_hours)`
- `DispatchTask(id, order_id, candidate_riders[], score, status, created_at)`
- `RiderLocationHistory(rider_id, lng, lat, ts, order_id)`

**关键深入**：

- **派单算法**：核心是"在 200 ms 内从 200 个候选骑手中选最优"。简化方案 = "网格 + 实时距离 + 骑手当前任务量 + 商家出餐时间预估"。
- **位置合并**：骑手 5s 上报一次，单骑手日 17,000 条，10 万骑手 = 17 亿/天；按网格 + 时间窗口合并 + 抽样保留。
- **容量估算**：200 万单 / 8 小时 = 25,000 单/分钟 = 416 单/秒；10 万骑手位置 QPS ≈ 20,000；订单/调度 TPS ≈ 500–1,000。
- **状态机**：订单、骑手、调度任务各自有状态机；非法迁移拒绝。

### 阶段 4：识别权衡（5–10 分钟）

- **中心化调度 vs 分布式匹配**：中心化（全平台最优但有单点）；分布式（局部最优但故障域小）。**建议**："订单撮合中心化、地理分片"。
- **同步派单 vs 异步撮合**：同步（用户感知快但耦合）；异步（解耦但用户等）。**建议**："同步派单 + 异步通知骑手"。
- **一致性 vs 可用性**：骑手位置可以最终一致；订单状态需要强一致；支付必须强一致。
- **公平 vs 效率**：算法是否要保证骑手接单公平？商家优先级？需要 ADR 记录。

### 阶段 5：运维与演进（5–10 分钟）

- **SLO**：派单 P99 ≤ 5 秒、接单成功率 95%、订单成功率 99.9%。
- **降级**：调度服务过载 → 切到"先到先得 + 人工"; 地图 API 不可用 → 用历史网格距离; 位置上报丢包 → 用最后已知位置 + 速度推算。
- **监控**：派单耗时分布、骑手位置丢包率、订单状态机非法迁移、调度公平性指标。
- **演进**：v1 = 中心化派单 + 简单规则；v2 = 引入学习排序；v3 = 网格化分片；v4 = 跨城调度。
- **不做**：不在 v1 引入深度学习模型；不在 v1 做跨城。

### 反问环节

- 当前团队规模和阶段？现有派单系统的最大痛点？
- 团队对算法 vs 工程投入的偏好？
- 公司对架构师角色的期望（深度还是广度）？

- [ ] 量化指标 ≥ 5 个？
- [ ] 作品集（ADR/博客/开源）可被验证？

### 系统设计能力

- [ ] 12+ 套高频题完成 RADIO 框架练习？

- [ ] 至少 5 套题包含权衡讨论和演进路径？

- [ ] 5 段 STAR-L 故事（最大决策、最大失败、跨团队、推动变革、培养他人）？

- [ ] 反思能归因到模型/沟通/执行而非外部因素？

### 谈判与选择

- [ ] 调研过同岗位市场区间？
- [ ] 明确自己的最低可接受值和优先级？
- [ ] 雇主选择不只看月薪，有 5 维以上评估？

## 9.10 练习

1. **能力矩阵自评**：用第 1 章的能力矩阵 8 域框架，给每个域写一段 200 字以内的"最有力证据 + 最失败证据"。计算加权差距 $G$ 和瓶颈 $B$。
2. **简历重构**：选取你过去 3 年最重要的 1 段经历，按 9.2.3 样例结构重写，重点突出决策证据和量化结果。
3. **系统设计高频题 × 4**：短链生成、朋友圈 feed、秒杀、消息推送，每题按 RADIO 框架独立做一次，找同伴评审。
4. **行为面试 5 段 STAR-L 故事**：每个故事不超过 3 分钟陈述，能回答追问。
5. **薪酬调研**：通过 3 个渠道（猎头/朋友/公开数据）调研 3 家目标公司 P7 架构师的总包区间。
6. **模拟面试 3 次**：同伴或付费教练，覆盖系统设计、行为面试、简历深挖。
7. **失败案例 ADR**：选一个你参与过的失败决策，写一份 ADR，包含"决策、证据、退出条件、复盘"，可用于面试回答"最大失败"。
8. **雇主对比表**：列 3 个候选 offer，用 9.6.2 框架做 7 维度对比，不只看薪酬。

## 9.11 常见误区

| 误区 | 真实情况 |
| --- | --- |
| "架构师面试就是画图和讲技术" | 真实考察 60% 是判断力（决策证据、权衡、反思），30% 是技术广度，10% 是工程基础 |
| "大厂给的钱最多" | 创业公司可能给期权 + 高 base；外企 base 高但股票波动大；金融科技合规要求高但稳定 |
| "刷算法题就够了" | 架构师面试常免算法；准备错方向浪费时间 |
| "简历写满技术栈最安全" | 招聘方认为"什么都懂 ≈ 什么都不深"；应突出 1–2 个深度领域 |
| "面试时我应该把方案讲完美" | 面试官更想看到"我如何推理、识别未知、考虑反例"；承认"这块我不确定"反而加分 |
| "架构师一定要有名校背景" | 行业头部公司越来越多 P7+ 来自非顶尖学校；能力证据可补足背景劣势 |
| "跳槽越频繁工资涨得越快" | 频繁跳槽（< 2 年）会被标记为"不稳定"；架构师更看重项目深度 |
| "50K 是固定目标" | 不同城市、不同行业差异巨大；目标应按能力 + 城市 + 公司 + 阶段综合定 |

## 9.12 本章小结

- 架构师职位的核心考察是**判断力、决策证据、组织影响和反思能力**，不是技术名词数量。
- 简历的"决策证据化"和"系统性影响"是 P7+ 候选人与 P6 候选人的核心差异。
- 系统设计面试用 RADIO 框架（澄清需求 → 高层架构 → 数据与深入 → 权衡 → 运维）准备，每套高频题独立练习 3 轮。
- 行为面试用 STAR-L（情境/任务/行动/结果/学习）准备，诚实呈现失败与归因。
- 薪酬谈判的锚点是"市场数据 + 多 offer 竞争 + 总包视角"，不是"我想要 X"。
- 雇主选择不只是看月薪，业务、技术、组织、成长同样重要。
- 求职是长期建设：作品集、博客、ADR 库、技术雷达的持续投入，比"临时抱佛脚"更有效。

> **下一章视角**：第 10 章将讨论进入架构师角色后的职业发展路径、影响力构建、长期竞争力和从资深架构师到 CTO/首席架构师的演进。
