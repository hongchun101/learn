# 第 12 章：面试题库（100+ 高频题）

## 12.1 基础篇（1-30）

### Q1：ClickHouse 是什么？核心特点？

**答**：ClickHouse 是俄罗斯 Yandex 开源的**列式 OLAP 数据库**。核心特点：
- 列式存储（按列压缩、按列扫描）
- 向量化执行（SIMD）
- 真正的 MPP 架构
- 完备的 SQL 支持
- 高吞吐写入（100万+/秒）
- 查询速度快（亿级数据秒级响应）

### Q2：ClickHouse 与 MySQL 的区别？

| 维度 | MySQL | ClickHouse |
|------|-------|------------|
| 场景 | OLTP | OLAP |
| 存储 | 行存储 | 列存储 |
| 索引 | B+Tree | 稀疏索引 |
| 写入 | 实时 | 批量 |
| 查询 | 点查 | 批量扫描 |
| 事务 | ACID | 最终一致 |
| 并发 | 高 | 中 |

### Q3：列存储的优势？

**答**：
1. **I/O 减少**：只读需要的列
2. **压缩率高**：同类型数据连续存储，压缩比 5-10 倍
3. **向量化执行**：CPU 缓存友好
4. **聚合快**：聚合时可跳过非聚合列

### Q4：MergeTree 的工作原理？

**答**：
- 数据按 `ORDER BY` 排序后存储
- 写入时生成不可变 Part
- 后台异步 Merge 多个小 Part 成大 Part
- 稀疏索引（每 8192 行一个 mark）

### Q5：ORDER BY 与 PRIMARY KEY 的区别？

**答**：
- `ORDER BY`：数据物理排序键（必须）
- `PRIMARY KEY`：稀疏索引基础（去重用，默认等于 ORDER BY）
- PRIMARY KEY 必须是 ORDER BY 的前缀

### Q6：什么是稀疏索引？为什么高效？

**答**：ClickHouse 每 8192 行记录一个 mark（起始位置 + 最大值），而不是每行索引。
- 优势：索引小，可全部加载内存
- 代价：精度低，定位到 mark 后还需扫描 8192 行

### Q7：为什么 ClickHouse 不适合单行 UPDATE？

**答**：
- Part 不可变设计
- 修改需要创建新 Part
- 大量小写入会导致 Part 爆炸
- 替代方案：用 `ALTER TABLE ... UPDATE`（异步、最终一致）

### Q8：ClickHouse 索引的选择性如何？

**答**：ClickHouse 索引对**高基数列不友好**。
- 适合：低基数 + 高频过滤列
- 例：`ORDER BY (event_type, user_id)` 优于 `ORDER BY (user_id, event_type)`

### Q9：PARTITION BY 有什么作用？什么时候用？

**答**：
- 作用：按分区裁剪数据、删除/备份粒度
- 最佳实践：按时间分区（`toYYYYMM(date)`）
- 避免：高基数列分区（产生大量空分区）

### Q10：ClickHouse 的压缩算法？

**答**：
- 默认 LZ4（速度快，压缩比 5x）
- 可选 ZSTD（压缩比 8x，速度慢）
- 列级编码：Delta、DoubleDelta、Gorilla 等

### Q11：为什么 ClickHouse 写入很快？

**答**：
1. LSM 树思想：顺序写，不修改
2. 批量合并：小 Part 合并成大 Part
3. 异步刷盘：不影响查询
4. 简单事务模型：无强一致性开销

### Q12：ClickHouse 查询快的原因？

**答**：
1. 列存储：只读相关列
2. 压缩：I/O 减少
3. 向量化：CPU 缓存友好
4. 稀疏索引：快速定位
5. SIMD 指令：CPU 加速
6. 并行执行：多核利用

### Q13：ClickHouse 的不足？

**答**：
- 不支持事务（无 ACID）
- UPDATE/DELETE 性能差
- 不擅长 JOIN（特别是大表 JOIN）
- 全文检索弱
- 高并发点查性能一般

### Q14：ClickHouse 适合什么场景？

**答**：
- ✅ 用户行为分析
- ✅ 日志分析
- ✅ 时序数据
- ✅ BI 报表
- ✅ 实时大屏
- ✅ A/B 测试

### Q15：ClickHouse 不适合什么场景？

**答**：
- ❌ 强事务系统
- ❌ 高频单行更新
- ❌ 大量 JOIN 复杂事务
- ❌ 高并发点查（KV 场景）
- ❌ 强一致性要求

### Q16：MergeTree 与 ReplicatedMergeTree 区别？

**答**：
- `MergeTree`：单机版本
- `ReplicatedMergeTree`：基于 ZooKeeper 协调的副本版本，支持数据同步

### Q17：什么是 ReplacingMergeTree？

**答**：自动去重的 MergeTree，merge 时按 ORDER BY 保留版本列最大的行。
```sql
ENGINE = ReplacingMergeTree(version_column)
```

### Q18：什么是 SummingMergeTree？

**答**：merge 时自动按 ORDER BY 聚合数值列。
```sql
ENGINE = SummingMergeTree
-- 相同 (sort_key) 的行自动 sum 数值列
```

### Q19：Distributed 表的作用？

**答**：逻辑视图，路由到所有分片：
- 写入时按分片键分发
- 查询时从所有分片拉取并合并
- 不存储实际数据

### Q20：什么是 Projection？

**答**：表内嵌的物化视图（24.x+ 推荐替代物化视图）：
- 自动维护
- 自动选择最优
- 节省存储（不复制数据）

### Q21：ClickHouse 怎么处理 NULL？

**答**：
- 避免 `Nullable`（性能损耗）
- 用默认值（0、''）
- 必须用 `Nullable` 时：业务确实需要 NULL 语义

### Q22：LowCardinality 的原理？

**答**：
- 字典编码：内部存字典 + 引用
- 适合枚举类型（< 1万种值）
- 节省 5-10 倍存储
- 加速 GROUP BY

### Q23：Decimal 和 Float 选哪个？

**答**：
- 金额：必须用 Decimal（精度保证）
- 科学计算：Float
- Decimal 运算比 Float 慢，但精度可控

### Q24：ClickHouse 的内存管理？

**答**：
- `max_memory_usage`：单查询内存上限
- `max_memory_usage_for_user`：单用户
- `max_server_memory_usage`：服务总内存
- 超限会 OOM kill 或落盘

### Q25：ClickHouse 的多线程模型？

**答**：
- `max_threads`：单查询并行度
- `background_pool_size`：后台任务（merge）
- `background_schedule_pool_size`：调度
- 默认 max_threads = CPU 核心数

### Q26：ClickHouse 怎么处理大结果集？

**答**：
- `LIMIT` 限制返回行数
- `max_result_rows` 限制单次返回
- 流式接口（HTTP chunked）
- 客户端分页（offset + limit）

### Q27：ClickHouse 的 JOIN 性能如何？

**答**：
- 弱于专用 OLTP 关系数据库
- 小表 JOIN 大表：字典最优
- 大表 JOIN：算法优化（hash/parallel_hash/grace_hash）
- 分布式 JOIN：GLOBAL JOIN 优化

### Q28：什么是 PREWHERE？和 WHERE 区别？

**答**：
- WHERE：先读所有列，再过滤
- PREWHERE：先读过滤列，过滤后再补齐其他列
- 性能：PREWHERE 节省 50-90% I/O

### Q29：ClickHouse 的事务支持？

**答**：
- 不支持跨表事务
- 单 INSERT 原子
- ReplacingMergeTree 实现最终一致
- 不支持 rollback

### Q30：ClickHouse 的副本机制？

**答**：
- 基于 ZooKeeper / ClickHouse Keeper
- 写入主副本，ZK 协调同步到从副本
- 读副本需要开启（`read_from_replica`）

## 12.2 进阶篇（31-60）

### Q31：ClickHouse 为什么不用 B+Tree？

**答**：
- B+Tree 适合点查和范围查
- ClickHouse 是 OLAP 场景，扫描为主
- 稀疏索引更小、可全部缓存
- 顺序读 + 压缩 + 向量化 > B+Tree

### Q32：ClickHouse 的 Merge 过程？

**答**：
1. 后台任务调度
2. 选 N 个相邻 Part
3. 并行读取、归并排序
4. 写入新 Part
5. 替换老 Part

### Q33：Part 太多会有什么影响？

**答**：
- 查询慢（要打开很多文件）
- Merge 压力大
- 启动慢
- 解决方案：调优 `parts_to_throw_insert`、`parts_to_delay_insert`

### Q34：什么是 TTL？

**答**：Time To Live，自动过期删除或迁移数据。
```sql
TTL event_date + INTERVAL 30 DAY;  -- 30 天后删除
TTL event_date + INTERVAL 30 DAY TO VOLUME 'cold';  -- 30 天后移到冷盘
```

### Q35：ClickHouse 的冷热分层如何做？

**答**：
- 存储策略（storage_policy）配置多盘
- TTL 自动迁移
- 例如：热数据 SSD / 冷数据 S3

### Q36：Kafka 引擎如何保证不丢数据？

**答**：
- `kafka_handle_error_mode = 'stream'`：错误数据进入错误流
- `kafka_commit_on_select = 1`：读取成功才提交 offset
- 但要结合业务幂等（ReplacingMergeTree）

### Q37：Materialized View 的工作机制？

**答**：
- 写入源表时，MV 自动消费并写入目标表
- 异步（不保证强一致）
- 多个 MV 可以串联

### Q38：ClickHouse 的查询执行模型？

**答**：
- 传统 Volcano 模型：每行一次函数调用
- ClickHouse 向量化：每 block（默认 65536 行）一次调用
- 性能提升 5-10 倍

### Q39：什么是 Block？

**答**：ClickHouse 处理的最小数据单元，包含一批行（默认 65536）。所有算子按 Block 处理，block_size 越大吞吐越好，内存占用越高。

### Q40：ClickHouse 的 SAMPLE 怎么工作？

**答**：
- 创建表时指定 `SAMPLE BY` 整数列
- 查询时 `SAMPLE 0.1` 表示 10% 采样
- 基于哈希的近似查询
- 适合统计估算

### Q41：什么是 -State 函数？

**答**：聚合的中间状态，可以存储在表中，多次合并。
```sql
SELECT uniqState(user_id) FROM events;  -- 状态
SELECT uniqMerge(stored_state) FROM table;  -- 合并
```

### Q42：AggregatingMergeTree 的工作原理？

**答**：
- 存储列定义为 `AggregateFunction(func, type)`
- merge 时自动合并状态
- 查询时用 `-Merge` 函数获取最终结果

### Q43：ClickHouse 的字典（Dictionary）是什么？

**答**：
- 内存中的 KV 查找表
- 数据源可以是 MySQL、ClickHouse、HTTP、MongoDB
- 替代 JOIN 提升性能 20-30 倍

### Q44：ClickHouse 的限流机制？

**答**：
- Quota：限制用户查询数、读行数等
- 单查询限制：`max_execution_time`、`max_rows_to_read`

### Q45：ClickHouse 的权限控制？

**答**：
- RBAC：角色 + 权限
- 用户 → 角色 → 权限
- 细粒度：表级、列级

### Q46：ClickHouse 怎么处理大数据量 JOIN？

**答**：
1. 字典 JOIN（小维表）
2. GLOBAL JOIN（分布式）
3. 算法优化（grace_hash）
4. 预先聚合 + 小结果 JOIN
5. 业务层拆分查询

### Q47：ClickHouse 的集群如何扩容？

**答**：
1. 新增节点加入 ZooKeeper
2. 启动 ClickHouse 注册到集群
3. 创建新分布式表
4. 双写或迁移数据
5. 切换查询
6. 下线老表

### Q48：ClickHouse 集群如何保证高可用？

**答**：
- ReplicatedMergeTree 多副本
- Keeper 协调
- 副本间数据自动同步
- 故障自动转移

### Q49：ZooKeeper 压力大怎么办？

**答**：
1. 迁移到 ClickHouse Keeper（自研，性能更好）
2. 增加 ZK 节点
3. 减少副本数
4. 优化 ZK 路径

### Q50：ClickHouse Keeper 是什么？

**答**：ClickHouse 24.x+ 自研的 ZooKeeper 替代品：
- 用 Raft 协议
- 性能更优
- 减少外部依赖

### Q51：ClickHouse 的瓶颈通常在哪？

**答**：
1. 磁盘 I/O（特别是 HDD）
2. 网络带宽（跨节点查询）
3. CPU（复杂计算）
4. 内存（聚合）
5. ZooKeeper（副本同步）

### Q52：如何诊断慢查询？

**答**：
```sql
-- 1. EXPLAIN
EXPLAIN PIPELINE SELECT ...;

-- 2. query_log
SELECT * FROM system.query_log
WHERE query_duration_ms > 1000
ORDER BY query_duration_ms DESC LIMIT 10;

-- 3. system.processes
SELECT * FROM system.processes ORDER BY elapsed DESC;
```

### Q53：ClickHouse 的 ProfileEvents 是什么？

**答**：查询执行过程中各类计数器：
- `RealTimeMicroseconds`：实际耗时
- `UserTimeMicroseconds`：用户态 CPU
- `OSReadBytes`：磁盘读
- `NetworkSendBytes`：网络发送

### Q54：ClickHouse 的 settings 有哪些调优关键？

**答**：
- `max_block_size`：65536
- `max_threads`：CPU 核数
- `max_memory_usage`：10GB
- `max_bytes_before_external_group_by`：内存不够落盘
- `join_algorithm`：hash/parallel_hash/grace_hash
- `use_uncompressed_cache`：1

### Q55：ClickHouse 的缓存机制？

**答**：
1. **mark 缓存**：mark 文件缓存
2. **解压缓存**：解压后的数据
3. **索引缓存**：稀疏索引
4. 配合 `use_uncompressed_cache = 1`

### Q56：ClickHouse 的物化视图 vs 视图？

**答**：
- 普通 VIEW：查询时展开
- MATERIALIZED VIEW：数据物理存储
- LIVE VIEW（实验）：实时刷新

### Q57：ClickHouse 如何实现近似去重？

**答**：
- `uniq`：基于 HLL（HyperLogLog）
- `uniqHLL12`：HLL12 算法
- `uniqExact`：精确（O(N) 内存）

### Q58：ClickHouse 如何实现近似分位数？

**答**：
- `quantile`：基于采样
- `quantileTDigest`：TDigest 算法
- `quantileExact`：精确（O(N) 内存）

### Q59：ClickHouse 与 Druid 区别？

| 维度 | ClickHouse | Druid |
|------|-----------|-------|
| 架构 | 中心化 | 中心化 + 历史/实时节点 |
| 写入 | 实时 + 批量 | 实时为主 |
| 查询 | SQL | SQL + JSON |
| 生态 | 成熟 | 一般 |
| 性能 | 极快 | 快 |

### Q60：ClickHouse 与 Elasticsearch 区别？

| 维度 | ClickHouse | ES |
|------|-----------|---|
| 场景 | OLAP | 搜索 |
| 索引 | 稀疏 | 倒排 |
| 写入 | 批 | 实时 |
| 查询 | SQL | DSL |
| 全文 | 弱 | 强 |

## 12.3 高级篇（61-90）

### Q61：ClickHouse 的代码结构？

**答**：
- `dbms/src/`：核心代码
- `dbms/src/Columns/`：列实现
- `dbms/src/Storages/`：存储引擎
- `dbms/src/Interpreters/`：查询解释
- `dbms/src/Processors/`：处理器 pipeline

### Q62：ClickHouse 是如何实现 SIMD 优化的？

**答**：
- 使用 `simdjson` 等 SIMD 库
- `vectorize` 函数自动向量化
- 整数、浮点运算走 SIMD
- 字符串、复杂计算手动向量化

### Q63：ClickHouse 的主备切换？

**答**：
- ReplicatedMergeTree 自动选主
- Keeper 协调
- 老主恢复后自动变从
- 故障转移秒级

### Q64：ClickHouse 的故障恢复流程？

**答**：
1. 检测到节点离线
2. Keeper 选举新主
3. 数据从其他副本拉取
4. 自动重建
5. 加入集群

### Q65：ClickHouse 的数据备份策略？

**答**：
1. **clickhouse-backup**：完整备份
2. **FREEZE PARTITION**：增量
3. **磁盘快照**：LVM/ZFS
4. **S3 备份**：异地容灾
5. **快照复制**：ReplicatedMergeTree 自动

### Q66：ClickHouse 的版本升级注意事项？

### Q71：ClickHouse 的最佳分区策略？

**答**：
- 按时间分区（`toYYYYMM(date)` 或 `toYYYYMMDD(date)`）
- 单分区不超过 100GB

### Q72：ClickHouse 的最佳排序键？

**答**：
1. 最高频过滤列放最左
2. 高基数列放后
3. 等值列放前，范围列放后
4. 常用 GROUP BY 列放前

### Q73：ClickHouse 的最佳压缩配置？

**答**：
- 时间列：`CODEC(DoubleDelta, LZ4)`
- 数值列：`CODEC(Delta, LZ4)` 或 `CODEC(Gorilla, LZ4)`
- 字符串：默认 LZ4
- 极致压缩：`CODEC(..., ZSTD(3))`
