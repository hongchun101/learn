# 第 2 章：核心概念与列存储原理

## 2.1 为什么列存储适合 OLAP

### 2.1.1 OLTP vs OLAP

```
OLTP（行存储，MySQL）         OLAP（列存储，ClickHouse）
- 高并发短事务                  - 低并发长查询
- 点查/范围查                   - 聚合/统计/扫描
- INSERT/UPDATE 频繁            - 批量写入/极少更新
- 单行读写                      - 批量读整列
```

### 2.1.2 数据存储差异

```sql
-- 同一张表：user_events
-- 100 万行，3 列：user_id, event_type, amount
```

**行存储**（MySQL InnoDB）：
```
Page 1: [1, view, 10.5] [2, click, 0.0] [3, view, 20.0] ...
Page 2: [4, purchase, 99.0] [5, view, 0.0] ...
```
查询 `SELECT SUM(amount) WHERE event_type='view'`：需要读**所有页的所有列**，即使我们只关心 amount 和 event_type。

**列存储**（ClickHouse）：
```
Column 1 (user_id):  [1][2][3][4][5]...   （紧凑连续存储）
Column 2 (event_type):[view][click][view][purchase][view]...
Column 3 (amount):   [10.5][0.0][20.0][99.0][0.0]...
```
同样查询：只需读 Column 2 和 Column 3，**I/O 减少 1/3**。

## 2.2 ClickHouse 的列存储实现

### 2.2.1 数据组织层级

```
Table
└── Partition（分区，toYYYYMM(date)）       ← 按时间/月分区
    └── Part（数据段，每次 INSERT 生成）   ← 不可变的有序文件
        ├── primary.idx（二级索引）         ← 稀疏索引
        ├── [Column].bin（列数据）          ← 压缩二进制
        ├── [Column].mrk2（列标记）         ← 列内偏移
        └── checksums.txt（校验和）         ← 完整性
```

### 2.2.2 块（Block）与向量执行

```sql
-- 经典查询
SELECT user_id, count() FROM events GROUP BY user_id;
```

ClickHouse 执行过程：
```
Step 1: 读取 user_id 列 → 形成 Block (block_size=65536 行)
Step 2: 哈希聚合 (vectorized) → 一次处理 65536 行
Step 3: 输出结果
```

**vs 传统 Volcano 模型**（MySQL/PostgreSQL）：
```cpp
// 传统行式逐行处理
for (auto &row : rows) {
  process(row);  // 一次处理一行
}

// ClickHouse 向量化
for (auto &block : blocks) {  // block = 65536 行
  processBlock(block);  // SIMD 优化
}
```

**性能提升 5-10 倍**（CPU 密集型查询）。

## 2.3 MergeTree 引擎核心

MergeTree 是 ClickHouse 的灵魂，**所有生产场景都用它**。

### 2.3.1 建表语法详解

```sql
CREATE TABLE events
(
    event_date  Date,
    event_time  DateTime,
    user_id     UInt64,
    event_type  LowCardinality(String),
    amount      Decimal(10, 2),
    -- 关键：建表决定查询性能
    INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 3
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_date)        -- 分区键：按月分区
ORDER BY (event_type, user_id, event_time)  -- 排序键：影响压缩与查询
PRIMARY KEY (event_type, user_id)        -- 主键：去重 + 二级索引
SETTINGS
    index_granularity = 8192,            -- 索引粒度：8192 行一个 mark
    enable_mixed_granularity_parts = 1,  -- 自适应粒度
    min_bytes_for_wide_part = 0;         -- 强制使用宽 part（推荐）
```

### 2.3.2 关键概念详解

#### 1. **PRIMARY KEY vs ORDER BY**
```sql
-- 主键用于去重（ReplacingMergeTree 时有效）
-- ORDER BY 决定数据在磁盘上的物理顺序
-- 二者可以不同，但 ORDER BY 必须以 PRIMARY KEY 开头

-- ✅ 正确
ORDER BY (event_type, user_id, event_time)
PRIMARY KEY (event_type, user_id)

-- ❌ 错误：PRIMARY KEY 不在 ORDER BY 开头会报错
```

#### 2. **分区（PARTITION BY）**
```sql
-- 最佳实践：按时间分区
PARTITION BY toYYYYMM(event_date)   -- 每月一个分区
PARTITION BY toYYYYMMDD(event_date) -- 每天一个分区（数据量大时）

-- 优势：
-- 1. 删除分区极快（毫秒级，drop partition）
-- 2. 查询可以裁剪到指定分区
-- 3. 备份/恢复按分区粒度

-- 避免：按高基数列分区（user_id），会产生 10万+ 分区
```

#### 3. **排序键（ORDER BY）**
```sql
-- 排序键就是数据在磁盘上的物理顺序
-- 查询时使用最左前缀原则会触发数据裁剪

-- 例如：WHERE event_type = 'click' AND user_id = 1001
-- 数据在磁盘上是 [event_type, user_id, ...] 排序
-- 通过 primary.idx 找到 user_id=1001 所在的 mark
-- 然后只读这部分数据

-- 设计原则：把查询最常用的列放前面
-- 把高基数列放在低基数列之后
-- 单值在前、范围在后
```

#### 4. **索引粒度（index_granularity）**
```sql
-- 每个 mark 对应 8192 行数据（默认）
-- mark 是 ClickHouse 索引的最小单位
-- mark 越少：索引越小、查询定位越快但精度差
-- mark 越多：索引越大、查询精度高但开销大
-- 默认 8192 是经过调优的平衡点（生产环境不建议改）
```

### 2.3.3 数据写入过程

```
INSERT INTO events VALUES (...)
       ↓
1. 在内存中排序
       ↓
2. 写入内存缓冲区（Buffer）
       ↓
3. 刷盘到磁盘形成 Part（不可变）
   ├── primary.idx
   ├── [col1].bin, [col1].mrk2
   ├── [col2].bin, [col2].mrk2
   └── ...
       ↓
4. 后台 Merge 任务
   把多个小 Part 合并成大 Part（按 ORDER BY 排序）
       ↓
5. 减少 Part 数量（避免 Part Explosion）
```

**关键特性**：
- ✅ 写入立即可查（不保证强一致性）
- ✅ Part 不可变（避免 MVCC 开销）
- ✅ 后台异步合并（不影响查询）

## 2.4 数据类型精讲

### 2.4.1 数值类型

```sql
-- 整数（按需选择最小够用的）
UInt8, UInt16, UInt32, UInt64
Int8, Int16, Int32, Int64

-- 浮点（避免用于金额！）
Float32, Float64

-- 定点数（金额、金额计算）
Decimal(P, S)  -- P=总位数, S=小数位
Decimal32(S), Decimal64(S), Decimal128(S), Decimal256(S)

-- 示例
amount Decimal(10, 2)  -- 最大 99999999.99
```

**性能差异**：
```sql
-- 测试：1 亿行聚合
SELECT avg(amount) FROM events;  -- Float64: 0.3s
SELECT avg(amount) FROM events;  -- Decimal(10, 2): 0.5s

-- 结论：金额用 Decimal，计算效率略低但精度有保证
```

### 2.4.2 字符串类型

```sql
-- String：通用字符串
-- FixedString(N)：定长字符串（优化存储）
-- LowCardinality(String)：低基数（<1万种不同值时大幅压缩）

-- 测试数据：event_type 100 万行只有 5 种值
CREATE TABLE t1 (event_type String) ENGINE = MergeTree ORDER BY tuple();
CREATE TABLE t2 (event_type LowCardinality(String)) ENGINE = MergeTree ORDER BY tuple();

-- 存储空间对比：t2 比 t1 节省 5-10 倍
```

### 2.4.3 时间类型

```sql
Date               -- 2 字节，YYYY-MM-DD（1970-2149）
Date32             -- 4 字节，扩展时间范围
DateTime           -- 4 字节，YYYY-MM-DD HH:MM:SS
DateTime64(precision) -- 8 字节，毫秒/微秒/纳秒精度

-- 最佳实践
event_date Date              -- 按天分区的列
event_time DateTime          -- 业务时间
created_at DateTime DEFAULT now()  -- 默认值
```

### 2.4.4 复合类型

```sql
-- Array：数组
tags Array(String)

-- Tuple：元组（固定结构）
address Tuple(city String, country String)

-- Map：键值对（25.1+ 推荐）
properties Map(String, String)

-- Nested：嵌套表
CREATE TABLE visits
(
    user_id UInt64,
    pages Nested(
        url String,
        duration UInt32
    )
) ENGINE = MergeTree ORDER BY user_id;
```

### 2.4.5 可为空类型（Nullable）

```sql
-- Nullable 会被特殊处理，开销较大
-- 避免使用 Nullable，改用默认值（如 0、''）

-- ❌ 不推荐
amount Nullable(Decimal(10, 2))

-- ✅ 推荐：使用默认值
amount Decimal(10, 2) DEFAULT 0

-- 例外：业务确实需要 NULL 语义
comment Nullable(String)
```

## 2.5 压缩机制

### 2.5.1 默认压缩算法

```sql
-- ClickHouse 默认 LZ4 压缩
-- 压缩比通常 5-10 倍

-- 查看压缩比
SELECT
    table,
    formatReadableSize(sum(bytes_on_disk)) AS disk_size,
    formatReadableSize(sum(data_uncompressed_bytes)) AS raw_size,
    round(sum(data_uncompressed_bytes) / sum(bytes_on_disk), 2) AS compression_ratio
FROM system.parts
WHERE database = 'tutorial' AND active
GROUP BY table;
```

### 2.5.2 压缩算法选择

```sql
-- 通用场景：LZ4（默认）
SETTINGS compress_lz4 = 1

-- 极致压缩（节省 30% 空间，但写入慢 50%）
SETTINGS
  compress_zstd = 1,
  zstd_window_log = 24  -- 0-30，越大压缩越好
```

### 2.5.3 编码优化

```sql
-- 整数：Delta 编码 + LZ4（适合递增 ID）
-- 时间：DoubleDelta 编码（适合单调递增）
-- 字符串：字典编码（适合低基数）

-- 测试：时间序列数据
CREATE TABLE ts
(
    ts DateTime CODEC(DoubleDelta, LZ4),
    value Float32 CODEC(Gorilla, LZ4)
) ENGINE = MergeTree ORDER BY ts;

-- 节省 50-80% 空间
```

## 2.7 实战：表设计 7 原则

```sql
-- 实战：电商订单表设计
CREATE TABLE dwd.orders
(
    -- 1. 必选字段
    order_id        String,              -- 业务主键
    order_date      Date,                -- 分区键（按天）
    order_time      DateTime,            -- 业务时间
    
    -- 2. 维度字段
    user_id         UInt64,              -- 用户 ID
    merchant_id     UInt32,              -- 商家 ID
    
    -- 3. 度量字段
    total_amount    Decimal(18, 2),      -- 订单金额
    pay_amount      Decimal(18, 2),      -- 实付金额
    discount_amount Decimal(18, 2),      -- 优惠金额
    
    -- 4. 状态/类型字段（用 LowCardinality）
    order_status    LowCardinality(String),  -- 订单状态
    pay_type        LowCardinality(String),  -- 支付方式
    
    -- 5. JSON 字段（ClickHouse 25.x 已稳定）
    extra           Map(String, String),  -- 扩展字段
    
    -- 6. 时间戳
    created_at      DateTime DEFAULT now(),
    updated_at      DateTime DEFAULT now()
)
ENGINE = MergeTree
PARTITION BY toYYYYMMDD(order_date)
ORDER BY (order_status, merchant_id, order_id)  -- 高频查询在最左
SETTINGS index_granularity = 8192;
```

**七大原则**：
1. **分区键按时间**（按天/月）
2. **排序键按查询模式**（最常用过滤列在最左）
3. **避免 Nullable**（用默认值替代）
4. **LowCardinality 处理枚举**（< 1万种值的字符串）
5. **Decimal 处理金额**（不用 Float）
6. **字符串谨慎使用**（必要时用 FixedString）
7. **及时删除老分区**（避免存储爆炸）
