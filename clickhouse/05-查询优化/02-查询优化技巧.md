# 05-查询优化 续：查询优化技巧与案例

## 5.11 慢查询优化十大法则

### 法则 1：选择合适的数据类型

```sql
-- ❌ 错误：用 String 存数值
amount String  -- 5GB存储，无法聚合

-- ✅ 正确：使用合适类型
amount Decimal(18, 2)  -- 1.5GB 存储
```

### 法则 2：避免 SELECT *

```sql
-- ❌ 错误：查询所有列
SELECT * FROM events WHERE user_id = 1001;
-- 读取所有 100 列的数据

-- ✅ 正确：只查需要的列
SELECT user_id, event_type, amount FROM events WHERE user_id = 1001;
-- 性能提升 5-10 倍
```

### 法则 3：合理使用 PREWHERE

```sql
-- 测试表：100 列，1 亿行
CREATE TABLE events_large (event_date Date, user_id UInt64, ..., col_100 String)
ENGINE = MergeTree ORDER BY (event_date, user_id);

-- 场景：查 user_id = 1001 在某一天的所有事件
-- event_date 过滤后剩 1% 数据

-- ❌ 普通 WHERE
SELECT * FROM events_large
WHERE event_date = '2024-01-01' AND user_id = 1001;
-- 耗时：8s

-- ✅ PREWHERE
SELECT * FROM events_large
PREWHERE event_date = '2024-01-01'  -- 先用这个过滤（1/365）
WHERE user_id = 1001;
-- 耗时：0.3s （27 倍提升）

-- ✅✅ 进一步优化：让 ClickHouse 自动选择
SET optimize_move_to_prewhere = 1;  -- 默认开启
```

### 法则 4：分批处理大结果集

```sql
-- ❌ 一次返回太多数据
SELECT * FROM events WHERE event_date BETWEEN '2024-01-01' AND '2024-12-31';
-- 返回 1 亿行，OOM

-- ✅ 用 LIMIT + 多次查询
SELECT * FROM events
WHERE event_date BETWEEN '2024-01-01' AND '2024-12-31'
LIMIT 1000 OFFSET 0;

-- ✅ 更好：先聚合再查明细
SELECT
    event_date,
    count() AS cnt
FROM events
WHERE event_date BETWEEN '2024-01-01' AND '2024-12-31'
GROUP BY event_date;
```

### 法则 5：使用 LIMIT BY 替代窗口

```sql
-- ❌ 窗口函数（开销大）
SELECT *
FROM (
    SELECT
        user_id,
        order_id,
        amount,
        ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) AS rn
    FROM orders
)
WHERE rn <= 5;

-- ✅ LIMIT BY（更快）
SELECT
    user_id,
    order_id,
    amount
FROM orders
ORDER BY user_id ASC, order_date DESC
LIMIT 5 BY user_id;
```

### 法则 6：避免在 WHERE 中使用函数

```sql
-- ❌ WHERE 中用函数（不走索引）
SELECT * FROM events WHERE toDate(event_time) = '2024-01-01';
-- 全表扫描

-- ✅ 直接用范围
SELECT * FROM events
WHERE event_time >= '2024-01-01 00:00:00'
  AND event_time < '2024-01-02 00:00:00';
-- 走索引
```

### 法则 7：使用物化视图预聚合

```sql
-- 原始查询：每次扫描 1 亿行
SELECT
    toStartOfHour(event_time) AS hour,
    count()
FROM events
WHERE event_date = today()
GROUP BY hour;

-- 优化：物化视图预聚合
CREATE MATERIALIZED VIEW events_hourly_mv
ENGINE = SummingMergeTree
ORDER BY (event_type, hour)
AS SELECT
    toStartOfHour(event_time) AS hour,
    event_type,
    count() AS cnt
FROM events
GROUP BY hour, event_type;

-- 查询物化视图（毫秒级）
SELECT hour, sum(cnt)
FROM events_hourly_mv
WHERE hour >= today()
GROUP BY hour;
```

### 法则 8：减少 DISTINCT

```sql
-- ❌ DISTINCT 去重（O(N) 内存）
SELECT DISTINCT user_id FROM events;

-- ✅ GROUP BY（略快）
SELECT user_id FROM events GROUP BY user_id;

-- ✅✅ uniq() 估算（O(1) 内存）
SELECT uniq(user_id) FROM events;  -- 精确度 99%
```

### 法则 9：使用合适的聚合函数

```sql
-- ❌ 精确去重（O(N) 内存）
SELECT uniqExact(user_id) FROM events;  -- 10s，10GB 内存

-- ✅ 估算去重
SELECT uniq(user_id) FROM events;  -- 0.3s，1MB 内存
```

### 法则 10：避免在 SELECT 中执行复杂计算

```sql
-- ❌ 在 SELECT 中计算
SELECT
    user_id,
    amount * 1.0 / 100 AS amount_yuan,
    if(amount > 1000, 'high', 'low') AS level
FROM orders;

-- ✅ 预计算到物化列
CREATE TABLE orders_with_calc
(
    user_id UInt64,
    amount Decimal(10, 2),
    amount_yuan Decimal(10, 2) MATERIALIZED amount / 100,
    level LowCardinality(String) MATERIALIZED if(amount > 1000, 'high', 'low')
) ENGINE = MergeTree ORDER BY user_id;

SELECT user_id, amount_yuan, level FROM orders_with_calc;
```

## 5.12 性能调优 checklist

### 5.12.1 表设计优化

```sql
-- ✅ 检查项
-- 1. 分区是否合理？
SELECT
    database,
    table,
    partition,
    formatReadableSize(bytes_on_disk) AS size,
    rows
FROM system.parts
WHERE active
ORDER BY bytes_on_disk DESC
LIMIT 20;

-- 2. 排序键是否合理？
SELECT
    database,
    table,
    sorting_key,
    primary_key
FROM system.tables
WHERE database NOT IN ('system', 'information_schema');

-- 3. 是否有未使用索引？
SELECT
    database,
    table,
    name AS index_name,
    type,
    expr,
    granularity
FROM system.data_skipping_indices
WHERE database NOT IN ('system');
```

## 5.13 实战案例

### 案例 1：日志查询从 30s 优化到 0.5s

**问题**：日志表 100 亿行，按 trace_id 查询单条链路耗时 30s

**优化步骤**：

```sql
-- 1. 原始表
CREATE TABLE logs
(
    log_time DateTime,
    trace_id String,
    message String
) ENGINE = MergeTree ORDER BY log_time;
-- 没有 trace_id 索引

-- 2. 添加 Bloom Filter 索引
ALTER TABLE logs
ADD INDEX idx_trace trace_id TYPE bloom_filter(0.01) GRANULARITY 4;
ALTER TABLE logs MATERIALIZE INDEX idx_trace;

-- 3. 优化查询
SELECT * FROM logs
WHERE trace_id = 'abc-123'
ORDER BY log_time;
-- 耗时：0.5s （60 倍提升）
```

### 案例 2：实时大屏 60s 优化到 1s

**问题**：实时大屏查询 60s 才出结果

**优化步骤**：

```sql
-- 1. 原始查询（60s）
SELECT
    minute,
    count() AS pv,
    uniqExact(user_id) AS uv
FROM events
WHERE event_time >= now() - INTERVAL 2 HOUR
GROUP BY minute;

-- 2. 创建物化视图（1s）
CREATE TABLE events_minute
(
    minute DateTime,
    cnt UInt64,
    uv AggregateFunction(uniq, UInt64)
) ENGINE = AggregatingMergeTree
ORDER BY minute;

CREATE MATERIALIZED VIEW events_minute_mv TO events_minute AS
SELECT
    toStartOfMinute(event_time) AS minute,
    count() AS cnt,
    uniqState(user_id) AS uv
FROM events
GROUP BY minute;

-- 3. 优化查询
SELECT
    minute,
    sum(cnt) AS pv,
    uniqMerge(uv) AS uv
FROM events_minute
WHERE minute >= now() - INTERVAL 2 HOUR
GROUP BY minute;
-- 耗时：0.05s （1200 倍提升）
```

### 案例 3：JOIN 性能从 30s 优化到 1s

**问题**：大表 JOIN 字典 30s 才出结果

**优化步骤**：

```sql
-- 1. 原始 JOIN
SELECT
    o.order_id,
    o.user_id,
    u.city
FROM orders o
LEFT JOIN users u ON o.user_id = u.user_id
WHERE o.order_date = '2024-01-01';
-- 耗时：30s

-- 2. 创建字典
CREATE DICTIONARY users_dict
(
    user_id UInt64,
    city String
)
PRIMARY KEY user_id
SOURCE(CLICKHOUSE(DB 'dwd' TABLE 'dim_user'))
LIFETIME(MIN 300 MAX 600)
LAYOUT(HASHED());

-- 3. 字典查询
SELECT
    order_id,
    user_id,
    dictGet('users_dict', 'city', user_id) AS city
FROM orders
WHERE order_date = '2024-01-01';
-- 耗时：1s （30 倍提升）
```
