# 第 7 章：高性能架构

## 7.1 集群架构基础

### 7.1.1 三个核心概念

```
Shard（分片）：
  - 数据按规则拆分到不同节点
  - 每个分片存储 1/N 数据
  - 横向扩展，提升查询并行度

Replica（副本）：
  - 同一分片的多份拷贝
  - 高可用：主挂从顶
  - 不提升查询性能（除非读副本）

ZooKeeper / ClickHouse Keeper：
  - 副本协调
  - 分片元数据
  - 分布式 DDL
```

### 7.1.2 典型架构

```
              ┌──────────────────┐
              │  Load Balancer   │
              └────────┬─────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   ┌────▼────┐    ┌────▼────┐    ┌────▼────┐
   │  Node1  │    │  Node2  │    │  Node3  │
   │ Shard1  │    │ Shard2  │    │ Shard3  │
   │ +R1+R2  │    │ +R1+R2  │    │ +R1+R2  │
   └────┬────┘    └────┬────┘    └────┬────┘
        │              │              │
        └──────────────┼──────────────┘
                       │
              ┌────────▼─────────┐
              │  ZooKeeper x 3   │
              └──────────────────┘
```

## 7.2 集群规划

### 7.2.1 容量规划公式

```
单机存储容量 = 日增量 × 保留天数 × 压缩比倒数 × 副本数

示例：
- 日增量：100 亿行（1TB 原始数据）
- 保留：90 天
- 压缩比：5 倍
- 副本：2 副本

单机存储 = 1TB × 90 / 5 × 2 = 36 TB

单机容量 10TB → 需要 4 个分片
```

### 7.2.2 服务器选型

| 场景 | CPU | 内存 | 磁盘 | 网络 |
|------|-----|------|------|------|
| 小型（< 10亿） | 16核 | 64GB | 2TB SSD | 10Gb |
| 中型（10-100亿） | 32核 | 128GB | 10TB SSD | 25Gb |
| 大型（100亿+） | 64核 | 256GB | 50TB NVMe | 100Gb |

## 7.4 ReplicatedMergeTree（副本表）

### 7.4.1 创建副本表

```sql
-- 每个节点执行，zk_path 和 replica_name 必须不同
CREATE TABLE events ON CLUSTER production_cluster
(
    event_date Date,
    event_time DateTime,
    user_id UInt64,
    event_type LowCardinality(String),
    amount Decimal(10, 2)
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/events',  -- ZooKeeper 路径
    '{replica}'                            -- 副本名
)
PARTITION BY toYYYYMMDD(event_date)
ORDER BY (event_type, user_id, event_time);
```

### 7.4.2 写入副本表

```sql
-- 写入本地副本即可，ZooKeeper 自动同步到其他副本
INSERT INTO events VALUES (...);
-- 也可以写入 Distributed 表，自动路由到正确分片
```

### 7.4.3 副本监控

```sql
-- 查看复制队列
SELECT
    database,
    table,
    replica_name,
    position,
    node_name,
    type,
    source_replica,
    parts_to_merge,
    is_currently_executing
FROM system.replication_queue
ORDER BY last_exception_time DESC
LIMIT 20;

-- 查看延迟
SELECT
    database,
    table,
    replica_name,
    absolute_delay,
    total_replicas,
    active_replicas
FROM system.replicas
ORDER BY absolute_delay DESC;
```

## 7.5 Distributed 表（分布式表）

### 7.5.1 创建分布式表

```sql
-- 在每个节点都创建（Distributed 表逻辑视图）
CREATE TABLE events_distributed ON CLUSTER production_cluster
AS events
ENGINE = Distributed(
    'production_cluster',   -- 集群名
    'db',                   -- 数据库
    'events',               -- 本地表
    cityHash64(user_id)     -- 分片键
);
```

### 7.5.2 分片键选择

```sql
-- 1. rand()：均匀分布，但 JOIN 时无法本地化
sharding_key = 'rand()'

-- 2. hash(列)：按列哈希，相同列值在同分片
sharding_key = 'cityHash64(user_id)'

-- 3. 多列组合
sharding_key = 'cityHash64(user_id, event_type)'

-- 4. 直接用列（按值范围）
sharding_key = 'toYYYYMM(event_date)'
```

### 7.5.3 分布式查询

```sql
-- 自动从所有分片拉取
SELECT count() FROM events_distributed;

-- IN 优化：会自动下推
SELECT * FROM events_distributed
WHERE user_id IN (1, 2, 3);
-- 会把 IN 发到所有分片，避免全量拉回

-- GLOBAL IN（join 时本地化）
SELECT g.*
FROM events_distributed AS e
GLOBAL INNER JOIN
(
    SELECT user_id FROM users WHERE city = 'Beijing'
) AS g ON e.user_id = g.user_id;
-- 比普通 JOIN 快 5-10 倍
```

### 7.5.4 写入策略

```sql
-- 1. 同步写入（默认）：所有分片都写完才返回
INSERT INTO events_distributed VALUES (...);
SETTINGS distributed_foreground_insert = 1;

-- 2. 异步写入：写入本地分片即返回
INSERT INTO events_distributed VALUES (...);
SETTINGS distributed_foreground_insert = 0;
-- 适用：实时高吞吐写入
```

## 7.7 高级架构模式

### 7.7.1 多级分片

```
写入层（Kafka） → 实时层（Realtime，1 周数据）
                → 归档层（Archive，永久）
                  - 冷数据在低成本存储（S3）
                  - 统一查询接口
```

### 7.7.2 读写分离

```sql
-- 主集群：写入
-- 副集群：查询

-- 通过远端表函数查询
SELECT * FROM remote('query_cluster', db.events)
WHERE event_date = today();

-- 或用 Distributed 表指向查询集群
```

### 7.7.3 冷热分层

```sql
CREATE TABLE events_tiered
(
    ...
)
ENGINE = MergeTree
ORDER BY ...
TTL
    event_date + INTERVAL 30 DAY TO VOLUME 'cold',
    event_date + INTERVAL 365 DAY DELETE
SETTINGS storage_policy = 'tiered_storage';

-- 配置存储策略
<storage_configuration>
    <disks>
        <hot_disk>
            <path>/var/lib/clickhouse/hot/</path>
        </hot_disk>
        <cold_disk>
            <path>/var/lib/clickhouse/cold/</path>
        </cold_disk>
        <s3_disk>
            <type>s3</type>
            <endpoint>https://s3.amazonaws.com/bucket/</endpoint>
        </s3_disk>
    </disks>

    <policies>
        <tiered_storage>
            <volumes>
                <hot>
                    <disk>hot_disk</disk>
                </hot>
                <cold>
                    <disk>cold_disk</disk>
                </cold>
                <archive>
                    <disk>s3_disk</disk>
                </archive>
            </volumes>
        </tiered_storage>
    </policies>
</storage_configuration>
```

## 7.8 实战：分片扩容

### 7.8.1 场景

原集群 3 分片，存储不足，需要扩容到 6 分片。

### 7.8.2 步骤

```sql
-- 1. 新建分片 4、5、6（添加节点到配置）

-- 2. 新建分布式表（指向新分片）
CREATE TABLE events_v2 ON CLUSTER production_cluster AS events
ENGINE = Distributed('production_cluster_v2', 'db', 'events', cityHash64(user_id));

-- 3. 数据迁移
-- 方案 1：双写（推荐）
-- 写入层同时写 events_v1 和 events_v2

-- 方案 2：迁移脚本
INSERT INTO events_v2
SELECT * FROM remote('old_cluster', db.events)
WHERE event_date >= '2024-01-01';

-- 4. 查询切换
SELECT count() FROM events_v2;

-- 5. 下线旧表
DROP TABLE events_v1;
```
