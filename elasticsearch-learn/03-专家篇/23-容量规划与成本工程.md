# 第 23 章 容量规划与成本工程

## 本章目标

学完本章,你能:

- 用 **数学公式** 估算集群规模(节点数、CPU、内存、磁盘、Heap)。
- 给出 **成本模型**,在云上算出每月账单。
- 区分 **热/温/冷/冻** 四层存储的成本权衡。
- 在 50K 面试中,清晰回答"集群该买多大"。

---

## 23.1 容量四元组

任何 ES 容量规划都要回答:

| 维度 | 单位 | 输入 |
| --- | --- | --- |
| **数据量** | GB / TB | 总文档 × 平均 _source 大小 × 副本数 × 索引开销 |
| **写入吞吐** | doc/s、MB/s | 峰值 × 1.5(冗余) |
| **查询 QPS** | query/s | 峰值 × 1.5 |
| **延迟 SLA** | P99 ms | 业务要求 |

> 三者至少定两个;第四个由业务反推。

---

## 23.2 磁盘容量公式

```
总磁盘 = 原始数据量 × 副本数 × 索引开销
```

| 开销 | 数值 | 备注 |
| --- | --- | --- |
| 倒排索引 | ×1.2 | text 分词字段 |
| doc_values | ×1.05-1.2 | keyword/数值聚合 |
| source | ×1.0 | 写盘原始 |
| translog(临时) | ×0.05 | 1% 持续 |
| 段合并放大 | ×1.1-1.3 | 写高峰 |
| 副本 | ×N | 配置 `number_of_replicas` |
| 安全余量 | ×1.5 | **必须**,留给 watermarks 与磁盘重平衡 |

> 综合:1 TB 源数据,2 副本 → 约 **1 × 1.3 × 2 × 1.5 ≈ 4 TB** 物理盘。

## 23.3 内存与 Heap

### 23.3.1 经验公式

```
Heap ≈ max(min(32 GB, 物理内存 / 2), 4 GB)
```

- 最小 4 GB(JVM 不让再小)。
- 推荐 ≤ 31 GB(Compressed Oops 临界,32 GB 后 64-bit 指针会失效)。
- 大内存机器(128 GB+)只给 31 GB,留给 **filesystem cache**。

### 23.3.2 数据驻留估算

Lucene 段进 filesystem cache,查询/聚合时 **首先** 命中 cache 才走磁盘。

```
cache 命中数据量 = total_shard_size × 命中率
```

经验:

- **text 高亮/聚合场景**:filesystem cache = 数据量 × 20%(聚合命中文本)
- **纯 keyword 聚合**:filesystem cache = 数据量 × 50%
- **时间序列(ILM 冷)**:cache = 数据量 × 10%

> 1 TB 索引,filesystem cache 200 GB;内存 256 GB 物理(heap 31 GB)刚好能撑。

### 23.3.3 内存杀手

| 现象 | 原因 | 治理 |
| --- | --- | --- |
| fielddata 飙 | text 聚合 | 用 `.keyword` 替 |
| request_cache 失效 | 每次 query 都变 | 业务合并同查询 |
| 大量 sort | fielddata/sort buffer | 减少 sort 字段、上 PIT |
| query_cache 占满 | cache size 没设限 | `indices.requests.cache.size` |

## 23.4 CPU 与线程池

### 23.4.1 CPU 密集型

ES 8.x 默认 `search` 线程池 = `min(5, 节点 CPU 核数 / 2)`。

- **搜索 + 聚合**:每核 1 个并发 search 任务。16 核 → 8 并发 search。
- **bulk 写入**:线程池 = 核数;瓶颈常在 **磁盘 IO** 而非 CPU。

### 23.4.2 经验配比

| 数据量 | 核数 | 内存 | 单机分片上限 |
| --- | --- | --- | --- |
| < 100 GB | 8 | 32 GB | 600 |
| 100 GB - 1 TB | 16 | 64 GB | 1000 |
| 1 - 10 TB | 32 | 128 GB | 1500(全 SSD) |
| 10 TB+ | 64+ | 256 GB+ | 用分层 / frozen tier |

> 单 shard 推荐 < 50 GB(30-50 GB 黄金);超过要 split。

## 23.5 分片数估算

### 23.5.1 公式

```
主分片数 = ceil(数据量 / 50 GB)
```

考虑未来增长 ×1.5-2。

### 23.5.2 上限

- 单分片 < 50 GB 文档,Lucene 段文件数 1 万以下。
- 集群总分片数 ≤ 节点数 × 1000(每节点 600-1000 推荐上限,过多元数据压力)。
- 单节点 ≥ 200 active shard 时,**master 集群状态会超 100ms** 推送,影响大集群。

### 23.5.3 案例

- 业务:3 TB 数据,3 副本,3 年增长 ×2。
- 主分片 = ceil(3 / 50) = 60 → 留 2× → **120 主分片**。
- 物理 = 3 TB × 1.3 索引开销 × 3 副本 × 1.5 安全 = **17.5 TB 物理**。
- 节点:17.5 TB / 10 TB(单节点 10 TB 可用)= 2 节点 → 加 1 副本冗余 = **3 数据节点 + 3 master**。

## 23.6 写入吞吐估算

### 23.6.1 经验值

| 节点 | 单机写入 | 单机查询 | 备注 |
| --- | --- | --- | --- |
| 8C32G SSD | 5k-20k doc/s | 1k-5k QPS | 文档小、聚合少 |
| 16C64G NVMe | 20k-80k doc/s | 5k-20k QPS | 通用 |
| 32C128G NVMe | 50k-200k doc/s | 10k-50k QPS | 写密集 |

### 23.6.2 决定因素

- 文档平均大小(1 KB 文档 vs 10 KB 文档相差 10×)。
- 字段数与 text 比例(text 多 → 倒排索引慢)。
- 副本数(写入 × 副本数 + 1)。
- refresh interval(`1s` 比 `-1` 慢得多)。

### 23.6.3 反推节点数

```
例: 业务 50k doc/s 写入,文档 2 KB,3 副本,1s refresh
    单机撑 ~25k doc/s
    节点数 = ceil(50k / 25k) = 2
    + 1 容灾 = 3 数据节点
```

## 23.7 查询 QPS 估算

### 23.7.1 单查询成本

| 类型 | 成本 |
| --- | --- |
| `match` 1 term | 5-20 ms |
| `bool` 5 个 must | 20-100 ms |
| 大聚合(terms 1w bucket) | 200ms-2s |
| KNN Top 100 | 20-100 ms |
| Scroll 1w doc | 5-30 s |

### 23.7.2 节点需求

```
search 节点数 = ceil(峰值 QPS × 平均查询成本 / 1000 ms × CPU 核数 / 并发数)
```

例:1k QPS,平均 100ms,16 核机器 → 1k × 0.1 / (16 × 0.5) = **12.5 → 13 节点**(粗略)。

实际生产会加 2-3× 余量。

### 23.8.2 单节点月成本

| 机型 | 月费 |
| --- | --- |
| 8C32G 1T SSD | ¥(8×60+32×10+1×1000×1) ≈ ¥1,800 |

### 23.8.3 集群总成本

```
3 数据节点 × ¥7,360 + 3 master × ¥1,800 + 监控 × ¥800 ≈ ¥26,480/月
```

### 23.8.4 分层优化

```mermaid
flowchart LR
  A[Hot 1d<br/>20% 数据<br/>2 副本] -->|Rollover| B[Warm 7d<br/>30% 数据<br/>1 副本]
  B --> C[Cold 30d<br/>30% 数据<br/>0 副本]
  C --> D[Frozen 90d+<br/>20% 数据<br/>S3]
```

| 层 | 数据量 | 副本 | 节点类型 | 月成本 |
| --- | --- | --- | --- | --- |
| Hot | 1 TB | 2 | 8C32G NVMe × 6 | ¥10,800 |
| Warm | 1.5 TB | 1 | 8C32G SSD × 4 | ¥7,200 |
| Cold | 1.5 TB | 0 | 8C32G HDD × 3 | ¥2,400 |
| Frozen | 1 TB | 0 | S3 (¥0.1/GB) | ¥100 |
| **合计** | **5 TB** | | | **¥20,500** |

不分层全 SSD:5 TB × ¥3/GB × 副本 = **¥30,000+**。

> **关键经验**:F分层可降本 40-60%,但要 **接受查询延迟** 上升 5-20×(frozen 走 S3)。

## 23.10 成本治理

### 23.10.1 存储

- **forcemmerge 老索引**(1 segment)节省 20-30% 磁盘。
- **冷数据 archived to S3**(frozen tier)。
- **降副本**:非核心索引 `number_of_replicas: 0`。
- **删字段**:大字段单独索引 + 定时归档。

### 23.10.2 计算

- **Spot / 竞价实例** 跑查询节点(可中断)。
- **K8s + HPA**:查询高峰扩容,低峰缩容。
- **Searchable snapshot**:几乎零内存代价。

### 23.10.3 网络

- 跨 region 流量是最贵的(¥0.8/GB 起);**CCR/CCS 走私有专线**。
- Bulk 用 **HTTP 压缩**:`Accept-Encoding: gzip`,省 60% 流量。

### 23.10.4 业务侧

- **冷热分层**:用户搜索 → Hot;BI 报表 → Warm;审计 → Frozen。
- **限速**:按租户限 QPS,避免一个租户耗尽集群。
- **去重**:写入前 `pipeline` 去重,避免冗余 doc。

## 23.11 50K 面试 5 大问题

1. **1 PB 数据需要多少节点?**
   - 1 PB 物理 × 70% 数据可用 × 分层(20% hot / 30% warm / 30% cold / 20% frozen) → 约 30-50 数据节点 + 3 master,月成本百万级。

2. **Heap 32 GB 上限为什么?**
   - JVM 8-11 启用 Compressed Oops,对象指针 4 字节;超 32 GB 失效,变 8 字节,**内存爆 + GC 慢**。ES 7.x+ 默认 32 GB 上限,生产不要超。

3. **分片数怎么定?**
   - `ceil(数据量 / 50 GB)`,并预留 2× 增长;**不** 按"节点数 × X"死板算,要看数据增长。

4. **ES 集群最贵的成本是什么?**
   - **JVM 内存** + **SSD 磁盘**。JVM 大 = 单机贵,SSD 大 = 存储贵。优化点在 **filesystem cache** + **冷热分层**。

5. **如何把月账单降一半?**
   - 分层(hot/warm/cold/frozen)+ 降副本 + forcemerge + 删历史 index + 业务瘦身,实测能省 40-60%。
