# L5 — Ecosystem

> Goal:  plug into the rest of the Kafka platform — Schema Registry,
> Kafka Connect, MirrorMaker 2.

## 1. Why it matters

A bare Kafka cluster is a durable log.  To be a *platform* you need
schema management, easy integration with databases and files, and
multi-cluster replication.  This rung covers each of those.

## 3. Code walkthrough

### `AvroProducer`

* `KafkaAvroSerializer` is wired to `Cluster.schemaRegistry()`.  Every
  send auto-registers a schema version if the topic is new.
* The lab lets you verify the schema shows up in the Schema Registry:
  ```bash
  curl -s http://localhost:18081/subjects/l5.avro-events-value/versions/latest
  ```

### `ProtobufProducer`

* Same idea with `.proto` files generated by the `protobuf-maven-plugin`.
  Note the `setAmount` / `setUrl` (oneof) — only one can be set.

### `ConnectClient`

* Pure HTTP — no Kafka client needed.  Lists connectors, reads status.
* The lab creates a `FileStreamSource` connector that watches
  `/tmp/connect-input.txt`.  Drop a line into the file and watch it
  appear in `l5.connect-source`.

### `MirrorMaker2Config`

* Produces the MM2 worker properties.  See
  `https://docs.confluent.io/platform/current/connect/mirror-maker/index.html`
  for the full feature set (offset sync, ACL sync, etc.).

## 5. Production traps

* **Schema evolution must be declared compatibly.**  Removing a
  field is a *backwards-incompatible* change in Avro unless a default
  is set; in Protobuf it is incompatible unless the field is
  `optional` or behind a `oneof`.
* **Connect offsets are stored in the broker.**  Don't use
  `offset.storage.topic` with RF=1 — a broker loss re-runs the whole
  pipeline from the beginning.
* **MM2 preserves topic names by default**.  To avoid collisions
  across clusters, set `topics.blacklist` and `replication.factor=3`.
